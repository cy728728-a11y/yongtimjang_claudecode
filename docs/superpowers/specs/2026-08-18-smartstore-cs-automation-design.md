# 스마트스토어 문의게시판 CS 자동화 — 설계

## 배경 / 목적

용팀장은 중국 구매대행 셀러로 CS 응대(특히 답변 문구 작성)에 시간을 많이 뺏기고 하기 싫어한다.
기존에 `cs-response` 스킬(수동 트리거: CS 상황을 붙여넣으면 답변 초안 + 시트 로그)이 있지만,
새 CS가 왔는지 사람이 직접 확인하고 내용을 옮겨 적어야 하는 부담은 그대로 남아있다.

이번 설계는 **"새 CS 감지"를 자동화**해서, 사람은 초안이 쌓인 대기함만 확인하고
복붙해서 발송하는 것까지만 하면 되게 만드는 것이 목표다.

## 범위

**대상 채널: 스마트스토어 문의게시판(고객문의) 단일 채널만.**

- 카카오톡(개인): 지인·가족 대화와 섞여있어 오탐 위험이 크다는 이유로 **제외**. 필요하면 기존
  `cs-response`(상황 설명 붙여넣기)로 수동 처리한다.
- 전화 / 문자: 텍스트 자동감지 인프라가 없어 애초에 자동화 불가. 기존 `cs-response` 수동 트리거 유지.
- **자동화 수준은 "초안까지"**. 발송(고객에게 실제 나가는 액션)은 항상 사람이 직접 한다 —
  고객 대응 실수는 되돌리기 어렵기 때문에 이번 단계에서는 자동발송을 설계에 넣지 않는다.

## 사전 조사 결과 (스파이크)

- 네이버 커머스API에 문의 조회/답변 엔드포인트가 실제로 존재함을 공식 GitHub Discussions에서 확인:
  - 조회: `GET /v1/pay-user/inquiries` (`answered=true/false/미설정` 필터, `startSearchDate`/`endSearchDate`, `page`/`size` 페이징)
  - 답변 등록: `POST /v1/pay-merchant/inquiries/:inquiryNo/answer` (이번 설계에서는 사용하지 않음 — 발송은 사람이 함)
- 워크스페이스에 이미 커머스API 인증 코드가 있다 (`naver-category-master` 스킬, `GET /v1/categories` 호출용).
  인증 방식: `bcrypt("{client_id}_{timestamp}", salt=client_secret)` → base64 서명, `.env`의
  `NAVER_COMMERCE_CLIENT_ID`/`NAVER_COMMERCE_CLIENT_SECRET` 사용.
- **미확정 사항**: 위 앱을 문의 조회 API에도 그대로 쓸 수 있는지(같은 앱, 스코프만 다를 수 있음)는
  실제 호출 전까지 모른다. 또한 현재 워크스페이스 루트 `.env`에 해당 키가 비어있는 상태다(다른 PC에
  있었을 가능성).
- **IP 화이트리스트 제약**: 이 앱은 호출 IP를 커머스API센터에 등록해두는 방식이라, 클라우드에서 돌리면
  IP가 매번 바뀌어 사실상 불가능하다. → **로컬 PC 실행 전제**로 설계한다(카톡을 제외했어도 이 제약은
  스마트스토어 채널에 그대로 적용됨).

## 아키텍처

```
[네이버 커머스API]
   │ GET /v1/pay-user/inquiries?answered=false
   ▼
[smartstore-inquiry-check 스크립트]
   │ 1) 이미 처리한 inquiryNo 필터링 (중복방지)
   │ 2) cs-response 분류/초안 로직 재사용
   │    - CS 유형 분류 (배송지연/통관/오배송/파손/환불/교환/품절/단순문의/기타)
   │    - 정보 부족하면 "확인필요"로 표시 (초안 대신 보류)
   │    - 정중한 존댓말 답변 초안 작성 (결론→근거→다음행동)
   ▼
[구글시트 "CS응대로그"] ← append (상태=대기 or 확인필요)
   │
   ▼
사람이 시트에서 확인 → 판매자센터에서 복붙 발송 (자동화 범위 밖)
```

## 컴포넌트

### 1. API 어댑터
- 새 스크립트(가칭 `.claude/skills/cs-response/scripts/fetch_inquiries.py` 또는 별도 스킬 내부)에서
  `naver-category-master/scripts/fetch_categories.py`의 인증(bcrypt 서명 발급) 코드를 재사용.
- 호출: `GET /v1/pay-user/inquiries?answered=false&startSearchDate=...&endSearchDate=...`
- **선행조건 (사용자 액션)**: `.env`에 `NAVER_COMMERCE_CLIENT_ID`/`NAVER_COMMERCE_CLIENT_SECRET` 채워넣기.
  첫 호출에서 401/403이 나오면 커머스API센터에서 문의 조회 스코프를 별도 신청해야 할 수 있음 —
  이 경우 자동화 착수 전에 사용자가 신청부터 해야 한다.

### 2. 분류 + 초안 생성
- 기존 `cs-response` 스킬의 "수행 순서" 2~3단계(정보부족 확인 → 답변 문구 작성) 로직을 그대로 재사용.
- 문의게시판 문의는 네이버가 주문정보를 함께 주는 경우가 많아 정보부족 케이스는 상대적으로 적을 것으로
  예상되나, 부족하면 초안 대신 "확인필요"로 표시하고 원문만 시트에 남긴다(사람이 판단).

### 3. 저장 — 시트 확장
기존 "CS응대로그" 시트(`cs-response`가 최초 실행 시 생성)에 컬럼 3개 추가:

| 기존 6열 | 추가 |
|---|---|
| 작업일 / CS유형 / 상황요약 / 고객원문 / 답변문구 / 비고 | **채널** / **문의번호** / **상태** |

- `채널`: 이번 스코프에서는 항상 "문의게시판" 고정값 (전화/문자로 수동 트리거 시엔 기존처럼 빈값 또는 해당 채널명)
- `문의번호`: 커머스API의 `inquiryNo` — 중복 감지·추후 조회의 키
- `상태`: `대기`(초안 완료, 발송 전) / `확인필요`(정보부족) / (발송완료는 자동 추적 안 함 — 아래 참고)

### 4. 중복 방지
- 처리한 `inquiryNo` 목록을 로컬 파일(`20-operations/cs-automation/processed-inquiries.json`)에 누적.
- 매 실행 시: API에서 받은 미답변 문의 중 이 파일에 없는 것만 신규 처리.
- 발송완료 추적은 별도 자동화하지 않는다 — 답변이 실제로 등록되면 다음 조회에서 `answered=true`로
  넘어가 애초에 미답변 목록에서 빠지므로, 시트의 "발송완료" 갱신은 굳이 자동화할 필요가 없다(YAGNI).

### 5. 실행 방식
- **온디맨드**: "문의 체크해줘" / "CS 확인해줘" 등 트리거 시 즉시 실행.
- **예약**: `CronCreate`로 로컬 세션이 열려있는 동안 주기 체크(예: 1시간마다). 단, 세션 종료 시 사라지고
  최대 7일 후 자동 만료된다는 제약을 실행 시 사용자에게 안내한다.

### 6. 범위 밖 (명시)
- 자동 발송 (`POST .../answer`) — 사용하지 않음.
- 카카오톡 / 전화 / 문자 자동감지 — 기존 `cs-response` 수동 트리거로 유지.
- 시트 상태의 "발송완료" 자동 갱신 — 위 4번 이유로 불필요.
- 완전 무인 클라우드 스케줄 — IP 화이트리스트 제약으로 불가.

## 에러 처리

- API 인증 실패(401/403): `.env` 키 누락, 호출 IP 미등록/변경, 스코프 미신청 순으로 원인을 안내
  (`naver-category-master`의 기존 실패 진단 패턴을 그대로 따름).
- API 응답에 문의는 있으나 주문정보가 비어있는 등 파싱 실패 케이스: 해당 건은 "확인필요"로 표시하고
  원문·에러 사유를 `비고`에 남겨 스킵하지 않는다(누락 방지).

## 테스트 계획

- `.env` 키 세팅 후, 실제 계정으로 `answered=false&size=5` 정도 소량 조회 드라이런 → 응답 구조 확인.
- 문의 1~2건으로 분류·초안 생성까지 End-to-End 실행 → 시트 append 결과 확인.
- 정보부족 케이스를 인위적으로 만들어(예: 원문에 주문번호 없는 문의) "확인필요" 분기 동작 확인.
- 같은 문의로 재실행 → 중복 append 안 되는지 확인(`processed-inquiries.json` 필터링 검증).
