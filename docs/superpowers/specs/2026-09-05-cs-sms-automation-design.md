# CS 전용 휴대폰 문자 CS 자동화 — 설계

## 배경 / 목적

용팀장(구매대행 셀러)은 CS 전용 안드로이드 휴대폰으로 오는 문자 문의를 CS 직원이 직접 확인하고
직접 답장까지 처리한다. `cs-response` 스킬(수동 트리거: CS 상황을 붙여넣으면 답변 초안 + 시트 로그)이
이미 있지만, 문자는 사람이 매번 옮겨 적어야 한다는 부담이 그대로 있었다.

[[2026-08-18-smartstore-cs-automation-design.md]] 에서는 스마트스토어 문의게시판만 자동화 대상으로
삼고, 문자/전화는 "텍스트 자동감지 인프라가 없어 애초에 자동화 불가"로 명시적으로 제외해뒀었다.
이번 설계는 그 빠진 조각(문자 채널의 자동 감지)을 채운다.

## 범위

- **대상 채널: CS 전용 안드로이드 휴대폰의 문자(SMS) 단일 채널만.**
- **자동화 수준은 "초안까지"** — 발송은 항상 CS 직원이 폰에서 직접 한다(고객 대응 실수는
  되돌리기 어렵기 때문에 자동발송은 설계에 넣지 않는다. 8/18 설계와 동일 원칙).
- 검토·발송 담당자는 CS 직원 본인(용팀장 본인이 아님) — 시트는 CS 직원이 보는 작업 도구다.
- 초안 생성 주기는 실시간이 아닌 **1시간 간격 폴링**으로 충분하다고 확인됨(2026-09-05).
  완전 실시간을 하려면 Apps Script에서 외부 AI API를 직접 호출하는 별도 경로가 필요해
  구조가 크게 달라지므로 이번 스코프에서는 채택하지 않는다.

## 사전 결정 사항 (브레인스토밍 중 확정)

1. **폰 → 시트 연결**: 안드로이드 자동화 앱(MacroDroid, 무료) 설치 → SMS 수신 트리거 →
   HTTP POST로 Google Apps Script 웹앱 호출. (대안이었던 "MacroDroid 내장 구글시트 액션 직접 사용"은
   구글 계정 인증·Pro 버전 요구 가능성으로, "폰을 PC에 상시 USB 연결해 ADB로 읽기"는 PC/폰
   24시간 상시 가동 부담으로 각각 기각.)
2. **시트 위치**: 기존 "CS응대로그" 시트를 재사용(8/18 설계에서 이미 "채널" 컬럼을 확장 여지로
   넣어둠). 채널별로 시트를 나누면 CS 직원이 확인할 곳이 늘어나므로 기각.
3. **초안 생성 실행 방식**: [[2026-08-19-email-automation]] 계열(`10-projects/이메일-자동화`)에서
   이미 검증된 패턴 재사용 — Claude Code 세션(CronCreate, 세션 종속·7일 만료)이 아니라
   **독립 Python 스크립트 + `ANTHROPIC_API_KEY` 직접 호출 + Windows 작업 스케줄러**로 무인·상시 실행.
   CS 업무는 대화 세션 유무와 무관하게 계속 돌아야 하므로 세션 종속 방식보다 이쪽이 적합.

## 아키텍처

```
[CS 전용 안드로이드 폰]
   │ MacroDroid: "SMS 수신" 트리거 → HTTP POST {token, from, body, timestamp}
   ▼
[Google Apps Script 웹앱] (시트에 bound, 비밀토큰 검증)
   │ 시트에 새 행 append (상태="신규")
   ▼
[구글시트 "CS응대로그"] ← 채널="문자"로 append (문의게시판과 시트 공유)
   │
   ▼
[sms_draft.py] — Windows 작업 스케줄러, 1시간마다 무인 실행
   1) 상태="신규" 행 조회
   2) cs-response 로직(유형분류 → 정보부족 판단 → 답변 초안)을 이식한 프롬프트로
      Claude API(`claude-sonnet-5`) 호출
   3) 결과를 같은 행에 반영: 상태="대기"(초안 완료) 또는 "확인필요"(정보부족)
   ▼
CS 직원이 시트에서 "대기" 건 확인 → 문구 검토/수정 → 폰에서 직접 문자 발송
(발송완료 표시는 선택사항, 자동 추적하지 않음 — 8/18 설계와 동일 원칙, YAGNI)
```

## 컴포넌트

### 1. 시트 스키마
8/18 설계에서 확정한 "CS응대로그" 시트의 9열을 그대로 재사용한다(새 컬럼 추가 없음):

| 열 | 문자 채널에서의 의미 |
|---|---|
| 작업일 | 문자 수신시각(ISO 타임스탬프) |
| CS유형 | 배송지연/통관/오배송/파손/환불/교환/품절/단순문의/기타 (cs-response 분류 체계 재사용) |
| 상황요약 | Claude가 요약 |
| 고객원문 | 문자 원문 |
| 답변문구 | 초안 (정보부족 시 비움) |
| 비고 | 정보부족 사유 등 |
| 채널 | 고정값 "문자" |
| 문의번호 | 발신번호 (문의게시판 채널의 inquiryNo와 다른 의미로 재해석해서 사용) |
| 상태 | 신규(MacroDroid가 최초 append 시) → 대기(초안 완료) / 확인필요(정보부족) |

### 2. Apps Script 웹훅
- 시트에 바인딩된 Apps Script를 웹앱으로 배포(실행: 나, 액세스: 링크를 아는 모든 사용자).
- POST body: `{"token": "...", "from": "발신번호", "body": "문자원문", "timestamp": "ISO8601"}`.
- 토큰이 스크립트 속성(Script Properties)에 저장된 값과 다르면 요청을 거부하고 아무것도 기록하지 않는다.
- 일치하면 시트에 행 append: [timestamp, "", "", body, "", "", "문자", from, "신규"].
- 토큰은 워크스페이스 루트 `.env`에 `CS_SMS_WEBHOOK_TOKEN`으로 저장(Apps Script 배포 시
  스크립트 속성에도 같은 값을 넣어야 함). 웹앱 URL은 MacroDroid 매크로 설정에 직접 입력하는
  값이라 별도 저장은 불필요.

### 3. MacroDroid 매크로 (CS 전용 폰에 설치, 사용자 액션)
- 트리거: SMS 수신(Received).
- 액션: HTTP Request(POST) → 위 Apps Script 웹앱 URL, JSON body에 발신번호/본문/토큰/타임스탬프.
- 무료 버전 기능 범위 내에서 가능.

### 4. `sms_draft.py` — 초안 생성 스크립트
- 위치: `20-operations/cs-automation/`(8/18 설계에서 이미 이 경로를 예정해둠 — 문의게시판
  자동화와 폴더 공유).
- 패턴: `10-projects/이메일-자동화/email_triage.py` 계열 재사용.
  - `gws_client.py`류 래퍼로 시트 읽기(`상태="신규"` 행 필터)·업데이트.
  - `classifier.py`류 모듈에 cs-response의 "수행 순서 1~3"(유형분류 → 정보부족 확인 → 답변 초안
    작성) 로직을 시스템 프롬프트로 이식. 모델은 `claude-sonnet-5`(고객 발송용 문구라 품질 우선,
    이메일 분류의 `claude-haiku-4-5-20251001`과 달리 저비용보다 품질 우선).
  - `.env`의 기존 `ANTHROPIC_API_KEY`를 그대로 재사용(이메일 자동화 구축 시 이미 발급됨).
- CLI: `python sms_draft.py [--dry-run] [--max N]` (이메일 자동화와 동일한 인터페이스 관례).

### 5. Windows 작업 스케줄러
- `10-projects/이메일-자동화/setup_scheduler.ps1` 패턴을 재사용해 1시간 간격(매시 정각) 등록.

### 6. 범위 밖 (명시)
- 자동 발송 — 하지 않음. 항상 CS 직원이 폰에서 직접 발송.
- 실시간 처리 — 하지 않음. 1시간 폴링으로 충분하다고 확인됨(2026-09-05).
- 발송완료 상태 자동 추적 — 하지 않음(YAGNI, 8/18 설계와 동일 이유).
- 카카오톡/전화 — 범위 밖(8/18 설계에서 이미 제외 확정).

## 에러 처리

- Claude API 호출 실패/응답 파싱 실패 → 안전하게 "확인필요"로 표시, 원문만 남기고 초안은 비움
  (이메일 자동화의 "애매하면 안전한 쪽" 원칙과 동일 — 여기서는 "틀린 초안을 보내는 것보다
  사람이 직접 쓰게 하는 게 낫다"는 방향으로 적용).
- Apps Script 토큰 불일치 → 요청 거부, 시트에 아무것도 기록하지 않음.
- gws 인증 만료/시트 API 실패 → 스크립트가 에러를 로그로 남기고 다음 시간 실행에서 재시도.
  이메일 자동화의 `state.py`(마지막 성공 실행시각 기록) 패턴을 재사용해 장애 감지 가능하게 한다.

## 테스트 계획

- Apps Script 웹훅에 curl(또는 Postman)로 가짜 문자 1건을 POST → 시트에 상태="신규" 행이
  정확히 생기는지 확인.
- `sms_draft.py --dry-run`으로 실행 → 실제 시트 반영 없이 분류/초안 결과만 콘솔 출력되는지 확인.
- 정보부족 케이스(예: 원문에 맥락이 전혀 없는 문자)를 인위적으로 넣어 "확인필요" 분기 확인.
- 실제 CS 전용 폰으로 문자 1~2건을 보내 MacroDroid → 웹훅 → 시트 → 스크립트 초안까지
  end-to-end 확인.
- Windows 작업 스케줄러 등록 후 수동 1회 트리거(`schtasks /run`)로 실제 동작 확인.
