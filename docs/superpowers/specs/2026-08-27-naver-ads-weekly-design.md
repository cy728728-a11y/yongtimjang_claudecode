# 네이버 검색광고 다계정 주간 관리 스킬 — 설계안

> **상태**: API 실측 완료 · **설계 승인됨** (2026-08-27 용팀장)
> 승인 내용: 접근안 **3번(매주 승인 후 실행)** · 쟁점 A **A-2(개별전환 후 인상)**
> 승인 전이므로 구현 코드는 아직 없다. 스크래치패드의 탐침 스크립트는 전부 throwaway.

## 1. 목적

용팀장이 운영하는 **여러 네이버 광고계정**을 주 1회 배치로 훑어,
아래 5개 규칙에 따라 상품을 분류하고 총괄 보고서를 만든다.
쓰기는 규칙 ① 한 곳뿐이고 나머지는 전부 리스트업이다.

| # | 조건 | 액션 |
|---|------|------|
| ① | 노출 0 | 입찰가 +10원 (**자동 쓰기**) |
| ② | CTR < 1% | 썸네일 교체 리스트 |
| ③ | 클릭 20회+ 인데 **구매완료** 0 | 원인분석 리스트 |
| ④ | CTR ≥ 2% | 효자상품 1순위 후보 |
| ⑤ | **구매완료** 발생 | 효자상품 확정 |
| → | 전 계정 합산 | 주간 총괄 보고서 |

## 2. 실측으로 확정된 API 계약

2026-08-27, cy728 계정(customer_id 4158478)에서 직접 호출해 확인했다.
추측이 아니라 응답 원문 기준이다.

### 2.1 인증

- Base: `https://api.searchad.naver.com`
- 계정마다 `CUSTOMER_ID` + `액세스라이선스(api_key)` + `비밀키(secret_key)` 3종을 따로 발급받는다.
  **한 계정의 키로 다른 계정을 볼 수 없다.** → 다계정 = 자격증명 N벌을 순회
- 헤더: `X-Timestamp` / `X-API-KEY` / `X-Customer` / `X-Signature`
- 서명: `HMAC-SHA256(secret, "{timestamp}.{METHOD}.{path}")` → base64.
  **서명 대상 path 에 쿼리스트링은 넣지 않는다.**
- 리포트 다운로드 URL 도 같은 서명이 필요하다 (path 는 URL 의 path 부분만).

### 2.2 상품별 입찰가 — 있다 ✅

쇼핑검색광고 소재(`type: SHOPPING_PRODUCT_AD`)는 최상위가 아니라 **`adAttr` 안**에 갖고 있다.

```json
"adAttr": { "bidAmt": 120, "useGroupBidAmt": false }
```

- `useGroupBidAmt: true` → 실제 적용가는 **광고그룹 기본입찰가**이고 `bidAmt` 는 잠자는 값
- `useGroupBidAmt: false` → `bidAmt` 가 실제 적용가
- cy728 실측: 소재 261개 중 **개별입찰 122개 / 그룹입찰 139개**

**쓰기 방법 (실측 성공)**

```
PUT /ncc/ads/{adId}?fields=adAttr
body = 조회한 소재 객체 전체, adAttr.bidAmt 만 교체
```

검증: 120원 → 130원 반영 확인 → 120원 복원 확인. 다른 방법(`fields=bidAmt` 등)은 시도 불필요.

**`useGroupBidAmt` 는 가역적이다 ✅ (2026-08-27 실측)**

같은 `PUT` 으로 `useGroupBidAmt` 도 바꿀 수 있고, **되돌릴 수 있다.**

```
그룹입찰 {bidAmt:50, useGroupBidAmt:true}
  → 개별입찰 {bidAmt:80, useGroupBidAmt:false}   (200, 반영 확인)
  → 그룹입찰 {bidAmt:50, useGroupBidAmt:true}    (200, 원상복구 확인)
```

이 실측 전에는 "개별입찰로 바꾸면 그룹 연동을 영구히 잃는다" 고 봤는데 **틀렸다.**
되돌릴 수 있으므로 쟁점 A 의 리스크 등급이 내려간다.

### 2.3 전환 지표 — `/stats` 는 못 쓴다 ⚠️

**가장 중요한 발견.** 용팀장 지적으로 잡아냈다.

`/stats` 의 `ccnt`(전환수) · `convAmt`(전환매출액) 은 **전환유형을 전부 합산한 값**이라
**장바구니 담기(`add_to_cart`)가 매출처럼 섞여 있다.**

cy728 실측 (30일, 2026-07-27~08-25):

| 전환유형 | 발생 소재 | 금액 |
|---|---|---|
| `add_to_cart` | 24개 | 7,321,700원 |
| **`purchase`** | **5개** | **596,920원** |

- 광고비 207,838원 → **진짜 ROAS 287%**
- 총전환으로 잘못 계산하면 **ROAS 3,810%** 로 보인다. **13배 착시.**

총전환 기준으로 효자상품을 뽑으면 담기만 하고 안 산 상품이 1순위가 된다.

- `breakdown` 파라미터는 **조용히 무시된다** — `conversionType`/`convType`/`pcMobile` 모두 같은 결과.
  400 을 주지 않고 200 에 안 쪼개진 값을 준다. 실패를 눈치채기 어려운 함정.
- 구매완료를 분리하려면 **`POST /stat-reports {"reportTp":"AD_CONVERSION"}`** 로
  일자별 TSV 리포트를 받아야 한다. 11번째 컬럼(0-based 10)이 전환유형.
- 리포트는 **하루치씩만** 생성된다 → 7일치면 7회 생성·폴링·다운로드
- **`salesAmt` 는 매출이 아니라 광고비**다. 매출은 `convAmt`. 이름에 낚이면 ROAS 가 뒤집힌다.

**결론: `/stats` 는 노출·클릭·CTR·광고비까지만 신뢰하고, 전환은 리포트에서 가져온다.**

### 2.4 노출 0 — 역산 필요

`/stats` 응답에서 **노출 0 소재는 행 자체가 빠진다** (impCnt=0 으로 나오지 않는다).
실측: 소재 261개 요청 → 210행 응답, 51개 미응답.

→ 규칙 ① 대상 = `게재중(enable=true) 소재 전체` **－** `통계 응답에 있는 소재`

`enable=false` 인 소재(261개 중 37개)는 꺼져 있어서 당연히 노출 0이다.
**이걸 안 거르면 꺼진 광고의 입찰가만 매주 올리게 된다.**

### 2.5 리포트 지연

`statDt` 를 어제(D-1)로 주면 `20007 해당 일자 지표 준비중입니다` 가 뜬다.
**D-2 부터 안전하다.** 주간 배치의 기간은 `D-2` 를 끝으로 잡는다.

### 2.6 불사자 연계 고리 (예상 못 한 수확)

소재마다 `referenceData.mallProductId` 가 붙어 있고 **261개 전부 100% 채워져 있다.**
스마트스토어 상품ID다.

→ 규칙 ②의 "썸네일 교체 리스트"가 눈으로 보는 목록이 아니라
**`bulsaja-thumbnail` 스킬에 그대로 먹일 수 있는 상품ID 배치**가 된다.
광고 성과 → 썸네일 재생성이 한 줄로 이어진다. **이 스킬의 최대 가치는 여기 있다.**

### 2.7 계정 간 편차 — 2계정 실측 (2026-08-27)

계정 2개를 붙여 비교했다. **구조가 계정마다 상당히 다르다.**

| | cy728 (4158478) | cy7728 (3415467) |
|---|---|---|
| 캠페인 구성 | SHOPPING 1 + WEB_SITE 1 | **SHOPPING 2** |
| 광고그룹 | 10개 | 13개 |
| 소재 총계 | 261개 | **5,142개** |
| 게재중(enable) | 224개 (86%) | **118개 (2.3%)** |

**설계에 미치는 영향**

1. **`enable` 필터는 선택이 아니라 필수다.** cy7728 은 소재 5,142개 중 **5,024개가 꺼져 있다.**
   안 거르면 매주 죽은 소재 5천 개를 판정하게 되고, 규칙 ① 이 꺼진 광고 입찰가만 올린다.
2. **SHOPPING 캠페인이 계정당 여러 개일 수 있다.** 단수 가정 금지 — 전부 순회한다.
3. **`WEB_SITE` 등 다른 캠페인 유형은 제외한다.** cy728 에 1개 있다.
4. **소재 목록 조회는 광고그룹 단위(계정당 10~13회)라 호출 수는 적지만, 응답 크기는
   계정마다 20배 차이난다.** 5천 개 소재 응답을 메모리에 통째로 들고 있지 않도록 그룹 단위로 흘린다.
5. **그룹 기본입찰가는 두 계정 다 70원** — 상한 300원이 당분간 안전하다는 근거가 하나 늘었다.

### 2.8 짧은 표본은 구매완료를 0으로 보이게 한다 ★

cy7728 은 **6일 표본에서 `purchase` 0건**이었다. 전환추적 미설정을 의심했는데 **틀렸다.**
같은 계정을 **30일 전수**로 다시 재니:

| 전환유형 | 건수 | 금액 |
|---|---|---|
| `add_to_cart` | 60건 | 7,298,600원 |
| **`purchase`** | **5건** | **493,730원** |

구매완료 발생 소재는 4개. **전환추적은 두 계정 다 정상이다.**

**교훈**: 구매완료는 절대 건수가 워낙 적어서(30일에 계정당 5건 안팎)
**짧은 기간으로 보면 그냥 사라진다.** 이것이 규칙 ③⑤ 에 30일이 필요한 진짜 이유다.
7~14일로 판정하면 "이 계정은 광고 경유 판매가 0건" 이라는 **거짓 경보**를 매주 띄우게 된다.

**설계 대응**
- ③⑤ 는 **30일 고정**. 사용자가 기간을 줄이지 못하게 한다(또는 줄일 때 경고).
- 그래도 30일 기준 구매완료가 0인 계정이 나오면 그때는 **명시적 경고**로 싣는다 —
  "30일 광고비 N원, 광고 경유 구매완료 0건". 계정 손익이 드러나는 자리다.

## 3. 설계 쟁점 — 검토 과정

> 결론만 필요하면 **§5 확정된 파라미터**를 보면 된다.
> 이 절은 각 값이 왜 그 값인지의 근거다.

### 쟁점 A — 그룹입찰 상품을 어떻게 할 것인가

노출 0 상품이 **그룹입찰을 따르는 상태(`useGroupBidAmt: true`)** 라면
+10원을 주려면 개별입찰로 전환해야 한다. 전환하면 그 상품은 그룹 기본입찰가 일괄 조정을 안 따라온다.
**단 §2.2 실측대로 되돌릴 수 있다** — 영구 손실이 아니다.

**규모 (cy728, 7일 기준)**

| | 건수 |
|---|---|
| 노출0 전체 | **14건** |
| ├ 개별입찰 (바로 +10원 가능) | 5건 |
| └ 그룹입찰 (전환이 필요한 것) | **9건 (64%)** |

게재중 소재 224개 중 그룹입찰 116 / 개별입찰 108 로 거의 반반이다.

| 안 | 내용 | 판정 |
|---|---|---|
| A-1 | 개별입찰 상품만 +10원, 그룹입찰은 보고서에만 | **기각.** 주간 액션이 5건으로 쪼그라들고 노출0 의 64% 를 방치한다 |
| **A-2 (추천)** | 노출0 인 그룹입찰 상품을 **개별입찰로 전환하고 `그룹 기본입찰가 + 10원`** 으로 시작 | 전 건 처리 가능. 가역적이라 리스크 낮음. **전환 사실을 이력 탭에 남겨 되돌릴 수 있게 한다** |
| A-3 | 그룹 안 노출0 비율이 N% 넘으면 **그룹 기본입찰가**를 올림 | 노출 잘 나오는 상품 입찰가까지 같이 오른다 |

**A-2 확정 (2026-08-27 용팀장 승인).** 전환 시작값을 `잠자던 bidAmt` 가 아니라 **`그룹 기본입찰가 + 10원`** 으로 잡는 게 핵심이다 —
잠자던 값은 그룹값보다 낮은 경우가 많아(실측: 그룹 70원인데 잠자던 값 50원)
그대로 쓰면 입찰가를 **올리려다 오히려 내리게 된다.**

### 쟁점 B — 입찰가 상한

매주 +10원이면 1년에 +520원이다. 상한이 없으면 노출 안 나오는 상품이 무한정 비싸진다.
실측: 개별입찰 상품의 현재 입찰가 분포는 **80~130원**이다.

**확정 (2026-08-28 용팀장): 상한 200원.**
200원에 도달했는데도 노출이 안 되는 상품은 **`상한도달-무노출` 리스트로 별도 집계**한다.
현재 최고가가 130원이므로 80원짜리는 12주, 130원짜리는 7주 만에 상한에 닿는다 —
**이 리스트는 두어 달 안에 실제로 쌓이기 시작한다.** 입찰가로 풀리지 않는 상품이라는
뜻이므로 키워드·카테고리·상품 자체를 봐야 할 대상이다.

3주 연속 인상 실패 시 중단 규칙은 **함께 유지**한다(상한에 닿기 전에 걸러내는 빠른 경로).
포기 리스트는 광고 끄기·상품 자체 교체를 검토할 대상이다.

### 쟁점 C·D — 판정 기간과 노출 하한

노출 하한이 없으면 노출 3회·클릭 0인 상품도 "CTR 0%" 로 들어온다.
기간과 하한을 바꿔가며 실제 건수를 쟀다 (cy728, 게재중 224개 기준):

| 기간 | ①노출0 | ②CTR<1% (하한없음) | ②CTR<1% (노출100+) | ④CTR≥2% (하한없음) | ④CTR≥2% (노출100+) | 광고비 |
|---|---|---|---|---|---|---|
| 7일 | **14** | 147 | 13 | 48 | 15 | 52,913 |
| 14일 | 10 | 135 | 29 | 52 | 20 | 102,177 |
| 30일 | 6 | 129 | **45** | 57 | **32** | 207,838 |

읽는 법:
- **하한 없이는 못 쓴다** — ② 가 147건(전체의 66%)이다. 노출100+ 를 걸면 실용적인 크기가 된다
- **①은 기간이 짧을수록 많다** (7일 14건 / 30일 6건). 30일 6건은 "한 달 내내 죽은 상품" 이라
  성격이 다르다 — 입찰 인상이 아니라 **광고 중단·상품 교체** 대상이다
- **②④는 기간이 길수록 많다** — 노출100+ 를 채우는 상품이 늘어서다

**추천**

| 규칙 | 기간 | 하한 |
|---|---|---|
| ① 노출0 → 입찰 +10원 | **7일** | enable=true 만 |
| ① ' 30일 내내 노출0 → **포기 후보** (별도 리스트) | 30일 | — |
| ② CTR<1% → 썸네일 교체 | **30일** | 노출 100+ |
| ③ 클릭20+/구매완료0 | **30일** | — |
| ④ CTR≥2% → 효자 후보 | **30일** | 노출 100+ |
| ⑤ 구매완료 발생 → 효자 확정 | **30일** | — |

전환 규칙(③⑤)에 30일이 필요한 이유: 14일에 구매완료가 **1건**뿐이었다. 7일로는 표본이 없다.

**② 는 주당 처리량 상한이 필요하다.** 30일 45건을 매주 썸네일 재생성하면 크레딧이 샌다.
**추천: 노출 많은 순으로 상위 20건.** 노출은 많은데 클릭이 안 되는 상품이 썸네일 문제가 가장 확실하다.

### 쟁점 E — 보고서 출력처

주간 총괄은 시트를 열지 않고 읽을 수 있어야 한다.

`이력` 탭은 쟁점 B 의 "3주 연속" 판정 근거다. **이 탭 없이는 상한 규칙이 작동하지 않는다.**

## 4. 실행 구조 — 접근안 3번 확정 (2026-08-27 용팀장 승인)

**주간 배치는 쓰기를 하지 않는다.** 입찰가 인상은 용팀장이 리스트를 보고 승인한 뒤
별도 명령으로 실행된다. 이것이 이 설계의 핵심 안전장치다.

```
[매주 자동]  수집 → 판정 → 시트 기록 → 보고서            ← 쓰기 0
                                    ↓
                         용팀장이 ①번 리스트 확인
                                    ↓
[승인 후]    입찰가 인상 실행 → 이력 기록                  ← 유일한 쓰기
```

### 4.1 진입점 (스킬 계약 `prep`/`run`/`apply` + 보조 쓰기 1개)

| 명령 | 하는 일 | 쓰기 |
|---|---|---|
| `prep --run-dir <R>` | 전 계정 순회: 소재 목록(enable 필터) · 7일/30일 `/stats` · 30일 `AD_CONVERSION` 리포트 → 디스크 | 없음 |
| `run --run-dir <R>` | 5개 규칙 판정 → `result.json`. **Claude 워커 불필요** — 전부 산술 판정이라 스크립트로 끝난다 | 없음 |
| `apply --run-dir <R>` | 구글시트 기록 + 마크다운 총괄 보고서 생성 + ② 리스트를 현황판에 `flag` | 시트만 |
| **`bids --run-dir <R> [--commit]`** | **보조 쓰기 진입점.** ①번 입찰가 인상 실행. `--commit` 없으면 dry-run | **광고 API** |

`bids` 는 스킬 계약 §"보조 쓰기 진입점" 예외에 해당한다 (2026-08-27 명시).
**`--commit` 없이는 절대 쓰지 않는다.** 기본은 dry-run 이다.

### 4.2 `bids` 가 지켜야 할 가드레일

1. `enable=true` 인 소재만
2. 7일 노출 0 인 소재만 (30일 노출0 은 별도 `포기 후보` 리스트로 — 입찰 인상 대상 아님)
3. 개별입찰이면 `bidAmt + 10`, 그룹입찰이면 **개별 전환 + `그룹기본가 + 10`**
   (잠자던 `bidAmt` 를 쓰면 안 된다 — 그룹값보다 낮은 경우가 많아 입찰가가 **내려간다**)
4. 상한 **200원**. 도달하면 인상하지 않고 **`상한도달-무노출` 리스트**로 별도 집계
5. **3주 연속 인상했는데도 노출 0** 이면 인상 중단 → `포기 후보` 이관
6. 실행 전 **원본 `adAttr` 전체를 `before_bids.json` 으로 백업** (옵션정리 스킬의 `before_commit.json` 선례)
7. 실행 결과를 이력 탭에 기록 — 3주 연속 판정과 되돌리기의 근거

### 4.3 되돌리기

`bids --run-dir <R> --revert` 로 `before_bids.json` 을 그대로 되쓴다.
`useGroupBidAmt` 도 함께 복원되므로 개별 전환도 취소된다 (§2.2 가역성 실측 근거).
