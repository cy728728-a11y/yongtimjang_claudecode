# 스킬 배포 파이프라인 설계

**작성일**: 2026-08-15
**상태**: 설계 승인 완료 → 구현 계획 대기
**선행 문서**: `2026-08-15-bulsaja-kit-수강생-배포-design.md` (썸네일·배송비 1차 배포)

---

## 1. 배경

1차 배포(썸네일·배송비)는 **플러그인 1개짜리 단발 작업**으로 만들었다. 그런데 실제
요구는 다르다:

- 배포할 스킬이 **계속 늘어난다** (썸네일·배송비·옵션·상품명, 앞으로 더)
- **같은 스킬을 수정본으로 재배포**하는 일이 반복된다 — 이게 가장 잦다
- 수강생 유형이 둘이다
  - 신규: 전 스킬을 한 번에 받고 싶어한다
  - 기존: 업데이트된 것만 받고 싶어한다

1차 구조로는 스킬이 늘 때마다 수강생이 재설치해야 하고, 배포할 때마다 손으로
같은 정화 작업을 반복해야 한다.

---

## 2. 목표 / 비목표

### 목표

- 스킬이 늘어도 **수강생의 마켓플레이스 등록은 평생 한 번**
- **전 스킬 묶음**과 **개별 스킬** 양쪽 설치 경로를 모두 제공
- 수정본 재배포 시 수강생이 **아무것도 하지 않아도** 최신을 받는다
- 배포 작업을 스킬 한 번 호출로 끝낸다 — 정화·검증·버전·푸시 자동
- **공개 저장소에 개인정보가 나가는 사고를 구조적으로 막는다**

### 비목표

- 카테고리 교정 스킬 배포 (§8 참조 — 조회 엔진이 없어 이번 범위 밖)
- 수강생별 접근 제어 (공개 저장소이므로 불가)
- 사용량·과금 추적

스캔에 걸린 `.env` 신호는 전부 `os.environ.copy()`(subprocess 환경 전달)였다.

## 4. 업데이트 모델 — 이 설계의 핵심

공식 문서에서 확인한 사실:

> "When auto-update is enabled for a marketplace, Claude Code refreshes the marketplace
> data and updates installed plugins to their latest versions."

> "when you install `plugin-name@marketplace-name`, Claude Code refreshes that
> marketplace before the lookup"

이 둘이 요구사항을 거의 해결한다.

| 수강생 상황 | 해야 할 일 |
|---|---|
| 신규 · 전부 원함 | 마켓플레이스 등록 + `install bulsaja-kit@bulsaja-kit` |
| 신규 · 일부만 원함 | 마켓플레이스 등록 + 원하는 플러그인만 `install` |
| 기존 · 스킬이 수정됨 | **아무것도 안 함** (자동 업데이트) |
| 기존 · 새 스킬이 나옴 | `install <새스킬>@bulsaja-kit` 한 줄 |

**주의**: 서드파티 마켓플레이스는 자동 업데이트가 **기본 꺼짐**이다. 수강생이 처음에
한 번 켜야 한다 — README와 설치 안내에 필수로 넣는다.

**버전을 올리지 않으면 업데이트가 나가지 않는다**(`version` 필드로 핀 고정).
배포 스킬이 이걸 자동으로 처리한다.

## 5. 저장소 구조

```
bulsaja-kit/
├─ .claude-plugin/
│   └─ marketplace.json          # metadata.pluginRoot = "./plugins"
├─ plugins/
│   ├─ bulsaja-kit/              # 묶음 — 전 스킬
│   │   ├─ .claude-plugin/plugin.json
│   │   ├─ skills/{4개 스킬}/
│   │   ├─ lib/eroomlib/
│   │   └─ config/
│   ├─ bulsaja-thumbnail/        # 개별
│   ├─ bulsaja-shipping-fee/
│   ├─ bulsaja-option-cleanup/
│   ├─ bulsaja-product-name/
│   └─ bulsaja-kit-doctor/       # 설치 점검 (묶음에도 포함)
├─ shared/
│   └─ eroomlib/                 # ★ 라이브러리 정본
├─ tests/
└─ README.md
```

### 왜 라이브러리를 복사하는가

공식 문서:

> "Copied plugins can't reference files outside their directory using paths like
> `../shared-utils`, because those files won't be copied."

플러그인은 자기 폴더 밖을 못 읽는다. 사본이 필수다.

### 사본이 어긋나는 것을 막는 장치

- **배포할 때마다 `shared/eroomlib` 에서 전 플러그인으로 다시 복사**한다. 사람이 손으로
  맞추지 않는다
- **테스트가 "모든 사본 == 정본"을 검사**한다. 어긋나면 배포가 실패한다

### 묶음과 개별을 같이 설치하면

같은 스킬이 두 번 로드되어 컨텍스트 비용이 2배가 되고 판단이 흔들릴 수 있다.
README에서 **둘 중 하나만** 쓰도록 안내하고, `doctor` 가 중복 설치를 감지해 알린다.

## 6. 라이브러리 정본 관리 정책

`shared/eroomlib` 은 **배포판이 소유한다.** 용팀장 워크스페이스의 `.claude/lib/eroomlib`
에서 자동 동기화하지 **않는다.**

이유: 배포판 라이브러리는 저장 계층이 개조돼 있다(`gsheets.py` → 로컬 JSON,
`_http.py` 추가, `matrix.py` 3곳 패치, `config.py` 교체). 원본을 덮어쓰면 그 개조가
날아간다. 매번 패치를 다시 적용하는 방식은 시간이 지나면 반드시 깨진다.

대신 배포 스킬이 **차이를 보고만 한다**: "원본 `snapshot.py` 가 배포판보다 새롭다.
옮길까?" 판단은 사람이 한다.

| 모듈 | 성격 |
|---|---|
| `gsheets.py` · `localstore.py` · `_http.py` · `config.py` · `__init__.py` | **배포판 고유** — 원본에 없거나 완전히 다름 |
| `matrix.py` | **패치본** — 원본에서 3곳 수정(`index_groups`·`_insert_header_row`·`sync_all`) |
| `snapshot.py` · `bulsaja.py` · `textnorm.py` · `envload.py` · `dedup.py` · `exclusion.py` · `review_page.py` | **거의 원본** — import 한 줄만 다름 |
| `gdrive.py` · `webdriver.py` | **배포 안 함** — 드라이브·셀레니움 결합 |

## 7. 배포 스킬 `skill-publish`

**트리거**: "수강생용으로 배포해줘", "스킬 배포", "배포판 만들어줘", "플러그인 올려줘"

### 흐름

```
① 대상 확정   스킬 이름 → 신규 배포인지 갱신인지 판별
② 결합 스캔   스킬 + 그것이 쓰는 라이브러리를 훑어 위험 목록 작성
③ 보고 후 정지  ← 판단이 필요한 것만 사용자에게 묻는다
④ 이식        플러그인 폴더 생성 + 라이브러리 동봉 + 묶음에도 반영
⑤ 정화        자동 처리분 치환
⑥ 검증        ← 게이트. 하나라도 실패하면 푸시하지 않는다
⑦ 푸시        버전 올림 + 커밋 + push
⑧ 공지문      수강생에게 보낼 문구 출력
```

### ② 결합 스캔 — 두 부류

**자동으로 고친다**

| 대상 | 처리 |
|---|---|
| 인명 (이룸·용팀장·용쌤) | 문맥에 맞춰 치환(조사 처리 포함) |
| 개인 절대경로 (`D:\python_work`, `/Users/...`) | 홈 기준 경로로 |
| 예시 마켓그룹명 (`1번_용쌤1-1`) | 중립 예시(`1-1그룹`)로 |
| 이메일 주소 | 예시로 |
| 스프레드시트·드라이브 ID | 제거 |
| "현황판" 등 시트 전제 용어 | "진행판" 등으로 |

**멈추고 묻는다**

| 대상 | 왜 사람이 판단해야 하나 |
|---|---|
| `.env` 자격증명 참조 | 빼는 게 맞는지, 수강생 설정으로 미룰지 |
| 구글시트·`gws` 직접 호출 | 로컬로 대체할지, 기능을 뺄지 |
| 형제 스킬 참조 | 같이 배포할지, 기능을 뺄지 |
| Workflow 팬아웃 | 순차로 바꿀 위치 확인 |
| 셀레니움·브라우저 로그인 | pip 의존과 수작업 세팅을 수강생에게 요구할지 |
| 라이브러리 원본이 배포판보다 새로움 | 옮길지 |

### ⑥ 검증 게이트

순서대로 전부 통과해야 푸시한다.

1. 정화 검사 — 금지 패턴 **0건**
2. 라이브러리 사본 == 정본
3. 이식한 스킬의 원본 테스트 통과
4. **실제 설치 테스트** — `claude plugin marketplace add <로컬경로>` →
   `claude plugin install` 을 실제로 실행해 설치가 되는지 확인
5. 매니페스트 정합 — 선언한 플러그인이 전부 존재하고 버전이 일치

4번이 핵심이다. 공개 저장소에 올리기 **전에** 설치 가능 여부를 실물로 확인한다.

### ⑦ 버전 규칙

- 개별 플러그인: 그 스킬이 바뀌면 patch 올림 (`1.0.0` → `1.0.1`)
- 묶음 플러그인: 어느 스킬이든 바뀌면 patch 올림
- 버전을 안 올리면 수강생에게 업데이트가 나가지 않으므로 **스킬이 자동으로 올린다**

## 8. 카테고리 교정 스킬을 이번에 배포하지 않는 이유

카테고리 교정의 핵심은 "키워드 → 네이버 카테고리 경로" 조회인데, 그 조회 엔진이
수강생 환경에 존재하지 않는다.

| 엔진 | 문제 |
|---|---|
| `aside-category` | Aside 브라우저의 상시 로그인 세션에 의존. 수강생 환경에 없고 세션 공유 불가 |
| `sellha-category` | 셀레니움 설치 + 크롬 프로필 복사 + 확장 설치 + 로그인이 필요. 게다가 보안프로그램이 크롬을 30초에 강제 종료해 실사용이 어렵다(그래서 Aside로 이관했다) |

조회 엔진 없이는 스킬이 껍데기가 된다. **수강생이 쓸 수 있는 조회 경로를 먼저 정한 뒤**
별도로 배포한다. 배포 스킬이 완성돼 있으므로 그때는 호출 한 번이면 된다.

부수적으로, 카테고리 스킬의 `gate_request_sheet.py`(불사자에 일괄 삭제를 요청하는
시트 생성)는 운영 전용 기능이라 배포 시 통째로 제외한다.

## 9. 스킬별 개조 명세

### 9.1 `bulsaja-option-cleanup`

썸네일과 같은 계층만 쓴다(`matrix`·`snapshot`·`config`·`gsheets`·`_col_letter`).
저장 계층이 이미 교체돼 있으므로 **스크립트 본문 수정은 사실상 없다.**

- 팬아웃(Workflow) → 배치 순차 처리로 문구 변경
- 진행판 부트스트랩 추가 (썸네일·배송비와 동일한 `_bootstrap_board`)
- `_shared/` 참조 해소, 인명 정화

### 9.2 `product-name`

- **`gdrive.resolve_raw_dir()` 제거** — 키워드 원본을 구글드라이브에서 받는 경로다.
  수강생은 접근할 수 없다. `--raw-dir <로컬폴더>` 로 대체하고, 미지정 시 기본값을
  `~/bulsaja-kit/keywords/` 로 둔다. 폴더가 비어 있으면 **무엇을 넣어야 하는지 안내하고
  멈춘다**(조용히 0건 처리하지 않는다)
- 팬아웃 → 배치 순차
- 시트 E열 원본 백업 → 로컬 원장(`ledger.json`)
- 진행판 부트스트랩 추가

**전제**: 수강생이 셀러라이프 키워드 엑셀을 직접 갖고 있어야 한다. README에 명시한다.

## 10. 검증 절차

1. 각 스킬의 원본 테스트가 배포판에서 그대로 통과할 것
2. 정화 검사 0건
3. 라이브러리 사본 정합
4. **`claude plugin` 셸 명령으로 실제 설치 테스트** — 묶음 1개 + 개별 5개 전부
5. 실제 마켓그룹으로 각 스킬 `prep` 완주 (크레딧 소모 단계는 제외)
