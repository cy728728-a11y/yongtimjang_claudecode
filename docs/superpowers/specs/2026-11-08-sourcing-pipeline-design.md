# 불사자 소싱 파이프라인 운영 설계

작성 2026-11-08 · 용팀장 + Claude 대화에서 정리 · 프로젝트 폴더 `10-projects/16-불사자-소싱-파이프라인/`
관련: `2026-10-18-sourcing-inspection-design.md`(검수 자동화), 스킬 `.claude/skills/sourcing-inspect`

## 1. 의도와 이유

운영 마켓(약 52개)에 **매달 10만 개를 새로 올리는 것**이 목표다. 이룸님 가공 단계에서 약 30%가 빠지므로 **매달 약 14만 개가 2차 검수를 통과해 '소싱테스트_통과' 그룹에 들어와야** 한다.

지금까지의 소싱은 일회성이었다. 키워드 3,336개로 마켓 28,765개를 모아 과거 판매 이력을 한 번 긁었고(상품 280,866개), 그 통과분이 지금의 저수지다. 2026-11-07 기준 잔량은 '소싱테스트_통과' 117,025개 + '신규소싱상품' 9,398개로, 11월 안에 바닥난다. 다음 달부터는 **계속 흐르는 공급 구조**가 있어야 한다.

핵심 발견 세 가지(2026-11-07 실측):
- 28,765 마켓 중 **실제로 5만~50만 원 판매 상품을 낸 마켓은 16,227개**. 나머지 절반은 빈 밭이었다.
- 28765 캠페인 최종 통과율 28.5%(1차 55%, 2차 52%). 단 검수 기준이 그 뒤 많이 바뀌어 **참고치일 뿐**이며 회차마다 다시 잰다.
- 1차 탈락의 96%가 금지 카테고리, 2차 탈락 1위가 지식재산권(37%).

## 2. 목표 · 비목표 · 반목표

**목표**
- 매달 약 14만 개의 2차 통과 상품을 '소싱테스트_통과'에 지속 공급한다.
- 같은 상품을 두 번 검수하지 않는다(크레딧·시간 낭비 0).
- **처음부터 무인으로 돈다**(용팀장 결정 2026-11-10). 사람 손은 "주간 보고 읽기"와 "로그인이 풀렸을 때 다시 로그인"뿐이다.

**비목표**
- 상품 100% 비중복. 마켓이 다르면 같은 상품이 올라가는 것은 감안한다.
- 가공·운영 마켓 복사·복사 후 삭제 등 이룸님 쪽 작업 방식 변경.
- '소싱테스트_통과' 그룹을 회차별로 쪼개기. 그룹은 지금 그대로 하나다.

**반목표(이렇게 되면 실패)**
- 수량을 채우려고 통과 상품을 여러 마켓에 일부러 돌려 올리기. 통과 그룹을 카탈로그처럼 재사용하지 않는다.
- 이미 본 상품을 다시 검수해 크레딧을 쓰는 것.
- 통과율을 옛 수치로 믿고 공급량을 약속하는 것.

## 3. 제약

- **엔잡곰소싱기는 화면에서만 다룰 수 있다.** 서버에 직접 묻는 길은 권한이 막혀 있고, 캠페인 안의 상품 목록만 기존 방식(`bulsa-sourcing-products`)으로 읽을 수 있다. 무인화를 위해 캠페인 생성·마켓 입력·수집 실행·수집사이트 내보내기는 **브라우저 자동 조작(Playwright, 창 없음, 로그인 상태를 기억하는 전용 프로필)** 으로 한다. 불사자는 네이버가 아니므로 자동 조작 금지 대상이 아니다.
- 웹 로그인 토큰은 7일(접근)·30일(갱신) 만료다. 전용 프로필이 살아 있으면 자동으로 이어지고, 완전히 풀리면 카톡 알림(auto-watch 경로)으로 용팀장에게 재로그인을 요청한다. 이것이 유일한 사람 개입 지점이다.
- 소싱기 마켓 모드는 두 가지뿐: **과거 판매 이력 전부** / **3일베스트**(최근 3일 안에 팔린 상품만, 소싱기의 공식 명칭). 마켓당 최대 100개. 3일베스트는 전에 팔린 상품이 또 팔리면 다시 가져오고, **다른 캠페인에 이미 있는 상품도 걸러 주지 않는다**(용팀장 확인 2026-11-10). 중복 제거는 전부 우리 장부 몫이다.
- **가격 범위는 앞으로 모든 캠페인에서 3만~50만 원**(용팀장 결정 2026-11-10). 지금까지의 28765·엔잡곰·260930 캠페인은 5만~50만 원으로 돌았으므로, 기존 마켓의 3만~5만 원 상품은 아직 한 번도 긁지 않은 밭이다.
- 불사자 MCP 분당 240회. 조회와 옮기기를 동시에 돌리지 않는다.
- 네이버에 직접 접속하지 않는다(소싱기가 대신 한다).
- 통과 상품 경로는 현재와 같다: 수집 → '신규소싱상품'(1007620) → 옮기기 → '소싱테스트_통과'(1008216, 부킹 계정).
- **옮기기는 그룹 변경만 한다**(Claude 결정). 판매가 재계산은 하지 않는다. 가격은 이룸님이 운영 마켓으로 복사할 때 그 마켓 공식으로 다시 매겨지므로 통과 그룹 단계의 가격은 의미가 없다. 옛 `transfer_group.py`의 복사·재계산·원본 휴지통 방식은 쓰지 않는다. 옮기는 대상은 **그 회차에 수집한 상품만**이다.
- '신규소싱상품'에 남아 있는 옛 상품 9,398개(과거 워크플로 통과분, 출처 불명)는 회차 흐름과 섞지 않는다. 별도 1회 작업으로 **현재 2차 기준으로 재검수**해 통과분은 '소싱테스트_통과'로 그룹 변경, 탈락분은 사유를 남기고 휴지통으로 보낸다(Claude 결정). 이 상품들은 이미 타오바오 매칭이 끝나 있으므로 1차·매칭은 건너뛴다.
- 검수 기준 정본은 `sourcing-inspect/rules/worker-prompt.md` + banned_keywords. 이 문서는 기준을 건드리지 않는다.
- 통과 그룹에서 복사 후 삭제하는 운영은 유지한다(이룸님의 "할 일 남은 것" 표시).

## 4. 공급원 세 개

| 구분 | 무엇 | 성격 | 기대 수율 |
|---|---|---|---|
| A. 새 마켓 전체 이력 | 키워드 캠페인으로 새로 찾은 마켓에 "과거 판매 이력 전부" 1회 | 마켓당 한 번뿐인 큰 수확 | 마켓당 약 10개 수집(참고), 통과 약 2.8개 |
| B. 기존 마켓 재수확 | 상품을 낸 적 있는 마켓 전체에 "3일베스트" 주기 실행 | 마켓이 계속 파는 한 계속 나오는 밭 | **미측정 → 파일럿으로 잰다** |
| C. 탈락분 재검토 | 용팀장이 탈락 뷰어에서 살리기 | 보조, 한도 있음 | 기존 메모리 `drop-review-viewer` 대로 |
| D. 기존 마켓 3만~5만 원 전체 이력(1회) | 28765·엔잡곰·260930 마켓 전부(빈 밭 포함)에 "과거 판매 이력 전부, 3만~5만 원" 1회 | 가격 하한을 내려서 생긴 일회성 큰 수확 | 미측정. 마켓 수가 3만 개 넘어 몇 주 걸릴 수 있으니 주간 끊기와 겹치지 않게 나눠 돌린다 |

용팀장의 걱정("본 상품을 빼면 갈수록 줄어든다")은 A에만 해당한다. B는 "내가 전에 뭘 캤는가"가 아니라 "마켓이 이번 주 얼마나 새로 팔았는가"가 공급량을 정한다. 중복 거르기는 검수 전에 로컬에서 공짜로 하므로, 중복 비율이 올라가도 크레딧은 안 늘고 소싱기 돌아가는 시간만 는다.

## 5. 대장(장부) 세 개

위치: `~/python_work/data/sourcing-pipeline/`. 모두 로컬 파일. 불사자가 정본인 것(그룹 소속, 업로드 여부)은 대장에 복제하지 않는다.

1. **마켓 대장 `markets.jsonl`** — 한 줄에 마켓 하나. 주소(slug), 처음 발견한 날, 전체 이력을 돌린 캠페인·날짜, 3일베스트를 마지막으로 돌린 날, 지금까지 낸 상품 수.
   - 초기값: 캠페인 "마켓 28765개 판매1이상"에 입력된 마켓 목록(용팀장 제공 파일), 엔잡곰마켓 2,428, 260930 키워드 캠페인 마켓. 이후 불사자 수집사이트 화면의 엑셀 내보내기(2026-11-07 기준 33,437개)로 동기화한다.
   - "상품 0개" 마켓은 빈 밭으로 표시한다.
2. **본 상품 대장 `seen_products.jsonl`** — 네이버 상품번호 기준. 처음 본 캠페인·날짜·판정. 초기값은 세 캠페인 스냅샷에서 뽑은 `seen_naver_products.txt` 461,189건이지만, **그중 170,132건(소싱테스트 그룹 조회분, `U01M…`)은 네이버 번호가 아니라 불사자 내부 번호**라 대조에 쓸 수 없다(2026-11-09 빌더 검토). 실제 네이버 번호는 약 291,000건. **이 구멍은 채우지 않고 감수한다**(용팀장 결정 2026-11-10). 네이버 번호는 같은 마켓 같은 상품만 잡는데, 그건 불사자 수집 단계의 그룹 중복 차단이 한 번 더 막기 때문이다. 내부 번호 17만 건은 대장에서 분리해 따로 보관한다.
3. **타오바오 대장 `seen_taobao.txt`** — 매칭 후 확정된 타오바오 상품번호. 초기값은 2차 검수 스냅샷(`1030_m28_s2_*`)에서 만든다. 소싱테스트 계열 17만 건은 스냅샷에 타오바오 번호가 없으므로 **밤에 상품 상세 조회로 천천히 채운다**(용팀장 결정 2026-11-10). MCP 분당 240회 한도 안에서 다른 작업이 없는 시간대에만 돌리고, 끝나기 전에도 파이프라인은 그때까지 채운 만큼으로 돈다. 채우는 범위는 '소싱테스트_통과'·'신규소싱상품' 현재 재고 전체와, 가능하면 운영 마켓 상품까지. 이 대장이 마켓 간 중복을 잡는 핵심이라 네이버 대장보다 우선한다.

**중복 판정은 2단계**
- 수집 직후: 네이버 상품번호가 대장에 있으면 검수 없이 휴지통(사유 `DUP_SEEN`, 휴지통 대장에 기록). 같은 마켓의 같은 상품이 3일베스트로 또 들어온 경우가 여기서 걸린다.
- 매칭 직후(2차 전): 타오바오 번호가 대장에 있으면 휴지통(사유 `DUP_TAOBAO`). 다른 마켓이 같은 타오바오 물건을 판 경우가 여기서 걸린다. 2차 AI 비용을 아끼는 단계다.
- 불사자 수집 단계의 "같은 그룹 중복 차단"은 3차 안전망으로 그대로 둔다.

## 6. 회차 운영(달력 기준)

- 키워드 캠페인은 끊지 않고 계속 돌린다(현재 53,490 키워드 캠페인). 끝날 때까지 멈추지도, 쓴 키워드를 지우고 고쳐 다시 돌리지도 않는다.
- 수집사이트의 마켓은 지우지 않는다. 불사자가 "이미 있는 마켓은 또 넣지 않는" 중복 차단을 하고 있으므로, 지우면 뒤의 키워드가 같은 마켓을 또 넣을 수 있다. 날짜 그룹으로 옮기는 것은 보기 편하라고 하는 선택 사항이다. "어느 마켓이 새 것인가"는 로컬 마켓 장부와의 대조로만 정한다.
- 수집사이트 엑셀 내보내기가 전체를 내보내는지 현재 그룹·페이지만 내보내는지는 빌더가 Playwright로 첫 내보내기를 할 때 확인한다. 후자면 그룹별로 나눠 내보낸다.
- **매주 일요일 밤(23:00)에 자동으로 "끊기"** 를 한다(요일은 Claude 결정, 월요일 아침 보고를 읽게 하려고). 끊기는 "그날까지 모인 새 마켓"을 묶는 행위다. 아래 1~5는 전부 무인이다.
  1. 수집사이트 엑셀 내보내기 → 마켓 대장 동기화 → **새 마켓 목록**(전체 이력 미실행) 파일 생성 `new_markets_YYMMDD.txt`.
  2. 자동 조작으로 소싱기에서 캠페인 **`R-YYMMDD-신규전체`** 생성(마켓 모드, 과거 이력 전부, 판매 1 이상, **3만~50만 원**, 마켓당 100개). 마켓 목록은 1의 파일을 넣는다. 새 마켓이 0이면 만들지 않는다.
  3. 같은 날 캠페인 **`R-YYMMDD-재수확`** 생성(마켓 모드, **3일베스트**, 가격 **3만~50만 원**, 마켓당 100개. 3일베스트가 곧 "3일 안에 판매"이므로 판매 건수 조건은 따로 없다). 대상은 "전체 이력을 끝냈고 상품을 낸 적 있는 마켓". **빈 밭 마켓은 재수확에서 제외**하되, 빈 밭 판정은 공급원 D(3만~5만 원 전체 이력)까지 끝난 뒤 "3만~50만 원에서 상품 0개"로 다시 내린다(Claude 결정). 5만 원 기준으로 비었던 1만 2천 마켓 중 일부는 3만~5만 원 상품으로 살아날 수 있다. 주기(매주/격주)와 규모는 파일럿 결과로 정한다.
  4. **수집 완료를 자동으로 감지**(캠페인 상품 수가 일정 시간 늘지 않으면 완료로 본다, 세부는 빌더)하고 자동 흐름: 캠페인 상품 받기 → **중복 제거(신규)** → 1차 → 이미지 매칭 → **타오바오 중복 제거(신규)** → 2차 → 상품수집('신규소싱상품') → 옮기기(그룹 변경, '소싱테스트_통과'). 기존 `run_inspect.py`/`apply_sourcing.py` 흐름에 중복 단계만 끼운다. 매칭이 비동기라 안 끝난 상품은 **다음 날 같은 시간에 다시 시도**하고, 3회 뒤에도 안 되면 사유를 남기고 넘어간다. 모든 백그라운드 실행에는 완료 감시를 같이 건다(메모리 `never-launch-without-watcher`).
  5. 회차 보고 `runs/<R>/report.md`: 마켓 수, 수집 수, 중복 제거 수, 1차·2차 통과 수와 통과율, 마켓당 수율, 다음 달 공급 예측. 요약 한 장은 프로젝트 폴더에도 남기고, **월요일 아침 카톡 '나에게 보내기'로 한 줄 요약**을 보낸다(auto-watch 경로 재사용). 실패·로그인 풀림도 같은 경로로 알린다.
- 캠페인 이름 규칙 `R-YYMMDD-신규전체` / `R-YYMMDD-재수확`. 마켓그룹은 새로 만들지 않는다.

## 7. 1단계: 재수확 파일럿(승인 후 첫 작업)

B의 수율을 모르면 월 공급 계산이 안 된다. 그래서 먼저 잰다.
- 대상: 28765 캠페인에서 상품을 낸 16,227 마켓 중 **상품을 많이 낸 순 1,000개 + 무작위 1,000개**, 총 2,000개.
- 캠페인 `R-YYMMDD-파일럿3일` (3일베스트, 3만~50만 원) 1회 실행. 파일럿은 **브라우저 자동 조작의 첫 시험**이기도 하다. 자동 조작이 안 되면 이번 한 번은 용팀장이 화면에서 만들고, 자동 조작은 2단계에서 완성한다.
- 측정: 마켓당 수집 수, 중복 제거 후 신규 수, 2차 통과 수. "상위 1,000"과 "무작위 1,000"을 따로 집계한다(재수확 대상을 좁힐 수 있는지 보려고).
- 산출: 월 공급 예측표. A(새 마켓 수 × 마켓당 수집 × 통과율) + B(마켓당 3일 수율 × 마켓 수 × 회차 × 통과율)가 14만에 닿는지, 안 닿으면 어느 쪽을 늘려야 하는지.

## 8. 성공 기준

- 12월 한 달 동안 '소싱테스트_통과' 유입이 14만 개 이상이거나, 미달이면 회차 보고로 **원인이 숫자로 보인다**(마켓 부족인지, 통과율 하락인지, 중복률 상승인지).
- 28765·엔잡곰·260930 계열 상품(네이버 번호가 대장에 있는 것)이 두 번 검수된 건이 0. 같은 타오바오 번호가 2차에 두 번 들어간 건이 0(대장 채우기가 끝난 범위에서).
- 용팀장이 매주 하는 일이 "월요일 카톡 한 줄 읽기"로 끝난다. 로그인 재요청은 한 달에 한 번 이하.

## 9. 빌더에게 맡기는 것

- 코드 위치: 기존 `sourcing-inspect` 스킬에 단계를 추가할지, `sourcing-pipeline` 스킬을 새로 둘지. 재사용을 우선한다.
- 브라우저 자동 조작의 세부: 로그인 상태를 어떻게 유지할지(전용 프로필), 캠페인 생성 화면의 입력 방법, 수집사이트 내보내기 범위 확인, 캠페인 ID를 화면에서 읽어 오는 방법. 소싱기 화면이 바뀌면 깨지므로 실패 시 즉시 카톡 알림이 가야 한다.
- 무인 스케줄의 실행 주체(맥북 launchd, 기존 sold-lock·auto-watch와 같은 방식)와 수집 완료 감지 규칙.
- 타오바오 대장 야간 채우기의 속도·시간대와 중단·재개 방식.
- 옛 9,398개 재검수 1회 작업의 순서(파이프라인 가동 전후 어느 쪽이든 무방).
- 대장 파일 형식의 세부, 수집사이트 엑셀 파일 파싱 방법, 보고서 양식.
- 중복 단계를 `run_inspect.py`의 새 단계로 넣을지 앞단 스크립트로 둘지.
- 모든 코드는 Python, 한국어 주석, try-except. 불사자 쓰기는 `apply_sourcing.py` 경로만 쓴다.
