# 불사자 소싱기 상품검수 자동화 (sourcing-inspect) — 설계

- 작성일: 2026-10-18
- 상태: 설계 초안 → 사용자 승인 대기

## 1. 목적

불사자 "엔잡곰소싱기"는 해외구매대행 마켓 약 3만 곳에서 1회 이상 팔린 상품을 캠페인 단위로 긁어 온다.
이 중 **팔 상품과 안 팔 상품을 가르는 검수**를 사람 대신 자동으로 처리한다. 사람은 기준을 정하고 결과를 가끔 훑어보기만 한다.

불사자에도 자체 "소싱워크플로우"(AI 자동검수)가 있지만, 판정을 100% 믿을 수 없어서 쓰지 않는다. 이 시스템이 그 자리를 대신한다.

### 대상 물량
- 1순위: 캠페인 **엔잡곰마켓** (campaignId `YWfs4MpPnVWHzYW`). 23,318건, 그중 21,738건이 타오바오 매칭 대기 상태.
- 2순위: 캠페인 **마켓 28765개 판매1이상** (campaignId `kwy9jllI5NICgPo`). 지금 수집 중이며 이후에 검수한다.
- 캠페인은 계속 늘어나므로 campaignId 를 인자로 받는다.

### 성공 기준
- 캠페인 하나의 전체 상품이 사람 손 없이 1차 → 이미지 매칭 → 2차 → 상품수집 → 마켓그룹 이동까지 흘러간다.
- 문제 상품(아래 §4 기준)이 마켓그룹으로 넘어가는 비율이 사람이 직접 검수했을 때보다 높지 않다.

### 실패로 보는 경우 (기술적으로 돌아가더라도)
- 금지 상품(지재권·위험물·금지 카테고리)이 마켓까지 올라간다. 놓친 상품 1건의 비용이 잘못 버린 상품 1건보다 훨씬 크다.
- 결과를 사람이 하나하나 다시 확인해야 한다. 그러면 자동화가 아니다.

## 2. 사용자 업무 흐름 (현재 수동 → 자동화 대상)

```
수집 (status=ready, taobao_match_status=pending)
  ↓
[1차 검수] 네이버 원본(왼쪽)만 보고 판정        ← 자동화
  ├ 탈락 → 휴지통
  └ 통과 → 체크 후 "이미지 매칭" 실행          ← 자동화
              ↓ (불사자 서버 비동기 처리, 대기 발생)
[2차 검수] 타오바오 매칭 상품(오른쪽)만 보고 판정 ← 자동화
  ├ 탈락 → 휴지통
  └ 통과 → 체크 후 "2. 상품수집" → 지정 마켓그룹 이동 ← 자동화
              ↓
(이후 기존 스킬: bulsaja-category-fix, product-name, option-cleanup 등. 범위 밖)
```

**핵심 원칙 (사용자 발언):** 2차에서는 왼쪽과 오른쪽이 같은 상품인지를 보지 않는다. 오매칭이라도 오른쪽(타오바오) 상품이 구매대행으로 팔아도 되는 물건이면 살린다. 어차피 팔 건 오른쪽 상품이고, 카테고리와 상품명은 이후 스킬로 다시 고치기 때문이다.

## 3. 데이터 원천 (2026-10-18 실측)

불사자 웹 API(`https://api.bulsaja.com`). 불사자 MCP 도구에는 소싱기 기능이 없다.

| 용도 | 엔드포인트 | 확인 상태 |
|---|---|---|
| 캠페인 전체 상품 목록 | `POST /api/sourcing/bulsa-sourcing-products` body `{"campaignId": "..."}` → `{success, data:[...]}`. 23,318건을 한 번에 반환(약 30MB) | **실측 완료** |
| 작업 그룹 | `GET /api/sourcing/work-groups?campaignId=` | 실측 (빈 배열) |
| 상품 상세 | `/api/sourcing/bulsa-sourcing-product-detail` | 경로만 확인 |
| 상태 일괄 변경 (휴지통 등) | `/api/sourcing/bulk-change-status` | 경로만 확인. **body 형식 미확인** |
| 검토 완료 처리 | `/api/sourcing/bulk-review-complete` | 경로만 확인 |
| 이미지 매칭 실행 | 미확인 (UI 버튼 동작) | **미확인** |
| 상품수집 / 그룹 이동 | `/api/sourcing/bulk-copy-market-group`, `/api/sourcing/bulk-update-groups` 추정 | **미확인** |
| 캠페인 정보 | `/api/sourcing/campaign/...` | 경로만 확인 |

### 상품 1건의 필드 (실측)
- 네이버 원본: `productName`, `productImageUrl`, `catId`(네이버 리프 카테고리 번호), `productPrice`, `sellerTags`, `brand`, `mallName`, `productUrl`, `salesCount`, `reviewCount`
- 타오바오 매칭: `taobaoResult[]`. 항목마다 `item.title`(중국어), `item.image`, `item.sku.def.price`, `item.itemUrl`, `item.itemId`가 있다. `averageTaobaoPrice`, `_hasHiddenCandidates`(후보가 여러 개) 도 있다.
- 기타: `overseaDeliveryFee`(원), `autoReview`(불사자 자체 AI 점수. 참고만 하고 판정에는 쓰지 않는다)
- 상태: `status` ∈ {`ready`, `first_review`, `reviewed`, …}, `taobao_match_status` ∈ {`pending`, `match_failed`, 없음}
- **무게 필드는 없다.** 100kg 판정은 `overseaDeliveryFee`와 비전 판정으로 추정한다.

### 인증
- 웹 로그인 JWT 를 쓴다(브라우저 localStorage `token`). 이 토큰은 **만료된다**(실측: 오래된 토큰은 401).
- 사용 계정: 구글 **cy17281728** 로 로그인한 불사자 계정. 맥북 Claude 크롬 프로필(Browser 2)에 현재 이 계정으로 로그인돼 있다. 이 프로필은 기본값이 cy728728 자동 로그인이라 계정이 바뀔 수 있다.
- MCP 토큰(`~/.claude.json`)과 인증 수단은 별개지만 **같은 불사자 계정**이다(사용자 확인 2026-10-18). 그래서 수집된 상품을 기존 스킬(category-fix·product-name 등)이 그대로 이어받는다. MCP 쪽 설정은 건드리지 않는다.

## 4. 판정 기준

판정 기준은 코드가 아니라 **규칙 파일 하나**에 둔다. 사용자가 계속 덧붙이기 때문이다.

### 4-1. 금지 카테고리 번호 (1차, 기계 판정)
- 사용자가 준 네이버 카테고리 번호 3,290개(작성자: 사용자 배우자). 원본: `docs/superpowers/specs/2026-10-18-sourcing-inspection-banned-cats.txt`(한 줄에 하나). 구현 때 규칙 파일로 옮긴다.
- 227개는 `30-knowledge/39-naver-category/naver-category-master.json` 의 리프 목록에 없다. 중간 단계 번호면 하위 리프까지 펼쳐서 적용하고, 폐지된 번호면 무시한다. 펼친 결과는 로그로 남긴다.
- 알려진 빈틈: 패션의류는 102개 중 56개만, 패션잡화는 320개 중 193개만, 화장품/미용은 191개 중 80개만 금지돼 있다. 사용자가 배우자에게 확인 후 답을 주기로 했다(2026-10-19 예정). **그 전에는 목록을 그대로 쓰되, 아래 4-2의 AI 판정이 패션·화장품을 따로 잡는다.**

### 4-2. 판매 불가 품목 (AI 판정)
사용자 기준과 스터디 공용 "구매대행 취급 불가" 26개 목록을 합친 것이다.

| 분류 | 품목 |

| 법규 | 뜰채·채망(어업법), 수전·샤워기(수도법), 가스·다이빙·LP·산소탱크, 의료용품, 휠체어, 무전기, 화장품(페이스페인팅 물감 포함), 스프레이류, 가습기 |
| 위험물 | 타카건·타카용품, 호신용품, 총기·가검·긴 검(총 모양 장난감 포함), 철장갑(방검장갑), 가축몰이 전기채·짖음방지기, 칼 |

| 기타 | 밤까는기계 |

- "웬만하면 안 함" 항목(캠핑·골프)과 애매한 경계(아이도 쓰는 일반 문구 등)는 **삭제** 쪽으로 판정한다. *(작성자 판단: 놓친 상품의 비용이 더 크다는 사용자 원칙을 따름)*
- 판정마다 사유 코드를 하나 남긴다. 사람이 결과를 훑을 때와 규칙을 고칠 때 쓴다.

### 4-3. 1차와 2차가 보는 것
| | 보는 것 | 주로 잡는 것 |
|---|---|---|
| 1차 (매칭 전) | `catId`, `productName`, `sellerTags`, `brand`, `productImageUrl`(네이버 썸네일) | 금지 카테고리, 금지 키워드, 패션, 브랜드, 캐릭터 |
| 2차 (매칭 후) | `taobaoResult` 대표 항목의 `title`·`image`·`price`, `overseaDeliveryFee` | 파손, 대형, 캐릭터·디자인 지재권, 매칭되면서 새로 생긴 금지품목 |

1차에서 걸러야 이미지 매칭 대기와 2차 판정 물량이 줄어든다.

## 5. 구조 (작성자 판단 — 기존 패턴을 따름)

워크스페이스의 기존 팬아웃 파이프라인(`catfix-fanout`, `thumb-fanout` 등)과 같은 3단 구조로 만든다.

1. **수집 (Python)**: API로 캠페인 전체를 받아 run-dir 에 스냅샷으로 저장한다. 상태별로 작업 대상을 고른다.
2. **기계 판정 (Python)**: 금지 카테고리 번호와 금지 키워드로 거른다. 비용 0. 여기서 걸린 건 AI에 보내지 않는다.
3. **AI 판정 (Workflow 팬아웃, Sonnet 워커)**: 남은 상품을 썸네일 장수 예산으로 배치에 나눠 판정한다. 결과는 run-dir 의 배치별 파일이 정본이다. 중간에 죽으면 남은 배치만 다시 돈다.
4. **반영 (Python)**: 판정 결과로 휴지통 이동, 이미지 매칭 실행, 상품수집과 그룹 이동을 API로 일괄 처리한다.

- 진실의 원천은 **불사자 서버 상태**다. 재실행하면 서버에서 다시 받아 이미 처리된 건은 건너뛴다. 로컬 대장을 정본으로 삼지 않는다.
- 스킬 하나(`sourcing-inspect`)로 묶고 "검수 돌려줘" 류 말로 시작한다.
- 1차와 2차 사이 대기: 이미지 매칭은 불사자 서버가 비동기로 처리한다. 같은 명령을 다시 돌리면 그 시점에 매칭이 끝난 상품만 2차로 집는다(폴링 데몬은 만들지 않는다). 정기 실행 여부는 범위 밖이다.

## 6. 안전장치

- **dry-run 먼저**: 모든 쓰기 작업은 미리보기(건수·사유별 분포·샘플)를 먼저 낸다.
- **파일럿**: 처음에는 엔잡곰마켓 500건 정도만 판정하고 결과를 사람이 훑는다. 반영은 하지 않는다. 기준이 맞으면 전량 자동 반영으로 넘어간다. *(작성자 판단)*
- 파일럿 이후 삭제는 묻지 않고 실행한다(기존 상시 위임 "삭제후보는 묻지 말고 바로"와 같은 원칙). 휴지통 이동이라 되돌릴 수 있다는 전제다. **영구 삭제는 하지 않는다.**
- 반영 전에 대상 상품 id 목록과 이전 상태를 run-dir 에 백업한다(되돌리기용).
- 웹 토큰이 만료되면 401에서 멈추고, 사용자에게 Claude 크롬 프로필에서 다시 로그인해 달라고 요청한다. 비밀번호는 다루지 않는다.

## 7. 아직 모르는 것 (구현 첫 단계에서 실측)

1. `bulk-change-status`, 이미지 매칭, 상품수집, 그룹 이동의 **요청 형식**. 사용자가 UI에서 1건씩 직접 누르는 동안 네트워크를 관찰해서 확보한다(Claude 가 누르지 않는다).
2. 휴지통이 별도 status 값인지, 휴지통 이동이 되돌릴 수 있는지.
3. 상품수집 대상 마켓그룹: **"신규소싱상품"** 마켓그룹(사용자 확정, 모든 캠페인 공통 기본값). 그룹 ID 는 실측으로 확인하고 인자로 바꿀 수 있게 둔다.
4. 스크립트가 JWT 를 어떻게 얻는지. Claude 크롬 프로필에서 읽어 오는 방법과 로그인된 브라우저 안에서 호출하는 방법 중 하나를 고른다(빌더 결정).
5. 30MB 전체 목록을 매번 받을지, 상태 필터 파라미터가 있는지.

### 7-1. 작성자 판단으로 정한 것 (검토 후 추가)
- **다시 검수할 대상**: 이미 `first_review`·`reviewed` 상태인 상품도 이 시스템 기준으로 다시 판정한다. 그 상태는 불사자 자체 판정 결과라 믿지 않기 때문이다. 1차 대상은 `taobaoResult`가 비어 있는 상품이고, 2차 대상은 `taobaoResult`가 있는 상품이다. 재실행할 때 건너뛸지는 서버 상태(휴지통 여부, 수집 여부)로 판단한다. `pending`이 "요청 전"인지 "처리 중"인지는 §7 실측에서 확인하고, 처리 중이면 1차 판정 후 탈락 건만 휴지통으로 보낸다.
- **매칭 실패**(`match_failed`)와 2차 시점에 매칭 결과가 비어 있는 상품은 휴지통으로 보낸다. 처리량이 우선이라는 기존 원칙("막히면 삭제하고 넘어간다")을 따른다.
- **`brand` 필드**는 값이 있다는 것만으로 탈락시키지 않는다. AI 판정의 입력으로만 쓴다.
- **AI 비용 구조**: 1차는 기계 판정 다음에 **텍스트 판정**(상품명·태그·카테고리 경로) 위주로 하고, 비전은 텍스트로 판단이 애매한 건에만 쓴다. 비전 판정은 2차의 기본이다. Claude Code 구독 안의 Workflow 워커로 돌린다(별도 API 과금 없음). 파일럿 때 처리 속도를 재서 전량 소요시간을 보고한다.
- **크레딧**: 이미지 매칭이나 상품수집에 크레딧·한도가 들면, 프로젝트 원칙대로 첫 실행 전에 견적을 보고한다. 화면의 사용 한도 표시(타오바오 9,999,998/400 등)로 보면 사실상 무제한일 가능성이 높다.
- **파일럿 합격 기준**: 파일럿 500건의 결과표(통과·탈락, 사유, 썸네일)를 사용자가 훑어본다. 통과 쪽에 금지품이 0건이고 탈락 쪽 오판이 사용자가 보기에 수용할 만하면 합격이다. 사람 라벨 기준값은 따로 만들지 않는다.

### 7-2. 파일럿 실측 (2026-10-18 밤)
- **토큰**: 웹 API 헤더는 `accesstoken`(7일) + `refreshtoken`(30일)이다. `scripts/web_token.py`가 Claude 크롬 프로필의 localStorage 에서 cy17281728 의 최신 쌍을 꺼내 `~/.eroom/bulsaja-web.json`에 저장한다(값은 출력하지 않음). 이후 Python 이 전체 목록 23,318건을 4초 만에 받는다.
- **금지 카테고리 번호**: 엔잡곰마켓 23,318건 중 걸린 게 **0건**이다. 불사자가 수집 단계에서 이미 거르고 있다. 227개 미등록 번호는 중간 단계 번호가 아니었다(마스터 전체에 없음). 그래서 펼칠 필요 없이 그대로 쓴다. 대신 **타오바오 매칭 후 다른 분야로 바뀌는 경우**를 막으려고 금지 분야를 AI 기준표(`CATEGORY`)에도 넣었다.
- **키워드 기계 판정**: 판매자 태그와 공백 제거 비교는 오탐이 많았다. 그래서 상품명만, 단어 경계를 유지해서 본다(2차는 타오바오 제목만). 엔잡곰 1차 기계 탈락은 632건이고 대부분 "호환"이다.
- **기준 보정**: ① SHIP 이 침대·테이블·옷장까지 떨어뜨려서 "100kg 이상 또는 깨지는 것"으로 좁혔다. ② 중국 내수 공장 브랜드는 IP 탈락에서 뺐다. ③ 금지 분야(CATEGORY)를 추가했다.
- **파일럿 결과(3차 기준)**: 1차 500건 중 통과 317 / 탈락 183. 2차 200건 중 통과 115 / 탈락 85. 누락과 지어낸 id 는 0건이다.
