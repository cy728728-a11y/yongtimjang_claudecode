- 배경은 **톤만 고정하고 공간은 상품에 맞춘다**
  (고정 톤 6개: 크림 오프화이트 벽 · 밝은 오크 · 왼쪽 위 자연광 · 오른쪽 아래 접지그림자 · 저채도 웜 · 베이지 걷은 소매)
- 제품 보존 실측 확인됨 — 불사자 내부 AI 는 68% 변조, gpt-image-2 는 6장 전부 정확

#### 이 문서의 옛 서술 3건이 틀렸다 (2026-09-01·09-08 실측)

| 옛 서술 | 실측 결과 |
|---|---|
| 커머스API 앱 권한에 상품 조회 스코프가 없다(403) | **오진.** 스코프는 있다 — `POST /v1/products/search` 200. 403 은 **그 상품이 다른 스토어 소유**라서 났다 |
| 원본 이미지는 불사자 `uploadThumbnails`·`urlRef` 에서 받는다 | **돌아가는 길이었다.** 광고 API 의 `referenceData` 에 `imageUrl`·`mallProductUrl`·`mallNo` 가 이미 다 있다 |
| `uploadedSuccessUrl.smartstore` 대조로 불사자 상품이 1:1 확정된다 | 대조 자체는 맞다. 그러나 **역방향 조회 API 가 없어** 상품명으로 후보를 훑어야 하고, 표본 8건 중 **1건만 매칭(12.5%)**. 3건은 후보 0건(불사자 쪽 이름이 이미 달라짐) |

**그래서 불사자를 파이프라인에서 뺀다.** `mallProductId` 가 곧 커머스API 의 키라서
조회부터 교체까지 한 API 안에서 닫힌다. 매칭률을 끌어올릴 필요가 없어졌다.

```
②리스트(mallProductId + imageUrl)  →  원본 다운로드  →  gpt-image-2 생성
   →  커머스API 이미지 업로드  →  PUT 대표이미지 교체
```

검증 상태: 조회 200 · 이미지 업로드(`POST /v1/product-images/upload`) 200 **실측 확인**.
마지막 `PUT`(대표이미지 교체)만 미검증 — 실제 스토어를 건드리므로 승인 후 1건으로 검증한다.

#### 진짜 병목 — 스토어당 앱 1개

권한이 아니라 구조다. **커머스API 는 스토어별로 앱을 최대 1개**만 등록할 수 있는데
광고에 걸린 스마트스토어가 **37개**다. 현재 루트 `.env` 의 앱은 `제이제이비컴퍼니` 한 곳만 잡는다.

| 발급 앱 | ②198건 중 커버 |
|---|---|
| **5개 (파일럿 확정)** | 97건 · **49%** |
| 10개 | 131건 · 66% |
| 20개 | 178건 · 90% |
| 37개 | 198건 · 100% |

주당 처리는 노출 상위 20건인데 **그 20건이 11개 스토어에 흩어진다** — 5개로 시작하면
주간 처리량도 그만큼 잘린다. 파일럿 결과를 보고 늘릴지 판단한다.

**교체할 값어치는 확인됐다** — ②리스트 198건 중 **193건(97%)이 등록 180일 초과, 중앙값 338일**.

#### 합의된 스킬 구조 (승인 대기)

별도 스킬 `naver-ads-thumbnail` 로 뺀다 — 주간 배치는 쓰기를 안 한다는 원칙을 지켜야 하고,
이건 실제 스토어에 쓰므로 승인 게이트가 따로 필요하다.

| 명령 | 하는 일 | 쓰기 |
|---|---|---|
| `prep` | 커버되는 스토어만 남겨 상품·대표이미지 조회, 원본 다운로드, **원본 URL 백업** | 없음 |
| `run` | gpt-image-2 생성 → 3축 검수 → 합격분만 후보 | 없음 |
| `apply --commit` | 이미지 업로드 → 대표이미지 교체 → 시트 원장 기록 | **스토어** |
| `revert --commit` | 백업한 원본 URL 로 되돌린다 | **스토어** |

`--commit` 없으면 전부 dry-run. `bids`·`prune` 가드레일을 그대로 따른다.
**이 4진입점 구조는 아직 용팀장 승인 전이다** — 승인되면 생성·검수 파이프라인 설계로 넘어간다.

이미 만들어 둔 것: `.claude/skills/naver-ads-thumbnail/scripts/verify_creds.py` (커밋됨) ·
`~/.eroom/naver-commerce.json.example`

### 3. 물갈이 후 광고 재투입 (자동화 막힘)

물갈이 재업로드 뒤 **광고에 소재를 새로 넣는 일**은 여전히 수작업이다
(네이버 광고 UI 에서 미투입 상품 전체 선택).

**2026-08-30 실측: 광고 API 에 "광고 미투입 상품 목록" 엔드포인트가 없다.**
`/ncc/product-group` · `/ncc/shopping-products` · `/tool/shopping-products` ·
`/ncc/channel-products` 전부 404. 비즈채널(`/ncc/channels`) 아래에도 상품 목록이 없다.

소재 등록(`POST /ncc/ads`) 자체는 `nccAdgroupId` + `referenceKey`(네이버쇼핑 상품ID) + `type`
만 있으면 될 것으로 보이나, **재업로드된 새 상품의 `referenceKey` 를 얻을 방법이 없다.**

**커머스API 우회는 살아있는 선택지다 (2026-09-08 정정).** 앞서 "앱 권한에 상품 조회 스코프가
없다(403)"고 적었던 건 오진이다 — 스코프는 있고, 403 은 남의 스토어 상품을 불렀기 때문이었다.
`POST /v1/products/search` 로 그 스토어 상품을 전부 나열할 수 있으므로,
**재업로드된 새 상품을 찾아 `referenceKey` 를 얻는 길이 열려 있다.**
다만 §2 와 같은 제약을 받는다 — 스토어당 앱 1개, 37개 스토어. §2 파일럿이 먼저다.

## 반드시 알아야 할 함정 5가지

1. **`/stats` 의 `convAmt`·`ccnt` 는 장바구니 포함 총전환이다.** 구매완료는 `AD_CONVERSION` 리포트의
   `purchase` 유형만. 실측 차이 **14배**(총전환 ROAS 3,844% vs 구매완료 275%).
2. **`salesAmt` 는 매출이 아니라 광고비다.**
3. **그룹입찰 상품의 인상 출발점은 그룹 기본가다.** 소재의 `bidAmt` 는 잠자는 값이다
   (실측: 잠자던 값 50 / 그룹 기본가 150 — 헷갈리면 올리려다 90원 내린다).
4. **노출 0 소재는 `/stats` 응답에서 행 자체가 빠진다.** 그래서 규칙 ① 은 역산이다.
5. **리포트는 D-2 부터 쓸 수 있다.** D-1 은 `20007 지표 준비중`.

## 미해결

**`AD_ABNORMAL_INTERLOCK` 은 고장이 아니다 — 물갈이 20일 사이클의 부산물이다** (2026-08-30 확인).
물갈이 삭제로 스마트스토어 상품이 사라지면 광고 소재가 연동을 잃고 자동 정지된다.
