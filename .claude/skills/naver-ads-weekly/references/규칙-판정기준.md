# 네이버 광고 주간 관리 — 규칙 판정기준

> 규칙 전문·가드레일·전환 함정을 모아둔 곳. **여기 한 벌만 있다** — SKILL.md 는 요약+링크다.
> 코드로는 `scripts/ads_rules.py`(6개 규칙 판정) · `scripts/ledger.py`(입찰 이력) ·
> `scripts/bids.py`(①번 실행) · `scripts/prune.py`(⑥번 실행) · `scripts/reports.py`(전환 리포트).
> 설계 근거의 전체 실측 기록은 `docs/superpowers/specs/2026-08-27-naver-ads-weekly-design.md`.

## 반드시 지킬 것 3가지

- `/stats` 의 `convAmt`·`ccnt` 는 장바구니 포함 총전환이다. 구매완료는 `AD_CONVERSION` 리포트의 `purchase` 유형만.
- `salesAmt` 는 매출이 아니라 광고비다.
- 그룹입찰 상품을 개별 전환할 때 출발점은 `잠자던 bidAmt` 가 아니라 `그룹 기본입찰가` 다. 헷갈리면 올리려다 내린다.

## 1. 전환 함정 — `/stats` 를 매출로 쓰지 않는다

`/stats` 응답의 `ccnt`(전환수)·`convAmt`(전환매출액)은 **전환유형을 전부 합산**한 값이다.
장바구니 담기(`add_to_cart`)가 구매완료(`purchase`)와 섞여서 나온다. `breakdown` 파라미터로
쪼개려 해도 **조용히 무시된다** — 400 을 주지 않고 200 에 안 쪼개진 값을 준다. 이게 가장
눈치채기 어려운 함정이다.

**cy728 실측 (30일, 2026-07-27~08-25)**

| 전환유형 | 발생 소재 | 금액 |
|---|---|---|
| `add_to_cart` | 24개 | 7,321,700원 |
| `purchase` | 5개 | 596,920원 (12배 차이) |

**4계정 합산 실제 성과**로 보면 착시가 더 뚜렷하다 — 총전환 기준 ROAS **3,844%**, 구매완료
기준 ROAS **275%**. 14배 넘게 부풀어 보인다.

> **보고서에는 구매완료 기준만 싣는다 (2026-08-28 용팀장 지시).**
> `장바구니`·`총전환`·`add_to_cart` 라는 낱말이 보고서(`report_md.build_report`)에 나오면 안 된다.
> 위 표는 "왜 `/stats` 값을 쓰면 안 되는가"를 남기는 설계 근거일 뿐, 실제 주간 보고서 표기가 아니다.

**구매완료를 뽑는 방법**: `POST /stat-reports {"reportTp": "AD_CONVERSION"}` 로 일자별 TSV
리포트를 받는다. 컬럼은 0-based 로 `adId`=5, `convType`=10, `cnt`=11, `amt`=12 (`reports.py`
의 `_COL_*` 상수). `convType == "purchase"` 인 행만 더한다. **리포트는 하루치씩만 생성된다** —
30일치면 30회 생성·폴링·다운로드해야 하고, `reports.fetch_purchases` 가 그 루프를 돈다.

**짧은 기간은 구매완료를 0으로 보이게 한다.** cy7728 을 6일 표본으로 봤을 때 `purchase` 가
0건이라 전환추적 미설정을 의심했지만, 같은 계정을 30일 전수로 다시 재니 `purchase` 5건·
493,730원이 나왔다. 구매완료는 절대 건수가 워낙 적어서(계정당 30일에 5건 안팎) 짧은 기간으로
보면 그냥 사라진다. **그래서 ③⑤ 는 30일 고정이다.** 그래도 30일 기준 0건인 계정이 나오면
"이 계정은 광고 경유 구매완료 0건"이라는 명시적 경고로 싣는다 — 계정 손익이 드러나는 자리다.

## 2. 노출 0 — 역산과 검수대기 제외

`/stats` 응답에서 **노출 0 소재는 행 자체가 빠진다**(`impCnt: 0` 으로 나오지 않는다). 그래서
규칙 ①의 대상은 다음 뺄셈으로 구한다(`ads_rules.classify` 의 `r1`):

```
게재중(enable=true) 소재 전체  −  7일 통계 응답에 있는 소재  −  검수 대기 중인 소재
```

**검수 대기는 반드시 뺀다.** 검수 중(`PENDING`·`UNDER_REVIEW`, `ads_rules.INSPECT_WAITING`)인
소재는 노출이 없는 게 정상이고, 입찰가를 올려도 노출이 생기지 않는다. 이걸 안 거르면 검수
중인 상품의 입찰가만 매주 헛되이 올리게 된다. 실측 격차가 크다:

| 계정 | 검수대기 소재 수 |
|---|---|
| cy728 | 5건 |
| ownway1 | **988건** (게재중 1,360개 중 73%) |

cy728 만 보고 "검수대기 제외"를 사소한 예외처럼 여기기 쉬운데, ownway1 이 이 규칙의 가치를
증명했다. 규칙 ①이 검수 중 소재를 걸렀다면 매주 988개 상품의 입찰가가 헛되이 올랐을 것이다.

**노출 0이 예산 부족 때문이 아니다.** 2026-08-30 실측: 노출0 비율이 cy728 4%·cy7728 8%·
ownway1 88%·pogeunae 75% 인데, 일일예산 소진율은 26~68% 로 예산이 남는다. 상품 수 대비
예산이 얇아(ownway1 은 상품당 22원) 개별 경쟁력이 없는 구조로 보인다. **입찰 인상은 예산
캡 안에서 도므로 안전하다** — 예산을 넘겨 쓰지 않는다.

## 3. `mallProductId` — 검수 통과 전에는 없다

소재의 `referenceData.mallProductId`(스마트스토어 채널상품ID)는 **검수를 통과(`APPROVED`)
해야 채워진다.** 검수 중 소재의 `referenceData` 는 12개 필드뿐이고, 승인 소재는 48개 필드다.
ownway1 실측: 게재중 1,360개 중 승인 372개는 전원 보유, 검수중 988개는 전원 미보유.

실질 영향은 작다 — 규칙 ②는 노출 100회 이상 조건이라 노출이 없는 검수 중 소재는 자연히
걸러진다. 다만 매칭·표시 코드는 `mallProductId` 가 `None` 인 경우를 안전하게 다뤄야 한다
(`ads_rules.ad_info` 는 `rd.get("mallProductId")` 로 없으면 `None` 을 그대로 돌려준다 —
호출부가 이걸 빈 문자열처럼 취급하면 된다).

## 4. 판정 기간·노출 하한 — 확정값과 근거

cy728 게재중 224개를 기간·하한을 바꿔가며 실측했다(2026-08-27).

| 규칙 | 기간 | 하한 | 근거 |
|---|---|---|---|
| ① 노출0 → 입찰 +10원 | **7일** | enable=true 만 | 30일이면 6건뿐(방치성 상품과 성격이 다름). 7일이면 14건 — 주간 액션에 맞는 크기 |
| ② CTR<1% → 썸네일 교체 | **30일** | **노출 100+** | 하한 없이는 147건(전체의 66%). 100+ 면 45건으로 실용적 |
| ③ 클릭20+/구매완료0 | **30일** | — | 짧은 기간엔 구매완료가 표본에서 사라짐(§1) |
| ④ CTR≥2% → 효자 후보 | **30일** | **노출 100+** | ②와 대칭 — 32건 |
| ⑤ 구매완료 발생 → 효자 확정 | **30일** | — | 14일에 1건뿐이라 표본 부족 |

코드 상수(`ads_rules.py`): `IMP_MIN = 100` · `CLICK_MIN = 20` · `CTR_LOW = 1.0` · `CTR_HIGH = 2.0`.

**② 는 주당 상위 20건만 처리한다** (`report_md.TOP_N = 20`, 노출 많은 순 정렬). 30일 45건을
매주 전부 썸네일 재생성하면 크레딧이 샌다. 노출은 많은데 클릭이 안 되는 상품이 썸네일 문제가
가장 확실하므로 그 순서로 자른다. 시트 기록(`sheets_out.py`)은 자르지 않고 전량 append 한다
— 상한은 마크다운 보고서에만 적용된다.

**최종 리뷰 Important 5 — ①③④ 도 마크다운 표에서는 top_n 으로 자른다.** ①은 하한이 없어
ownway1 실측 1,195행 하나만으로 `report.md` 가 298KB(2,694줄)까지 불어났다 — 문서 존재
이유가 "시트를 열지 않고 읽는 것"인데 이 크기면 아무도 안 읽는다. `report_md.build_report`
가 ①③④ 표에도 `limit=top_n`·`_count_label` 을 적용해(②와 같은 방식) 잘렸으면 "N건 중
상위 20건"으로 명시한다(41KB 로 축소 확인, 2026-08-30). **잘리는 건 표시일 뿐이다** —
`bids`·`prune` 은 `report.md` 가 아니라 `result.json` 전체를 읽어 처리하므로 실행 대상은
줄지 않는다. 시트는 여전히 자르지 않고 전량 append 한다. ⑤는 계정당 20건 미만이라 그대로 둔다.

## 5. 입찰 인상(①) 가드레일 8종

`bids.run_bids` / `ledger.py` 구현 기준.

1. `enable=true` 인 소재만 (`ads_rules.live_ads`)
2. **7일** 노출 0 인 소재만. 30일 노출0(즉 한 달 내내 죽은 상품)은 입찰 인상 대상이 아니라
   별도로 다뤄야 할 방치 후보다 — 판정 결과의 ①은 7일 기준 리스트만 담는다
3. 개별입찰이면 `bidAmt + 10`. 그룹입찰(`useGroupBidAmt: true`)이면 **개별 전환 +
   `그룹 기본입찰가 + 10원`** 으로 시작한다(`bids.plan_raise` 의 `base` 계산). 잠자던
   `bidAmt` 를 쓰면 안 된다 — 그룹값(예: 70원)보다 낮은 경우가 많아(실측 50원) 입찰가가
   **내려간다.** 전환은 가역적이다(§7).
4. 상한 **200원**(`ledger.BID_CAP`). 도달하면 인상하지 않고 사유 `"상한도달"` 로 표시된다.
   실측 개별입찰 상품의 현재가 분포는 80~130원이라, 80원짜리는 12주·130원짜리는 7주 만에
   상한에 닿는다 — 이 리스트는 몇 달 안에 실제로 쌓인다. 입찰가로 안 풀리는 상품이라는
   뜻이므로 키워드·카테고리·상품 자체를 봐야 한다.
5. **3주 연속 인상했는데도 노출 0** 이면 인상을 중단한다(`ledger.FAIL_STREAK = 3`, 사유
   `"연속실패중단"`). 상한에 닿기 전에 가망 없는 소재를 걸러내는 빠른 경로다.
6. 실행 전 원본 `adAttr` 를 `<run-dir>/before_bids_<계정>.json` 에 백업한다. 백업이 실패하면
   인상 자체를 중단한다(`bids.run_bids` 의 `aborted: "backup_failed"`).
7. 실행 결과(인상/상한도달/연속실패중단/입찰가불명 건수)를 이력에 기록한다.
8. **오늘 이미 인상한 소재는 다시 올리지 않는다**(`ledger.bid_decision` 의 `today` 인자,
   최종 리뷰 Critical 1). `bids --commit` 이 중간에 죽고 `prep && run && bids --commit` 으로
   자연스럽게 복구하면, `plan_raise` 가 목표 입찰가를 스냅샷의 `bid` 에서 계산하기 때문에
   이력을 안 보면 이미 100→110 된 소재가 그날 다시 110→120 으로 오른다. `run_bids` 가
   오늘 날짜를 `plan_raise` 에 넘기고, 이력에 그 소재의 오늘 날짜 (되돌리지 않은) 인상
   기록이 있으면 사유 `"오늘이미인상"` 으로 건너뛴다.

`ledger.bid_decision` 이 돌려주는 사유 문자열은 5가지다: `"인상"` · `"상한도달"` ·
`"연속실패중단"` · `"입찰가불명"`(현재 입찰가를 못 구한 경우) · `"오늘이미인상"`.

### 가드레일 5는 배선이 필요하다 — 그리고 "회복" 판정은 실제 노출로만 한다

`ledger.py` 에 `record_still_zero`·`record_recovered` 함수가 있어도, **부르는 곳이 없으면
`streak` 이 영원히 0** 이라 "3주 연속 노출 0 이면 중단" 규칙이 실전에서 절대 발동하지 않는다.
`bids.update_streaks` 가 그 배선이다 — `run_bids` 가 **판정보다 먼저** 호출해서, 지난 회차에
올린 소재가 이번 회차에도 여전히 노출 0인지 반영한 뒤에 이번 회차 판정을 시작한다. 같은
회차를 두 번 돌려도 streak 이 중복으로 오르지 않도록 `_last_streak_update` 날짜로 막는다.

**최종 리뷰 Critical 2 — "①에 없음" ≠ "노출 회복".** 규칙 ①은 검수중·비활성·삭제된 소재를
제외하므로, 상품명을 한 번 고쳐 검수에 들어가기만 해도 이번 회차 ①노출0 목록(`zero_ids`)
에서 빠진다. 이걸 무조건 "인상이 통했다"로 보고 `record_recovered` 를 부르면 streak 이
조용히 0으로 리셋돼 "3주 연속 중단"이 영원히 발동하지 않는다(ownway1 실측: 검수중 988건).
그래서 `update_streaks` 는 `recovered_ids` 를 별도로 받는다 — `run_bids` 가 이번 회차
`stats_7d.json` 을 읽어 그 안에 행이 있는(= 실제로 노출이 생긴) 소재 id 집합을 넘긴다.
`zero_ids` 에도 `recovered_ids` 에도 없는 소재(검수중 등으로 ①에서 빠졌지만 노출도 없는
것)는 streak 을 **건드리지 않는다**(유지).

### 이력 파일 위치

`<data_root>/naver-ads/ledger/<계정alias>.json` — run-dir 이 아니라 계정별 고정 위치다
(회차가 바뀌어도 연속 실패 판정이 이어져야 하므로). `data_root` 는 `eroomlib.config` 의
`paths.data_root` 설정을 우선하고, 없으면 `~/python_work/data`.

## 6. 되돌리기 — `bids --revert`

`bids --revert`(`bids.run_revert`)가 `before_bids_<계정>.json` 백업을 읽어 각 소재의 원본
`adAttr` 을 그대로 다시 `PUT` 한다(`bids.build_revert_body`) — `useGroupBidAmt` 도 함께
복원되어 개별 전환도 취소된다(§7의 가역성 실측 근거). `--commit` 없이는 무엇을 되돌릴지만
보여준다. 되돌린 소재는 이력에서 지우지 않고 마지막 인상 항목에 `reverted` 플래그를 남긴다
(`ledger.record_reverted`) — 그래야 `bid_decision` 의 "오늘이미인상" 판정(§5 가드레일 8)이
되돌린 뒤 같은 날 다시 인상하는 걸 막지 않는다. `result.json` 이 필요 없다 — 백업 파일과
`ads.json` 스냅샷만 있으면 된다.

## 7. 입찰가 쓰기 — 실측 검증된 사실

- 쓰기 방법: `PUT /ncc/ads/{adId}?fields=adAttr`, body 는 **조회한 소재 객체 전체**에서
  `adAttr` 만 교체(`bids.build_body`). `fields=bidAmt` 같은 다른 방법은 검증되지 않았다.
- `useGroupBidAmt` 전환은 **가역적**이다(2026-08-27 실측): 그룹입찰 → 개별입찰 → 그룹입찰로
  되돌려도 200 이 오고 값이 정확히 복원된다. "개별입찰로 바꾸면 그룹 연동을 영구히 잃는다"는
  우려는 틀렸다.
- `apply_raise` 도 `prune.delete_ads` 와 같은 회복력을 갖는다(최종 리뷰 Important 9):
  429·500·502·503·연결 오류는 최대 4회 재시도(지수 백오프), 성공 시까지 페이싱 0.08초.
  2,242건 연속 PUT 중 429 하나로 그 소재가 그 주 인상에서 빠지던 문제를 없앤다.


**판정 결과의 `⑥삭제대상`(`ads_rules.classify`)은 `enable=false` 인 소재 전체를 담는다** —
사유를 가리지 않는다. 실제로 지우는 건 그중 **일부뿐이다.** `prune.deletable()` 이
`statusReason == "AD_ABNORMAL_INTERLOCK"`(연동 비정상)인 것만 다시 걸러
`prune.DELETE_REASONS` 로 좁힌다. 검수중(`AD_UNDER_REVIEW`)과 검수거부(`AD_DISAPPROVED`)는
보고엔 잡히지만 지우지 않는다 — 검수중은 곧 살아나고, 거부는 고쳐서 재검수할 수 있어
지우면 둘 다 재등록 노동이 된다. `report.md` 의 "⑥ 꺼진 소재" 건수도 전체(off) 기준이므로
"삭제될 것"으로 읽으면 안 된다 — 실제 삭제 대상은 `prune` 실행 로그의 `삭제대상 N` 이다.

삭제 API: `DELETE /ncc/ads/{adId}` → 성공 `204`, 이미 없으면 `404`(둘 다 성공으로 처리).
`429`·`500`·`502`·`503`·연결 오류는 최대 4회 재시도(지수 백오프)한다.

**삭제 전 전량 백업이 선행 조건이다.** 백업이 실패하면 그 계정은 삭제를 건너뛴다
(`prune.run_prune` 의 `aborted: "backup_failed"`). 백업·진행 파일 위치:

```
<data_root>/naver-ads/paused-backup/paused_<계정>_<날짜>.json     # 삭제 대상 전량(재등록용)
<data_root>/naver-ads/paused-backup/delete_progress_<계정>.jsonl  # 건별 진행(재실행 시 건너뜀)
```

진행 파일은 **성공한 것만** "완료"로 건너뛴다 — 하드 에러(400·403 등)까지 건너뛰면 실제로는
안 지워졌는데 영영 재시도하지 않고 매주 조용히 스킵된다.

**최종 리뷰 Critical 3 — commit 직전에 현재 상태를 다시 조회한다.** `run_prune` 은 `prep`
때 만든 `ads.json` 스냅샷으로 삭제 대상을 고르는데, SKILL.md 의 흐름 자체가
`prep` → **사람 검토** → `prune --commit` 이라 그 간격이 몇 시간~며칠이다. 그 사이 되살아난
소재(사용자가 UI 에서 켰거나 연동이 스스로 복구됐거나)를 스냅샷만 믿고 지우면 되돌릴 수
없다. 그래서 `commit` 분기에서 `collect.fetch_ads(acct)` 로 현재 상태를 다시 조회하고,
`prune.revived_filter(target_ads, fresh_ads)` 로 삭제 집합을 "지금도 deletable() 인 것"과
교집합한다 — 되살아난 건수는 로그(`재확인 결과 N건이 되살아나 제외`)와 반환값(`revived`)
으로 남는다. 조회는 계정당 11~13회로 DELETE 수천 번에 비하면 무시할 비용이다.

## 11. 시트 기록 — 실패해도 배치는 죽지 않지만, 실패 단위는 규칙이다

`apply --sheet` 는 `sheets_out.write_sheet` 가 `eroomlib.gsheets.append_rows`/`ensure_tab`
을 불러 쓴다(429 백오프 재시도 포함, 다른 스킬 두 개도 쓰는 검증된 헬퍼) — **과거 이 문서가
언급하던 `sheets_out._gws()` 헬퍼는 제거됐다.** 2026-08-30 실측: 시트ID
`1-oSQepeUGbdmRfSizJHUIjgHu-UYxMtyS504mzDeJKI` 의 5개 탭(①~⑤)에 합계
2,242/198/78/138/38행이 실제로 기록됐다.

gws 인증 만료든 다른 API 오류든, `apply --sheet` 의 시트 쓰기가 전부 실패해도 **시트 기록만
실패 로그를 남기고** 판정(`result.json`)과 마크다운 보고서(`report.md`)는 정상 산출된다 —
`write_sheet` 가 규칙마다 try/except 로 감싸기 때문이다.

**단, 실패 단위는 계정이 아니라 규칙이다.** `write_sheet` 는 규칙(탭)마다 **전 계정의 행을
한 번에 합쳐** append 하므로, 한 규칙이 실패하면 그 규칙의 **모든 계정 행**이 함께 빠진다.
"한 탭이 실패해도 나머지 계정 기록은 계속 시도한다"는 옛 서술은 틀렸다 — 계정별로 나뉜
재시도 단위가 없다.

## 연동끊김(AD_ABNORMAL_INTERLOCK)의 정체 — 물갈이 부산물 (2026-08-30 용팀장 확인)

**미해결 미스터리가 아니라 운영 사이클의 정상 부산물이다.**

용팀장은 전시 최신성을 위해 마켓그룹마다 **20일 주기로 물갈이**(삭제 → 재업로드)를 한다
(`bulsaja-mulgari-delete` · `bulsaja-mulgari-upload` 스킬이 그 일정을 관리한다).

```
물갈이 삭제   → 스마트스토어 상품이 사라짐 → 광고 소재가 연동을 잃고 AD_ABNORMAL_INTERLOCK 으로 자동 정지
물갈이 업로드 → 새 상품ID로 재등록        → 기존 광고 소재는 죽은 채 남고, 광고에 **새로 소재를 추가**해야 한다
```

그래서 계정을 새로 붙일 때마다 수백~수천 건이 나온다(누적 7,340건 삭제).
**급증해도 이상 신호가 아니다** — 물갈이를 크게 돌린 직후일 뿐이다.
`prune` 은 그 사이클의 뒤처리를 자동화한 것이고, 앞으로도 계속 나오는 게 정상이다.

> 남은 수작업: 물갈이 재업로드 뒤 **광고에 소재를 새로 넣는 일**은 아직 사람이 한다
> (네이버 광고 UI 에서 미투입 상품을 전체 선택). 광고 API 에 "광고 미투입 상품 목록" 을
> 주는 엔드포인트가 없어 자동화가 막혀 있다 — 2026-08-30 실측으로 확인.
