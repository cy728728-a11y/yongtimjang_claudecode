# ⑤ 상품명 생성 (product-name)

키워드→상품명 파이프라인의 마지막 단계. 마켓그룹 하나(≈1000 상품)를 받아 **썸네일로 실물 확인 → 키워드 2~5개 선택 → 상품명 생성 → 불사자 반영**.

> **파이프라인 위치**: 상품→상품명 5단계 중 ⑤ — 전체 흐름·배턴 계약은
> [`keyword-pipeline-flow.md`](../keyword-pick/references/keyword-pipeline-flow.md). 배치 인프라는 `keyword-pick`·`bulsaja-category-fix`에서 빌려 쓴다.

## 최상위 원칙 — 카테고리가 먼저, 그 다음이 상품명 (2026-07-24 이룸님)

**네이버 노출은 카테고리 매칭 + 키워드 매칭이다.** 카테고리가 틀리면 키워드가 아무리 좋아도
안 뜬다 → ①카테고리를 맞춘다(`bulsaja-category-fix` 선행) ②그 카테고리에 실재하는
키워드로 상품명을 짓는다.
**직결어가 하나도 없는 상품은 대부분 "상품명 문제"가 아니라 "카테고리 문제"다**(→ Step 5 ②).

## 확정 규칙 (요약 — 전문은 워커 지시서)

| 항목 | 규칙 |
|------|------|
| **term 수** | **내용어 목표 6 무조건** / 4~5 허용(경고) / 3 이하·7 이상 실패. 옵션명 몫은 빼고 센다 |
| **대표옵션 마커** | 상품명 맨 끝에 **`기본형` 고정 부착**(딱 1번). **term 수에 세지 않되 `term분해`의 마지막 원소**로 넣는다 |
| **채우는 순서** | ① 저상품수 직결어 → ② 적합한 대형 키워드 → ③ 실물과 맞는 원본 단어·옵션명/원문 확인 단어 |
| **사용 키워드** | **2~5개**. 상품명은 후보 없이 1개 확정 |
| **적합도** | 키워드는 **원문 그대로** 이어 붙인다. term으로 쪼개 재배열하면 그 검색어로는 상위노출 0 |
| **배치** | 원본 단어(a·b·c)와 키워드(1·2)를 **`a 1 b 2 c` 로 번갈아**. 자리 부족하면 `c→b→a` 순으로 삭제, 키워드는 안 자름 |
| **중복 term** | 최대 **1종·2회**. 뒤집으면 term 2종 이상을 공유하는 키워드 쌍은 함께 못 쓴다(→ 부분 반영 레시피) |
| **동의어 중복** | **판정하지 않음** (사전이 없고 term별 패널티가 달라 규칙화 불가) |
| **키워드 확보** | 최소 2개. 부족하면 상품수 1만씩 계단 확장(무제한) → 상위뷰. **다 소진해도 1개뿐이면 보류하지 않고 그 1개 + 원본 단어로 만든다**(`키워드확장` 증빙 필수 → R4 예외, 2026-08-05). **0개면 `무키워드모드` 배치에 한해 원본 단어만으로**(`무키워드사유` 필수 → R4·R5·R6 면제, 2026-08-06) |
| **원본 상품명** | **완전 대체**. 단 시트 E열에 백업(되돌리기 경로) |
| **규격어 키워드** | `3단`·`스텐`·`60cm` 가 붙은 키워드를 쓰면 그 규격의 옵션을 `대표지정` 열에 남긴다 → 옵션정리가 대표로 세운다. 아래 절 참조 (2026-08-05) |

**우선순위: ①상품 적합성(관계없는 것 금지) → ②상품수 낮은 직결어 → ③내용어 6 무조건** — 적합성이 상한이다.

### 대표옵션 마커 `기본형` (2026-07-30 이룸님)

**네이버는 '대표상품'(추가금 0원인 대표옵션)을 상품명으로 작성하라고 요구한다** →
**썸네일 = 대표옵션 = 상품명**이 같은 옵션 하나를 지칭해야 한다. 상품명 맨 끝과
**대표옵션명 끝**에 같은 `기본형` 을 붙여 짝을 지목한다
(옵션 쪽 = [`../bulsaja-option-cleanup/references/옵션명-규칙.md`](../bulsaja-option-cleanup/references/옵션명-규칙.md) 규칙 17).

**마커에 한해서는 대표옵션이 무엇인지 몰라도 된다** — 무조건 끝에 붙인다. 스킬 간 데이터
계약을 새로 만들지 않는 게 이 방식의 요점이다. 마커는 고정 접미어라 변별력이 0이므로 term
수에서 뺀다. (단 **규격어 키워드를 쓰면 대표를 실제로 지정한다** — 아래 §규격어 대표 지정.
그 경로는 옵션 정보를 본다.)

**색상 예외** — 배치의 `옵션동일가`(prep 이 `_same_price_options` 로 계산)가 true 면 색상
term 생략 가능. 전문은 워커 지시서 §3-3(정본).

### 규격어 대표 지정 (2026-08-05 이룸님)

저상품수 1순위는 그대로다. **고른 키워드에 규격어가 있을 때만** 도는 조건 분기다.
규격어 = 수량+단위(`3단`·`3인용`·`9구`) · 소재어(`스텐`·`원목`) · 치수(`60cm`·`15L`).
**크기어(`대형`·`소형`·`미니`)는 제외** — 상대 표현이라 옵션 매칭이 불안정하다.

| 그 규격이 옵션에서 | 판정 | 결과 |
|---|---|---|
| 일부 옵션만 해당 (2층/3층이 따로 있다) | **(가)** | 그 옵션(복수면 최저가)을 `대표지정` 열에 |
| 전 옵션 공통이거나 제목에만 | **(나)** | 규격어 유효. 대표는 최저가(종전) |
| 옵션에도 제목에도 없음 | **(다)** | 규격어 키워드를 버리고 다음 후보로 |

판정은 `spec_match.py` 가 한다 — 표기가 한/중 제각각이라(`3단`·`3층`·`三层`) 표가 정확하다.
(나) 판정에 **중국어 원문과 제목을 함께 보는 게 핵심**이다. 옵션 규칙 6이 전 옵션 공통
정보를 이름에서 일부러 지우므로, 한국어 옵션명만 보면 정당한 규격어를 (다)로 오판한다
(용쌤1-3 실측 81건 중 (나)가 52건 = 64%).

배치의 `옵션명`은 앞 8개 요약이라 실물 라인이 안 보일 수 있어 `옵션구성`(전량)을 따로 싣는다.
발단 사례·전문 = [`00-system/04-specs/2026-08-05-상품명-대표옵션-규격어-design.md`](../../../00-system/04-specs/2026-08-05-상품명-대표옵션-규격어-design.md) ·
받는 쪽 규칙 = 옵션명-규칙.md 규칙 19(정본).

**반쪽 마커 이관** — `rename --commit` 성공 후, 대표옵션명에 `기본형` 이 없는 상품은
현황판 `옵션` 열에 재작업 플래그를 찍는다(`_handoff_base_suffix`). 마커는 신규 처리분에만
적용하므로 "옵션은 옛 규칙으로 끝났고 상품명만 이번에 도는" 상품이 생긴다 — 그 짝을 복구하는 경로.

## 저장 위치 (고정)

- **탭 `상품명` (30열)** — `--sheet`/`--tab`으로 교체 가능
  ```
  상품id / 작업일 / 마켓그룹 / 카테고리 / 원본상품명 / 새상품명 /
  키워드1~5 각각 (키워드N / 키워드N_상품수 / 키워드N_검색량) /
  term분해 / term수 / 중복어 / 반증 / 상태 / 메모 / 속성제안 / 태그제안 / 대표지정
  ```
  (= `run_names.py NAME_HEADER` 30열. 마지막 AD열 `대표지정` 포함 — 옵션정리가 읽는 계약 열.)
  키워드별 상품수·검색량을 남기는 이유: 통다운은 매번 갱신되므로 **선택 당시의 좌표는 사후
  복원이 안 된다.** AB·AC(속성제안·태그제안)는 2026-07-27, AD(대표지정)는 2026-08-05 추가 —
  기존 시트는 append가 헤더만 1회 채운다(**새 열은 항상 맨 뒤에만** 붙인다. 앞 열이 밀리면
  rename 의 상태 write back 이 엉뚱한 열을 친다 — 상태는 Z 고정).
  **키워드 1개 경로**는 메모 앞에 `[키워드1개] <소진 증빙>` 이 박힌다(R4 예외의 시트 흔적).
- **탭 `관련어` (8열)** — `상품id / 작업일 / 카테고리 / 관련어 / 상품수 / 검색량 / 채택 / 사유`
  **"안 본 것"과 "보고 버린 것"을 구분하는 유일한 기록.** 재검수는 여기서 시작한다.
- **스프레드시트** — 그룹별 카테고리교정 로그 시트. 고정 기본값 없음.
  `--group-name "2번_용쌤2-1"` → 드라이브 `20-불사자-상품관리 > 카테고리교정/`에서
  `카테고리교정_<그룹명>` 시트를 찾는다. **못 찾으면 즉시 중단**(다른 그룹 로그 오염 방지).
  직접 지정은 `--sheet <id>`. 전체 현황은 같은 폴더 `00_마스터-인덱스`.
- **run_dir**: `<데이터루트>/product-name/runs/<이름>` (`workspace.toml [paths].product_name_runs`.
  중간산출물, git 오염 방지)
- **상태 저장소 = 시트 그 자체.** 상품명 탭 **A열에 상품id가 있으면 처리 완료**로 본다
  (상태값 무관) → 재실행해도 건너뜀. 재작업은 `--redo`로만 뚫는다.
- **삭제대기 게이트는 A열이 아니라 현황판에 있다** (2026-08-15). 제외카테고리로 삭제 예정인
  상품은 현황판 뒤 7개 작업 열에만 `삭제대기(제외카테고리)` 가 찍힌다 — **A열 멱등만으로는
  안 걸린다.** `prep` 이 대상 산출 직후 `_drop_gone` 으로 뺀다(판정 1벌 =
  `category_gate.already_gone`, **7개 열 중 하나라도** 삭제대기·상품삭제·해당없음이면 제외).
  > 안 걸었을 때 실측(용쌤4-1): **대상 227건 중 137건(60%)이 삭제 예정 상품**이었고
  > 93건은 rename 까지 반영됐다. 워커 비용 4.45M 토큰의 절반 이상이 지워질 상품에 쓰였다.
  > **한 열이 아니라 7개 열을 보는 게 핵심이다** — `append` 가 `상품명` 열을 덮어쓴 뒤에도
  > `썸네일` 열이 남아 있어서 사고를 찾을 수 있었다. 게이트를 열 하나로 좁히면 그 성질이 사라진다.

## Workflow

### Step 1. 대상 확인
**마켓그룹**(이름 또는 groupId — `bulsaja_market_groups`로 조회) + 통다운 날짜(`--source-date`, **생략하면 드라이브 최신 + 7일 규칙**)

### Step 2. prep — 썸네일·카테고리·키워드후보 수집

```bash
python .claude/skills/product-name/scripts/run_names.py prep \
  --group-id <ID> --group-name "2번_용쌤2-1" \
  --run-dir "<데이터루트>/product-name/runs/<이름>" \
  --source-date 260712 [--limit 20] [--no-parent] [--ids U01abc U01def [--redo]]
```

> **`--ids`** = 지정한 상품만(1건~몇 건 · 보류 재작업). 마켓그룹에 없는 id는 경고.
> **`--redo`** = `--ids`와 함께만 — 시트 A열에 이미 있는 건도 재대상으로. 멱등 판정이
> **A열 존재 기준**이라 상태를 비우는 것만으로는 안 걸린다. 면제는 1회용(`append`가
> `redo.json` 소진).

> **`--ids` 는 기존 run-dir 에 덧붙이는 경로다 — 덮어쓰지 않는다** (2026-08-15 용쌤2-1
> 3회차 실측 · 결함 3건 수정 완료). 셋 다 **에러 없이 조용히 사라지던** 것들이라, 고치기
> 전 회차는 로그 숫자를 직접 세야만 사고를 알 수 있었다.
>
> | 무엇이 | 종전(결함) | 지금 |
> |---|---|---|
> | 배치 번호 | 항상 `batch_001` 부터 다시 매겨 **기존 배치를 덮어썼다**(14개짜리 run-dir 에 `--ids <1건>` → batch_001 의 2건 소멸) | `_next_batch_no` 로 이어붙이고 인덱스도 합친다 |
> | `redo.json` | 그 회차분으로 **통째로 덮어썼다**. 앞서 자동 편입된 14건이 면제에서 빠져 `append` 가 전부 `스킵(이미처리)` — **워커 비용은 다 쓰고 시트엔 2행** | `_merge_exempt` 로 기존 목록에 합친다(소진분 `redo.json.done` 은 제외 — 되살리면 두 줄 들어간다) |
> | `workdata.json` | 캐시 재사용이라 거기 없는 id 는 `[4/6] 대상 0건 / 카테고리미설정 스킵 1건` 으로 떨어져 "카테고리 교정 먼저" 로 멈췄다(그룹 목록 API 누락분을 `group.json` 에 손으로 넣어도 여기서 막혔다) | `_fill_workdata` 가 **캐시에 없는 건만** 조회해 덧붙인다(스냅샷 적중 시 MCP 0회) |
>
> `--views-only`·`--targets-json`·전량 prep 은 **종전대로 1번부터 새로 만든다** — 그쪽은
> 전체를 다시 짜는 경로라 이어붙이면 중복된다.
>
> **그래도 `###APPEND### 총 N행` 의 N 을 대상 수와 대조해라.** 위 셋은 막혔지만 조용한
> 누락은 이 숫자로만 드러나는 부류다.

> **다른 단계가 넘긴 재작업은 자동으로 편입된다 (2026-08-06 이룸님).** prep 이 현황판
> `상품명` 열의 `재작업(옵션: …)` 을 읽어 **A열에 이미 있어도 대상에 넣고**(`_matrix_redo`),
> 사유를 배치의 `재작업사유` 로 워커에게 실어 보낸다 — `--ids --redo` 를 손으로 칠 일이
> 없다. 다른 축은 현황판이 원장이라 원래 자동으로 집혔는데 **상품명만 원장이 `상품명` 탭이라
> 신호가 닿지 않았다**(옵션이 flag 를 찍어도 아무도 안 집었다).
> 옛 `생성완료` 행은 `append` 가 `재작업` 으로 내린다(`_retire_stale_rows`) — `rename` 은
> **상태=생성완료 인 행 전부**를 반영하므로, 안 내리면 새 이름과 옛 이름이 둘 다 실린다.

> **현황판** — `append`·`rename` 이 그룹 시트 `00_진행` 탭의 **상품명 열만** 갱신한다
> (`eroomlib/matrix.py`). `생성완료`는 아직 불사자 미반영이라 `진행중(미반영)`,
> `rename` 이 반영하면 `완료`가 된다. 스킬 공통 규칙은 [`_shared/스킬-계약.md`](../_shared/스킬-계약.md).

> **공용 스냅샷** — ③의 `workdata`와 ⑤의 썸네일은 상품id 기준 캐시(`eroomlib/snapshot.py`)를
> 먼저 본다. 카테고리 교정이 이미 받아둔 그룹이면 조회 0회. 무시하려면 `--force`.
> `rename` 이 성공하면 **스냅샷의 `상품명`만 되쓴다** → 다음 스킬이 옛 상품명을 읽지 않는다.

하는 일: ①마켓그룹→상품목록 ②상품명 탭 대조로 미처리분만(멱등) ③`workdata`로 현재 카테고리·
썸네일URL·**원문명·옵션명** ③b카테고리교정 시트 J·K 읽기(`jk_map.json`) ④카테고리 미설정은
`skipped.json`으로 분리 ⑤썸네일 다운로드(**K열 있으면 건너뜀**) ⑥통다운→카테고리별 키워드
(`cat_prefilter.py`) ⑦카테고리 뷰 생성 + **카테고리 단위 배치**(`cat_view.py`)

> **뷰에서 잘리는 것 2종**(`cat_view.py load_rows`) — 셀러라이프 `브랜드키워드` O열
> (실측 26%, 정답 손실 0)과 블랙리스트 **`제외키워드` 정확일치**(2026-08-09 추가).
> 후자는 비용이 아니라 **상표 리스크** 때문이다 — 그 시트는 상표 위험으로 판정돼 이룸님이
> 승인한 명단이고 뷰는 그 키워드로 상품명을 만든다. 여기서 AI 판정은 하지 않는다(명단 조회만).
> 컷 건수는 뷰 첫 줄에 남는다. 끄려면 `--keep-excluded`. 판정 1벌은 `eroomlib/exclusion.py`.
> `제외카테고리`·`제외브랜드` 는 뷰에 넣지 않는다 — 전자는 카테고리 뷰가 통째로 비어
> `키워드부족`→보류→재교정이라는 제일 비싼 경로로 가고, 후자는 부분일치인데 손실 검증이 없다.

산출물 — `views/<카테고리>.txt`(전 행 + 특징어 인덱스) · `batches/batch_001.json`(카테고리 1개분, 최대 10건):

```json
{"카테고리": "가구/인테리어>침실가구>서랍장",
 "카테고리뷰": ".../views/….txt", "카테고리파일": ".../prefiltered/….xlsx",
 "상위뷰": ".../views/상위_….txt",
 "products": [{"productId": "U01…", "원본상품명": "…", "썸네일경로": "…",
   "실물판정": "자키+에어펌프+전동렌치 세트",   // J열. 있으면 이게 실물(신버전)
   "썸네일URL": "https://…",                    // K열. 썸네일경로가 비면 여기서 fetch
   "원문명": "沪工电动液压千斤顶…",              // 중국어 원문(가공 전)
   "옵션명": ["3톤 세단 모델잭…"],               // 실제 판매 단위(가공 전)
   "옵션동일가": false}]}                        // true = 전 옵션 추가금 0원 → 색상 예외
```

> **첫 실행은 통다운 스캔(수 분~수십 분) 때문에 오래 걸린다.** 백그라운드로 돌린다.
> 같은 run-dir로 재실행하면 manifest 캐시가 걸려 재스캔하지 않는다.
> prep이 끝나면 Step 3(Workflow 팬아웃)으로 바로 진행한다 — 수동 중단점은 없다
> (2026-07-29 Workflow 모드 채택으로 삭제, 2026-08-05 잔존 포인터 정리).

### Step 3. [워커] 배치별 상품명 생성

**판단 규칙 전문은 [`references/배치-워커-프롬프트.md`](references/배치-워커-프롬프트.md) §3-1~3-7이다.**
오케스트레이터는 규칙을 읽지 않는다 — 배치를 나눠주고, 결과를 모으고, 표본만 검수한다.

#### 위임 — 한 그룹은 컨텍스트 하나에 안 들어간다

한 그룹(≈1000 상품) Step 3 판단 총량 **≈ 4.4M 토큰**. 가능한 이유는 **디스크 우선 설계** —
배치가 자기완결형, 상태저장소 = 디스크(`named_*.json`) + 시트(멱등).

> **비용 규칙 3개·폴백 모드 A/B/C → [`references/팬아웃-비용.md`](references/팬아웃-비용.md).**
> 요지: ①워커 1명=배치 1~2개 ②팬아웃 구간은 Opus 금지 ③메인 턴 수 최소화 (341건 $494→≈$140).

#### Step 3 실행 = Workflow 모드 (기본, 2026-07-29)

오케스트레이션을 백그라운드 워크플로(`pname-fanout`)로 뺀다 — 메인 세션 컨텍스트 재과금
(867건 실측 92M 토큰)이 사라지고, `/model`·`/clear` 수동 중단점이 **없다.**

1. pending 계산(디스크 스캔): `batches/` vs `named/` 대조로 named 없는 배치를 고르고,
   viewKB 는 각 배치의 `카테고리뷰` 파일 크기(`os.path.getsize`)로 재서
   `[{n, path, viewKB}]` 를 만든다(워크플로는 파일시스템이 없어 호출자가 넘겨야 한다).
2. `Workflow` 도구를 `{name: "pname-fanout", args: {runDir, promptPath, batches}}` 로 호출.
   워커는 `agent(model: sonnet, effort: low)`. **배치 200개 초과면** 압축형
   `{runDir, promptPath, viewKB: [...], batchNums: [...]}` (인라인 40KB가 메인을 먹는다).
3. 반환값에서 보류·검증을 읽는다. **`passed`/`failed`는 배치 수, `products_*`가 상품 수 —
   판단은 상품 수로.** 재팬아웃 전에 **Step 3.5(fix-r9)를 먼저** 돌린다.
4. fix-r9 후에도 `재팬아웃필요배치` 가 있거나 pending 재계산에 남은 배치가 있으면(워커가
   named 를 못 쓰고 죽은 경우) 해당 named 를 지우고 **1회만** 재호출 — args 에 아래
   **재팬아웃 표준 문안**을 `emphasis` 로 싣는다. 둘 다 비어야 Step 4(append).
   재호출 후에도 남으면 보류로 종합보고.

> **재팬아웃 표준 문안(emphasis)** — 그대로 복사해 쓴다 (2026-08-05 개정):
> "**R4: 채택 키워드는 2개 이상이 원칙이다.** 1개밖에 못 찾겠으면 상품수 계단을 1만씩 넓혀
> 뷰 전체를 다시 훑고, 그다음 `상위뷰`까지 연다. **그래도 1개뿐이면 보류하지 말고 그 1개를
> 통 키워드로 쓰고 나머지 자리를 원본 상품명·원문·옵션명 단어로 채워 내용어 6을 만든다.**
> 이때 `키워드확장` 필드에 소진 증빙(어디까지 넓혔는지·상위뷰 결과)을 반드시 남긴다 —
> 없으면 R4가 실패시킨다. `보류(키워드부족)` 은 직결어가 **0개**이거나 원본까지 다 뒤져도
> 내용어 4를 못 채울 때만 쓴다."

### Step 7. rename — 불사자 반영 (표본검수 직후 **자동 커밋**, 2026-08-04 이룸님)

```bash
python .claude/skills/product-name/scripts/run_names.py rename --run-dir "<R>" --group-name "2번_용쌤2-1"           # 미리보기 — 대상 수를 종합보고에 기록
python .claude/skills/product-name/scripts/run_names.py rename --run-dir "<R>" --group-name "2번_용쌤2-1" --commit  # 승인 대기 없이 즉시
```
표본검수 의심건 mark 가 끝난 직후 바로 `--commit` 한다 — 이룸님 승인을 기다리지 않는다
(2026-08-04 이룸님 확정. 2026-08-06부터는 이게 전 스킬 기본값이다 —
`_shared/스킬-계약.md` §반영은 기본 자동이다. **시트 기록 의무는 그대로다**).
rename 은 run-dir가 아니라 **시트 전체의 `생성완료`를 집으므로, 1회 호출로 본 라운드+재진입
라운드 분이 모두 반영된다.**
- **`상태=생성완료` 행만** 반영. 50건씩 나눠 호출(불사자 상한). 원본은 시트 E열에 남는다
- **배치 거부는 자동으로 분해 재시도한다(50 → 10 → 1).** 불사자는 배치 안에 "내 상품이 아닌
  상품"(=삭제된 상품)이 1건이라도 있으면 **배치 전체를 거부**한다. 1건 단위에서도 거부된
  것만 진짜 불량으로 확정(2026-07-27 용쌤1-1: 불량 2건이 정상 98건을 같이 죽였던 결함)
- **끝나면 시트 상태열을 자동 갱신** — 성공 `반영완료`, 확정 불량 `상품삭제(이룸님)`.
  통신 오류로 못 던진 건은 `생성완료` 그대로(멱등 → 재실행하면 다시 잡힌다).
  오류가 연달아 3회면 남은 건은 호출 없이 넘기고 중단한다(재시도 폭풍 방지)
- ⚠️ **`--commit`이 도는 동안 그 시트의 상태열을 직접 편집하지 않는다.** 시작할 때 읽은
  상태열을 끝날 때 통째로 다시 쓴다(update 1회) — 중간에 손으로 고친 값은 되돌아간다.
  다른 열은 안 건드린다 (2026-07-27 이룸님: 방식 A 유지). `mark` 도 같은 패턴이다
- **회귀 테스트**: `python .claude/skills/product-name/scripts/test_run_names.py`
  — **`run_names.py`를 손대면 이걸 먼저 돌린다**

### Step 8. 종합보고 — 유일한 보고 지점 (2026-08-04~05)

전 단계가 자동이므로 **이룸님 개입 = 시작 1회 + 이 보고 확인 1회**다. `보류(표본의심)` 등
판정 큐 처리도 "이 보고 확인"의 일부다 — 별도 3번째 개입이 아니다. 반영이 끝난 뒤
한 번에 보고한다(반영은 보고를 기다리지 않는다). 항목:

1. **반영**: N건 커밋(미리보기 대상 수 대비) · 불량 n(`상품삭제(이룸님)`)
2. **자동 삭제**: `상품삭제(실물불명·자동)` 목록(상품id·상품명·근거) — 불사자는 휴지통이라 복구 가능
3. **자동 재교정**: 대상(의심 x + 미설정 y) → 저장 s (자동저장 a · 유도 b · consensus c) · 실패 f
4. **재진입 라운드**: 생성 g건 · **2회째 의심 m건(목록+사유 — 재교정 금지분)** ·
   **키워드부족 `_kw1` 라운드**: 대상 x → 생성 y(그중 키워드 1개 경로 z) · 2회째 부족 w ·
   **무키워드 `_nokw` 라운드**: 대상 n(= `holds --catfix-run` 의 `무키워드대상`) → 생성 m.
   통다운 갱신 시 1순위 재작업 대상이므로 **목록을 싣는다**
5. **표본검수**: 표본 수 중 의심 k건(목록 + 걸린 기준(a~d) + 사유).
   **k≥3이면 체계적 결함 경고 + 공통 패턴 분석** 필수
6. **잔여 보류**: 키워드부족 2회째(직결어 0) · consensus 합의없음/실물판정의심/변형없음 ·
   `이미정확`인데 직결어 0 · **옵션뒤집힘 대기**(옵션정리 복구를 기다리는 목록)
7. **수동 필요**: 속성·태그 제안 건수(스마트스토어 수동 입력) · 반쪽 마커 이관 수 · 캡챠 발생 이력
8. **시트 링크**

### 유지되는 개입 — 자동화하지 않는 것 (2026-08-05 확정)

| 개입 | 왜 자동화 안 하나 |
|---|---|
| 캡챠/차단 해제 | 캡챠는 `captcha-relay` 스킬(판단은 Aside 위임, 입력·제출은 Claude). `needs_human`·타임아웃이면 이룸님. 차단은 시간을 두고 재개. 발생 시 해당 조회만 멈추고 나머지는 진행 |
| 실물불명·제외카테고리 **외** 사유의 상품삭제 | 비가역 판단. 자동 삭제 경로는 둘 — `상품삭제(실물불명·자동)`(이 스킬) · `상품삭제(제외카테고리·자동)`(catfix `category_gate.py`, 2026-08-09 이룸님). 그 밖의 사유는 이룸님 판단 |
| 속성·태그 스마트스토어 입력 | 불사자 MCP에 저장 API가 없다 — 시트 AB·AC열 제안까지만 |
| 재팬아웃 1회 후에도 남는 배치 | 워커 반복 실패 = 구조 문제 신호. 자동 재시도 상한 1회 유지 |
| `보류(표본의심)` 최종 판정 | 종합보고를 보고 이룸님이 상태 원복(재반영) 또는 폐기 |

> ⚠️ **zsh에서 `--ids $IDS` 는 안 된다** — 변수 확장이 단어 분할되지 않아 prep이 "0건
> 매칭"으로 조용히 끝난다. `--ids $(cat ids.txt)` 또는 `${=IDS}` 를 쓴다.

## 검증 규칙 (name_check.py)

| | 규칙 | 실패 조건 |
|---|------|-----------|
| R1 | term 분해가 상품명을 정확히 분할 | term을 이어붙인 게 상품명(공백제거)과 다름 |
| R2 | 고유 **내용어** term 수 **4~6** (목표 6) | 3 이하 또는 7 이상. 4~5는 통과+경고 |
| R3 | 중복 term 1종·2회 (마커 제외) | 2종 이상 중복 / 같은 term 3회 이상 |
| R4 | 사용 키워드 **2~5개**. **1개=`키워드확장` / 0개=`무키워드사유`** 증빙이 있으면 통과(경고) | 증빙 없는 0·1개 / 6개 이상 / 키워드 중복 |
| R5 | **적합도** — 키워드가 상품명에 **연속 문자열 그대로** | 어느 키워드도 그대로 없으면 실패. 일부만 만점이면 경고 |
| **R6** | **절차 — 관련어 목록·반증 답변 존재** | 둘 중 하나라도 비면 실패 |
| **R7** | **채택보다 싼 관련어에 사유 존재** | 채택 최저 상품수보다 낮은 관련어에 `사유`가 빔 |
| **R8** | **대표옵션 마커** — 끝이 `기본형`, 딱 1번, `term분해` 마지막 원소 | 안 끝남 / 2번 이상 / term분해 마지막이 아님 |
| **R9** | **배치** — 원본 단어와 키워드가 `a 1 b 2 c` 로 번갈아 놓였는가 | 키워드끼리 붙은 뒤에 원본 단어가 남아 있음(= 앞자리를 비우고 뒤에 몰았다) |
| **R11** | **유통 브랜드** — 코스트코·이케아·다이소 류를 상품명에 넣었는가 | 원본에 없는데 새로 붙였으면 실패 / 원본에 이미 있었으면 경고 |

R11은 2026-08-14 표본검수에서 나왔다(2-1). 상표 리스크는 사전 대조로 확정할 수 있다.

> **같은 날 R10('근거 없는 term' 경고)도 만들었다가 그날 되돌렸다.** 상품명 term 이
> 원본·원문·옵션·키워드 어디에도 없으면 경고하는 규칙이었는데, 실측 표본 35건 중
> **23건이 오탐**이었다. 증거의 절반이 중국어 원문이고 상품명은 한국어라 문자열 대조로는
> `고속`↔`高速` · `북유럽`↔`北欧` · `3단`↔`三层` 을 못 넘는다. 발단이 된 사례
> ('발광글자')조차 원문 `广告发光字` 에 근거가 있어 **잡으려던 건 자체가 오탐**이었다.
> 폐기 사유는 `name_check.evidence_text` docstring 에 남겼다 — 다시 만들지 마라.
> **실물 오지칭(미용실의자→거울)은 기계로 못 막는다. 표본검수가 마지막 방어선이다.**

R6·R7은 산술이 아니라 **절차** 검증이다 — "후보를 다 안 보고 스스로 잘라 찍은 것"을 기계가
잡는다. 단건 확인(R6·R7 건너뜀): `name_check.py --name "<상품명>" --terms "<a,b,…>"
--keywords "<k1,k2>"`.
