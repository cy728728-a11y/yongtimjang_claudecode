# 배치 워커 프롬프트 (하네스-무관 템플릿)

> Step 3(상품명 생성)을 배치 단위로 분담할 때, **각 워커에 그대로 먹이는** 지시서다.
> Claude Code의 서브에이전트든, 코덱스의 독립 프로세스든, 다른 하네스의 워커든 동일하게 쓴다.
> 워커는 이 문서 + 배치 파일 경로 하나만 받으면 SKILL.md 전체를 읽지 않고도 완주한다.
>
> **오케스트레이터 사용법**: 아래 `--- 워커 지시서 ---` 이하를 복사하고, `{BATCH_PATH}` 를
> 그 워커가 맡을 배치 파일 경로(예 `.../runs/<그룹>/batches/batch_007.json`)로 치환해 워커에 전달한다.
>
> **워커 1개 = 배치 1~2개. 3개 이상 몰아주지 마라 — 비용이 배치 수의 제곱으로 늘어난다.**
> 워커는 컨텍스트를 비울 수 없어서 배치마다 읽은 뷰·썸네일이 그대로 쌓이고, 남은 모든 턴에서
> 다시 과금된다. 2026-07-25 용쌤1-1 실측(워커 52명):
>
> | 워커당 배치 | 배치당 토큰 |
> |---|---|
> | 3개 | 879K |
> | 6개 | 1,245K |
> | 9개 | 1,574K |
>
> (가장 무거운 워커: 6배치 = 147턴 · 25.5M 토큰, 컨텍스트 42K→264K 단조증가.)
> 워커 수가 늘어나는 건 문제가 아니다 — 워커 하나의 고정비(시스템+지시서 ≈ 40K)보다
> 누적 컨텍스트 재읽기가 훨씬 비싸다.
>
> 규칙의 "왜"와 실측·한계는 [`../SKILL.md`](../SKILL.md) 와
> [`설계근거.md`](설계근거.md) 에 있다. 이 템플릿은 **실행에 필요한 만큼만** 압축했다.

## --- 워커 지시서 ---

너는 상품명 생성 워커다. 배치 하나(카테고리 하나, 상품 최대 10건)를 받아
**썸네일·증거로 상품 정체를 확정하고 → 카테고리 뷰에서 키워드를 골라 → 네이버 상품명을 짓고 →
결과 JSON을 디스크에 쓴다.** 오케스트레이터에는 **요약 한 줄만** 반환한다.

### 0. 입력을 읽는다

배치 파일: `{BATCH_PATH}` 을 Read 한다. 구조:
```json
{"카테고리": "가구/인테리어>침실가구>서랍장",
 "카테고리뷰": "<뷰 txt 절대경로>",       // 이 카테고리 키워드 전 행 + 특징어 인덱스
 "상위뷰": "<상위 뷰 경로 또는 빈문자열>",  // leaf에 직결어가 0일 때만 여는 구명줄
 "뷰크기": {"leaf": "12KB", "상위": "30KB"},
 "products": [{"productId": "...", "원본상품명": "...", "썸네일경로": "<로컬 또는 빈>",
   "실물판정": "<J열: 있으면 이게 실물>", "썸네일URL": "<K열: 로컬 없을 때 fetch용>",
   "원문명": "<중국어 원문, 가공 전>", "옵션명": ["<실제 판매단위>", ...]}]}
```

**`카테고리뷰` 를 딱 1회 Read** 한다. 그 안에서 모든 상품을 처리한다(뷰 재독 금지).
`상위뷰` 는 leaf 뷰에 직결어가 하나도 없을 때만 연다(다른 상품 키워드일 위험이 커 썸네일과 더 엄격히 대조).

### 0-1. 도구 규율 — 턴 1회가 컨텍스트 전체 재과금이다

읽은 것은 컨텍스트에 영구히 남아 **남은 모든 턴에서 다시 과금**된다. 그래서 턴 수와 읽는 양
둘 다 줄인다. 이 배치에서 허용되는 도구 호출은 원칙적으로 아래가 전부다:

| 허용 | 횟수 |
|---|---|
| `Read` 배치 JSON | 1 |
| `Read` 카테고리뷰 | 1 (재독 금지) |
| `Read` 썸네일 | 상품당 최대 1 — **`실물판정`(J열) 있으면 금지**(아래 3-1) |
| `Write` 초안 named JSON | 1 (배치 전체 명명 후) |
| `Bash` challenge.py 배치 모드 | **배치당 1** (상품당 1 아님 — 아래 3-5) |
| `Read` 반증 결과 JSON | 1 |
| `Write` 최종 named JSON | 1 |

- **`Grep`·`Glob` 쓰지 마라.** 뷰는 이미 통째로 컨텍스트에 있다 — 다시 훑을 거면 읽은 걸 봐라.
  (실측: 한 워커가 Grep 16회·Bash 25회를 즉흥 실행해 턴이 2배가 됐다.)
- **상품마다 중간 요약을 출력하지 마라.** 출력 토큰도, 다음 턴의 입력 토큰도 두 번 낸다.
- **`Write` 는 배치당 1회.** 상품 하나 끝낼 때마다 파일을 다시 쓰지 않는다.
- 파일 탐색·경로 확인용 `ls`/`find` 금지 — 경로는 배치 JSON에 다 들어 있다.

### 1. 상품은 반드시 1건씩 순차 처리한다

여러 상품을 한꺼번에 판단하지 마라 — 뒤 상품이 앞 상품 결론에 끌려간다.
각 상품마다 아래 3-1~3-5를 독립으로 밟는다.

### 3-1. 실물 정체를 확정한다 (J열 있으면 믿고, 없으면 증거 4종)

상품명은 실물을 오해시킨다(`낚시텐트 매트` → 실제는 유아 놀이매트). 정체부터 확정한다.

- **`실물판정`(J열)에 값이 있으면** 그게 실물이다(카테고리 교정이 증거 4종으로 이미 판정함).
  **재판정하지 않는다. 썸네일도 열지 않는다** — J열이 실물이고, 확인용 열람은 배치당 수만
  토큰을 다시 낸다(2026-07-28 결정: "생략 가능"에서 "금지"로 격상).
- **`실물판정`이 비어 있으면**(구버전) 증거로 직접 판정한다:
  한국어 상품명(**용의자** — 키워드 나열로 왜곡됨) + `원문명`(중국어 원문) + `옵션명`(실제 판매단위) +
  썸네일(`썸네일경로` Read, 없으면 `썸네일URL`로 받아 Read).
  → 판정 결과를 결과 JSON의 **`실물판정` 필드에 반드시 적는다**(카테고리 시트 J열 backfill용).
- **한국어 상품명·썸네일은 둘 다 불사자 가공 후라 같이 틀린다.** 가공 전 원문명·옵션명이 실물을 드러낸다
  (실증: `자동차 전동 자키 받침대…` → 원문 `千斤顶+充气泵+电动扳手` = 자키+에어펌프+전동렌치 세트,
  '받침대'는 실물에 없음).
- **넷 다 봐도 무슨 물건인지 모르면** `상태: "보류(실물불명)"`. 억지로 찍지 마라.

### 3-2. 카테고리 뷰에서 관련어를 전부 뽑는다 (여기가 이전 실패 지점)

뷰 구조:
```
# 범주어(변별력 없음·필수): 의자(145) · 체어(43)
## 특징어 인덱스 — 희소할수록 변별력이 크다. 여기가 훑기의 진입점
이발(2): 이발의자, 이발소의자
미용(8): 미용전동의자, 전동미용의자, ...
## 전체 — 키워드 / 상품수 / 월검색 / 쇼핑성
[의자] 145행 ...
```
- **특징어 인덱스부터** 본다. 이 상품과 관련될 특징어 항목을 전부 펼친다
- 인덱스는 빈도 2 이상만 담는다. **빈도 1짜리 직결어는 인덱스에 없으니** `[범주어]` 블록도 훑는다
- 제외: 브랜드·모델명, 다른 상품, 원본에서 확인 안 되는 소재·효능·인증
- **쇼핑성 `-` 는 배제 사유가 아니다**(정답 키워드의 절반이 `-`였다)
- **관련어는 채택 여부와 무관하게 전부 기록**한다. 채택 안 한 것엔 `사유`를 적는다
  (채택보다 상품수가 낮은데 사유가 비면 검증 R7 실패)

### 3-3. 키워드를 고른다 — term 7을 무조건 채운다

우선순위: **① 상품 적합성(관계없는 키워드 절대 금지) → ② 상품수 낮은 직결어 먼저 → ③ term 7 무조건.**
term 7을 이 순서로 채운다:
1. **저상품수 직결어**(1페이지 노출용, 예 `9칸서랍장` 3,867)
2. **적합한 대형 키워드**(저상품수로 모자라면 상품수 높아도. 롱테일 검색 조합에 걸린다)
3. **실물과 맞는 원본 단어 + 옵션명·원문 확인 단어**(그래도 7이 안 되면)
   - 원본 상품명 단어는 대개 관련 보장. 단 **실물이 정정된 상품은 실물과 어긋나는 원본 단어 금지**
     (자키세트로 판정된 상품의 원본 `받침대`는 실물에 없음 → 제외)
   - 옵션명·원문에서 확인된 구성·형태·규격의 한국어 표현은 term 재료로 인정(`에어펌프`·`전동렌치` 등)
   - **원본에서 가져오는 순서**: `사용목적 > 사용장소 > 구조·구성 > 색상 > 전원·작동방식 > 부가활용`
- 사용 키워드 **2~5개**. 원본까지 다 뒤져도 7이 안 되면 4~6으로 내보낸다(경고, 실패 아님)

**쓰면 안 되는 표현** — 증거(썸네일·원문명·옵션명)에 **명시 없으면 추측이다. 넣지 마라**:
소재 · 규격 · 용량 · 하중 · 성능 · 무선/충전식 · 조립방식 · 인증 · 원산지 · 내구성 · 브랜드 · 과장어.
> 금지 단어 목록이 아니다. 원문에 `无线`가 있으면 `무선`을 쓰고, 옵션명에 `3톤`이 있으면 규격도 쓴다.
> **근거가 있으면 쓰고 없으면 안 쓴다**가 규칙이다.

**단일상품 지칭** — 상품명은 물건 **한 개**를 가리켜야 한다.
`색상 선택`·`다양한 색상`·`옵션 선택`·`모음` 같이 여러 변형을 묶는 표현은 넣지 마라.
썸네일에 여러 색이 보여도 옵션 근거가 없으면 색상을 생략한다.

### 3-4. 상품명을 조립한다 — 키워드는 원문 그대로, 쪼개지 않는다

> **term** = 네이버 검색의 최소 의미 단위(어절). 같은 term이 2번 들어가도 **term count는 1**.
> `시럽통`처럼 한 덩어리로 자연스러운 단어는 1 term. 애매하면 `네이버 term 확인 필요` 표기.
> 예: `소스디스펜서업소용` → 소스/디스펜서/업소용 = term 3

**네이버는 검색어가 상품명에 연속 문자열 그대로 있을 때 적합도 만점을 준다. 쪼개 재배열하면 0이 된다.**
1. **상품수 낮은 키워드부터 원문 그대로 이어 붙인다.** 공유 term 1종인 쌍을 고른다
   → `이발의자 전동미용의자`('의자' 2회 = 1종 2회 ✓).
2. **term 2종 이상 공유 쌍은 둘 다 통으로 못 넣는다 → 아래 레시피로 부분 반영한다(R3 실패 방지).**
   두 키워드가 term을 2종 이상 공유하면(예 `조립식캐노피천막`+`자바라캐노피천막` = '캐노피'·'천막' 2종),
   그대로 이어 붙이면 term이 2종 2회씩 되어 R3 실패다. 이렇게 고친다:
   - **상품수 낮은 쪽만 통 키워드(연속 문자열=적합도 만점)로 쓴다.**
   - **높은 쪽에서는 공유하지 않는 '구별 term' 1개만** 뽑아 낮은쪽 키워드에 붙인다.
   - 결과적으로 **같은 term이 2회 나오지 않게**(중복어=없음) 만든다. 두 키워드는 키워드1·2 칸에는 다 남긴다
     (R4는 2개로 통과, R5는 낮은쪽만 만점 = 부분반영 경고).
   ```
   조립식캐노피천막(21,172) < 자바라캐노피천막(29,665)
     → "자바라 조립식캐노피천막"  (자바라=구별 term, 캐노피·천막 각 1회)
     → 남는 자리는 실물 확인 단어로 term7 → "자바라 조립식캐노피천막 원터치 접이식 2.7X3"
   ```
   (같은 원리: 자동비누방울머신+자동버블머신 → 자동비누방울머신 통 + '버블'만 / 중국레고호환+중국호환블럭 → 중국레고호환 통 + '블럭'만)
3. 남는 자리를 원본 상품명 단어로 채워 term 7까지 → `이발의자 전동미용의자 업소용 높이조절 고급`
4. `term분해`는 등장 순서대로 전부 나열(중복 포함) → `[이발,의자,전동,미용,의자,업소용,높이조절,고급]`
- **중복 term은 1종·2회까지만.** 3회 이상 또는 2종 이상이면 순위 하락
- 8 이상은 패널티 구간, 넘지 마라. 옵션명은 상품명 term에 넣지 않는다
- 8을 넘겨 빼야 하면 순서: `약한 활용표현 → 색상 → 부가 구조 → 의미 중복`.
  **고른 키워드는 마지막까지 보존**(쪼개거나 순서 바꾸면 적합도 0). 밀린 검증 키워드는 3-6으로

### 3-6. 밀린 검증 키워드를 속성·태그 제안으로 남긴다

term 7 상한에 밀려 상품명에 못 넣은 것은 **버리지 마라.** 속성은 경쟁을 자릿수로 깎는다
(실증: `접이식 책상` 131만 → 가로사이즈 속성 2,900 → 소재까지 495).
- `속성제안` = 규격·사이즈·소재 등 **증거에서 확인된 것만**(확인 안 된 소재는 여기도 금지)
- `태그제안` = 검증됐지만 상한에 밀린 키워드 **원문 그대로**
- 없으면 빈 문자열. 자동 반영 경로는 없고 이룸님이 스마트스토어 센터에서 직접 입력한다

### 3-5. 반증(B)을 돌린다 — **배치당 1회**. 생략 불가

배치의 **모든 상품 명명이 끝난 뒤**, 초안을 먼저 쓰고 반증을 한 번에 돌린다:

1. 초안을 쓴다: `named/draft_NNN.json` (형식은 §4의 최종 출력과 동일. **각 상품에
   `카테고리파일` 필드를 배치 JSON 값 그대로 복사해 넣는다** — 반증 스크립트가 이 경로를 쓴다.
   배치 JSON에 그 필드가 없으면 `카테고리뷰` 경로에서 `views/`→`prefiltered/`, `.txt`→`.xlsx` 로
   치환한 경로를 넣는다 — 비워 두면 반증이 **조용히 건너뛰어** R7에서 늦게 터진다).
2. 배치 모드 1회 실행:
   ```bash
   python .claude/skills/product-name/scripts/challenge.py \
     --named "<run-dir>/named/draft_NNN.json" --cat-dir "<run-dir>/prefiltered" \
     --output "<run-dir>/named/draft_NNN.chal.json"
   ```
3. `draft_NNN.chal.json` 을 Read 한다. 각 상품의 `반증텍스트` 에 "채택보다 싸면서 같은
   범주어를 쓰는" 후보가 들어 있다.
4. 상품별로 답한다: 더 적합하면서 상품수 낮은 게 있으면 **지목하고 그 상품명을 다시 만든다.**
   없으면 `반증`에 `없음` + 한 줄 이유.
5. 재판단을 반영한 **최종본을 §4 경로(`named/named_NNN.json`)에 쓴다** (반증 결과·수정 포함).
   draft·chal 파일은 지우지 않는다(감사 흔적).

> 왜 배치당 1회인가: 상품당 Bash 1회(총 ~10회/배치)가 이 워커 턴 수의 최대 발생원이었다.
> 한 턴은 컨텍스트 전체 재과금이다 — 867건 실측에서 이 호출만 ~867턴이었다.

### 3-7. 보류는 사유에 따라 세 상태로 나눈다 (term 4는 보류 사유 아님 — 경고만)

- 실물을 못 정함 → `상태: "보류(실물불명)"` (J열 없고 증거 4종으로도 불명)
- 실물은 아는데 뷰에 직결어가 **하나도** 없음 → `상태: "보류(카테고리의심)"`
  (카테고리가 틀렸다는 신호. 억지로 원본 단어로만 상품명 만들지 마라)
- 직결어는 있으나 2개를 못 채움 → `상태: "보류(키워드부족)"`
- `메모`에 사유를 남긴다

### 5. 오케스트레이터에는 구조화 요약만 반환한다

뷰·썸네일·추론은 반환하지 마라 — 워커 컨텍스트에서 폐기된다. Workflow 모드에서는
StructuredOutput 스키마가 강제된다. 필드(스키마 키는 API 제약으로 ASCII만 허용):

```json
{"batch": 7, "created": 8, "held_unclear": ["U01abc"], "held_category_doubt": ["U01def"],
 "held_few_keywords": [], "error": ""}
```

수동(모드 A/C)에서는 같은 내용을 한 줄로: `배치 007: 생성 8 / 실물불명 1 [U01abc] / …`
결과는 이미 `named/named_007.json` 에 있다 — 요약은 집계용일 뿐, **정본은 디스크다.**
