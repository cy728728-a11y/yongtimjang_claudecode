# 불사자 옵션 정리

> 매출 직결 스킬이다. **무엇을 팔고 무엇을 내리고 어느 가격을 대표로 세우나**를 바꾼다.
> 공통 규칙(스냅샷·현황판·계약)은 [`_shared/스킬-계약.md`](../_shared/스킬-계약.md).

## 왜 필요한가

수집된 상품의 옵션에는 **파는 물건이 아닌 행**이 섞여 있다 — 구매금지 안내, 사이즈표,
보증금·추가금, 부속품 단독, 다른 모델, "맞춤제작 고객센터 문의". 그대로 올리면
고객이 엉뚱한 걸 주문하고, 대표가격이 왜곡되고, 옵션명이 중국어·접두사로 남는다.

## 흐름

```bash
# ① prep — 현황판에서 대상 확정 → 스냅샷(옵션 포함) → 옵션 이미지 → 배치
python .claude/skills/bulsaja-option-cleanup/scripts/run_options.py prep \
  --group-name "1번_용쌤1-1" --run-dir "<데이터루트>/option-cleanup/runs/<이름>" [--limit 5]
#    대표썸네일·옵션값 이미지는 긴 변 512px 로 줄여 나간다(`--max-px`, `0`=원본).
#    실측상 치수 숫자(`45*39`·`19cm`)가 원본과 같이 읽힌다 — _shared/스킬-계약.md §이미지 해상도

# ② run — Claude(또는 워커)가 배치를 읽고 판단 → results/result_NNN.json
#    판단할 것: 메인상품이 무엇인가 · 어느 행이 비상품인가 · 이름을 뭐라 지을까
#              · 최저가 동률이면 어느 쪽이 대표 썸네일과 닮았나

# ③ apply — 계산·검증 → 시트 기록 → Claude 표본검수 → 자동 저장
python ... run_options.py apply --run-dir <R>            # 미리보기 = Claude 표본검수 입력
python ... run_options.py apply --run-dir <R> --commit   # 저장 (표본검수 통과 직후 바로 — 승인 대기 없음)
```

> **저장 승인은 상시 위임돼 있다 (2026-08-05 이룸님).** 미리보기 결과(정리대상·보류 집계)를
> 보고하되 **답을 기다리지 않고 바로 `--commit` 까지 진행한다.** "저장할까요?"라고 묻지 않는다 —
> `before_commit.json` 으로 되돌릴 수 있고, 매번 승인 대기가 그룹마다 흐름을 끊었기 때문이다.
> 다만 **감사에서 누락이 잡히면 스크립트가 `--commit` 을 막는다** — 그건 그대로 둔다(보고 후 판단).

대상 선정은 **현황판 쿼리 1줄**이다(`00_진행` 탭의 `옵션` 열이 빈 상품). 1건이든 1000건이든 같다.
특정 상품만 하려면 `--ids`.

## run 실행 = Workflow 모드 (대량 기본, 2026-08-01)

공통 규약(메인 직독 금지·동시성 opt-in·재개·멱등·폴백·4벌 동시 수정)은
[`_shared/스킬-계약.md`](../_shared/스킬-계약.md) §팬아웃 공통 규약 — 여기 다시 적지 않는다.
이 축의 예산: **이미지 워커당 ≤16장 · 상품 ≤10건**.

1. `python … run_options.py pending --run-dir <R>` — 남은 배치를 Workflow args JSON 으로 출력.
   배치당 `[번호, 이미지수, 상품수]` 압축형(`compact`)이다 — 경로는 워크플로가 합성한다.
   **손으로 줄이거나 배치를 골라 담지 마라.** 출력을 통째로 넘긴다
2. `Workflow` 도구를 `{name: "optclean-fanout", args: <출력 그대로>}` 로 호출.
   워커는 `agent(model: sonnet, effort: low)` — 지시서는
   [`references/옵션-워커-프롬프트.md`](references/옵션-워커-프롬프트.md), 판단 정본은
   [`references/옵션명-규칙.md`](references/옵션명-규칙.md) 하나다
3. 완료 반환의 `재팬아웃필요배치` 가 비었는지 확인 (워크플로 내부에서 이미 1회 자동
   재팬아웃한 결과다). 남았으면 `pending` 재계산 후 **1회만** 재호출
4. `apply --run-dir <R>` 미리보기 — **워크플로는 results 생성까지다.** 시트 기록·표본검수·
   저장(`--commit`)은 메인이 한다. apply 는 감사(배치 대비 누락·환각 대조)를 먼저 찍고,
   누락이 있으면 `--commit` 을 차단한다(`--allow-missing` 은 의도된 부분 처리 전용).
   같은 pid 가 두 결과 파일에 오면 apply 가 마지막 파일을 채택한다.

> **동시 서브에이전트 기본 가이드라인(≤15)은 이 팬아웃에 적용하지 않는다** — 워커는
> 디스크에만 쓰고 상호 간섭이 없으며, 상한은 이미지예산(워커당 ≤16장)·상품상한(≤10건)과
> 하네스 동시성 캡이 관리한다. 이 문장이 그 명시적 opt-in 이다.

**재개·멱등**: `results/result_NNN.json` 존재 = 그 배치 완료. 같은 pid 가 두 파일에 오면
apply 가 마지막 파일을 채택한다. **폴백**(소량·워크플로 불가 환경): 메인 또는 Agent 워커가
같은 지시서로 배치를 직접 처리한다 — 워커 1명 = 배치 1~2개.

## 대량 그룹(수백 건)의 저장 — 반드시 지킬 것 (2026-08-04 용쌤2-1에서 학습)

저장은 **상품당 4호출**(이름 저장 → 재조회 → 포함/제외·대표·순서 저장 → 재조회)이라
**분당 10~12건**이 한계다. 700건이면 **1~1.5시간**은 정상이다. 그날 15시간이 걸린 건
느려서가 아니라 아래 3가지 때문이었다 — 다시 밟지 않는다.

| 그날의 사고 | 이제는 |
|---|---|
| 워커가 유지 옵션만 이름을 고쳐, 제외 옵션에 남은 `A. ` 접두사로 **저장이 전량 실패** | `_fill_prefix_names` 가 접두사 남은 값을 자동 정리(코드로 방어) |
| 워커가 productId 뒷자리를 잘라 적어 감사가 `--commit` 을 차단 → 재팬아웃 2회 낭비 | `_repair_truncated_ids` 가 배치 정본과 접두사 대조로 자동 복구 |
| **저장 루프가 죽은 걸 9시간 몰랐다** (분리 프로세스 + 알림 없음) | 아래 두 줄을 반드시 같이 건다 |

**① 재개는 기본이다.** `apply --commit` 은 성공한 상품을 `run-dir/committed.json` 에
**건별로 즉시** 남기고 다음 실행이 건너뛴다. 중단돼도 진도는 산다 — 겁내지 말고 다시 돌린다.
재개 회차는 MCP 를 0회 치고 **현황판·이관만 채운다**(그게 재실행의 주 용도다).
전건 다시 저장하려면 `--ignore-committed`.

> 이 재개는 **2026-08-14에야 코드에 들어왔다.** 그전까지 이 문단은 문서에만 있었고
> `run_options.py` 에는 `committed` 라는 낱말조차 없었다(2-2 에서 발견 — 현황판을
> 채우려고 다시 친 회차가 700건을 처음부터 다시 저장해 1시간을 썼다).
> **문서가 코드를 앞서가면 그 문서를 믿고 짠 운영이 조용히 배로 든다.**

**② 오래 걸리는 저장은 "띄우고 잊기" 금지.** 분리 프로세스로 돌릴 거면 **진도 감시를
같이 건다.** 감시 없이 띄우면 죽은 걸 알 방법이 없다(그날의 최대 손실 = 9시간 공회전).

```bash
# 진도가 목표에 닿으면 알림 1회 — 저장을 띄운 직후 같이 건다
until [ "$(python -c "import json;print(len(json.load(open('<R>/committed.json'))))" \
        2>/dev/null || echo 0)" -ge <목표건수> ]; do sleep 60; done; echo "옵션 저장 완료"
```

**③ 분리 프로세스에 한글 인자를 넘기지 않는다.** PowerShell 로 넘긴 `--group-name
"2번_용쌤2-1"` 이 인코딩이 깨져 시트 조회 0건 → 60회차가 즉시 실패만 반복했다.
**`--sheet <시트id>` 로 넘긴다**(ASCII 라 안전하다).

**④ 시트 기록과 저장을 분리한다.** 미리보기에서 시트·검수표를 이미 썼으면
저장 회차는 `--no-sheet --no-review` 로 돌린다 — 원장 탭 쓰기가 쿼터(429)에 걸려
저장 시작까지 몇 분을 잡아먹는다.

> **`--no-sheet` 는 이제 원장 탭(`옵션`·`옵션축`)만 막는다** (2026-08-14 수정).
> **현황판(`00_진행`)과 이관 flag 는 `--no-sheet` 와 무관하게 항상 나간다.**
>
> 전에는 셋이 한 플래그에 묶여 있었다. 그래서 25-2(254건)·2-2(664건) 두 번 다
> **저장은 전건 됐는데 현황판 `옵션` 열은 `재작업(…)` 그대로**였고 썸네일·상품명으로 갈
> `이관` 도 안 나갔다 — 다음 회차가 같은 상품을 통째로 다시 집는 상태다.
> 두 번 밟았으니 운영 수칙이 아니라 코드로 막는다.
>
> 현황판까지 끄는 건 `--no-matrix` 다(검증·재현 전용 — 썸네일 스킬과 같은 이름·같은 뜻).
> **평상시 쓰지 마라.** 이걸 쓴 회차는 `--commit` 을 한 번 더 쳐서 복구한다.

> ⚠ **`--commit` 재실행은 "MCP 0회"가 아니다 — 확인하고 쳐라 (2026-08-14 3-3 실측).**
> `committed.json` 이 있으면 저장을 건너뛴다고 믿고 660건짜리 회차에 그대로 쳤다가
> **615건이 재저장됐고 그중 32건의 옵션 이름이 한 칸씩 밀렸다**(순백 옵션에 "문의필요"가
> 붙고, 문의 안내행에 멀쩡한 상품 이름이 붙었다). 대표·제외·가격·순서는 안 깨지고
> **이름 배정만** 깨진다 — `기본형` 마커 검증이 실패하는 걸로 드러난다.
>
> 원인: `committed.json` 은 1회차가 **끝날 때** 쓰이는데, 2회차가 그보다 먼저 시작하면
> 빈 상태를 읽는다. 파일 존재 여부가 아니라 **1회차가 완주했는지**가 조건이다.
>
> **재실행 전에 `committed.json` 의 건수가 1회차 반영 건수와 맞는지 먼저 본다.**
> 안 맞으면 `--ids` 로 5건만 쳐서 건너뛰는지 확인하고 전건에 건다.
> 이미 밟았으면 `restore --ids <실패건>` → `apply --ids <실패건> --commit` 으로 복구한다
> (실측 32건 중 30건 복구·검증 통과).

## 결과 파일 형식 (워커가 만드는 것)

```json
{"products": [{
  "productId": "U01...",
  "메인상품": "아크릴 3단 사이드테이블 (색상만 다름)",
  "유지": ["19491740168", "..."],
  "제외": [{"id": "3254774", "사유": "맞춤제작 — 실제 수령품 확인 불가"}],
  "이름": {"1": "주황색", "2": "블랙 기본형"},
  "대표후보": "19491740169",
  "축교정": [{"차원": 0, "제안": "모델", "사유": "축은 '색상'인데 값이 전부 모델 구분"}],
  "이관": [{"단계": "썸네일", "사유": "대표 썸네일이 검정인데 옵션에 검정 없음"}],
  "메모": "6색 동가·동일 치수라 치수를 이름에서 뺌"
}]}
```

- `유지` = **메인상품인 판매행 id 전부**. 1.5배 상한·재고 0 걸러내기는 스크립트가 한다
  (사유가 자동으로 남는다 — 사람이 미리 빼면 왜 빠졌는지가 사라진다).
- `이름` 키 = **옵션값 vid**(판매행 id 아님 — 위 예시의 `"1"`·`"2"` 가 vid 다.
  `유지` 의 `19491740168` 같은 판매행 id 를 키로 쓰면 엉뚱한 차원이 바뀐다).
  복합 옵션이면 스크립트가 차원 좌표로 바꿔 쓴다.
  단 **두 차원에 같은 vid 가 있으면 `"@차원:vid"`** 로 줘야 한다(→ 저장은 2단계로 나뉜다 절).
- **대표옵션 이름 끝에는 ` 기본형`** 을 붙인다(규칙 17) — 워커는 유지 중 **최저가**에 붙이면
  되고, 규격어 지정(규칙 19) 상품은 스크립트가 마커를 옮긴다(`retarget_base_suffix`).
  25자 안에서 흡수하고, 대표가 아닌 옵션엔 붙이지 않는다. 복합옵션은 대표 조합에서
  **값이 2개 이상인 마지막 차원**의 값에(값 1개 차원은 선택 항목이 아니다 — 규칙 17 하위 절).
- `대표후보` = 최저가가 **동률일 때만** 의미가 있다. 더 비싼 걸 지정하면 무시하고 경고한다.
- **`축교정` = 옵션 축(선택 항목) 이름이 값과 어긋날 때만** (규칙 18). 어긋난 축만.
- **`이관` = 옵션 범위 밖에서 발견한 문제를 그 단계에 넘긴다.** 메모에만 적으면 유실된다
  (파일럿 5건 중 3건이 그랬다). `단계` 는 현황판 열 이름(`썸네일`·`상품명`·`상세` …).
  자세한 규칙은 [`_shared/스킬-계약.md`](../_shared/스킬-계약.md).
- **`삭제후보` = 상품명이 가리키는 물건과 옵션 실물이 아예 다른 품목** (2026-08-06 이룸님)
  → 아래 §상품명으로 되돌리기.

## 상품명으로 되돌리기 (2026-08-06 이룸님)

옵션 원문을 읽다 보면 **상품명이 틀린 게 보인다.** 그런데 상품명만 원장이 `상품명` 탭이라
현황판 재작업 표시가 닿지 않았다 — 옵션이 flag 를 찍어도 상품명 prep 이 "상품명 탭 A열에
없는 것"만 대상으로 잡아 **아무도 안 집었다.** 양쪽을 이었다.

| 워커가 넣는 것 | 무슨 일이 일어나나 |
|---|---|
| `이관: [{"단계": "상품명", "사유": …}]` | 현황판 `상품명` 열에 `재작업(옵션: 사유)` → **상품명 prep 이 자동 편입**(`_matrix_redo`). 사유가 배치에 실려 워커에게 간다 |
| `삭제후보: "<근거>"` | 상태 `보류(삭제대상)` → 옵션 **저장하지 않음** + `deletion_candidates.json` → 메인이 **묻지 않고 바로** `bulsaja_market_delete` |

> **삭제 승인도 상시 위임돼 있다 (2026-08-17 이룸님).** `deletion_candidates.json` 은
> 판정 큐가 아니라 **작업 지시서**다. 목록을 보고하되 답을 기다리지 않고 지운다.
> `deleteAction=MARKET_AND_SOURCE` · `scope=ALL` — 상품명이 딴 물건을 가리키는 리스팅은
> **마켓에서도 내려야 한다**(1-2 실측 17건이 전부 스마트스토어에 올라가 있었다).
> 소싱분은 휴지통이라 복구 가능하다. 지운 뒤 현황판 `옵션` 열에 `상품삭제(사유)`,
> 나머지 작업 열은 `해당없음` 으로 닫는다 — 안 닫으면 다음 회차가 유령을 집는다.
>
> `"잠금된 상품은 삭제 불가"` 는 결함이 아니라 이룸님이 앱에서 건 삭제 잠금이다(§잠금).
> **잠금 1건이 섞이면 그 호출의 소싱 이동이 통째로 보류된다** — 잠금 건을 빼고 다시 보낸다.

되돌릴 신호 셋(이 밖은 이관하지 않는다):
**①스펙·규격이 원문과 다름**(8인치인데 '10인치') **②대표충돌**(상품명이 규격어로 지정한
대표가 실물에 없거나 부속) **③뒤집힘 복구 후 지칭 불일치**(부속→본품 복구했는데 상품명이
아직 부속을 가리킴). **품목 자체가 다르면** 이관이 아니라 `삭제후보` 다.

- **상품명 이관만 저장 성공 여부와 무관하게 넘어간다**(`HANDOFF_ALWAYS`). 나머지 이관은
  종전대로 저장된 건만 — 썸네일 이관은 대표가 확정돼야 대조 대상이 생기기 때문이다.
- **품목대조(2026-08-10)**: `apply` 가 상품명과 워커의 `메인상품` 을 **전수 기계대조**해
  한 낱말도 안 겹치면 `상품명` 이관을 자동으로 하나 더 붙이고 검수표·요약에 찍는다.
  워커 판정만으로는 샌다 — 2026-08-09 용쌤2-1 에서 워커 27건 뒤에 13건이 더 나왔다.
  **저장은 막지 않는다**(위양성이 섞인다: 개집↔도그하우스 같은 동의어도 걸린다).
  실측 725건에 25건(3.4%) 발화.
  상품명 이상이 가장 잘 보이는 자리가 하필 `보류(대표충돌)`(= 저장 안 되는 상태)이라,
  저장을 조건으로 걸면 그 신호가 통째로 사라졌다. **전건이 보류인 회차도 이관은 넘긴다**
- 상품명 쪽 재진입은 자동이다 — `append` 가 옛 `생성완료` 행을 `재작업` 으로 내려
  rename 중복 반영도 막는다(`_retire_stale_rows`). 사람이 시트를 손볼 일이 없다

### 썸네일에서 되돌아온 건 — 대표옵션 이미지가 실물인지 본다 (2026-08-07 이룸님)

`재작업사유` 에 **`기준이미지없음`·`대표옵션의심`** 이 있으면(썸네일이 되돌린 건) 워커가
대표로 세울 옵션의 **이미지 1장을 열어 실물인지 확인**한다(워커 프롬프트 §2-10).
비제품이면 다음 후보로, 실물이 나올 때까지 — 대개 1~2장. **그 사유가 없으면 안 연다.**

**왜 이미지를 봐야 하나** — 옵션명으로는 알 수 없다. 실측(3-2): `1m 원목벤치 월넛 기본형`·
`가시나무자단 9칸 기본형`(둘 다 도면)과 `브러시 단일노즐 기본형`(실물)이 **이름만으로는
전혀 구분되지 않았다.** 옵션명은 제품이 뭔지를 적은 것이고, 이미지가 도면이냐는 판매자가
뭘 올렸느냐라 두 정보가 독립이다.

**실물 이미지를 가진 옵션이 하나도 없으면** `이관` 에 `실물기준없음` 이라는 낱말을 넣어
썸네일로 되돌린다. 썸네일 `prep` 이 그 낱말을 보고 그 상품을 **대표옵션 기준에서 빼
후보 이미지에서 고르는 경로**로 보낸다(`R.NO_REAL_BASE`).
**이게 썸네일↔옵션 왕복의 종결 상태다** — 이 낱말이 없으면 썸네일이 같은 대표옵션을 또
기준으로 잡아 무한히 왕복한다. 실물 옵션이 없는 상품은 실재한다(3-2 57건 중 3건이
고유 옵션이미지 1장뿐).

> **워커가 안 붙이면 코드가 붙인다** (2026-08-15). 용쌤2-1 에서 옵션 57건을 고쳐 31건을
> 썸네일로 돌려보냈는데 2회전에서 `대표옵션의심` 8건 · `기준이미지없음` 1건이 **또** 나왔다
> — 낱말이 안 붙어 왕복이 안 닫힌 것이다. 잘린 productId 와 같은 부류의 지시 불이행이라
> 지시문으로는 안 막힌다.
>
> 이제 `_handoff` 가 **왕복 2회차부터** 자동으로 붙인다: 배치의 `재작업사유` 가 이미
> 썸네일발(`기준이미지없음`·`대표옵션의심`)인데 워커가 썸네일로 되돌리며 `실물기준없음`
> 을 안 넣었으면 앞에 끼워 넣고 `[왕복종결]` 을 찍는다. 첫 이관에는 붙이지 않는다 —
> 그건 옵션이 대표를 새로 세워 정상적으로 넘기는 것이다.
> 붙여서 손해 볼 것도 없다: 썸네일이 후보 이미지에서 고르는 경로로 갈 뿐이고, 새로 세운
> 대표도 후보에 그대로 들어 있으며 크레딧도 안 든다.
>
> **그런데 그 장치가 한 번도 발화하지 못하고 있었다** (2026-08-15 3회차 실측 · 수정 완료).
> 판정 근거인 `재작업사유` 에 낱말이 아예 안 실려 왔다 — 썸네일은 판정 낱말을 **자기 열의
> `보류(...)` 에만** 쓰고 옵션 열로는 워커가 쓴 산문만 넘겼기 때문이다("대표옵션은 프레임+
> 걸이 기본형인데 기존대표는 풀세트 구성"). 그래서 3바퀴를 돌고도 같은 24건이 되돌아왔고
> 낱말이 붙은 건 1건뿐이었다. 이제 썸네일이 `_to_option_reason` 으로 **낱말을 맨 앞에 박아**
> 넘긴다. 두 스킬이 같은 낱말을 본다는 계약은 교차 테스트로 고정돼 있다
> (`test_thumb_prescreen.py::test_옵션_스킬이_이_값을_왕복_2회차로_읽는다`).

### 썸네일 보류는 미아가 된다 — `apply` 가 되찍어 회수한다 (2026-08-15)

썸네일 `prep` 의 대상은 현황판 썸네일 열의 **빈칸 + 재작업**(`matrix.pending`)이다.
**`보류(...)` 는 안 집는다.** 그런데 옵션정리는 워커가 `이관` 을 남길 때만 썸네일 열을
되찍었다 — 대표가 이미 맞다고 판단하면 아무것도 안 찍는다.

실측: 옵션 3회전이 48건을 저장했는데 썸네일로 배턴이 간 건 20건뿐이고 **26건이 `보류` 인
채 남았다.** 옵션 축이 아예 안 건드린 보류 25건까지 더해 **51건이 어느 축도 안 집는
상태**였다. 에러도 경고도 없다 — 로그 숫자를 직접 세야만 드러난다.

이제 `apply --commit` 이 저장 성공분 중 썸네일 열이 `보류(대표옵션의심)`·
`보류(기준이미지없음)` 인 건을 자동으로 되찍는다(`_recover_orphans` → `[미아회수]`).
**두 갈래로 나눠 보낸다** — 안 나누면 왕복이 그대로 또 돈다:

| 대표가 | 원래 보류가 | 보내는 값 | 왜 |
|---|---|---|---|
| **바뀌었다** | (무관) | `대표 재지정 완료 — 재판단(…)` | 기준이 실제로 달라졌으니 썸네일이 새 대표옵션 이미지로 대조하면 풀릴 수 있다 |
| **그대로다** | `기준이미지없음` | `실물기준없음: 대표 확인 완료(변경 없음) …` | 대표옵션 이미지가 비제품인데 옵션이 못 고쳤다 = 기준이 아예 없다. 후보에서 직접 고르게 해 왕복을 끝낸다 |
| **그대로다** | `대표옵션의심` | `대표 확인 완료(변경 없음) — 재판단(…)` | **대표옵션 이미지는 실물이다.** 쟁점은 "그게 본품이냐"였고 옵션이 "맞다"고 확인했다 — 그 이미지를 기준으로 대조해야 풀린다 |

> **셋째 줄이 처음엔 빠져 있었다** (2026-08-17 실측으로 갈랐다). 대표가 안 바뀌면 전부
> `실물기준없음` 으로 닫았는데, 그러면 `prep` 이 **멀쩡한 대표옵션 기준을 빼버린다.**
> 실내분수가 그 사례다 — 대표옵션은 흰색 연꽃형 3단 분수라는 또렷한 실물 사진인데
> 기준에서 빠졌고, 워커가 후보(전부 파란색)에서 고를 수밖에 없어 파란 계단형이 나왔다.
> 원래 문제가 그대로 남고 크레딧만 나갔다.
> **"대표가 안 바뀐 것"과 "기준이 없는 것"은 다른 얘기다.**

`보류(생성실패)`·`보류(주의)` 처럼 **옵션이 풀 수 없는 보류는 건드리지 않는다** — 없는
일감을 만들지 않는다. 워커가 이관을 남긴 건도 덮어쓰지 않는다.

## 막히면 지우고 넘어간다 — 처리량이 먼저다 (2026-08-17 이룸님)

> "상품 하나하나에 너무 연연하지 마라. 시간이 오래 걸리거나 토큰을 많이 소비하는 등
> 골치아픈 문제가 생기면 그냥 삭제하고 다음 상품으로 넘어가라. **많은 상품을 빠르게
> 진행하는 것이 가장 중요하다.**"

수백 건짜리 그룹에서 한 상품에 매달리는 건 언제나 손해다. 그 상품 하나를 살리는 값이
나머지 수백 건의 진도보다 클 수 없다. **사후 판정 큐를 만들지 마라** — 큐는 사람 손을
부르고, 그게 이 파이프라인이 피하려는 바로 그것이다.

| 이런 상태면 | 이렇게 한다 |
|---|---|
| `보류(저장실패)` 가 **두 회차 이상** 반복 | 삭제. 서버가 계속 거부하는 상품은 원인 규명 값이 없다 |
| 제외 200 초과 대표 지정 거부(§알려진 함정 미해결) | 삭제. **재팬아웃해도 안 풀린다** |
| 축·이름 하나 살리려고 상품별 수작업이 필요 | 축은 포기하고 상품은 살린다(축은 표기다) |
| 워커가 같은 자리에서 두 번 실패 | 삭제 |

**예외는 잠금 상품 하나다.** `삭제보류(잠금)` 은 이룸님이 판매된 상품에 건 보호라
스킬이 풀 수 없다 — 현황판에 남기고 종합보고에 상품id 를 낸다.

지운 뒤엔 반드시 현황판을 닫는다(`상품삭제(사유)` + 나머지 열 `해당없음`).
**빈칸으로 두면 다음 회차가 없는 상품을 집는다.**

[`references/옵션명-규칙.md`](references/옵션명-규칙.md) §메인상품 선별 (2026-08-01 이동 — 워커 규칙 정본을 한 파일로).

**옵션명** — 중국어 원문 기준으로 고친다(한국어 표시명은 기계번역이라 틀려 있다).
공백 포함 25자 · 정렬용 접두사(`A. `) 제거 · 군더더기 제거 · 확인된 차별점만 ·
**고유성을 지키는 최단 이름**. 전문은 [`references/옵션명-규칙.md`](references/옵션명-규칙.md).

**대표·판매범위·순서**(스크립트가 계산 — `option_rules.py`)
1. 메인상품이면서 **팔 수 있는**(가격 있고 재고 있는) 행만 후보
2. **상품명이 규격어로 지정한 대표가 있으면 그것**(아래 참조). 없으면 최저가가 대표 —
   동률이면 대표 썸네일과 가장 닮은 것 → 그래도 동률이면 원본 순서
3. **기준가 ±50% 가 판매 범위** — 상한 `×1.5`, 하한 `×0.5`(같은 값 포함). 밖은 판매 제외
4. 판매가 오름차순 = 업로드 순서. **대표가 전체 맨 앞**
5. ±50% 는 **메인상품 후보를 확정한 뒤에만** 적용 — 부속품이 섞인 채 계산하면
   기준가가 500원이 되어 본품이 전멸한다

>   고칠 게 확정된 상태가 아니라는 뜻이라, `종류` 로 덮으면 개악이다

아님에 더해 **금지문자 `, [ ] / { } ( ) * ? \ ^ $ |` 없음**과 **같은 상품 내 축끼리

그 호출이 통째로 실패하기 때문이다.

`완료` 이며 그 축만 원장에 `보류(…)` 로 남는다. 축은 표기고 ②는 무엇을 파느냐다.
**이룸님이 `옵션축` 탭에서 `무시`·`반영` 으로 판단한 축은 재실행이 건드리지 않는다.**

### 원장에 쌓인 축을 태운다 — `axis` (2026-08-17)

`apply --commit` 이 저장하는 축은 **이번 run 에 든 상품**뿐이다. 그런데 `옵션축` 탭에
쌓여 있던 축은 전부 **옵션이 이미 `완료` 인 상품**의 것이라 현황판 `pending` 에 안 잡힌다
— MCP 에 축 필드가 없던 시절에 판정만 해둔 것이기 때문이다. **저장부만 고치면 그 backlog
는 영영 안 나간다**(1-2 실측 278행 중 제안이 있는 200행이 그 상태였다). 그렇다고 옵션을
통째로 다시 돌릴 이유는 없다 — 바뀌는 건 축 표기 하나고 무엇을 파느냐는 이미 정해져 있다.

```bash
python ... run_options.py axis --sheet <시트>            # 미리보기(원장에 안 쓴다)
python ... run_options.py axis --sheet <시트> --commit   # 저장 + 원장 갱신
```

**원장이 현재 상태와 어긋나면 보내지 않는다.** 제안은 그때의 축 이름을 보고 지은 것이라,
그 사이 축이 달라졌으면 근거가 사라진 것이다.

| 현재 축 이름이 | 하는 일 |
|---|---|
| 제안과 같다 | `반영` 으로 적고 **호출하지 않는다**(이미 그렇게 돼 있다) |
| 원장의 `현재축명` 과 다르다 | `보류(축이 바뀌었다: …)` — 사람이 다시 본다 |
| 그 밖 | 저장 → 재조회 검증 → `반영` / `보류(검증실패)` |

판정·검증은 `apply` 와 **같은 함수**를 쓴다(`axis_saveable`·`axis_verify`) — 경로가 둘이어도
판정은 하나다. 저장분은 스냅샷의 `옵션` 도 되쓴다(안 하면 다음 회차 워커가 옛 축을 보고
같은 제안을 또 내서 원장이 다시 부푼다). 회귀는 `test_option_prep.py::AxisLedgerReplayTest`.

> **1-2 실측(2026-08-17)**: 200축 중 **165축 반영 · 30축 보류**. 보류 30 중 **25건이
> 같은 원인** — 제안에 `/` 가 들어갔다(`색상/마감`·`모델/용량`·`등급/무게`). 그 제안들은
> 금지문자 규칙이 생기기 **전**(2026-08-06)에 지은 것이라 워커 탓이 아니다.
>
> 그래서 **`/` 만은 코드가 `·` 로 고쳐 보낸다**(`axis_repair` — 이룸님 판단, 2026-08-17).
> 금지문자 중 유일하게 뜻이 확실하다: `색상/마감` = "색상과 마감이 섞였다"이고 `색상·마감`
> 이 그 뜻 그대로다. 괄호 같은 건 무엇으로 바꿀지 기계가 모르니 종전대로 거부해 사람에게
> 남긴다. 고친 값은 원장 `제안축명` 에도 되쓴다 — **원장에 적힌 제안과 실제로 보낸 값이
> 달라지면 원장이 거짓이 된다.**

**대표옵션 마커 — 대표 이름 끝에 ` 기본형`** (2026-07-30 이룸님)
네이버는 '대표상품'(추가금 0원 옵션)을 상품명으로 쓰라고 요구한다 → **썸네일 = 대표옵션 =
상품명**이 한 옵션을 지칭해야 한다. 상품명 끝에도 같은 `기본형` 이 붙어(→ `product-name` R8)
**같은 단어가 짝을 지목한다.** 25자는 그대로 — 본문을 줄여 흡수한다.
대표가 아닌 옵션엔 붙이지 않는다. 복합옵션은 대표 조합에서 **값이 2개 이상인 마지막 차원**에
붙인다(값 1개 차원은 건너뛴다, 2026-08-05).

**어긋나면 `apply` 가 기계적으로 맞춘다** — 대표에 붙이고 나머지에서 뗀다(2026-08-06).
붙일 자리(`대표값키`)는 스크립트가 알고 있어 판단이 아니다. 워커가 빠뜨렸다고 사람을
한 바퀴 더 돌리지 않는다. **25자를 넘기거나 이름이 겹쳐 못 맞추는 것만** 상태가
`보류(기본형)` 이 되고, 그때도 **이름만 미저장, 판매·대표·순서는 저장한다**(아래 §부분저장).

## 저장은 3단계로 나뉜다

불사자 MCP가 **이름 변경과 순서 변경을 같은 호출에 넣는 것을 거부한다**(쿠팡 기존 옵션
연결 보호). 그래서:

```
① renameValues 만 저장 → 재조회 → 이름 검증(중국어·접두사·25자·중복)
② includeSkuIds / excludeSkuIds + mainSkuId + skuOrder 저장
③ renameGroups(축 이름) — **단독 호출** → 재조회 → 검증 7항목 + 축 이름 대조
```

**③은 MCP 가 막아서 나눈 게 아니다**(축 이름은 순서와 같은 호출에 넣어도 된다).
일부러 뗀 것이다 — 축 이름이 하나라도 거부되면 그 호출이 통째로 실패해서, **표기 문제
하나가 무엇을 파느냐(②)까지 되돌린다.** `기본형` 마커가 판매 구성을 막았던 3-1 워터건
사고와 같은 구조다(→ §부분저장). ③이 실패해도 ②는 이미 저장됐고 상품은 `완료` 다.
③을 재조회 **앞**에 두어 `after` 한 번으로 검증까지 끝낸다(추가 조회 0회).

**이름을 바꾸는 대상은 옵션값(차원)이지 판매행이 아니다.** 1차원 상품은 `vid` 로 찍고,
복합 옵션은 `vid` 가 차원마다 1부터 다시 시작하므로 반드시 `groupIndex`/`valueIndex` 로 찍는다
(스냅샷의 `vid고유` 플래그가 이걸 알려준다. vid 로 찍으면 **엉뚱한 차원이 바뀐다**).

> **두 차원에 같은 vid 가 있으면 vid 키를 거부한다**(2026-07-30). 예전엔 첫 차원에 조용히
> 붙어서 2번째 이후 차원 값은 **이름을 바꿀 방법이 아예 없었다.** 그때는 결과 JSON 의
> `이름` 키를 `"@1:1"`(차원 1의 vid 1) 형식으로 준다 — 배치의 옵션 이미지 키와 같은 관례다.

**최종 검증 7항목**(실패하면 '완료'라 하지 않는다): 옵션 수 불변 · 대표 정확히 1개이며
판매 포함 · 포함/제외가 계획과 일치 · **상한 초과·하한 미만이 살아있지 않음**(±50% 양쪽) ·
판매가 무단 변경 없음 · 표시명 중복 0 · **`기본형` 이 대표 값 하나에만 붙어 있음**(이름을
바꾼 저장에서만).

### 부분저장 — 이름 규칙만 어기면 ②는 저장한다 (2026-08-06 이룸님)

저장이 상품 단위로 **전부-아니면-전무**였다. 그래서 표기 규칙 하나(`기본형` 마커)가
**무엇을 파느냐**까지 같이 막았다 — 3-1 워터건은 워커가 뒤집힘(본품 19행 제외·부속
예비배터리 1행만 판매·대표)을 정확히 복구해 놨는데 마커가 없다는 이유로 통째로 미저장돼,
**스마트스토어에 배터리만 팔리는 채로** 남아 있었다(w1 69건 중 12건이 이렇게 빠졌고
그중 2건이 뒤집힘이었다). 마커는 ①(이름)에 붙는 표시라 ②와 무관하다.

- 1차 방어는 **자동 교정**이다(위 §대표옵션 마커) — 마커는 붙일 자리가 정해져 있어
  스크립트가 붙인다. 여기 남는 건 **25자 초과·이름 충돌**처럼 본문을 줄여야 하는 건뿐이다
- `보류(기본형)` → **①만 건너뛰고 ②(판매·대표·순서)를 저장**한다. 검증도 이름·마커
  항목을 건너뛴다(`verify(names=None)`)
- **완료로 끝내지 않는다**: 현황판 `옵션` 열에 `재작업(옵션: 기본형 마커 누락 …)` 을
  남겨 다음 회차 `pending(include_redo=True)` 이 자동으로 다시 집어간다.
  빈칸이면 사유가 사라지고, `보류(…)` 면 영영 안 잡힌다
- 로그 마지막 줄이 `반영 N건 / 부분저장 M건 / 실패 K건` 으로 바뀌었다 —
  **`실패 0건` 이 "다 됐다"가 아니다**
- 나머지 보류(`대표충돌`·`남길 옵션 없음`·`이름규칙`)와 `확인요` 는 종전대로 저장하지
  않는다. 그건 **무엇을 팔지가 아직 안 정해진** 상태라 저장하면 틀린 구성이 들어간다

## 불사자 저장 ≠ 마켓 반영

`--commit` 은 **불사자 서버의 상품 데이터**만 바꾼다. 이미 마켓에 올라간 상품이면
판매 화면은 그대로다 — **수정 업로드를 따로** 해야 반영된다(별개 작업).
미업로드 상품이면 나중에 올릴 때 정리된 상태로 올라간다(= 정리하기 가장 안전한 타이밍).
업로드 여부는 `workdata` 의 `uploadedSuccessUrl` 이 마켓별로 값을 갖는지로 본다
(dict 자체는 항상 있으니 **값이 전부 null 인지**를 봐야 한다).

## 되돌리기

`apply --commit` 은 저장 **직전에** `run-dir/before_commit.json` 을 남긴다.
스냅샷은 저장 성공 시 새 값으로 덮어써지므로 **이 백업이 유일한 원본**이다.

```bash
python ... run_options.py restore --run-dir <R> [--ids U01a U01b]
```

## 기록

- 그룹 시트 `옵션` 탭 — 상품별 메인상품·유지/제외·대표·기준가·상한·순서·상태·`옵션명변경`
  **순서·제외·대표는 id 가 아니라 이름으로 적는다** — `1 > 2 > 13` 은 사람이 승인할 수 없다.
  이미 있는 상품id 는 건너뛰지 않고 **그 행을 갱신**한다(되돌려 다시 돌리면 옛 계획이 남는다).
- `apply` 는 표 아래에 **검수표**(옵션명 기존→교정 · 판매 순서+가격 · 제외 사유)를 찍는다.
  `--no-review` 로 끌 수 있다. 세로 러너(onestep)도 같은 내용을 `--emit` JSON 에서 읽어
  종합보고에 싣는다.
- 그룹 시트 `옵션축` 탭 — **축 이름 원장**(규칙 18). 키는 (상품id, 차원).
  `반영`(저장함) / `대기`(제안 없음 — 사람 몫) / `보류(사유)`.
  이룸님이 `상태` 를 `반영`·`무시` 로 바꾼 행은 **재실행이 덮지 않고, 그 축을 저장하지도
  않는다**(`_axis_ignored` 가 제안 단계에서 뺀다).
  **이 탭의 상태 갱신은 `--no-sheet` 와 무관하게 나간다** — 현황판과 같은 이유다.
  실제로 바꿔놓고 원장에 `대기` 로 남기면 이미 반영된 축을 앱에서 또 손보게 된다.
  대신 미리보기 회차의 원장 쓰기는 종전대로 `--no-sheet` 가 막고, `--commit` 회차는
  **실제 결과로 한 번만** 쓴다(대기→반영 왕복 없음).
- 현황판 `00_진행` 의 **`옵션` 열만** 갱신 (`완료` / `보류(사유)`)
- 스냅샷의 `옵션` 필드를 저장 후 값으로 되쓴다 → 다음 스킬이 옛 옵션을 읽지 않는다

|---|---|

| 치수가 전 옵션 동일 | 이름에서 뺀다. 고유성은 색·구성이 만든다(고유성을 지키는 최단 이름) |
| 기존 한국어 이름끼리 거의 같음 | 원문을 봐야 다름이 보인다(`三腿两层` vs `三腿大两层` → '대형'을 넣어 고유화) |

| 상품명이 아예 딴 품목(청소기인데 옵션은 깔창) | 이름을 다시 지어도 못 판다. `이관` 이 아니라 **`삭제후보`** — 저장하지 않고 삭제 대상으로 뺀다 |
| 보류로 끝난 상품이라 이관을 생략 | **상품명 이관은 저장 여부와 무관하다.** `보류(대표충돌)` 이 곧 상품명 이상 신호라 여기서 빼면 원인이 영영 안 잡힌다 |
| 최저가 동률인데 대표후보 미지정 | 원본 순서로 정하고 **경고**한다. **저장은 막지 않는다**(2026-08-07 이룸님 — 대표는 원본 순서여도 되고, 썸네일만 대표옵션과 같으면 된다). `apply` 가 **썸네일 열에 재작업을 자동으로 찍어** 넘긴다. 전에는 `경고 하나 = 확인요` 라 사람 큐로 갔다(3-2 에서 4건) |
| 축이 `색상` 인데 값이 모델·소재·규격 | 타오바오 `颜色分类` 는 범용 SKU 축이다. **값을 축에 맞추지 말고** `축교정` 으로 넘긴다(규칙 18) — 2026-08-17부터 그 제안이 실제로 저장된다 |
| 축 이름이 `보류(겹친다)` 로 안 바뀜 | 같은 상품 안에서 축끼리 같은 이름을 못 쓴다. 워커가 축 둘에 같은 이름(`종류`)을 제안했거나, 안 바꾸는 축과 겹쳤다. **겹친 축은 전부 되돌린다** — 어느 쪽을 살릴지는 사람 판단이다 |
| **본품이 전부 `현재제외` 이고 싼 부속이 대표** | 수집 상태가 뒤집힌 것이다. 실측 7건 중 4건 — 롤테이너는 본품 6종이 전부 제외되고 선반 부속만 팔리고 있었다. `현재제외` 를 근거로 쓰지 말고 **가격 계단·원문 접두 한자(`加`·`送`·`单独`)·상품명 핵심어**로 직접 판정한다([`옵션명-규칙.md`](references/옵션명-규칙.md) §현재 상태를 믿지 마라) |
| 워커가 "이질 제품 혼재라 판독 불가"로 보류 | **그건 보류 사유가 아니라 제외 작업 지시다.** 섞인 걸 빼는 게 이 스킬의 일. 보류는 4개 신호를 다 돌린 뒤 최후수단 |
| 유지 옵션만 이름 줬는데 "중복으로 인식되는 최종 옵션 이름" 거부 | 손대지 않은 **기존 이름**이 25자에서 잘려 서로 같아진 것이다(접두사·공백 제거 후 비교). 충돌하면 **전 옵션에 원문 기준 이름을 준다** — 치수·구성이 고유성을 만든다 |
| 삭제하려는데 "다른 작업이 처리 중인 상품은 삭제 불가" | 이룸님이 **불사자 앱에서 건 삭제 잠금**이다(결함 아님). 아래 §잠금 |
| 제외 목록이 200개를 넘어 저장이 막힘 | `excludeSkuIds` 스키마 상한이다. **`includeSkuIds` 가 화이트리스트로 동작**하니 제외를 생략한다(자동) |
| **제외 200개 초과 상품에서 대표 지정이 계속 거부됨 (미해결)** | `"대표 옵션을 판매 제외하거나 대표 상태가 올바르지 않습니다…"` 가 **대표오류 fallback**(`run_options.py:118-129` — 이름+대표+포함/제외를 같은 호출에 싣는 경로)까지 갔는데도 떨어진다. 2026-08-15 2-3 실측 2건이 r4·r5 **두 라운드 다** 실패 — `U01KRZBANWB88A5Z7822JW6BT00`(중량랙, 옵션 378·제외 225) · `U01KRZBANR9H8Y91N0JEDPF2V1B`(카운터테이블, 옵션 585). 공통점은 둘 다 `excludeSkuIds` **분할 경로**를 탄다는 것. 원인이 스크립트인지 서버 제약인지 아직 못 갈랐다 — **재팬아웃해도 안 풀리니 반복하지 마라.** `보류(저장실패)` 로 남고 `pending` 에 안 잡힌다. **현재의 우회로는 불사자 앱에서 대표를 직접 세우는 것.** 재현 케이스 2건이 있으니 이 자리를 손댈 때 근거로 쓴다 |

## 잠금 — 삭제만 막고 수정은 막지 않는다

불사자 앱에는 **상품 삭제 잠금**이 있다. 이룸님이 직접 거는 것이라 스킬이 풀 수 없다.

- `bulsaja_market_delete` 가 `"다른 작업이 처리 중인 상품은 삭제 불가"` 로 되돌린다.
  `bulsaja_work_progress` 에는 **아무것도 안 잡힌다**(대기·진행 0) — 그래서 잔여 잠금이나
  결함으로 오해하기 쉽다. 실제로는 정상 동작이다.
- **옵션 수정은 막히지 않는다.** 잠긴 상품에 `bulsaja_option_update` 미리보기를 걸면
  확인키가 정상 발급된다(2026-08-05 실측). 그러니 잠금 때문에 저장을 건너뛰지 않는다.

**처리 규칙**
1. 삭제가 잠금으로 막히면 **현황판 `옵션` 열에 `삭제보류(잠금)`** 을 남긴다.
   빈칸으로 두면 다음 회차가 다시 집어가고, `해당없음` 으로 두면 삭제된 줄 착각한다.
2. 삭제된 건은 `해당없음` 으로 구분해 적는다.
3. **종합보고에 잠금 목록을 상품id와 함께 따로 낸다** — 잠금 해제는 불사자 앱에서 이룸님만
   할 수 있으므로(스킬이 풀 수 없다), 이 건들만은 자동화 대상이 아니라 사후 판정 큐다.

## 워커준수 검사 — 표본검수 **앞**에 온다 (2026-08-15)

`apply` 가 표를 찍은 직후, **표본검수보다 먼저** `[워커준수]` 수치를 낸다. 순서가 규칙이다 —
**사유가 없으면 표본을 봐도 판정이 안 된다.** 4-1 표본검수에서 제외 0건인 상품 2건을
"제외 과다"로 의심하는 오판이 실제로 났다(검수표의 제외는 스크립트가 만든 파생값이었다).

- **미언급** — `유지`·`제외` 어디에도 안 적힌 판매행. **행 단위로 센다**(상품 단위로 보면
  450행 중 234행만 빠뜨린 상품을 놓친다). 그 행들은 사유 없이 제외로 떨어진다.
- **상태근거** — `현재제외`·`현재대표` 를 제외 근거로 쓴 행. 상태는 자주 뒤집혀 있어
  근거가 못 된다(§알려진 함정). **뒤집었다고 서술한 건 정상**이라 걸리지 않는다.
- **무분류수** — 사유 앞 토막이 8분류가 아닌 제외행 수. 분류가 붙어야 `대표충돌` 이
  기계로 갈린다.

위반이 있으면 `<run-dir>/worker_qc.json` 에 `재실행대상` 상품id 가 떨어진다 — 그대로
재팬아웃하면 된다. **저장은 막지 않는다**: 제외 목록 자체는 유지 여집합이라 완전하고,
흔들리는 건 "사유를 믿어도 되는가"뿐이다. 재실행 판단은 수치를 보고 사람이 한다.

> 제외 사유의 정본은 **워커가 쓴 문장**이다(`plan(drop_reasons=…)`). 워커가 안 쓴 행만
> `비상품/메인상품 아님(사유 미기재)` 로 남아 원장에서 구분된다. 1.5배 상한·재고 0 은
> 그대로 스크립트가 만드는 파생 사유이고, 워커 문장이 이를 덮지 못한다.

### 보류·저장실패를 다시 돌리기 전에 — 사유부터 현황판에 찍는다 (2026-08-15 2-3 실측)

`보류(…)` 상태값만으론 워커에게 **왜 틀렸는지가 안 간다.** 배치에 실리는 건 현황판
문자열인데 `보류(남길 옵션 없음)` 만 보면 워커는 같은 판정을 그대로 반복한다.
`matrix.flag_many` 로 **무엇을 다시 보라는 지시**를 옵션 열에 찍고 나서 `prep` 한다.

```python
matrix.flag_many(sheet, "옵션", {pid: "전량제외 판정 재검토 — 현재제외를 근거로 쓰지 "
                                      "마라. 가격계단·원문 접두한자(加/送/单独)·상품명 "
                                      "핵심어로 본품을 직접 판정할 것"}, from_task="옵션")
```

실측(2-3 r4→r5) — 사유를 실어 재팬아웃한 결과:

| 실은 사유 | 결과 |
|---|---|
| `전량제외 판정 재검토 — 현재제외를 근거로 쓰지 마라. 가격계단·원문 접두한자(加/送/单独)·상품명 핵심어로 본품을 직접 판정할 것` | 14건 중 **13건 복구** |
| `저장실패(이름중복) — 유지분만 고치지 말고 전 옵션에 원문 기준 고유 이름을 줄 것` | 5건 중 **4건 복구** |
| `25자 초과로 이름 미저장 — 본문을 줄일 것` | 3건 **전건 복구** |

복구 내용이 위 §알려진 함정의 실증이다 — PE관은 원문이 전부 `얇은 모델 100m` 라 겹치던
걸 **구경(20/25/32mm)** 으로, 우편함은 `빨간 우편함` 2개를 **꽃무늬 유무**로, 라운지소파는
`MA 블루` 2개를 **동봉 테이블 종류**로 갈랐다.

## 표본검수 + 종합보고 (자동 반영 모델, 2026-08-06)

`apply` 미리보기가 나오면 Claude 가 **그룹당 표본 N건**(기본 10건 또는 5%, 큰 쪽)을 골라
검수표를 직접 판정한다 — 제외가 과했는지, 이름이 원문과 어긋나는지, 대표가 규격어 지정과
맞는지. 통과하면 바로 `--commit`. **이룸님 승인을 기다리지 않는다** (2026-08-06 확정 —

- 의심건은 반영하지 않고 현황판에 `보류(표본의심)` 로 남긴다 — 종합보고에서 이룸님이
  원복(재반영) 또는 폐기를 판정한다.
- **종합보고 1회**로 마감: 저장/보류/삭제/잠금 수치 · 의심건 목록 · 삭제잠금 목록 ·
  `옵션축` 대기 증가분 · `이관` 으로 넘긴 건. 이룸님 개입 = 시작 1회 + 이 보고 확인 1회.
