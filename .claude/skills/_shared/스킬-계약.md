# 스마트스토어 스킬 계약

> 불사자 상품을 다루는 스킬이 지켜야 할 규칙 1벌. **새로 만드는 스킬은 이 문서를 따른다.**
> 기존 2개(카테고리교정·상품명)는 명령어 이름이 다르다 — 아래 §기존 스킬 예외 참조.

## 왜 계약이 필요한가

스킬이 늘면 **같은 상품을 저마다 다시 조회**하고, **대상 선정 방식이 스킬 수만큼** 생긴다.
계약은 그 두 가지를 막는다. 러너는 이 계약만 알면 되고, 그 스킬이 무슨 일을 하는지 몰라도 된다.

## 진입점 3개

```
prep   --ids <상품id...> --run-dir <R>     스킬 고유 준비물 (뷰 생성·외부 조회 등)
run    --batch <배치파일>                   판단 → 결과 JSON (팬아웃 단위)
apply  --run-dir <R>                        검증 → 시트 → 불사자 저장 → 스냅샷·현황판 갱신
```

- **`run` 은 불사자를 직접 부르지 않는다.** 필요한 건 전부 스냅샷과 배치 파일에 실려 있다.
  (`run` 은 대개 스크립트가 아니라 **Claude 워커**다. 그 경우 배치 파일이 곧 인터페이스다.)
- **쓰기 권한은 `apply` 가 갖는다.** 저장 뒤 스냅샷·현황판 갱신까지 `apply` 의 책임.
  스킬이 날짜와 함께 SKILL.md 에 명시한 **보조 쓰기 진입점**은 예외로 인정한다
  (선례: bulsaja-thumbnail `fallback`·`audit --commit` 2026-08-06 — 시트·현황판까지 자기가 갱신).
- 배치·결과 JSON은 **자기완결형** — 워커가 대화 맥락 없이 파일 경로 하나로 완주할 수 있어야 한다.

### 반영은 기본 자동이다 (2026-08-06 이룸님 확정 — product-name 모델로 전 스킬 통일)

```
시트 기록(원장) → Claude 표본검수 → 자동 반영 → 종합보고
```

- **이룸님 개입 = 시작 1회 + 종합보고 확인 1회.** 표본검수 판정 주체는 Claude(메인)이고,
  의심건은 반영하지 않고 `보류(표본의심)` 류 상태로 빼서 종합보고에 싣는다.
- **크레딧 소모 단계(썸네일 생성 등)도 자동** — 사용량은 종합보고에 사후 보고한다.
- **삭제·마켓 영향 작업도 자동** 처리하되 종합보고에 **전수 목록**을 싣는다
  (선례: product-name 실물불명 자동 삭제 2026-08-05).
  **제외카테고리 `삭제대기` 도 2026-08-11 부터 자동 삭제**다 — 런 출구가
  `category_gate.auto_delete()` 로 지운다. 묻지 않는다(이룸님 지시).
- **시트 기록 의무는 예외 없이 유지** — 자동 반영도 쓰기 전에 원장부터 남긴다.
- 반영 전 승인 게이트는 **스킬 SKILL.md 에 날짜와 함께 명시된 곳에만** 남는다.
  현재 남은 사람 개입: `captcha-relay` 의 `needs_human` 에스컬레이션(사람만 답할 수 있는 것) 뿐.
- 가로(대량 스킬)·세로(onestep) 어느 경로든 같은 정책이다 — onestep 도 시작 1회 + 종합보고 1회.
- 선례 이력(스킬별 예외 → 전면 기본값): category-fix 확신도≥70 자동저장 2026-07-12 →
  product-name rename 자동 커밋·실물불명 자동 삭제 2026-08-04~05 → thumbnail 생성 무승인·
  2회 불합격 원본 fallback 즉시 반영 2026-08-06 → **전 스킬 통일 2026-08-06**.

## 상품 데이터는 스냅샷에서 받는다

`eroomlib/snapshot.py`. 직접 `bulsaja_product_workdata` 를 부르지 않는다.

```python
from eroomlib import snapshot
recs, errors = snapshot.ensure(pids)          # 캐시에 있으면 조회 0회
path, err = snapshot.materialize_image(url, out_dir, pid, i)   # 썸네일도 캐시
```

**저장한 스킬이 자기가 바꾼 필드만 되쓴다.** 그래서 "이 스냅샷이 낡았나" 판정이 필요 없다.

```python
snapshot.update(pid, 기존카테고리=새경로)   # 카테고리 저장 후
snapshot.update(pid, 상품명=새이름)         # rename 후
```

원문명·옵션명원문·원본링크는 **불변** — 절대 재조회하지 않는다. 강제는 `--refresh`.

## 대상 선정은 현황판에서 한다

`eroomlib/matrix.py`. 그룹 시트의 `00_진행` 탭 = 상품 1행 × 작업 1열.

```python
from eroomlib import matrix
m = matrix.read(sheet)                 # 러너 시작 시 1회
ids = matrix.pending(m, "옵션")         # 그 작업이 빈 상품 = 이번 대상
...
matrix.mark_many(sheet, "옵션", {pid: "완료", ...})   # 끝나면 자기 열 1개만
```

- **자기 열 1칸만** 쓴다. 상세 로그는 지금처럼 자기 탭에 남긴다.
- 값: 빈칸(미착수) / `완료` / `해당없음` / 그 밖의 문자열(보류 사유·진행중 등 원장 값 그대로).
  `pending` 은 **빈칸만** 고른다 — 보류는 사람이 이미 판단한 것이라 자동 재처리하지 않는다.
- 쓰기는 **작업 끝에 열 통짜 1회**(`mark_many`). 건건 즉시 치면 시트 호출이 2배가 되는데
  얻는 게 없다 — **매트릭스는 원장이 아니라 파생본**이라, 중단돼도 원장(상세 탭)이 남아 있고
  `matrix.py rebuild` 로 언제든 다시 만든다.
- ★ 이 "열 통짜 1회"는 **현황판(`00_진행`)에만** 적용된다. **상세 로그 탭(원장)은 건건 즉시
  기록이 정상**이다 — 중단·재개 안전장치가 원장의 역할이기 때문(category-fix G열 선례).
  같은 "시트 기록"이라도 두 층의 쓰기 정책이 다르다는 것을 혼동하지 않는다.
- 새 작업 열이 필요하면 `matrix.TASKS` 에 추가한다. 기존 시트는 `rebuild` 가 헤더를 확장한다.

### `--no-sheet` 로 현황판을 막지 않는다 (2026-08-14 — 두 번 밟고 계약으로 올림)

**원장 탭 쓰기와 현황판·이관 쓰기는 다른 플래그로 뗀다.**

| 플래그 | 막는 것 | 언제 |
|---|---|---|
| `--no-sheet` | **원장 탭만**(`옵션`·`옵션축`·상세 로그·검수표) | 미리보기에서 이미 썼을 때. 쿼터(429) 절약 |
| `--no-matrix` | 현황판(`00_진행`) + 이관 flag | **검증·재현 전용.** 평상시 금지 |

원장 탭은 수백 행이라 쿼터를 먹어서 저장 회차엔 끄고 싶은 게 정상이다. 그런데 현황판은
**한 열 update 1회**라 끌 이유가 없고, 끄면 그 회차의 성과가 통째로 안 보인다 —
저장은 다 됐는데 `pending` 이 같은 상품을 다시 골라 **다음 회차가 전부 다시 돈다.**

실측 2번: 옵션정리 25-2(254건)·2-2(664건). 둘 다 `--no-sheet` 하나에 셋이 묶여 있어서
벌어졌다. **운영 수칙으로 막지 말고 플래그를 갈라라.** 썸네일(`run_thumbs.py`)이 원래
갈라 놓은 형태가 정본이고, 옵션정리를 2026-08-14 에 거기 맞췄다.

> 카테고리(`run_all.py`)의 `--no-sheet` 는 예외다 — 하위 스크립트에 `--sheet` 자체를
> 안 넘기는 구조라 시트 id 가 없으면 현황판도 쓸 자리가 없다. 분리할 대상이 아니다.

### 재개 파일은 문서만 있고 코드에 없기 쉽다

오래 도는 저장(옵션 700건 ≈ 1시간)은 **성공분을 건별로 디스크에 남기고 다음 실행이
건너뛰어야** 한다(`committed.json` · `delete_progress.jsonl`). 재실행의 주 용도는
"덜 된 것 마저"가 아니라 **"저장은 됐는데 현황판이 빈 것 채우기"** 다 —
그래서 재개 회차는 MCP 0회로 현황판만 채우고 끝나야 한다.

2-2 에서 SKILL.md 에는 이 문단이 있는데 `run_options.py` 에는 `committed` 라는 낱말조차
없었다. 그걸 믿고 "한 번 더 치면 기록만 채워진다"고 운영해서 700건을 처음부터 다시
저장했다. **문서에 재개가 적혀 있으면 `grep` 으로 코드에 있는지 먼저 확인한다.**

## 다른 단계에 일감을 넘길 땐 메모가 아니라 현황판에 찍는다

작업을 하다 보면 **자기 범위 밖**의 문제가 보인다 — 옵션을 보다가 썸네일에 없는 색을 발견하고,
옵션 원문을 보다가 상품명 오표기를 발견한다. 이걸 자유 텍스트 메모로 남기면 **받는 쪽이
읽을 경로가 없다**(실측: 옵션정리 파일럿 5건 중 3건이 그렇게 유실됐다).

```python
matrix.flag(sheet, pid, "썸네일", "대표색 불일치", from_task="옵션")   # 1건
matrix.flag_many(sheet, "썸네일", {pid: 사유, ...}, from_task="옵션")  # 가로: 열 통짜 1회
```

현황판 칸에 `재작업(옵션: 대표색 불일치)` 가 찍힌다. 받는 단계는 이렇게 집어간다.

```python
ids = matrix.pending(m, "썸네일")        # 미착수 + 재작업 (재작업이 기본 포함)
why = matrix.redo_pending(m, "썸네일")   # {상품id: 사유} — 워커에게 실어 보낸다
```

- **가로(1000건)**: 한 바퀴 도는 동안 flag 만 쌓아 두고, 그 단계 차례에 몰아서 처리한다
- **세로(1건)**: 모아둘 이유가 없다 → `onestep redo --step <단계> --reason "..."`
- **`완료` 인 단계도 다시 잡힌다** — 이게 핵심이다. `pending` 이 빈칸만 골랐을 때는
  완료된 단계가 영영 재처리되지 않았다(용쌤1-1 상품명 재시도 143건을 손으로 추리던 이유)
- **빈칸에도 찍을 수 있다** — 대상은 그대로고 **사유만** 붙는다. 미착수 상품에 대해
  "이건 이래서 주의해라"를 전달하는 정상 경로다
- **삭제 상품(`해당없음`)에는 넘기지 않는다** — `flag` 가 알아서 거른다
- 재작업을 마친 스킬은 평소대로 `완료` 를 쓰면 표시가 지워진다.
  `rebuild` 는 재작업 표시를 **보존한다**(원장은 '옛 작업을 완료했다'고만 말하므로 되살릴 수 없다)

> `include_redo=False` 는 "이번엔 신규 미착수만" 이 필요할 때의 옵트아웃이다.
> 처음엔 이게 기본값이었는데, 그러면 빈칸에 사유를 실는 순간 대상에서 빠지는 모순이 생겼다.
> **대상 여부와 사유 전달을 한 값에 묶었으면 둘 다 켜져 있어야 한다.**

## 경로·시트ID·계정은 코드에 박지 않는다

`eroomlib/config.py` + 워크스페이스 루트의 `workspace.toml`.

```python
from eroomlib.config import cfg
cfg("paths.category_fix_runs")            # ~/eroom-data/... 를 코드에 쓰지 않는다
cfg("drive.category_folder", required=True)
```

배포본은 이 층만 교체한다. SKILL.md 본문에도 id 를 적지 않고 이름으로만 참조한다.
run-dir 표기는 `<데이터루트>/<축>/runs/<이름>` 으로 쓴다 — 데이터루트는 현재 맥 기준
`~/eroom-data`(2026-08-03 이관). 절대경로를 문서에 박지 않는다.

## 팬아웃 공통 규약 (catfix·pname·optclean·thumb-fanout 4개 워크플로)

각 SKILL.md 는 이 절을 링크만 하고 다시 적지 않는다.

- **메인 세션이 배치를 직접 순차로 읽지 않는다** — 컨텍스트 누적 재과금
  (product-name `references/팬아웃-비용.md` 모드 B 안티패턴). 백그라운드 Workflow 로 뺀다.
- **동시 서브에이전트 기본 가이드라인(≤15)은 팬아웃에 적용하지 않는다** — 워커는 디스크에만
  쓰고 상호 간섭이 없으며, 상한은 하네스 동시성 캡이 관리한다. 이 문장이 그 명시적 opt-in 이다.
- **재개·멱등**: 결과 파일 존재 = 그 배치 완료. 재실행하면 없는 배치만 다시 돈다.
  워크플로 내부에서 누락분 **1회 자동 재팬아웃**(pname 제외 — 검증 phase 로 대체)하고,
  그래도 남으면 외부(메인)에서 **1회만** 재호출한다.
- **폴백**(소량·워크플로 불가 환경): Agent 도구로 워커 1명 = 배치 1~2개.
- **4벌은 의도적으로 분리 유지한다(2026-08-06 이룸님 — 통합 실익 낮음 판정).** 공통부를 고칠
  때는 반드시 **4벌 동시 수정**. 축별 차이는 예산뿐: pname 뷰 30KB / catfix 이미지 16장 /
  optclean 이미지 16장+상품 10건 / thumb 이미지 24장+상품 8건.
  thumb-fanout 은 `mode: 'audit'` 로 정합검사 배치도 같은 예산으로 분배한다
  (`pending --audit` 산출 — 생성 팬아웃과 결과 폴더가 달라 같은 run-dir 병렬 안전).

**팬아웃이 끝나면 `python3 .claude/lib/costtools/pack_curve.py --collect`.**
워커 로그는 오래 안 남는데, 이게 "워커당 몇 건이 싼가"의 유일한 근거다(비용 0 · 멱등).

### 워크플로 반환 숫자는 디스크와 어긋날 수 있다 — 커밋 전에 직접 센다 (2026-08-15)

`완료배치 N` · `선택 M` 같은 반환값은 **집계 시점의 값**이라 디스크와 어긋난 사례가 두
세션에서 나왔다 — 2-3: `thumb-fanout`(run) 이 "완료배치 7 / 선택 22 / 재팬아웃필요배치
없음" 을 반환했는데 `result_002.json` 이 **디스크에 없었다**(apply 감사가 누락 4건으로
잡았고 `pending` 이 정확히 그 배치만 다시 내놨다 · 재팬아웃 1회로 복구, 비용 0).
25-2: 선택 201 + 보류 14 반환 → 실제 188/14.
**`재팬아웃필요배치` 가 비어 있어도 안심하지 마라.**

```bash
print('배치',len(b),'결과',len(r),'누락',sorted(b-r)[:5],'환각',sorted(r-b)[:5])"
```

누락이 나오면 `pending` 을 다시 뽑는다 — **그 배치만** 정확히 내놓는다.
축별 `apply`·`--commit` 이 같은 대조를 자체 내장하고 있으면 그 경고를 정본으로 본다
(thumb `apply` 감사 · `verdict --commit` exit 3 · `audit --commit` 미대조 경고 ·
optclean `apply` 감사).

### 이미지 해상도 — `--max-px` (2026-08-07 실측)

**워커에게 주는 이미지는 긴 변 512px 로 줄인다. `verdict` 만 원본을 유지한다.**
축소는 공용 `snapshot.materialize_image(..., max_px=)` 한 곳에서 일어나고, 줄이는 대상은
**언제나 복사본**이다(스냅샷 캐시 원본은 안 건드린다 — 다른 스킬이 더 큰 해상도를 원할 때
되돌릴 수 있어야 한다).

| 축 | 기본 px | 플래그 |
|---|---|---|
| catfix 실물 판별 | 512 | `fetch_thumbs.py --max-px` |
| pname 실물 판별 | 512 | `run_names.py --thumb-px`(→ fetch_thumbs 로 전달) |
| optclean 대표썸네일·옵션값 | 512 | `run_options.py prep --max-px` |
| thumb run·audit | 512 | `run_thumbs.py prep/audit --max-px` |
| **thumb verdict** | **0(원본)** | `run_thumbs.py verdict --max-px` |

근거 — 표본 9건·이미지 17장을 512/768/원본(800~1024px)으로 만들어 **해상도별 별개 워커**에
블라인드로 판독시켰다. 인쇄 글자 판독 성공: **512=85 · 768=84 · 원본=93**.
① **768 은 512 보다 나은 게 없다** → 중간값을 두지 않는다. ② 512 는 원본의 91% 를 유지하며
비전 토큰을 **3.3배** 줄인다(17장 19,149 → 5,767). ③ 512 에서도 스펙 표기(`型号3000W`),
치수(`45*39`·`19cm`), 색상코드(`#FEFAE`), 모델명(`五铸®RC3563`)이 원본과 같이 읽혔다.

verdict 만 예외인 이유: 3축 중 `제외(글자변조)` 는 제품 각인 브랜드 글자를 원본↔생성본으로
**대조**하는데, 같은 실측에서 인버터 브랜드를 512 는 `讯浦`, 768 은 `锐霸` 로 갈라 읽었다.
판독은 512 로 충분해도 이 축은 오독이 곧 거짓 재작업이고 **재생성에 크레딧이 나간다.**

> 한계: 표본 9건은 통계가 아니라 존재 증명이다. 원본이 800~1024px 인 현재 데이터 기준이며,
> 더 큰 원본이 들어오면 다시 재야 한다.

> **비용을 재거나 줄이려 할 때는 먼저** [`product-name/references/팬아웃-비용.md`](../product-name/references/팬아웃-비용.md)

> A/B 기록 · `.output` 로그 집계법. 토큰 수로 게이트를 잡으면 틀린다.
>
> 재는 도구 자체의 함정 둘(2026-08-07 실측, 전문은 같은 문서 §④): **① Workflow 워커 로그는
