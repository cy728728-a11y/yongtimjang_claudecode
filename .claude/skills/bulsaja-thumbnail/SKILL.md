# 불사자 썸네일

> 검수는 항상 로컬 HTML 페이지로 한다(이미지가 승인 대상이라 텍스트 검수표가 안 통한다).
> 공통 규칙(스냅샷·현황판·계약)은 [`_shared/스킬-계약.md`](../_shared/스킬-계약.md),
> 불사자 공통 안전선(통신·검증·실패 보존)은 [`_shared/불사자-안전규칙.md`](../_shared/불사자-안전규칙.md).
>
> **각 규칙의 근거·사고 이력은 [`references/사고-이력.md`](references/사고-이력.md).**
> 실행 중엔 읽지 않는다 — 규칙을 바꾸거나 코드를 손볼 때만 본다.

## 왜 필요한가

수집 직후 대표 썸네일은 타오바오 원본(워터마크·중국어·경쟁사 로고 노출)이다. 불사자
내부 AI로 배경을 바꾸면 워터마크 없는 깨끗한 대표이미지를 만들 수 있다. 다만 생성은
크레딧이 들고(장당 5), **승인 없이도 대표이미지가 자동 반영될 수 있어**(실측 확인)
방어 로직 없이 돌리면 승인 전 이미지가 그대로 판매화면 후보가 된다.

| 프롬프트 | 생략(불사자 저장 디폴트 사용, 실측 확인) | Claude 가 직접 작성 |

## 흐름

```bash
# ① prep — 현황판 대상 확정 → 스냅샷 → 기작업(이미 가공됨) 자동 완료 처리 → 후보 이미지 → 배치
python .claude/skills/bulsaja-thumbnail/scripts/run_thumbs.py prep \
  --group-name "1번_용쌤1-1" --run-dir "<데이터루트>/thumbnail/runs/<이름>" [--limit 5] [--ids U01...]
#    이미지는 긴 변 512px 로 줄여 나간다(`--max-px`, `0`=원본). audit 도 같다.
#    **verdict 만 기본이 원본**(글자변조 대조 축) — §이미지 해상도

# ①.5 prescreen — 선기록건의 기준이미지 적격성(크레딧 0 · 조회 0) → §기준적격
python ... run_thumbs.py prescreen --run-dir <R>                       # → prescreen_batches/
python ... run_thumbs.py prescreen --group-name "…" --run-dir <R> --commit
#    단일특정→그대로 / 다중혼재→batches/ 승격(②로 되돌아감)
#    실물없음→썸네일 보류(기준이미지없음) + 옵션 열 재작업 flag(대표를 실물로 다시 세울 것)

# ② run — Claude 가 배치를 읽고 기준 이미지 선택(+레시피 모드면 배경전략·프롬프트 작성)
#    → results/result_NNN.json

# ③ apply — 생성도 반영도 승인 대기 없음 (검수 판정 주체 = Claude)
python ... run_thumbs.py apply --run-dir <R>              # 미리보기(대상+기준이미지+예상크레딧). 선택
python ... run_thumbs.py apply --run-dir <R> --generate   # 바로 생성(크레딧 소모) → review.html
#    **50건 초과면 접수모드가 기본** — `THUMB_POLL_TIMEOUT=20` + recover. §대량 회차는 접수모드로

# ④ verdict — 생성본 3축 판정(크레딧 0). **9건 이상이면 팬아웃** → §검수 판정
python ... run_thumbs.py verdict --run-dir <R>            # → verdict/batches/ + Workflow args
python ... run_thumbs.py verdict --run-dir <R> --commit   # 판정 수합 → decisions.json

# ⑤ apply --commit — 판정 직후 바로 반영, 승인 대기 없음
python ... run_thumbs.py apply --run-dir <R> --commit
```

> **생성도 반영도 묻지 않는다** (2026-08-06 이룸님 · `_shared/스킬-계약.md` §반영은 기본
> 자동이다). **검수 판정 주체가 Claude 다** — 3축 기준으로 상품마다 직접 판정하고,
> 불합격은 §검수 불합격 자동 처리대로 처리한 뒤 바로 `--commit`. review.html 은 이룸님
> 사후 검토용으로 계속 만든다. 사용한 크레딧 합계는 **종합보고에 필수 기재**.

대상 선정은 **현황판 쿼리 1줄**(`00_진행` 탭의 `썸네일` 열이 빈 상품 + 재작업). prep의
기작업 처리는 **3갈래**다(2026-08-05 수정 — 판별 규칙은 아래 §기작업 판별):

| 스냅샷 상태 | 처리 |
|---|---|
| 가공됨(`cdn.bulsaja.com`) + 대표옵션 이미지 있음 | **정합검사 대상**(자동 완료 금지) — `audit_targets.json` 기재, 현황판은 빈칸 유지 |
| 가공됨 + 대표옵션 이미지 없음 | 완료 백필(종전 — 대조할 근거가 없다) |
| 미가공 | 생성 대상(종전) |

> ★ **`audit_targets.json` 이 비어 있지 않으면 정합검사를 같은 회차에 자동으로 돌린다**
> (2026-08-06 이룸님 — 별도 지시 불필요). 생성 팬아웃과 **병렬**로 돈다 — §정합검사 참조.

**404 = 소싱 원본 소멸 신호 → 자동 삭제** (2026-08-06 이룸님). **대표 원본 404**(prep 이
`deletion_candidates.json` 기재)와 **대표옵션 이미지 404**(audit 이 `audit_delete_404.json`
기재) 둘 다, 메인이 `bulsaja_market_delete`(scope ALL · MARKET_AND_SOURCE · 확인키 2단계)로
**묻지 않고 즉시 삭제**한다(불사자는 휴지통이라 복구 가능).

**삭제 직후 `mark-deleted` 를 부른다 — 생략 금지** (2026-08-16):
```bash
python … run_thumbs.py mark-deleted --group-name "…" --run-dir <R>   # → 해당없음 확정 + 보고용 목록
```
삭제는 메인이 MCP 로 하고 스크립트는 그 사실을 모른다. 확정을 빠뜨리면 현황판이
`보류(…삭제대상)` 인 채 남고, **다음 회차 prep 이 이미 지운 상품을 또 삭제 대상으로 집는다**
(실측: 25-2 후속 회차에서 5건 재등장 — 이중 삭제 직전까지 갔다). 멱등이라 여러 번 불러도
안전하고, 출력이 곧 **종합보고에 붙일 목록**(상품id·상품명·사유)이다.

## run 실행 = Workflow 모드 (대량 기본, 2026-08-01)

공통 규약(메인 직독 금지·동시성 opt-in·재개·멱등·폴백·4벌 동시 수정)은
[`_shared/스킬-계약.md`](../_shared/스킬-계약.md) §팬아웃 공통 규약 — 여기 다시 적지 않는다.
이 축의 예산: **이미지 워커당 ≤24장 · 상품 ≤8건**.

- **prep 이 대표옵션 확정건을 선기록한다** — `대표옵션이미지경로` 있는 상품은 판단이
  0(규칙 0 "고르지 않는다")이라 prep 이 직접 `results/result_000.json` 에 기록하고
  배치에서 뺀다. **배치 = 비전 판단건만.** 옵션정리를 먼저 돌린 그룹이면 팬아웃 자체가
  거의 필요 없어진다(순서: 옵션 → 썸네일이 여기서도 이득).
  ⚠ **선기록건은 `prescreen` 을 먼저 돌린다**(아래 §기준적격) — 선기록은 대표옵션이
  도면·배너여도 그대로 기준으로 쓰기 때문.
  `prep` 이 이번 대상 중 **옵션 단계 미완료 비율을 세어 한 줄 경고**한다. **막지는 않는다**
  — 재작업 flag 소진처럼 순서를 뒤집어야 하는 정당한 회차가 있다.
- 대량 팬아웃 시 **`prep --batch-size 4` 권고** — 상품당 이미지가 최대 6장(대표1+후보5)이라
  기본 10건이면 배치 하나(~60장)가 이미지예산(24장)을 단독 초과해 패킹이 무의미해진다.

1. `python … run_thumbs.py pending --run-dir <R>` — 남은 배치를 Workflow args JSON 으로 출력
2. `Workflow` 도구를 `{name: "thumb-fanout", args: <출력 그대로>}` 로 호출.
   워커는 `agent(model: sonnet, effort: low)` — 지시서는
   [`references/썸네일-워커-프롬프트.md`](references/썸네일-워커-프롬프트.md).
   워커 결과는 **판단 필드만** 남기고, 나머지(기존썸네일 등)는 apply 가 배치(정본)에서
   조인한다 — 워커 환각이 백업·복원 경로에 못 들어간다
3. 완료 반환의 `재팬아웃필요배치` 가 비었는지 확인 (워크플로 내부에서 이미 1회 자동
   재팬아웃한 결과다). 남았으면 `pending` 재계산 후 **1회만** 재호출
4. 메인이 `apply --run-dir <R> --generate` 를 **바로** 부른다(승인 대기 없음).
   **워크플로·워커는 `--generate` 를 절대 부르지 않는다** — 자동반영 방어·복원이 걸린
   구간이라 메인이 직접 잡고 있어야 하고, 감사에서 누락 상품이 있으면 차단된다
   (`--allow-missing` 은 의도된 부분 생성 전용)

## 기준적격 (prescreen — 생성 전, 크레딧 0 · 조회 0, 2026-08-07)

**왜 있나.** 선기록(규칙 0)은 대표옵션이 **도면·배너여도 비전 판단 없이** 기준이미지로 쓴다.
`배경생성-기본.md §1-1`(비제품이면 실물 후보로 갈아끼운다)은 팬아웃을 탄 건에만 적용되므로
**선기록건은 아무도 안 본 채로 태워진다.** 생성 전에 여기서 한 번 걸러낸다.
(실측·실증 → [`사고-이력.md`](references/사고-이력.md))

```bash
python … run_thumbs.py prescreen --run-dir <R>            # → prescreen_batches/ + args
python … run_thumbs.py pending --run-dir <R> --prescreen  # 남은 배치 → Workflow args
# → Workflow {name: "thumb-fanout", args: <출력 그대로>} (mode: prescreen)
python … run_thumbs.py prescreen --group-name "…" --run-dir <R> --commit
```

- 워커는 **기준이미지 1장만** 연다. `agent(model: haiku, effort: low)` — 지시서는
  [`references/기준적격-판정기준.md`](references/기준적격-판정기준.md).
- **묻는 것은 "도면이냐"가 아니라 "제품이 하나로 특정되나"다** — 도면 자체는 사고 원인이 아니다.

| 판정 | `--commit` 이 하는 일 |
|---|---|
| `단일특정` | 그대로 생성 |
| `다중혼재` | 선기록에서 빼고 `batches/` 로 **승격** → run 팬아웃이 후보에서 고른다(②로 되돌아감) |
| `실물없음` | 선기록에서 빼고 썸네일 `보류(기준이미지없음)` + **옵션 열 재작업 flag** — 뿌리가 옵션이라 대표옵션을 실물로 다시 세워야 풀린다(`R.TO_OPTION_VERDICTS` 와 같은 규칙) |

- **모르는 값·판정 누락은 `다중혼재`(fail-closed).** 비용이 비대칭이다 — 놓치면 재생성
  크레딧, 과잉이면 워커 1회(크레딧 0).
- **왕복은 1회로 끝난다** (2026-08-07 이룸님). `실물없음` 으로 넘긴 건을 옵션정리가 받으면
  대표로 세울 옵션의 **이미지 1장을 열어 실물인지 본다**(옵션 워커 프롬프트 §2-10 —
  옵션명으로는 도면인지 알 수 없다). 실물 옵션이 하나도 없으면 사유에 **`실물기준없음`** 을
  넣어 되돌리고, `prep` 이 그 낱말을 보면 **선기록하지 않고 비전 배치로** 보낸다
  (`R.NO_REAL_BASE`) — 썸네일 워커가 후보에서 고른다. 카운터 없이 왕복이 닫힌다.
- **옵션 열로 넘길 때 판정 낱말을 맨 앞에 박는다** (`_to_option_reason`, 2026-08-15 3회차).
  옵션 쪽 종결 장치(`_close_roundtrip`)는 왕복 2회차를 낱말(`대표옵션의심`·`기준이미지없음`)
  로 알아보는데, 종전엔 그 낱말이 **썸네일 열의 `보류(...)` 에만** 남고 옵션 열로는 워커가
  쓴 산문만 갔다. 그래서 종결 장치가 한 번도 발화하지 못했고 **3바퀴를 돌아도 같은 24건이
  되돌아왔다**(낱말이 붙은 건 1건뿐). 세 경로(`prescreen` 실물없음 · `audit` 대표옵션의심 ·
  `apply --commit` 판정)가 모두 이 함수를 거친다. 두 스킬이 같은 낱말을 본다는 계약은
  교차 테스트(`test_thumb_prescreen.py::test_옵션_스킬이_이_값을_왕복_2회차로_읽는다`)로 고정.
- **`보류` 로 세운 건은 옵션이 되찍어야 돌아온다.** `prep` 은 빈칸+재작업만 집으므로
  (`matrix.pending`) `보류(...)` 는 스스로 못 빠져나온다. 옵션 `apply --commit` 의
  `[미아회수]`(`_recover_orphans`)가 그 경로다 — 옵션정리 SKILL.md §썸네일 보류는 미아가 된다.
- **멱등하다** — 승격·보류분은 선기록에서 빠지므로 `--commit` 을 두 번 불러도 안전하다.
- 미판정(팬아웃 미완)이 있으면 그 건은 **종전대로 생성된다.** commit 이 건수를 경고로 찍으니
  남은 배치를 마저 돌리고 다시 commit 한다.
- 승격이 있으면 `pending` → `thumb-fanout`(run) 을 **한 번 더** 돈 뒤 `apply --generate`.

| `cdn.bulsaja.com`(경로 무관) | 가공됨(AI썸네일/AI상세 생성 완료) — **단, 대표옵션이 있으면 정합검사부터**(§정합검사) |
| **`*.fal.media`**(서브도메인 포함) | **가공됨** — 생성 엔진이 직접 내주는 출력. 위와 같이 취급 |

정본은 `thumb_rules.PROCESSED_HOSTS` 다. 판정은 항상 **대표(0번)만** 본다(후보 자리에
가공된 URL이 섞여 있어도 무시). `cdn.bulsaja.com` 안의 경로는 구분하지 않는다 — 호스트만 본다.
`shop-phinf.pstatic.net`(네이버 업로드본)은 일부러 미가공으로 둔다.

> 반드시 대조한다. **실측 불일치율: `cdn.bulsaja.com` ≈ 35% · `fal.media` ≈ 43%.**
> **견적에 쓸 것**: 가공됨 N건 → 재생성 예상 `0.35N × 5크레딧` + audit 비용 0.

## 정합검사 (audit — 기존 대표 vs 대표옵션, 크레딧 0, 팬아웃 병렬)

가공된 대표가 **대표옵션과 같은 물건인지**를 비전으로 대조한다. 생성과 성격이 다르다 —
크레딧 0, 이미지 2장/건, 결과는 판정뿐.

**대상은 이번 회차 것뿐이다 — 현황판 `완료*` 전건 재대조는 하지 않는다(2026-08-06 이룸님).**
중복인 데다, 같은 이미지 쌍의 판정이 흔들려 멀쩡한 상품에 재작업이 되살아난다.
과거 그룹 소급 감사만 **`--sweep`** 으로 명시하고, 그때도 **`--sample 30` 으로 불량률부터 잰다.**

```bash
python … run_thumbs.py audit --group-name "1번_용쌤1-3" --run-dir <R> [--limit N] \
  [--targets <prep run-dir>/audit_targets.json]  # prep과 다른 run-dir로 감사할 때 필수
  [--sweep --sample 30]                          # 소급 감사(옛 그룹)일 때만
# → audit_batches/audit_batch_NNN.json (배치당 12건 = 이미지 24장)
python … run_thumbs.py pending --run-dir <R> --audit    # → Workflow args (mode: audit)
# → Workflow {name: "thumb-fanout", args: <출력 그대로>} — 워커가 판정기준대로 대조해
#   audit_results/audit_result_NNN.json 작성 (소량이면 팬아웃 없이 Claude 가 직접 판정)
python … run_thumbs.py audit --run-dir <R> --commit   # 판정을 현황판에 반영
```

- **본 흐름 자동 편입(2026-08-06)**: prep 이 `audit_targets.json` 을 만들었으면 위 4단계를
  같은 회차에 자동으로 돌린다. **생성 팬아웃과 병렬 실행이 안전**하다 — 배치·결과 폴더가
  분리돼 있고(`batches/`+`results/` vs `audit_batches/`+`audit_results/`) 정합검사는 쓰기가
  현황판 `--commit` 1회뿐이다. 순서 규칙 하나: **`audit --commit` 은 생성 경로의
  `apply --commit` 과 몰아서 마지막에** 친다(현황판 열 통짜 쓰기 충돌 방지).
- **불일치 재작업 합류(1회 한정)**: `audit --commit` 이 찍은 `재작업(정합검사: 사유)` 건은
  같은 회차에서 `prep --ids <불일치...> --run-dir <R>a` 로 1회 재-prep 해 생성 경로에
  합류시킨다(새 run-dir — 배치 번호 충돌 방지). 그 라운드에서 또 불일치가 나오면 다시
  태우지 않고 종합보고로(무한 루프 방지 — 기존 재작업 경로와 같은 규칙).
  ⚠ **`audit --commit` 이 반드시 먼저다.** 현황판에 재작업 flag 가 찍혀 있어야 `prep` 이
  그 상품을 **생성 대상**으로 잡는다. flag 없이 `prep --ids` 만 치면 `가공됨 + 대표옵션
  있음` 분기로 떨어져 **도로 `audit_targets.json` 으로 분류되고 실제 대상 0건**이 나온다 —
  조용히 0건이라 오독하기 쉽다. `###PREP### 대상 N건` 이 넘긴 id 수와 같은지 확인할 것
- 대상: prep 이 넘긴 `audit_targets.json` (+ `--sweep` 이면 현황판 `완료*`), 그중 대표옵션
  이미지가 있는 상품만(없으면 대조 근거가 없다).
  ⚠ `audit_targets.json` 은 기본으로 **자기 run-dir 에서만** 찾는다 — prep 을 다른
  run-dir 로 돌렸으면 **`--targets` 로 명시**해야 한다.
  **`audit_targets.json` 도 없고 `--sweep` 도 없으면 `exit 2` 로 멈춘다** — 0건으로 조용히
  끝나면 "감사했는데 깨끗하다"로 읽히기 때문
- **소급 감사(`--sweep`)를 쓸 자리**: audit 이 없던 시절 마감한 그룹(1-1·1-2·25-2 등).
  앞으로 처리하는 그룹은 해당 없음
- 판정 기준·결과 형식: [`references/정합검사-판정기준.md`](references/정합검사-판정기준.md)
  — 팬아웃 워커의 지시서도 이 문서다(`pending --audit` 가 promptPath 로 싣는다)
- `--commit`: `불일치` → `재작업(정합검사: 사유)` flag / `일치` → `완료(정합확인)` /
  **`대표옵션의심`(대표옵션 쪽이 본품 아님) → 썸네일 열 보류 + 옵션 열 재작업 flag** /
  **`대조불가`(판단불가) → flag 하지 않는다**(무한 재작업 루프 방지, 집계만)
- **대표옵션 이미지가 404 면 대조불가가 아니라 삭제 대상이다** — audit 이 배치에서 빼고
  `audit_delete_404.json` 으로 분리한다 → §404 자동 삭제 정책대로 메인이 즉시 삭제
- **`audit --commit` 은 배치 대비 미대조 건수를 경고한다.** `verdict` 처럼 차단하지는
  않는다(크레딧도 자동반영도 안 걸리고, 현황판이 빈칸으로 남아 다음 prep 이 다시 집는다).
  **⚠ 경고가 뜨면 그 회차 감사는 전건이 아니다** — `pending --audit` 로 남은 배치를 마저
  돌리고 다시 `--commit`. 목록은 `audit_missing.json`

```json
{"products": [{
  "productId": "U01...",
  "상품명": "원목바텐의자 바체어",
  "기준이미지": 3,
  "기준이미지경로": "<run-dir>/thumbs/U01..._cand_3.jpg",
  "모드": "레시피",
  "프롬프트": "제품 잠금: ... (레시피 모드만 채운다. 기본 모드는 비워서 디폴트 사용)"
}]}
```

- **`대표옵션이미지경로`가 있으면 그게 기준 이미지다 — 고르지 않는다**(아래 절).
- `기준이미지` = 배치의 `후보이미지[].index` 중 하나(원본 적합성 8기준으로 고른다).
  세트 상품은 판매 구성을 온전히 보여주는 것 우선, 임의로 최고가 옵션을 대표로 삼지 않는다.
- 기본 모드는 `프롬프트`를 비운다 — 채우면 디폴트 대신 그 프롬프트가 쓰인다.
- 재작업 대상(옵션정리 등에서 이관된 건)은 배치의 `재작업사유`를 반드시 반영해 기준 이미지를
  고른다(예: 바체어 — "옵션엔 검정 없음" → 검정 아닌 후보를 기준으로).

## 판단 규칙 (기준 이미지 선택 — 두 모드 공통)

### 0. 대표옵션이 있으면 그게 기준이다 (2026-07-30 이룸님)

**네이버는 '대표상품'(추가금 0원인 대표옵션)을 상품명으로 작성하라고 요구한다** →
**썸네일 = 대표옵션 = 상품명**이 같은 옵션 하나를 지칭해야 한다.
상품명·옵션명은 `기본형` 이라는 같은 단어로 짝을 맞추지만(→ `product-name` R8 ·
`bulsaja-option-cleanup` 규칙 17), **썸네일은 글자가 없어서 마커를 쓸 수 없다.**

그래서 배치에 `대표옵션명`·`대표옵션이미지`·`대표옵션이미지경로`를 싣는다.

| `대표옵션이미지경로` | 기준 이미지 |
|---|---|
| **있음 + 제품 사진** | **그 이미지로 고정.** 아래 8기준으로 고르지 않는다 |
| **있음 + 비제품**(도면·배너·색상칩) | **고정하지 않는다** — 후보 중 그 대표옵션과 같은 구성·색의 실물 사진을 고른다 (2026-08-06 이룸님) |
| 없음 | 종전대로 후보 중에서 8기준으로 고른다 (옵션정리 미완료·단일상품) |

> **규칙 0은 "어느 옵션인가"를 정하지 "어느 사진인가"를 정하지 않는다.** 옵션 이미지가
> 치수 도면이면 배경교체가 도면을 뭉개 정체불명 이미지가 된다.
> **선기록건은 워커가 안 보므로 검수에서 잡는다.** 전문·복구 절차 =
> [`references/배경생성-기본.md`](references/배경생성-기본.md) §1-1.
>
> `prep` 이 끝나면 `대표옵션 기준 이미지 N건 / 비전 판단 M건` 을 찍는다 — M이 크면
> 옵션정리를 먼저 돌리는 게 맞다(순서: 옵션 → 썸네일).

### 1. 대표옵션이 없을 때 — 원본 적합성 8기준

전체 보임 / 충분히 큼 / 글자·워터마크 없음 / 옵션 혼재 없음 /
손·소품 가림 없음 / 색·구조 선명 / 배경 분리 / 해상도 충분. 세트는 가장 비싼 옵션을
임의로 대표 구성으로 정하지 않는다. 상세는 [`references/배경생성-기본.md`](references/배경생성-기본.md).

## 기준 이미지는 "대표로 올렸다가 되돌리는" 방식으로 태운다

생성 도구는 **넘겨준 이미지를 쓰지 않는다** — 그 상품의 **첫 번째 대표이미지**를 배경교체한다
(`mode` 기본값 `first`). 그래서 `apply --generate` 는 상품마다 이렇게 돈다.

```
기준 이미지를 0번으로 올림(update_thumbnails)  →  생성  →  무조건 원래 배열로 원복
```

- 기준이 이미 0번이면 올리지 않는다.
- **기준이 썸네일 배열 밖이어도 맨 앞에 끼워 넣는다** — 대표옵션 이미지는 옵션 쪽 URL이라
  배열에 없는 게 보통이다(실측 303/311건).
- 원복은 `finally` — 생성이 실패해도 임시로 올린 이미지가 대표로 남지 않는다.

### `올림 -` = 맹목 배경교체 — 태우기 전에 이것만 본다

`-` = 올릴 게 없다 = **불사자가 기존 대표를 그대로 배경교체한다.** 그 대표가 대표옵션과
다른 물건이면 다른 물건이 예쁘게 재생성될 뿐이고, 재생성해도 같은 증상이 반복된다.

- 미리보기에 **`기준출처`** 열이 붙는다 — `워커선택` / `대표옵션` / `기존대표`
- `기존대표` = 워커 판단도 대표옵션도 없이 떨어진 건. 미리보기가 그 id 를 따로 모아 경고한다
- 생성 로그: `[기준] <pid>: 올릴 것 없음(기존대표) — 기존 대표를 그대로 배경교체한다`

## 자동반영 방어 (apply --generate 가 자동 수행, 실측 확인된 위험)

생성 완료 직후 대표이미지가 **판정 없이 이미 바뀌어 있을 수 있다**(2026-07-28 파일럿
실측 확인 — 헤르메스 06 §7 경고와 일치). `apply --generate`는 생성 직후 재조회해서
대표가 바뀌었으면 `--commit` 전까지 **원래 순서로 자동 복원**한다. 이 복원은 무료
(`thumbnail_update` 재호출뿐). 복원 자체가 실패하면 반드시 경고를 남기고 멈춘다.

## 검수 판정 (verdict — 생성본 3축, 크레딧 0, 팬아웃 병렬)

판정 주체는 Claude 다. **9건 이상이면 메인이 직접 보지 않고 팬아웃한다** — 이 축의 예산이
워커당 이미지 ≤24장·상품 ≤8건이라, 9건부터는 워커 1명 몫을 넘긴다. 상품당 이미지가 최대
3장([기존대표|대표옵션|생성본])이라 190건이면 380장이 메인 컨텍스트에 쌓인다.

```bash
python … run_thumbs.py verdict --run-dir <R> [--batch-size 8]
# → verdict/batches/vbatch_NNN.json (배치당 8건) + Workflow args JSON 출력
python … run_thumbs.py pending --run-dir <R> --verdict    # 미완 배치만 다시 args 로
# → Workflow {name: "thumb-fanout", args: <출력 그대로>} (mode: verdict) — 워커가
#   판정기준대로 3축 판정해 verdict/results/vresult_NNN.json 작성
python … run_thumbs.py verdict --run-dir <R> --commit     # → decisions.json
python … run_thumbs.py apply --run-dir <R> --commit       # 반영
```

- **워커는 `agent(model: haiku, effort: low)`** — Sonnet 과 정확도 동률에 실비 −58%
  (근거 → [`사고-이력.md`](references/사고-이력.md))
- **8건 이하면 팬아웃 없이 Claude 가 직접 판정**하고 `decisions.json` 을 손으로 적는다
  (`verdict` 를 안 거쳐도 된다 — `apply --commit` 은 `decisions.json` 만 본다)
- 판정 기준·판정값·결과 형식: [`references/검수-판정기준.md`](references/검수-판정기준.md)
  — 팬아웃 워커의 지시서도 이 문서다(`verdict` 가 배치에 `판정기준` 으로 싣고
  `pending --verdict` 가 promptPath 로 넘긴다). **3축의 정본은 그 문서** 하나다
- **미판정을 통과로 둔갑시키지 않는다**: `verdict --commit` 은 배치 대비 누락이 있으면
  `decisions.json` 을 **쓰지 않고 exit 3**. 누락을 넘기면 판정 안 한 상품이 `decisions.json`
  에 없다는 이유로 `apply --commit` 에서 전부 `사용가능` 으로 반영된다. 배치에 없는
  상품id(워커 환각)는 경고 후 버린다
- **잘린 `productId` 는 코드가 스스로 복구한다 — 손으로 고치지 마라.**
  `prescreen`·`audit`·`verdict`·`run` 수합부가 전부 `thumb_rules.heal_pid` 를 거쳐
  **자기 배치 안 접두 매칭**으로 되살린다(그 경계는 넘지 않는다 — 넘으면 남의 판정이
  엉뚱한 상품에 붙는다). 그냥 commit 하면 된다.
  **`[복구] 잘린 productId N건` 이 찍히면 워커 품질 문제다** — 자주 뜨면 지시서를 손봐라.
  **예외 — 가운데가 빠진 형태는 자동 복구가 안 된다**(예: `…MKRWQG1` → `…MKRW1`).
  접두가 안 걸려 환각으로 분류되고 감사가 commit 을 막는다. 이때만 배치 정본과
  **내용(상품명 ↔ 메인상품)** 을 대조해 결과 파일의 id 를 고친다(재팬아웃 불필요, 비용 0)
- **재생성분만 다시 판정하려면 `verdict --run-dir <R> --ids <상품id…>`**.
  앞 라운드의 `vresult` 는 `verdict/rounds/NNN/` 으로 보존되고 새 라운드는 빈 결과에서
  시작한다. `--commit` 은 `decisions.json` 을 **덮어쓰지 않고 합친다** — 지목 안 한 상품의
  판정이 사라지면 `apply --commit` 이 그 건들을 전부 `사용가능` 으로 반영해 버린다
- 정합검사(audit)와 **결과 폴더가 다르다**(`verdict/results/` vs `audit_results/`) —
  같은 run-dir 에서 병렬로 돌려도 안전하다. 둘 다 크레딧 0
- 이미지 확보 실패(생성본 다운로드 불가)는 조용히 빠지지 않는다 — 경고를 찍고 대상에서
  빼며, 그 상품은 `verdict --commit` 의 누락 검사에도 안 잡히므로 종합보고에 적는다

## 검수 페이지 (Claude 판정 자료 + 이룸님 사후 검토용)

`apply --generate`가 `review.html`을 만든다 — 상품별로 [기존 대표 | **대표옵션(기준)** |
생성본(미반영) | 원본 후보들]을 나란히 표시(전부 공개 https 주소라 업로드 없이 그대로 임베드).
재작업 사유·소모 크레딧도 같이 보인다. 이 페이지는 **표시 전용**.

대표옵션을 생성본 바로 왼쪽에 두고 대표옵션명을 카드 머리글에도 적는다 — 판정할 게
"생성본이 대표옵션과 **같은 물건**인가"라서 떨어져 있으면 대조가 안 된다.

`--commit`은 Claude 판정이 끝난 직후 바로 부른다 — `decisions.json`이 없으면 생성
성공분 전부를 **사용가능**으로 반영하므로, **판정에서 거른 상품은 반드시 decisions.json 에
먼저 적는다**(팬아웃 경로는 `verdict --commit` 이 대신 쓴다):

```json
{"U01...": {"판정": "제외", "사유": "색상 일치하지만 그림자가 부자연스러움"}}
```

검수 기준(3축, 두 모드 공통)의 **정본은
[`references/검수-판정기준.md`](references/검수-판정기준.md)** 다 — 메인이 직접 판정할
때도 워커와 같은 문서를 읽는다(두 곳에 적어두면 어긋난다). 요지만: ①제품 정확성
(생성본이 대표옵션과 같은 물건인가 — **절대 자동 통과 금지**, 2026-08-05 이룸님)
②클릭성 ③오인 위험. 재생성은 **상품당 누적 최대 2회**(`run_thumbs.py` 누적 카운트 기준).

**검수 불합격 자동 처리** (2026-08-06 이룸님 — 묻지 않고 Claude가 수행, 종료 보고에
유형별 **상품id 필수**):

| 불합격 유형 | 처리 |
|---|---|
| **대표옵션 자체가 본품이 아님**(부속·구성품 단독 — 상품명·원문명이 가리키는 본품과 다른 물건) | **재생성·fallback 금지** — 기준이 틀렸으니 어느 쪽도 교정이 아니다. `decisions.json` 판정을 `제외(대표옵션의심)` 으로 적으면 `--commit` 이 썸네일 열 `보류(대표옵션의심)` + **옵션 열 재작업 flag** 를 자동으로 찍는다(옵션정리가 대표를 복구하고 `이관(썸네일)` 을 되찍으면 재진입 — 2026-08-06 캠핑박스/걸이판 사례) |
| **제품에 박힌 글자 변조**(브랜드 표기·각인 등) | 재생성하지 않고 넘어간다(보류 종결, 기존 대표 유지) — AI 글자 재현은 재생성해도 같은 유형으로 또 틀린다 |
| **기준이 비제품 이미지**(도면·배너·색상칩)라 생성본이 뭉개짐 | **옵션 단계로 되돌린다**(2026-08-07 이룸님 — `대표옵션의심` 과 같은 경로). 뿌리가 대표옵션이라 재생성·fallback 은 둘 다 같은 비제품 기준을 다시 쓰는 것이라 교정이 아니다. 판정 `제외(기준이미지없음)` → `--commit` 이 썸네일 열 `보류(기준이미지없음)` + **옵션 열 재작업 flag**(대표를 실물 사진 있는 값으로 다시 세울 것)를 자동으로 찍는다. 판정값 2종은 `thumb_rules.TO_OPTION_VERDICTS` |
| **옵션이 이미 `실물기준없음` 이라고 답했는데 또 옵션 사유가 나옴** | **되돌리지 않고 종결한다**(2026-08-17). `--commit` 이 현황판 옵션 열을 보고 자동으로 가른다(`R.close_roundtrip`) → 썸네일 열 `보류(실물기준없음·왕복종결 …)`, 옵션 flag 없음 |
| 그 외(구성·색·형태가 대표옵션과 다름, 이미지 손상) | 대표옵션 이미지를 기준으로 **재생성**(상품당 누적 최대 2회) — `apply --ids <상품id> --generate` |
| **2회째도 불합격** | **대표옵션 원본 이미지를 그대로 대표로 저장**(AI 생성 없이, 크레딧 0) — `fallback --ids <상품id> --reason "…"`. **불사자에 즉시 반영한다 — 별도 승인 게이트 없음**(원본은 실물 그 자체라 정합이 보장된다. 2026-08-06 이룸님). 원본의 워터마크·중국어 글자 여부는 보고에만 명기 |

```bash
# 재생성(2회까지) — --ids 없이 부르면 재개 모드라 이미 태운 건은 건너뛴다
python … run_thumbs.py apply --group-name "…" --run-dir <R> --ids U01… --generate
# 재생성분만 다시 판정 — 앞 라운드는 verdict/rounds/ 로 보존, decisions 는 합쳐진다
python … run_thumbs.py verdict --run-dir <R> --ids U01…
# 2회째도 불합격 → 원본대체(크레딧 0, 시트·현황판까지 한 번에)
# **--run-dir 을 반드시 준다** — 그래야 decisions.json 에 `원본대체` 가 남아 되감기지 않는다
python … run_thumbs.py fallback --group-name "…" --run-dir <R> --ids U01… --reason "AI 2회 모두 …"
```

> **`fallback` 은 `decisions.json` 에 `원본대체` 를 남기고, `apply --commit` 은 그 건을
> 건너뛴다** — 순서가 어느 쪽이든 안전하다. `--run-dir` 없이 부르면 경고가 뜬다.
> 회차 끝에 현황판 `완료` 합계를 세는 습관은 그대로 둔다.

## 결과 미수신 회수 (recover — 크레딧 0, 2026-08-06 · 429 확장 2026-08-14)

**접수 뒤에 난 실패는 실패가 아니라 "아직"이다.** 접수는 됐고 크레딧도 이미 나갔는데
결과만 못 받은 것뿐이다. **타임아웃도 `HTTP 429` 도 같은 부류다.**
판별 기준은 에러 문구가 아니라 **taskId 유무**다:

- 429 가 `generate`(접수)에서 났으면 taskId 자체가 없다 → 진짜 실패, 재생성 대상
- 429 가 `poll`(결과 조회)에서 났으면 taskId 가 남는다 → **접수는 이미 성공** = 회수 대상

둘 다 같은 문구로 찍히니 로그만 보고 재생성하면 크레딧을 두 번 낸다.
**어떤 실패든 `recover` 를 먼저 돌려라** — 회수할 게 없으면 그냥 "회수할 건이 없다"고 끝난다.

```bash
python ... run_thumbs.py recover --run-dir <R> [--ids U01a U01b]
# → 회수 N건 / 대기 M건 / 실패 K건. 대기분은 나중에 같은 명령을 다시 부르면 된다(멱등)
```

- **`taskId` = "결과를 아직 못 받은 접수 번호"**. `apply --generate` 가 **접수 직후
  즉시** 기록하고(폴링 중 kill 돼도 단서가 남는다), 결과를 받으면 사라진다.
  필드가 남아 있다는 것 자체가 회수 대상 신호다.
- 회수분도 **자동반영 방어**를 태운다 — 접수 후 시간이 흘렀으니 오히려 더 필요하다.
- 회수는 **재생성횟수를 1 올린다** — 접수 자체가 시도였다. 회수가 상한을 우회하면 안 된다.
- 나머지 필드(후보·기준이미지·재작업사유)는 배치(정본)와 `before_generate.json` 에서
  조인한다 — 회수 결과가 백업·복원 경로를 오염시키지 않는다.
- **타임아웃 상한을 늘리는 것보다 이쪽이 낫다** — 상한을 늘리면 큐가 밀렸을 때 전체
  벽시계가 그대로 늘어난다(생성은 상품마다 동기).

## 불사자 저장 ≠ 마켓 반영

`--commit`은 불사자 서버의 대표이미지만 바꾼다. 이미 마켓에 올라간 상품은 판매 화면이
그대로다 — 수정 업로드를 따로 해야 반영된다. 미업로드 상품이면 다음 업로드 때 반영된다
(정리하기 가장 안전한 타이밍). 업로드 여부는 `workdata`의 `uploadedSuccessUrl` 각 마켓
값이 전부 null 인지로 본다.

| 수십·수백 건을 메인이 직접 판정 | 상품당 이미지 3장이라 190건 = 380장. 컨텍스트가 터진다 — **9건 이상은 `verdict` 팬아웃** |
| 워커가 배치 상품 일부만 결과에 담음 | 빠진 상품은 `사용가능` 으로 반영된다 = 검수 건너뛴 게 통과로 둔갑. `verdict --commit` 이 exit 3 으로 막으니 **그 에러를 무시하고 진행하지 않는다** |
| 세트 상품 대표를 최고가 옵션으로 오인 | 판매 구성을 온전히 보여주는 원본이 우선이지 가격 순이 아니다 |
| mcp-assets 경로를 보고 "가공 안 됨"으로 오판 | 경로는 무시, 호스트만 본다 |
| `가공됨` = 완료로 백필 | "손을 댔다"는 뜻이지 "맞게 됐다"는 뜻이 아니다. 대표옵션이 있으면 반드시 대조 |
| 배경교체가 제품을 보존한다고 믿고 검수 생략 | 실측은 색 변조·없는 것 추가·스펙 오표기·색상코드 글자까지 낸다 — 3축 ①제품 정확성은 절대 자동 통과 금지 |
| audit `대조불가`를 재작업으로 flag | 다음 prep 이 또 집고 audit 이 또 대조불가 → 무한 루프. 집계만 한다 |
| **수백 건 회차에서 `apply --commit` 의 시트 쓰기가 죽음** | 시트를 행 단위로 써서 분당 쿼터(60)를 넘긴다. **불사자 반영과 `###COMMIT###` 은 그 앞에서 이미 끝나 있다** — 죽었다고 반영이 안 된 게 아니다. 지금은 경고만 찍고 현황판 갱신은 진행한다. 그래도 실패했으면 `--commit --no-sheet` 재실행. **시트 본문이 한 번 기록됐으면 이후 재커밋은 무조건 `--no-sheet`** |
| **`--ids` 로 `--commit` 을 좁혔다고 믿음** | `--ids` 는 **생성 단계만** 좁힌다. `--commit` 은 `decisions.json` 전체를 돌아 **run-dir 전량이 재커밋된다.** 멱등이지만 저장 호출이 몰려 **429 로 무더기 `보류(저장실패)`** 가 난다. **소수만 반영하려면 그 건만 담은 run-dir 을 써라** |
| 타임아웃·`HTTP 429` 를 실패로 보고 재생성 | 크레딧을 두 번 낸다. 폴링에서 난 429 는 **접수가 이미 성공**한 것이라 taskId 가 남아 있고 서버엔 결과가 나와 있다. **에러 문구로 판단하지 말고 `recover` 를 먼저 돌려라** |
| 타임아웃이 많다고 `POLL_TIMEOUT` 을 늘림 | 상한을 늘리면 큐가 밀렸을 때 전체 벽시계가 그대로 늘어난다 — 회수 경로가 있으면 짧게 두는 게 낫다 |
| **큐가 막힌 시간대에 기본 설정으로 밀어붙임** | 기본 300초로 돌리면 **건당 5분씩 전건 실패**한다 — 아래 §큐가 막혔을 때 |
| **50건 넘는 회차를 인라인으로 밀어붙임** | 접수모드는 비상 수단이 아니다. 큐가 정상이어도 인라인 80초/건 vs 접수모드 20초/건 — 아래 §대량 회차는 접수모드로 |
| **생성을 kill 하고 곧장 재개** | 짝 없는 `[기준]`(미승인 이미지가 대표로 살아있음)과 접수분(크레딧 이미 나감)이 둘 다 방치된다. **restore → recover → 재개** 순서 — 아래 §안전하게 kill 하기 |

### 대량 회차는 접수모드로 돈다 (큐가 정상이어도)

생성은 상품마다 **동기**다. 인라인으로 돌면 서버가 이미지를 만드는 시간을 상품마다 혼자
기다린다 — **큐가 완전히 정상이어도 건당 약 80초.** 접수만 하고 넘어가면 서버가 여러 건을
병렬로 만들고 `recover` 가 0크레딧으로 걷어온다.

| 방식 | 건당 | 120건 환산 |
|---|---|---|
| 인라인(`POLL_TIMEOUT=300` 기본) | 약 80초 | 약 2시간 40분 |
| 접수모드(`THUMB_POLL_TIMEOUT=20`) | 약 20초 | **약 40분** |

```bash
THUMB_POLL_TIMEOUT=20 python … run_thumbs.py apply --run-dir <R> --generate  # 접수 위주
python … run_thumbs.py recover --run-dir <R>                                 # 수확(크레딧 0·멱등)
```

**판단 기준: 대상이 50건을 넘으면 접수모드를 기본으로 잡는다.** 아래 §큐가 막혔을 때가
쓰는 것과 같은 수단이지만 **비상 수단이 아니다** — 큐 상태와 무관하게 대량이면 이게 빠르다.
소량(≤50건)은 인라인이 단순해서 낫다(recover 왕복이 필요 없다).
`POLL_INTERVAL=10` 이라 `THUMB_POLL_TIMEOUT` 은 10의 배수로 준다(20 권장).
`recover` 는 대기 0 이 될 때까지 몇 번을 불러도 안전하다(멱등).

### 큐가 막혔을 때 — 접수모드로 갈아탄다

**판단 기준: 연속 3건 타임아웃 · 성공 0.** 그대로 두면 건당 5분씩 전건 실패한다.

```bash
# 1) 안전지점에서 끊는다 → 아래 §안전하게 kill 하기
# 2) 이미 접수된 건부터 회수한다 (크레딧 0 · 멱등)
python … run_thumbs.py recover --run-dir <R>
# 3) 폴링을 60초로 줄여 **접수만** 빠르게 돌린다
THUMB_POLL_TIMEOUT=60 python … run_thumbs.py apply --run-dir <R> --generate --ids ${=IDS}
# 4) 접수가 끝나면 다시 회수한다. 대기 0 이 될 때까지 반복해서 불러도 된다
python … run_thumbs.py recover --run-dir <R>
```

⚠ **3번에서 `--ids` 를 반드시 쓴다.** 재개 모드(`--ids` 생략)는 `생성본` 이 있는 건만
건너뛴다(`thumb_rules.generate_plan`) — **taskId 만 있는 접수분은 다시 접수돼 크레딧이
이중으로 나간다.** 2번 `recover` 로 `생성본` 을 먼저 채웠다면 재개 모드도 안전하다.

### 안전하게 kill 하기 — 그리고 **restore → recover → 재개** 순서로만 재개한다

생성 루프는 상품마다 `[기준] 대표(0번)로 올림 → 생성 → [방어] 승인 전 상태로 복원` 이다.
끊으면 **짝이 안 맞는 상품**이 남는다 = 승인 안 한 이미지가 대표로 살아 있다.

두 줄 개수가 같아지는 순간을 폴링으로 잡으려 하지 마라 — 방어 직후 바로 다음 `[기준]`
이 찍혀 창을 계속 놓친다. **그냥 끊고 사후에 짝을 찾는 쪽이 확실하다.**
순서를 틀리면 둘 다 사고가 나므로 아래 ①②③ 순서를 지킨다.

**① 짝 없는 `[기준]` 을 찾아 복원** — 미승인 이미지가 대표로 남는 것을 먼저 막는다

```bash
python3 -c "import re,sys;L=open(sys.argv[1]).read().splitlines();b=[m.group(1) for l in L if (m:=re.search(r'\[기준\] (\w+):',l))];g={m.group(1) for l in L if (m:=re.search(r'\[방어\] (\w+):',l))};print([x for x in b if x not in g])" <생성로그>
python … run_thumbs.py restore --run-dir <R> --ids <위에서 나온 pid>
```

**② `recover` 로 접수분을 먼저 수확** (크레딧 0 · 멱등)

```bash
python … run_thumbs.py recover --run-dir <R>
```

**③ 그 다음에 재개한다.**

**②를 건너뛰면 크레딧을 두 번 낸다.** 재개 판정(`thumb_rules.generate_plan`)은 `생성본`
이 있는 건만 건너뛰므로 **taskId 만 있는 접수분은 미생성으로 보고 다시 접수한다.**
"끊었으니 그 건은 실패"가 아니라 **"접수는 됐고 크레딧도 이미 나갔다"** 가 맞다.

### `보류(저장실패)` 를 믿지 마라 — 재저장 전에 실물부터 대조한다

`보류(저장실패)` 는 "저장이 안 됐다"가 아니라 **"저장 *시도* 가 실패로 끝났다"** 다.
커밋이 *이미 저장된 값* 을 다시 쓰려다 429 로 죽어도 이 값이 남는다.
실측 사례에선 저장실패 9건이 전부 이미 저장돼 있었다 — 조회 5분이 재저장 229건을 아꼈다.
대조법:

```
decisions.json 의 `사용가능` × generated.json 의 `생성본`  vs  workdata()['썸네일'][0]
```
