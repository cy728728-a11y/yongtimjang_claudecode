# 불사자 카테고리 교정 (Aside 기준)

불사자 상품의 잘못된/미설정 카테고리를 **네이버 정답 카테고리**로 교정하는 스킬.

핵심 아이디어: **네이버 가격비교**가 상품명(또는 키워드)이 속한 카테고리 경로를
`생활/건강 > 공구 > 원예공구 > 농기계` 처럼 알려준다.

> ★ **2026-08-04: 조회 엔진이 셀하 → Aside 로 바뀌었다.** 셀하가 막혀 못 쓴다.
> 이제 **Aside 브라우저 + 불사자 확장**으로 네이버 가격비교를 직접 열어 읽는다
> ([`../aside-category/SKILL.md`](../aside-category/SKILL.md)).
> 크롬 프로필·셀레늄·`.env` 자격증명이 **전부 필요 없어졌다.**
> 대신 전제가 셋: **Aside 앱 실행중 · 불사자 확장 설치 · 네이버 로그인 유지.**
> 하나라도 빠지면 전건 `파싱실패`다.
>
> 반환 스키마(`카테고리경로`·`최종차수`·`확신도`·`상태`)는 셀하와 같아 아래 흐름은 그대로다.
> 파일명 `sellha.json`, 시트 열 `sellha경로`, 상태 `sellha조회실패`, 플래그 `--skip-sellha` 는
> **이름을 유지**한다 — 기존 run-dir 의 `--resume` 과 시트 재개 로직이 그 이름에 물려 있다.

그 경로의 **최종 차수(예 `농기계`)** 를 불사자 카테고리 검색에 넣으면 동일 경로가 나오고, 그걸로 저장한다.
조회 경로 = 네이버 카테고리이므로, 불사자 스마트스토어 후보의 전체 경로와 **정확히 일치**한다 → 매칭이 자명.

> **자동 반영이 기본이다 (2026-08-06 이룸님 확정 — `_shared/스킬-계약.md` §반영은 기본 자동이다)**:
> ① `변경대상` + **확신도 ≥ 70%** → 바로 저장 (2026-07-12 확정, 임계 70 하향 2026-07-24).
> ② 확신도 <70·`매칭불가`·`부분일치확인요` → **consensus 자동 승격**(§검색어 변형 consensus) →
>   그래도 남으면 **Claude 가 증거 4종·recheck 이미지로 최종 판정**해 확신이 서면 유도 저장,
>   못 서면 `보류` 로 남긴다. 이룸님 승인 대기는 없다 — 보류 목록은 종합보고에 싣는다.
> ③ 근접저장(폴백 3단계)도 Claude 판정으로 자동 저장하되 I열 플래그 + 종합보고 **전수 목록** 필수.
> **마켓 범위(이룸님 확정, 2026-07-12)**: 저장은 전 마켓 동시 반영(쿠팡 포함)으로 그대로 진행한다
> — 도구가 스마트스토어 단독 저장을 지원하지 않으므로. 이룸님은 스마트스토어 기준으로 검증한다.

## 사전 요구사항

- **Aside 브라우저**(macOS 15+) 실행중 + **불사자 확장** 설치 + **네이버 로그인** 유지.
  CLI 는 `~/.local/bin/aside`(다른 경로면 `ASIDE_BIN` 환경변수). 자격증명 파일 없음.
  조회는 `aside repl` **호출당 ~120초 벽**이 있어 자동으로 ≈7건씩 쪼개 돈다(v1.8.1). 호출부는
  신경 쓸 게 없지만, `결과가 비어 있다`로 죽으면 이걸 먼저 의심한다 → `aside-category/SKILL.md`.
- **Python**: 워크스페이스 `.venv`. 셀레늄은 이제 안 쓴다.
- **불사자 MCP**: `mcp__bulsaja__*` (연동됨).
- **구글시트**: `gws` CLI (로그 시트 작성용).

## Workflow

### Step 1. 대상 상품 수집
대상 상품 ID를 모으는 경로 두 가지:
- **(A) 시트 A열에서 읽기 (기본, 마켓그룹 단위 작업)**: 이룸님이 `카테고리교정_<마켓그룹명>` 시트 A열에
  상품 ID를 채워둔다 → `gws sheets spreadsheets values get` 으로 A·G(상태)열을 읽어 대상 확보.
- **(B) 불사자 MCP 조회**: `bulsaja_product_list`(keyword/최신순) 또는 `bulsaja_product_find_by_code`.

- **재개 스킵(중단·재개 안전장치) — "대상선정 스킵" 집합**: 시트에서 **`상태`(G열)가 이미 채워진 행은 건너뛴다.**
  `자동저장완료`/`저장완료`/`이미정확`/`매칭불가`/`sellha조회실패`/`부분일치확인요`/`보류(정체불명)`/`승인보류`
  = 1바퀴 처리가 끝난 것(뒤 3개는 후처리 큐로 따로 소진한다).
  **`상태`가 빈 상품 ID만** Step 2~6을 돌린다. → PC를 덮었다 켜도 처음부터 다시 하지 않고 이어서 진행.
  ※ 이 8종은 **대상선정 스킵**용이다 — `apply` 의 **원장 보호** 4종(`저장완료`·`자동저장완료`·
  `이미정확`·`상품삭제…` = `matrix.CATFIX_DONE`, "진짜 완료")과 다른 집합이니 혼동하지 않는다.
- **소수 테스트 기본**: 처음엔 3~5개로 검증 후 확대(이룸님 확정 사항).
- 각 상품에서 `productId` 와 `상품명` 을 추린다.

### Step 2. 현재(이전) 카테고리 읽기 (불사자 MCP)
각 `productId` → `bulsaja_product_workdata(mode="full")` →
`data.uploadCategory.ss_category` 의 `name`(스마트스토어 현재 카테고리).
- `name` 이 빈 문자열이면 **"미설정"** (= 이전 카테고리 없음).
- 이 값이 로그의 **이전 카테고리** 컬럼.

### Step 3a. 실물 정체 판별 → 대표 검색어 추출 (기본, 2026-07-24 개편)

**한국어 상품명은 정답지가 아니라 용의자다.** 상품명·썸네일은 둘 다 불사자 가공 **후** 산출물이라
**같이 틀린다.** 그래서 가공 **전** 원본(**②중국어 원문명·③옵션명**)을 독립 증거로 함께 본다.
증거 4종(①한국어 상품명 ②중국어 원문명 ③옵션명 ④썸네일)은 추가 호출 비용 없이 `prep` 이
`names.json` 으로 모아 넘긴다(②③은 `workdata` 응답에, ④는 `prep` 이 전건 미리 받아둠).

증거 4종을 종합해 **A 일치 / B 정정확정 / C 정체불명** 셋 중 하나로 판정한다.
- **A·B** → 실물 기준 대표 검색어 도출 → 조회. **B는 미루지 않고**(조회 두 번 방지) `실물판정` 기재.
- **C** → `상태:"보류(정체불명)"`, 조회를 태우지 않고 2바퀴(Step 3b)로. **조금이라도 애매하면 C.**

#### Step 3a 실행 = Workflow 모드 (기본, 2026-07-31)

**대량(수백 건)은 메인 세션이 오케스트레이션하지 않는다.** 배분·수합 턴이 메인 컨텍스트에
쌓여 `/clear` 가 필요해지고, 그게 지금까지 세션이 쪼개지던 유일한 이유였다(상품명 실측 92M 토큰).
백그라운드 워크플로(`catfix-fanout`)로 빼면 그 재과금과 수동 중단점이 **사라진다.**

```bash
# ① 배치 만들기 (names.json → batches/batch_NNN.json + index)
run_all.py batch --run-dir <R> [--size 8]

# ② 남은 배치를 Workflow args 로 그대로 찍는다 (디스크 = 정본, named 없는 것만)
run_all.py pending --run-dir <R>
```
③ `Workflow` 도구를 `{name: "catfix-fanout", args: <②의 출력>}` 로 호출.
   워커는 `agent(model: sonnet, effort: low)` — **메인 모델과 무관하다.** 이 축의 예산:
   **이미지 워커당 ≤16장.** 공통 규약(동시성 opt-in·재개·폴백)은
   [`_shared/스킬-계약.md`](../_shared/스킬-계약.md) §팬아웃 공통 규약.
   워커 지시서 = [`references/판정-워커-프롬프트.md`](references/판정-워커-프롬프트.md)
   (판정 규칙 자체는 `대표검색어-도출.md` 를 워커가 직접 Read 한다).

④ 반환의 `재팬아웃필요배치` 가 비어야 다음으로 간다. 워크플로가 이미 **1회 자동 재팬아웃**한다.
   그래도 남으면 `pending` 을 다시 찍어 재호출.

```bash
# ⑤ merge → finish → steer 를 한 프로세스로. **백그라운드로 띄운다**
run_all.py auto --run-dir <R>
```
조회가 ~10초/건이라 수백 건이면 몇 시간이다(셀하 시절 ~15초에서 단축). `auto` 는 그 전
구간(병합·조회·저장·유도저장)을 한 프로세스로 묶어 두었으므로 **메인은 띄우고 끝나면 결과만 읽는다.**
중간에 죽어도 조회는 `--resume`, 시트 G열은 체크포인트라 다시 돌리면 이어간다.

> **이룸님 개입 = 시작 1회 + 종합보고 확인 1회 (2026-08-06 — 끝의 보류 큐 판정도 자동으로
> 흡수).** 자동 유도저장은 확신도 ≥ 임계인 것만 건드리고(`steer_items`), 미달분은
> consensus → Claude 판정으로 자동 소진한다. 그래도 남은 보류만 종합보고에 싣는다.

**폴백 — Workflow 를 못 쓰는 하네스**
- **모드 A**: `Agent` 도구로 Sonnet 팬아웃. 워커 1명 = 배치 1~2개. 지시서는 같은 파일을 쓴다
- **모드 B — 서브에이전트 없음(코덱스 등)**: `batches_index.json` 을 K등분해 K개 독립 프로세스
- **재개**: `named/named_NNN.json` 존재 = 그 배치 완료. 겹쳐 돌려도 멱등 덮어쓰기

> **증거 4종 상세·실증·판정 기준·대표검색어 12규칙 프롬프트 전문(실측 튜닝)·예시 →
> [`references/대표검색어-도출.md`](references/대표검색어-도출.md).**
> 이 파일은 `product-name` 스킬도 실물 판정에 함께 참조하는 **공유 자산**이다(원문 그대로 유지).

`keywords.json` 출력 형식:
```json
[{"productId":"U01...","name":"차량용 유압자키","실물판정":"자키+에어펌프+전동렌치 세트",
  "근거":"원문 千斤顶+充气泵+电动扳手, 옵션 전건 동일"},
 {"productId":"U01...","상태":"보류(정체불명)","실물판정":"","근거":"원문=조명, 옵션=거치대, 썸네일 판독 불가"}]
```

#### 대표 검색어 추출 (판정한 실물 → 검색어)

**원문 상품명을 그대로 넣지 않는다.** 판정한 실물 기준으로 **대표 검색어**(분야 한정어를 붙인
2단어 이상)를 뽑는다. 단일 넓은 단어는 대중 분야(자동차·주방·미용)로 오검색되므로 분야를 못 박아야
확신도가 오른다(실측: 1인용소파 34%→원목 라운지체어 100%).

> **12규칙 프롬프트 전문·예시 → [`references/대표검색어-도출.md`](references/대표검색어-도출.md)** (실측 튜닝, 원문 유지).
> 규칙 10(상품명에 없는 속성 추측 금지)은 지키되, **원문·옵션에서 확인된 구성은 추측이 아니다.**

각 상품 `{productId, 핵심어}` 를 JSON으로 만들어 조회 스크립트에 넘긴다(브라우저 1개로 일괄):
```bash
# 입력 예: [{"productId":"UB36...","name":"브레이크패드"}, {"productId":"UB37...","name":"미니오두막"}, ...]
#   ("name" 필드에 원문이 아니라 도출한 핵심어를 넣는다)
PYTHONIOENCODING=utf-8 .venv/bin/python \
  .claude/skills/aside-category/scripts/aside_category.py \
  --input <입력.json> --output <결과.json> --resume
```

- 항목별 반환: `productId · 검색어 · 카테고리경로 · 최종차수 · 확신도 · 카테고리코드 · 후보목록 · 상태 · error`
- `상태`: `성공` | `조회실패`(검색결과 없음) | `파싱실패` | `차단감지` | `캡챠감지`
- **`차단감지`·`캡챠감지`면 즉시 멈춘다.** 캡챠는 [`captcha-relay`](../captcha-relay/SKILL.md)
  스킬로 푼다 — **명령·검증 절차는 그 SKILL.md 가 정본**이다. 풀리면 `--resume`,
  `needs_human`·`timeout` 이면 재시도 없이 이룸님에게 보고.
- 검색에 쓴 핵심어를 **Step 5 `검색어(사용)` 열에 반드시 기재**.
- 애드혹 조회는 `--query "키워드1" "키워드2"` (productId 없이).

#### 검색어 변형 consensus — 확신도가 낮을 때만 (2026-07-27, 헤르메스 13 흡수)

**전건에 쓰지 않는다.** 헤르메스 13은 상품마다 검색어 변형 2~3개를 조회해 **2개 이상에서 전체
경로가 일치**할 때 확정하는데, 그대로 들이면 조회비가 3배가 된다(1000건 × 10초 = 그룹당 8시간).

**확신도 < 70인 건에만** 보조 판정으로 쓴다 — 어차피 자동저장이 안 돼 수동 큐로 가는 건들이다.
**실행은 `run_all.py consensus prep/run` 으로 자동화됐다(2026-08-05)** — 아래 수동 절차는
규칙의 정의이자 폴백이다:
1. 같은 실물에 대해 검색어 변형 2개를 더 만든다
   (①구체명 → ②띄어쓰기 변형 → ③상위 대표명. **분야 한정어는 셋 다 유지**)
2. `aside_category.py --input` 으로 함께 조회 — **원검색어는 재조회하지 않는다.**
   1바퀴 결과(merged 의 sellha경로)가 이미 1표다(자동화가 조회비를 3배→2배로 줄인 방법)
3. **3개 중 2개 이상이 전체 경로 일치** → 그 경로를 채택하고 `확신도`는 **일치한 표 중**
   최고값으로 기록, I열에 `consensus(2/3)` 표기 → `category_steer` exact 모드로 저장
4. 일치가 없으면 기존대로 수동 큐(`부분일치확인요`)로 남긴다

```bash
run_all.py consensus prep --run-dir <R>   # 미저장 잔여(변경대상<70·매칭불가·부분일치) 추출
#   → consensus_targets.json + 안내. Claude가 건당 변형 2개를 consensus_variants.json 에 작성
run_all.py consensus run  --run-dir <R>   # 변형 조회 → 2/3 판정 → 통과분 유도 저장(+현황판)
#   실패분은 consensus_fail.json (합의없음 / 실물판정의심 / 변형없음) — 수동 큐·종합보고 몫
```

> 변형이 서로 다른 경로를 가리키면(`실물판정의심`) **검색어가 아니라 실물 판정이 틀렸을
> 가능성**이 높다. 그때는 변형을 더 만들지 말고 Step 3b(`recheck` 이미지 사다리)로 보낸다.
> product-name 발(發) 자동 루프에서는 recheck 을 다시 태우지 않고 종합보고로 보낸다(1회 한정).

`aside_category.py` 의 전체 인자·차단 대응 옵션은
[`../aside-category/SKILL.md`](../aside-category/SKILL.md) 가 정본이다.

### Step 3b. 2바퀴 — `보류(정체불명)` 큐 증거 보강 (한 바퀴 다 돈 뒤)

**중간에 멈추지 않는다.** 1바퀴(A·B)를 전건 다 돌린 뒤 C 큐만 모아서 처리한다.
그래야 ① 판단이 동질적인 뭉치에 집중되고 ② 그 그룹이 어떤 상품군인지 이미 파악된 상태에서 본다.

```bash
PYTHONIOENCODING=utf-8 .venv/bin/python \
  .claude/skills/bulsaja-category-fix/scripts/run_all.py recheck \
  --run-dir "<데이터루트>/category-fix/runs/<이름>"
```
`keywords.json` 에서 `상태`가 `보류…` 인 건을 자동으로 추려 **이미지 사다리**를 싼 것부터 내려받는다
(`--ids` 로 직접 지정도 가능). 산출: `recheck.json` + `recheck/` 이미지.

**이미지 사다리 (싼 것부터)**:
1. **남은 썸네일 2·3장** — `workdata` 가 이미 6장까지 받아둔 URL이라 **사실상 공짜**. 여기서 상당수 풀린다.
2. **옵션 이미지** (`uploadSkus[].urlRef`, 최대 3장) — 옵션은 실물 변형이라 정체가 드러난다.
   **상세페이지 원본 이미지에 가장 가까운 소스**다.
3. 그래도 불명 → **이룸님께 보고**. 혼자 추측해서 엉뚱한 카테고리에 넣지 않는다.

> 내려받는 이미지는 `fetch_thumbs.py` 가 **긴 변 512px 로 줄인다**(`--max-px`, `0`=원본).
> 카테고리 판정은 실물 정체만 보면 되므로 여유가 크다 — 근거는
> [`../_shared/스킬-계약.md`](../_shared/스킬-계약.md) §이미지 해상도.

> **상세페이지 이미지 자체는 안 쓴다.** `workdata` 의 `uploadDetailContents.renderContent` 는 비어 있어
> 별도 호출·타오바오 직크롤이 필요하고, 상품당 수십 장 세로 이미지라 대량에는 비현실적이다.
> 옵션 이미지가 그 대용이며, 원문명·옵션명(텍스트)이 이미 상세페이지와 **같은 소스**다.

**절차**: `recheck.json` 의 `추가이미지` 경로를 **Read 로 열어 직접 본다** → 원문명·옵션명원문과 종합해
실물 확정 → Step 3a 12규칙으로 검색어 재도출 → `keywords.json` 의 해당 건을 갱신(`상태` 제거 + `name` 기재)
→ `finish` 재실행(`--resume` 라 기존 성공분은 재조회하지 않는다).

> **`finish` 재실행은 안전하다(2026-08-04 수정).** `apply` 가 시작할 때 시트 G열을 1회 읽어
> **이미 완료인 행(`저장완료`·`자동저장완료`·`이미정확`·`상품삭제…`)은 건너뛴다.**
> 전에는 `decisions.json` 전건을 덮어써서, `steer`·근접저장으로 `저장완료`가 된 행이
> 재실행 때 `매칭불가` 로 되돌아갔다(불사자 저장은 멀쩡하고 원장만 거짓이 됨).
> 일부러 전건 재조회·덮어쓰기를 하려면 `finish --overwrite-done` (= `apply --force`).

## 저장 4단계 폴백 (요약 — 전문은 references)

**핵심 원리**: `bulsaja_product_category` 는 **keyword 자동매칭만** 지원한다(code 직접지정 불가).
자동매칭 = keyword 검색 스마트스토어 후보의 **1순위**. 그래서 동명 leaf를 그대로 넣으면 엉뚱한
상위경로가 잡힌다(미용가위→반려동물, 글러브→야구). **keyword를 조정해 원하는 경로를 1순위로 올린다.**

정확일치가 안 되는 `부분일치확인요`·`매칭불가` 는 이 순서로 소진한다(각 단계 실패분만 다음으로):

| 단계 | 방법 | 도구 |
|---|---|---|
| 1 | **leaf + 분야 한정어 유도 저장** — preview 후 목표 경로와 정확일치할 때만 commit | `category_steer.py` (exact) — 대량은 `run_all.py steer` 가 자동 (확신도 ≥ 임계만) |
| 2 | **실물 재확인 후 재검색** — 원문명·옵션명·추가 이미지로 실물 정정 → 재조회 | `run_all.py recheck` → `aside_category.py` |
| 3 | **근접 카테고리 저장** — 조회 경로가 불사자에 아예 없을 때. **Claude 판정으로 자동 저장**(세분화 차이만 허용, 2026-08-06) — I열 플래그 + 종합보고 전수 목록 필수 | `category_steer.py` (near) |
| 4 | **종합보고 → 이룸님 수동지정** — 알려준 경로를 target으로 1단계 재실행 | — |

### Step 5. 구글시트 로그 작성 (원장)
아래 컬럼으로 구글시트에 기록한다. 이 표가 곧 원장이고, 종합보고가 이 시트를 요약한다
(제안표를 이룸님께 먼저 보여주고 기다리는 흐름은 2026-08-06 폐지 — 자동 반영 모델).

| 상품id | 상품명 | 이전 카테고리 | 변경 카테고리(제안) | 검색어(사용) | 확신도 | 상태 | 실물판정 |
|--------|--------|---------------|---------------------|--------------|--------|------|----------|

- **검색어(사용)**: 조회에 실제 넣은 키워드. 실물 정정(B)이면 정정어 + `(실물정정)` 표기.
- **실물판정(J열)**: 증거 4종으로 판정한 실물 정체(예 `자키+에어펌프+전동렌치 세트`).
  **후속 `product-name` 스킬이 이 열을 읽어 재활용한다** — 썸네일을 다시 판독하지 않아도 되게.
  - **양방향 계약**: 이 스킬(v1.7.0~)이 J열을 채운다. **J열이 빈 구버전 그룹**은 후속
    `product-name`이 증거 4종으로 직접 판정한 뒤 **그 결과를 이 J열에 backfill**한다
    (J{row} 단일 셀 update — 다른 열 불변). 그래서 한 번 상품명 작업을 거친 구버전 그룹은
    다음부터 신버전처럼 J열 재활용이 된다.
- **상태** 값: `변경대상`(제안) / `이미정확`(이전==제안, 변경 불필요) / `sellha조회실패` /
  `매칭불가` / `부분일치확인요` / **`보류(정체불명)`** / (저장 후) `저장완료` / `승인보류`.
- 구글시트: `gws`(계정은 `workspace.toml [accounts].gws` — 폴더/시트 생성 계정)로
  **마켓그룹별 로그 시트**에 기록. **요청 바디는 `--json`, URL/쿼리 파라미터는 `--params`.**
  - **구조(2026-07-12 확정)**: 드라이브 `20-불사자-상품관리 > 카테고리교정/` 폴더에 **마켓그룹당 개별 시트**.
    폴더·마스터 인덱스의 id 는 **`workspace.toml` 의 `[drive]`·`[sheets]`** 에서 읽는다
    (`eroomlib.config` — SKILL.md 에 id 를 박지 않는다, 계약 §경로·시트ID).
  - **시트 이름 규칙**: `카테고리교정_<마켓그룹명>` (예: `카테고리교정_5번_용쌤25-2`).
  - 대상 마켓 시트를 `카테고리교정` 폴더에서 이름으로 찾고, 없으면 새로 만들고
    (헤더 1행 기록) 마스터 인덱스(`00_마스터-인덱스`)에 행을 추가한다.
  - 상품 ID는 이룸님이 해당 마켓 시트 A열에 미리 채워둔다 → 그 ID들을 대상으로 실행(Step 1을 목록조회 대신 시트 A열 읽기로 대체 가능).
  - **건건 즉시 기록(중단·재개 안전장치)**: 상품 ID가 A열에 미리 있으므로 **append 하지 말고**, 그 상품
    ID가 있는 **행을 찾아 B~H열을 update** 한다. 상품 **1건 처리(조회→판정→저장)가 끝날 때마다 곧바로**
    그 행 상태를 기록 → 크래시 시 잃는 건 진행 중이던 1건뿐, 나머지는 시트에 남는다.
    - 행 찾기: A열을 읽어 productId의 행 번호(예 5행) 확보 → `range="시트1!B5"` 로 update.
    - (A열에 ID가 없던 신규 건은 예외적으로 append 후 그 행을 갱신.)
  - **열 구성 (A~K, 2026-07-24 J·K 추가)**: `sheet_log.py` 가 `B{row}:K{row}` 를 한 번에 덮어쓴다.
    ```
    A 상품id / B 상품명 / C 이전카테고리 / D 변경카테고리 / E 검색어(사용) / F 확신도 /
    G 상태 / H 기록일 / I 위험·근접플래그 / J 실물판정 / K 썸네일URL
    ```
    - **기존 시트에는 J·K 헤더를 1회 추가해야 한다** (`J1=실물판정`, `K1=썸네일URL`).
      값은 `B:K` 로 덮어쓰므로 헤더만 넣으면 그다음부터 자동으로 채워진다.
  - 헤더 행은 시트 생성 시 1회만.
  - 완료 후 시트 URL을 이룸님께 안내.

### Step 6. 판정 → 저장 (불사자 MCP)
**저장 분기 (2026-07-12 규칙, 2026-08-06 전체 자동화)**:
- **자동 저장**: 상태=`변경대상` **AND 확신도 ≥ 70%** → 바로 저장. 시트 상태 `자동저장완료`.
- **Claude 판정 저장**: 확신도 < 70% 인 `변경대상` → consensus(§검색어 변형 consensus)로
  자동 승격을 먼저 시도, 그래도 남으면 Claude 가 증거 4종·recheck 이미지로 최종 판정해
  확신이 서는 건만 유도 저장(상태 `저장완료`). 못 정한 건은 `보류` — 종합보고 목록행.
- **`이미정확`**: 기존 카테고리 == 조회 카테고리(`>` 주변 공백 무시)면 **조회·저장을 아예 안 태운다**
  (확신도 무관 — 어느 쪽이든 카테고리는 그대로다). 2026-08-04까지 상태표에만 있고 코드에 없었다.
- **폴백 후처리**: `매칭불가`/`부분일치확인요`/`sellha조회실패` 는 여기서 끝이 아니라 **저장 4단계 폴백**

#### ★ 저장 규율 — 저장은 스크립트가 한다 (2026-07-31)

**메인이 `bulsaja_product_category` 를 직접 호출해 저장하지 않는다. 건수 예외 없다.**

| 대상 | 명령 |
|---|---|
| 정규 경로(조회 정확일치) 대량 | `run_all.py finish` (또는 `auto` = merge→finish→steer 한 번에, 백그라운드) |

**이유 두 가지 — 비용보다 스냅샷이 먼저다:**

1. **스냅샷** — 직접 호출은 로컬 스냅샷을 갱신하지 않는 유일한 경로다(스크립트는 commit 직후
   `snapshot.update`). 빠지면 상품명 `prep` 이 옛 카테고리로 뷰를 만든다 — 2026-07-30 실측
   상품명 76건 무효. **1건이어도 위험하다.**
2. **비용** — 2026-07-29 메인 직접 호출 149회 = 1시간 $266(응답의 `마켓별후보` 가 턴마다
   재과금). 스크립트는 메인 턴 1회 + subprocess 라 재과금 0.
   (같은 원리의 상품명 쪽 대책 = Workflow 팬아웃 → `product-name/references/팬아웃-비용.md`)

> **조회(preview)만 하는 직접 호출은 무방하다** — 이 규율은 **저장(commit)** 에 걸린다.

스크립트가 실제로 하는 호출:
```
bulsaja_product_category(productId=<id>, keyword=<조회 최종차수>)
```

  지정한다. **스마트스토어(ss_category)** 는 조회 경로와 정확히 일치하지만, 쿠팡·해외직구 등 타 마켓은
  같은 키워드로 자동매칭돼 **부정확할 수 있다**(예: `농기계`→쿠팡 '사다리/운반용품'). 이룸님은 네이버
  셀러이므로 스마트스토어 기준으로 검증한다. 타 마켓까지 정밀히 맞추려면 마켓별로 별도 확인 필요.
- 저장 후 해당 행 상태를 `저장완료`로 갱신(구글시트도 갱신).

## 재교정하면 그 상품의 상품명도 무효다 (2026-07-27, 헤르메스 13 흡수)

**카테고리를 바꾼 상품의 기존 생성 상품명·키워드는 전부 폐기한다. 부분 회수는 없다.**

이유는 `product-name` 의 최상위 원칙 그대로다 — 상품명 키워드는 **그 카테고리의 뷰에서** 뽑는다.
카테고리가 틀렸다면 그 뷰도 틀렸고, 거기서 고른 키워드·상품명·관련어 기록이 **전부 잘못된
모집단에서 나온 것**이다. 새 카테고리에서 다시 뽑아야 한다. "키워드 하나만 갈아끼우기"는 안 된다.

**현황판·원장 마킹은 자동이다** — 카테고리가 실제로 바뀌어 저장되면 `apply` 가
① 현황판 `상품명` 열에 `재작업(카테고리: …)` 을 찍고(2026-07-28 — `product-name` 이
`pending` 으로 다시 집어간다), ② 원장(상품명 탭)의 옛 행 상태를 `재작업(카테고리변경)` 으로
바꾼다(2026-08-05, `run_names.py mark`. **행은 지우지 않는다** — E열 원본상품명이 유일한
되돌리기 경로. 안 바꾸면 `rename` 이 옛 상품명까지 함께 반영한다).
`관련어` 탭은 무효 마킹 생략(카테고리 열로 자체 구분, 2026-08-05).

상품명 재작업은 **새 run-dir**(같은 run-dir 는 workdata 캐시가 옛 카테고리 뷰를 만든다)에서
`run_names.py prep --ids <...> --redo` 로 돌린다 — 멱등 판정이 A열 존재 기준이라 `--redo`
없이는 건너뛴다. 면제는 1회용(`append` 가 `redo.json` 소진). 이미 `반영완료` 건은 원본
상품명(E열)으로 되돌릴지가 상품마다 달라 **종합보고 판정 큐**에 싣는다.

> 반대 방향 계약은 `product-name` §Step 5 ②(`보류(카테고리의심)`)다 — 상품명 쪽에서 카테고리
> 이상을 감지하면 이 스킬로 돌려보내고, 이 스킬이 카테고리를 바꾸면 상품명을 되돌려보낸다.

## 대량처리 (수백~수천 건)

수십 건 이상은 인라인(대화) 처리 불가 — `workdata`(~6KB+/건) 응답이 컨텍스트에 쌓여 토큰 초과.
**불사자 MCP는 원격 HTTP 서버**라 파이썬이 대화 밖에서 JSON-RPC 직접 호출해 무거운 응답을
스크립트 안에서 소비하고 요약만 파일·시트로 남긴다.

```bash
bulsaja_mcp.py probe                        # 1순위: HTTP MCP 실동작 검증
run_all.py --sheet <S> prep --run-dir <R> [--limit N]  # collect → workdata → 썸네일 → names.json
run_all.py batch   --run-dir <R> [--size 8]   # names.json → batches/ (팬아웃 단위)
run_all.py pending --run-dir <R>              # 남은 배치 → Workflow args JSON
#   (Workflow `catfix-fanout` 이 워커에 분배 → named/named_NNN.json)
run_all.py auto    --run-dir <R>              # merge → finish(조회·저장) → steer(유도)
run_all.py recheck --run-dir <R> [--ids ...]  # 2바퀴: 보류 건 이미지 사다리
run_all.py consensus prep --run-dir <R>       # 잔여 저확신·매칭불가 → 변형 대상 추출
run_all.py consensus run  --run-dir <R>       # 변형 조회 → 2/3 판정 → 유도 저장
```

**★ `--sheet <그룹 시트 id>` 는 `prep` 에 한 번 넘긴다** — `run-dir/run_meta.json` 에 박혀
이후 단계(`finish`·`steer`·`auto`·`consensus`)가 자동으로 물려받는다. 안 넘기고 시트가
필요한 단계를 부르면 **중단**된다(2026-08-14 이전엔 `sheets.keyword_default`, 즉 **다른 그룹
시트로 조용히 폴백**해서 `--ids` 가 0건 매칭으로 죽었다 — 3-2 재교정에서 실제로 밟았다).
`--sheet` 를 다시 주면 그 값이 이기고 run_meta 도 갱신된다.

`auto` 를 쪼개 쓰려면 `merge` / `finish` / `steer` 를 따로 부른다(같은 동작).
`finish`·`auto` 의 `--overwrite-done` = 시트에 이미 `저장완료` 인 행까지 덮어쓴다(기본은 보호).
**회귀 테스트**: `.venv/bin/python .claude/skills/bulsaja-category-fix/scripts/test_run_all.py`
— `run_all.py` 의 batch/merge/steer 계산부와 `apply` 원장 보호(`rows_to_skip`·`is_already_correct`)를
손대면 이걸 먼저 돌린다. (`bulsaja_mcp` 를 import 하므로 시스템 python 말고 `.venv`.)
**run-dir = `<데이터루트>/category-fix/runs/<이름>`** (`workspace.toml [paths].category_fix_runs`.
그룹당 썸네일 ~1000장이라 스킬 폴더에 두면 git 레포가 부푼다).

**현황판** — 저장이 끝나면 그룹 시트 `00_진행` 탭의 **카테고리 열만** 갱신한다
(`eroomlib/matrix.py`). 상세 로그는 지금처럼 시트1에 남는다. 현황판은 파생본이라
어긋나면 `python .claude/lib/eroomlib/matrix.py rebuild --sheet <id> --group <그룹>` 로 다시 만든다.
스킬 공통 규칙은 [`_shared/스킬-계약.md`](../_shared/스킬-계약.md).

**공용 스냅샷** — `workdata`·썸네일은 상품id 기준 캐시(`eroomlib/snapshot.py`)를 먼저 본다.
상품명 스킬이 이미 받아둔 상품이면 조회 0회. 무시하려면 `prep --refresh`.
카테고리를 저장하면 **저장한 쪽이 스냅샷의 `기존카테고리`만 되쓴다** → 다른 스킬이 옛 값을
읽는 일이 없고 TTL·재조회가 필요 없다. 규칙 전문은 `snapshot.py` 모듈 docstring 1곳.

**★키워드 규율(파일럿 교훈)**: 상품 고유 명사를 넓은 category성 단어로 바꾸지 말 것. 분야
한정어만 '추가'한다. (오답 예: 침대안전바→"보행보조기", 조바이스→"바이스클램프".)

**리스크**: 확신도 100%여도 키워드가 상품을 잘못 대표하면 **확신에 찬 오답**. 확신도는

**검색어↔상품명(필요시 썸네일)** 을 대조한다. 대분류변경(I열)도 오답 신호가 아니다.

## 제외카테고리 상품 게이트 (2026-08-09)

블랙리스트 `제외카테고리` 조각에 걸리는 상품은 가공 대상이 아니라 **삭제 대상**이다

(§76)라 **이미 교정이 끝난 재고는 그룹을 다시 돌려도 게이트를 다시 지나지 않는다.**

| | 대상 | 형태 |
|---|---|---|
| 게이트 | 앞으로 교정될 것·재교정될 것 | catfix 저장부에 붙박이 — **자동, 켤 것 없음** |
| 스캔 | 이미 교정이 끝난 재고 | `scripts/category_gate.py scan` 1회 실행 |

### 붙박이 게이트 — 자동으로 도는 것 (건드릴 일 없음)

**판정·표시·큐 규칙은 스캔과 같은 코드다**(`category_gate.gate_records`). 저장이 일어나는
자리 두 곳에서 저절로 돈다 — 메인이 따로 부를 명령이 없다.

| 자리 | 잡는 것 | 왜 거기 |
|---|---|---|
| `bulsaja_mcp.py` apply — **decisions 루프 출구**(현황판 쓰는 자리) | `자동저장완료` · `이미정확` | `이미정확` 은 **저장을 하지 않는다**(§Step 6). 저장 직후에 달면 그 건이 통째로 빠진다 |
| `category_steer.py` — **저장 직후**(스크립트 안) | 유도(1단계) · consensus · **근접(3단계)** | 근접 저장은 Claude 가 이 스크립트를 `--input` 으로 직접 부른다. `run_all` 쪽에 달면 그 경로가 통과한다 |
| `run_all.py prep` — 런 시작 | 지난 런의 **미삭제 잔여**(`삭제대기`) | 삭제 잠금은 일시적이라 다시 치면 대개 성공. 큐를 다시 만들고 **이번 대상에서 뺀다** |

- **태우는 건 확정분뿐**(`CATFIX_DONE`). 의심 건(`매칭불가`·`부분일치확인요`·`보류(정체불명)`·
  `변경대상`)은 삭제하지 않는다 — 재교정에서 확정되면 그때 걸린다(스스로 풀린다).
- **게이트는 재작업 플래그 앞에 선다.** 제외 대상이면 `재작업(카테고리: …)` 을 찍지 않는다
  (찍으면 `pending` 이 다시 집어가 막으려던 상품명 비용이 그대로 나간다).
- 걸린 건은 현황판 뒤 7열이 `삭제대기(제외카테고리)` 가 되고 **삭제 큐가 run-dir 아래
  `gate/` 에 쌓인다**(`gate/delete_queue.json`). **여기서 비용 차단은 끝난다.**
- **실제 삭제도 자동이다 (2026-08-11 이룸님: "삭제대기건은 나에게 묻지 말고 삭제한다").**
  `run_all.py auto` 의 출구가 `category_gate.auto_delete()` 를 부른다 — 메인이 큐를 보고
  판단하던 자리가 없어졌다. 승인을 묻지 않는다. 종합보고에 삭제 목록(상품id·상품명·
  카테고리·걸린 조각)과 **근접저장 구분 표기**를 싣는다.
  끄려면 `--no-autodelete`(그러면 예전처럼 `삭제대기` 로만 남는다).
- 블랙리스트를 못 읽는 등 게이트가 실패해도 **저장·교정은 그대로 간다**(경고만). 이미 저장이
  끝난 뒤라 죽이면 잃는 게 더 크고, 놓친 건은 `scan` 이 나중에 훑는다.
- 끄려면 각 명령에 `--no-gate`(검증·재현용).

```bash
# `auto` 가 끝에 이걸 자동으로 부른다. 손으로 다시 돌릴 때만 쓰는 명령:
python .claude/skills/bulsaja-category-fix/scripts/category_gate.py autodelete \
  --run-dir <R>/gate [--rounds 3] [--wait 180]
#   = delete(--yes --resume) → finalize → 잔여 재큐 를 라운드로 반복
```

**왜 라운드인가**: 서버 대기열이 병목이라 한 번에 다 안 넘어간다(§아래). `미접수`·`미확정`
은 상품 문제가 아니라 대기열이 그때까지 안 돈 것이라, 기다렸다 다시 내면 넘어간다.
라운드 2부터는 `<gate>/retryN/` 에 새 큐를 깔고 돈다 — 같은 자리에서 다시 돌리면
`delete_progress.jsonl` 배치키가 겹쳐 `--resume` 이 전부 건너뛴다.
`잠금` 사유는 스킬이 못 푸는 것이라 재큐에서 뺀다. 끝까지 남은 건 `삭제대기` 그대로
두고(비용 0) 다음 런의 `prep` 이 다시 잡는다.

> **`category_steer.py` 가 현황판을 안 쓰던 버그도 이때 고쳤다**(2026-08-09). 현황판 쓰기가
> `run_all.py _post_steer_matrix` 에 있어서, 근접 저장분은 시트1 I열에만 남고 `00_진행`
> 카테고리 열이 비어 있었다. 이제 저장하는 자리(`category_steer.post_matrix`)가 카테고리
> 완료·게이트·상품명 재작업을 한꺼번에 처리하고, `run_all` 은 결과만 읽는다.

### 재고 스캔 — 1회 명령

```bash
python .claude/skills/bulsaja-category-fix/scripts/category_gate.py scan   # 읽기만
python ... apply --run-dir <R> --yes      # 현황판 7열 `삭제대기(제외카테고리)` + 삭제 큐
python ... autodelete --run-dir <R>       # delete→finalize→재큐 라운드 (권장·묻지 않음)
python ... delete --run-dir <R> --yes --resume   # 1회 삭제만(스크립트가 MCP 직접 호출)
python ... finalize --run-dir <R>         # 성공분만 `상품삭제(제외카테고리·자동)` 로 승격
python ... retry                          # 현황판의 `삭제대기` 잔여분으로 큐 재생성
python scripts/gate_request_sheet.py --run-dir <R>   # 불사자 일괄 처리 요청 시트 1장
```

### 삭제는 서버 대기열이 병목이다 (2026-08-09 실측)

**대기열은 한 번에 한 건씩 처리한다.** 한 그룹 293건을 넣었더니 대기 148건이 쌓이고
이후 제출이 `삭제 작업 원자적 생성 실패로 전체 그룹 미접수` 로 반려됐다(재제출 배치를
50→10건으로 줄여도 155/293이 여전히 미접수 — **배치 크기 문제가 아니라 대기열 포화**다).
접수된 64건은 5분(8회 조회) 동안 하나도 확정되지 않았다.
→ **수천 건 규모는 이 경로로 못 넘긴다.** `gate_request_sheet.py` 로 요청 시트를 만들어
불사자에 일괄 처리를 요청한다. 급하지 않다 — 비용 차단은 `apply` 에서 이미 끝났다.

**`delete` 가 읽는 응답 5종** — `market_delete` 결과는 **상품 단위**로 온다.

| 응답 | 뜻 | 처리 |
|---|---|---|
| `삭제 대기열 접수됨` + 작업번호 | **접수일 뿐 성공이 아니다** | 작업번호로 사후 확정(폴링) |
| `원자적 생성 실패로 전체 그룹 미접수` | 대기열 포화 | 더 작은 배치로 재제출 |
| `업로드된 마켓이 없고 이미 휴지통인 상품` | **이미 지워져 있다** | **성공으로 센다** |
| `잠금된 상품은 삭제 불가` | 이룸님이 앱에서 건 잠금 | 스킬이 못 푼다 |
| 그 밖 | — | 사유 그대로 실패 |

**접수 ≠ 성공.** 실측: 접수 3건 중 1건이 실패해 삭제복구 대기열로 갔고(`PRODUCT_TRASHED`),
198건을 60초 뒤 한 번 조회했더니 성공 0·대기 30·조회에 안 잡힘 168이었다. 한 번 보고
끝내면 **전부 실패로 기록된다** → `성공`·`실패` 만 종결로 보고 나머지는 다시 조회한다.
끝까지 안 잡히면 `미확정` 으로 남긴다(`삭제대기` 유지 = 비용 0, 재실행이 다시 확인).

배치 결과는 `delete_progress.jsonl` 에 **즉시** 한 줄씩 쌓는다 — 삭제는 되돌리기 어려운
방향이라 "어디까지 했나"를 메모리에만 두지 않는다. `--resume` 이 거기서 이어받는다.

- **모집단은 시트1**(원장). 확정 카테고리 = D열, 비면 C열. 불사자 MCP 호출 0회.
- **태우는 상태 = `CATFIX_DONE` 3종 + 구버전 확정 2종** — 의심 건은 삭제하지 않는다.
  재교정에서 확정되면 그때 걸린다(스스로 풀린다). **근접저장은 확정으로 보고 삭제하되 구분 표기.**

  | 구버전 상태 | 건수 | D열이 저장값인가 | 게이트가 보는 열 |
  |---|---|---|---|
  | `근사매칭저장` | 201 | **예**(스냅샷 대조 확인) — `저장완료`+I열 `근접저장` 의 구버전 표기 | D · **근접 구분 표기** |
  | `기존유지` | 29 | **아니오** — D는 기각된 후보(E열 `(근사후보)…`, 확신도 빈칸) | **C** |
  | `현행유지(…)` | 16 | 아니오 — D가 `(현행유지)` 리터럴 | 태우지 않음(C로 폴백만) |

  이 세 값은 **현재 코드 어디에도 없다**(grep 0건). 구버전 그룹에만 남아 있다.
  `기존유지` 를 D로 읽으면 20건이 걸리지만 그건 안 쓴 후보를 판정한 것이고, C로는 1건이다.
- **찍는 건 뒤 7개 열**(`상품명`~`업로드`). `카테고리` 는 실제로 확정된 사실이라 `완료` 유지.
  `matrix.pending` 이 빈칸만 고르므로 **표시만으로 상품명·옵션·썸네일 비용이 0**이 된다 —
  삭제가 잠금으로 늦어져도 다음 단계는 기다릴 필요가 없다.
- **`삭제대기` 를 빈칸으로 되돌리지 않는다.** 빈칸을 보는 건 게이트가 아니라 일반 스킬들이라
  되돌리는 순간 막으려던 비용이 그대로 나간다. 잡는 주체는 `retry` 다.
- 판정 1벌은 `eroomlib/exclusion.py` — 매칭 규칙이 `sellerlife-keyword/detect.py` 와 같다
  (부분일치·정규화 없음). 설계 정본은 `00-system/04-specs/2026-08-09-제외카테고리-재고스캔-design.md`.
- **회귀 테스트**: `.venv/bin/python .claude/skills/bulsaja-category-fix/scripts/test_category_gate.py`
  — 게이트·스캔 공용 판정부(`gate_select`·`already_gone`·`_make_queue`·현황판 캐시 동기화)를
  손대면 이걸 먼저 돌린다.

  | I열 값 | 의미 |
  |---|---|
  | (빈칸) | 조회 정확일치 자동저장 — 정규 경로 |
  | `consensus(2/3)` | 확신도 <70에서 검색어 변형 합의로 확정(§검색어 변형 consensus) |
