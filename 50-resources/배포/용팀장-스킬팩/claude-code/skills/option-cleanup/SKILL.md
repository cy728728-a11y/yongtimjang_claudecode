# 옵션 정리

> ⚠️ **매출 직결 작업이다.** **무엇을 팔고 무엇을 내리고 어느 가격을 대표로 세우나**를 바꾼다.
> 3개 스킬 중 **가장 마지막에, 가장 천천히** 한다. 처음엔 1~3건으로 시작한다.

## 왜 필요한가

수집된 상품의 옵션에는 **파는 물건이 아닌 행**이 섞여 있다 — 구매금지 안내, 사이즈표,
보증금·추가금, 부속품 단독, 다른 모델, "맞춤제작 고객센터 문의".
그대로 올리면 고객이 엉뚱한 걸 주문하고, 대표가격이 왜곡되고, 옵션명이 중국어·접두사로 남는다.

## Workflow

### Step 1. 대상 확인

- 마켓그룹 또는 상품 ID — `bulsaja_market_groups` / `bulsaja_product_list`
- **처음엔 1~3건.** 결과를 눈으로 확인하고 늘린다

### Step 2. 상품·옵션 정보 수집

각 `productId` → `bulsaja_product_workdata(mode="full")`:
- 옵션 목록: **판매행 id · 옵션값 · 중국어 원문 · 한국어 표시명 · 판매가 · 재고**
- 옵션 이미지 (`uploadSkus[].urlRef`)
- 대표 썸네일
- 옵션 차원 구조 (단일 차원인가, 복합 옵션인가)

### Step 3. 판단

**규칙 정본: [`references/옵션명-규칙.md`](references/옵션명-규칙.md)** — 그대로 따른다.

판단할 것은 **세 가지뿐**이다:
1. **메인상품이 무엇인가** — 이 상품이 결국 파는 물건
2. **어느 행이 비상품인가** — 제외 8분류에 해당하는가 (사유를 반드시 적는다)
3. **이름을 뭐라 지을까** — 중국어 원문 기준, 25자 이내, 서로 겹치지 않게

**계산은 규칙대로 한다** (대표·1.5배 상한·순서):
1. 메인상품이면서 **팔 수 있는**(가격·재고 있는) 행만 후보
2. **최저가가 대표.** 동률이면 대표 썸네일과 가장 닮은 것
3. **대표가 × 1.5 = 판매 상한.** 초과는 판매 제외
4. **판매가 오름차순 = 업로드 순서.** 대표는 동가 그룹 안에서 맨 앞
5. **1.5배 상한은 메인상품 후보를 확정한 뒤에만.**
   부속품이 섞인 채 계산하면 기준가가 500원이 되어 **본품이 전멸한다**

**대표옵션 이름 끝에 ` 기본형` 을 붙인다** (규칙 17).
상품명 끝에도 같은 `기본형` 이 붙어서 짝을 지목한다.

### Step 4. 검수표 제시 → 승인

**저장 전에 반드시 아래 3개 표를 보여준다.**

**① 옵션명 교정표**

| 판매행 | 중국어 원문 | 기존 한국어 | 교정 후 | 글자수 |
|---|---|---|---|---|

**② 판매 계획표** (판매가 오름차순)

| 순서 | 옵션명 | 판매가 | 대표 | 판매 |
|---|---|---|---|---|
| 1 | 검정색 기본형 | 24,000 | ★ | O |
| 2 | 주황색 | 24,000 | | O |
| … | | | | |

기준가 · 상한(기준가×1.5) · 유지 N건 / 제외 M건을 표 아래 명시한다.

**③ 제외 사유표**

| 옵션 | 판매가 | 제외 사유 |
|---|---|---|
| 맞춤제작 문의 | 1,000 | 실제 수령품 확인 불가 |
| 사이즈표 참고 | 100 | 사이즈표만 있는 행 |
| 60,000원 5단 | 60,000 | 상한(36,000) 초과 |

### Step 5. 저장 — 2단계로 나눠서

불사자는 **이름 변경과 순서 변경을 같은 호출에 넣는 것을 거부한다**
(쿠팡 기존 옵션 연결 보호). 그래서 순서가 정해져 있다:

```
① 옵션명(renameValues) 만 저장 → 재조회 → 이름 검증
② 판매 포함/제외 + 대표옵션 + 순서 저장 → 재조회 → 검증
```

**이름을 바꾸는 대상은 옵션값(차원)이지 판매행이 아니다.**
복합 옵션이면 옵션값 id가 **차원마다 1부터 다시 시작**하므로,
반드시 어느 차원인지 함께 지정한다. 안 그러면 **엉뚱한 차원이 바뀐다.**

**최종 검증 7항목** (하나라도 실패하면 '완료'라고 하지 않는다):
1. 옵션 수 불변
2. 대표가 정확히 1개이며 판매에 포함돼 있음
3. 포함/제외가 계획과 일치
4. 상한 초과가 살아있지 않음
5. 판매가 무단 변경 없음
6. 표시명 중복 0
7. **`기본형` 이 대표 값 하나에만 붙어 있음**

### Step 6. 기록 (로컬 CSV)

`옵션정리_기록.csv` 에 append 한다. 헤더:
```
상품id,작업일,메인상품,유지수,제외수,대표옵션명,기준가,판매상한,옵션명변경,제외사유,상태,이관,메모
```

- **순서·제외·대표는 id가 아니라 이름으로 적는다.** `1 > 2 > 13` 은 사람이 승인할 수 없다
- **되돌리기용 백업**: 저장 **직전에** 원래 옵션 상태를 `옵션백업_<상품id>.json` 으로 남긴다.
  이게 유일한 원본이다
- 같은 상품을 다시 처리하면 **기존 행을 갱신**한다(옛 계획을 남기지 않는다)

## 옵션 범위 밖 문제는 넘긴다 — `이관`

옵션 작업 중 발견한 **다른 단계의 문제**는 `이관` 열에 적는다.
메모에만 적으면 유실된다 (파일럿 5건 중 3건이 그랬다).

| 발견한 것 | 이관 대상 |
|---|---|
| 대표 썸네일이 검정인데 옵션에 검정이 없음 | 썸네일 |
| 상품명이 원문과 다름 (8인치인데 '10인치') | 상품명 |
| 카테고리가 실물과 안 맞음 | 카테고리 |

## 불사자 저장 ≠ 마켓 반영

**저장은 불사자 서버의 상품 데이터만 바꾼다.**
이미 마켓에 올라간 상품이면 **판매 화면은 그대로다** — 수정 업로드를 따로 해야 반영된다.

- **미업로드 상품이면** 나중에 올릴 때 정리된 상태로 올라간다 (= 정리하기 가장 안전한 타이밍)
- 업로드 여부는 `workdata` 의 `uploadedSuccessUrl` 이 마켓별로 값을 갖는지로 본다
  (dict 자체는 항상 있으니 **값이 전부 null인지**를 봐야 한다)

## 보류 상태

| 상태 | 조건 |
|---|---|
| `보류(기본형 수동판단)` | 복합옵션의 마지막 차원 값이 1개뿐 → 규칙대로 붙이면 전면 오염 |
| `보류(메인불명)` | 무엇이 메인상품인지 판별 불가 |
| `보류(대표동률)` | 최저가 동률인데 썸네일로도 구분 불가 |

보류 건은 **저장하지 않고** 사용자에게 목록으로 보고한다.
