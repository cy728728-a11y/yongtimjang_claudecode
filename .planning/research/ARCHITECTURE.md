**Domain:** 검증된 Python CLI 3종을 감싸는 로컬 단독 웹 관제탑 (브라운필드 래퍼)
**Researched:** 2026-09-19
**Confidence:** HIGH — 결론 대부분을 이 맥북에서 **실제 코드 실행·MCP 조회로 실측**했다. 추정으로 남긴 곳은 그 자리에 명시했다.

### 1.2 Component Responsibilities

| # | 컴포넌트 | 소유하는 것 | 절대 하지 않는 것 |
|---|---|---|---|
| ① | **보드 투영기** | run-dir 산출물(JSON) → 화면 행. 정렬·필터·배지 | 판정 재계산. 마진·CTR·규칙 임계값을 다시 세지 않는다 |
| ② | **엔티티 해소기** | `mallProductId ↔ productId` 링크표의 생성·신선도·미해상 목록 | 추측 매칭 저장. 확정 근거(`uploadedSuccessUrl.smartstore` 일치) 없으면 **미해상으로 남긴다** |
| ③ | **잡 러너** | subprocess 기동·환경주입·로그파일·종료코드·취소·잡 락 | 업무 판단. 무엇을 실행할지는 사람이 미리보기를 보고 정한다 |
| ④ | **불사자 읽기 게이트웨이** | workdata / product_list / traffic_analytics / market_group_products **읽기 호출**과 그 캐시 | **쓰기 도구 호출 금지.** generate·update·copy·delete 는 전부 ③을 거쳐 CLI 가 부른다 |
| — | run-dir 리더 | 회차 목록·산출물 파싱·스키마 버전 대응 | 산출물 수정 |
| — | 상품 캐시 | productId 단위 상태 스냅샷 + 링크표 + 신선도(TTL/세대) | 진실의 원천 행세. 서버 플래그가 정본 |
| — | 잡 레지스트리 | 잡 수명주기·PID·고아 탐지·승인 로그 | 재개 상태 보관 — 그건 run-dir 체크포인트 소유다 |

**경계의 한 줄 규칙:** 읽기는 ④가 직접 MCP 를 때려도 되고, **쓰기는 ③을 통해 CLI 만** 한다. 이 선을 지키면 "검증된 가드레일을 우회했다" 는 사고가 구조적으로 불가능해진다.

## 2. Recommended Project Structure

```
webapp/                          # 새 디렉터리. 기존 .claude/skills 는 건드리지 않는다
├── app.py                       # FastAPI 앱 조립 + 라우터 등록만
├── config.py                    # eroomlib.config.cfg 위에 웹앱 전용 설정을 얹는 얇은 층
├── adapters/                    # ← 기존 CLI 와 맞닿는 유일한 곳
│   ├── cli_spec.py              # 커맨드 카탈로그: argv 조립 · dry/commit 여부 · 락 자원명
│   ├── runner.py                # Popen · env 주입 · 로그파일 · 종료감시 · 취소
│   └── rundir.py                # run-dir 명명·탐색·산출물 파싱 (읽기 전용)
├── domain/
│   ├── resolve.py               # 엔티티 해소 — 3전략 + 확정 근거 검사
│   ├── detail_state.py          # 🔴/🟡/⚪ 판정 (정규화 포함, §6.2)
│   └── board.py                 # run-dir + 캐시 → 보드 행 조립
├── gateway/
│   └── bulsaja_read.py          # eroomlib.bulsaja.BulsajaMCP 상속. 읽기 도구만 노출
├── store/
│   ├── schema.sql               # jobs / job_locks / product_cache / ad_link / approvals
│   └── db.py
├── routers/                     # board / jobs / previews / stream / admin
├── templates/                   # Jinja2
└── tests/
    ├── test_cli_spec.py         # argv 조립이 SKILL.md 의 명령과 글자 단위로 같은가
    ├── test_resolve.py          # 확정 근거 없는 매칭을 저장하지 않는가
    └── fixtures/                # 실제 run-dir 산출물 축소본
```

### Structure Rationale

- **`adapters/` 를 한 겹으로 격리한 이유:** CLI 가 바뀌면(서브커맨드 추가, 플래그 변경) 고칠 파일이 `cli_spec.py` 하나다. 라우터 여기저기에 `subprocess.run([...])` 가 흩어지면 `--commit` 을 빠뜨린 경로가 언젠가 생긴다.
- **`webapp/` 을 `.claude/skills/` 밖에 둔 이유:** 스킬 디렉터리는 Claude 가 자동 로드하는 공간이다. 웹앱 파일이 섞이면 스킬 설명이 오염되고, 수강생 배포판(`bulsaja-kit`) 분리선도 흐려진다.
- **`domain/` 에 규칙이 아니라 *조립*만 두는 이유:** 판정 규칙(6규칙·마진공식·게이트)은 전부 CLI 쪽 `ads_rules.py` / `coupang_rules.py` 소유다. `domain/` 은 이미 판정된 값을 화면 모양으로 바꾸고, **CLI 가 아직 하지 않는 일(상태 3단계 판정, 엔티티 해소)만** 새로 갖는다.

## 3. 읽기/쓰기 분리 — 이 시스템의 척추

### 3.1 세 개의 통로

```
읽기(자유)      run-dir 파일          → 제한 없음. 파일시스템이다
읽기(측정됨)    불사자 MCP 읽기 도구   → 게이트웨이 통과. 캐시 우선. 호출량 계측
쓰기(좁은 문)   CLI subprocess only   → 미리보기(dry) → 사람 확인 → --commit
```

### 3.2 쓰기 3단 계약 (PROJECT.md 자동화 진화 경로가 요구하는 구조)

모든 쓰기 버튼은 **같은 argv 를 두 번 실행**한다. 플래그 하나만 다르다.

```
1단계 판정   CLI 가 이미 만든 판정 산출물을 읽는다        (result.json / gate.json)
2단계 미리보기 같은 argv + dry-run   → stdout·산출물을 화면에 띄운다
3단계 실행    같은 argv + --commit  → 잡 러너가 돌린다
```

**왜 argv 를 재조립하지 않고 재사용하나:** 미리보기와 실행이 다른 argv 를 쓰면 "본 것과 다른 게 나갈" 수 있다. 미리보기 시점의 argv 를 잡 레코드에 저장하고, 실행은 거기에 `--commit` 만 덧붙인다. 2단계 자동화(전부 실행)와 3단계(스케줄)는 **사람 확인만 빠지고 경로는 동일**해야 한다 — 새 경로를 만들면 그 경로만 검증이 안 된 채 무인으로 돈다.

| 버튼 | 미리보기 명령 | 실행 명령 | 되돌리기 |
|---|---|---|---|
| 입찰가 인상 | `run_ads.py bids` | `bids --commit` | `bids --revert --commit` (before_bids 백업) |
| 꺼진 소재 정리 | `run_ads.py prune` | `prune --commit` | 없음 — 삭제는 비가역. 백업 JSON 만 남는다 |
| 상세페이지 | `detail_batch.py --submit-only` 견적 | `--run-dir X --pages N` | 없음 — 크레딧 소모. 견적이 유일한 방어 |
| 썸네일 교체 | (썸네일 스킬 dry) | commit | `thumbnail-done` 기준 |
| 쿠팡 복사 | `run_coupang.py apply` | `apply --commit --limit N` | 잠금 해제 후 삭제 (승계되므로 번거롭다) |

**비가역 3종(prune / 크레딧 접수 / 쿠팡 apply)은 화면에서 시각적으로 다른 색이어야 한다.** 되돌릴 수 있는 것과 같은 버튼처럼 보이면 3단계 자동화에서 섞여 나간다.

## 4. 엔티티 해소 — 이 프로젝트 최대 아키텍처 리스크

### 4.1 먼저: 조인이 정말 필요한 곳은 두 군데뿐이다

이 리스크의 절반은 "전부 조인해야 한다"는 잘못된 전제에서 온다. 실제로는 이렇다.

| 버튼 / 화면 | 필요한 키스페이스 | 조인 필요? | 근거 |
|---|---|---|---|
| 입찰가 인상 (규칙①) | 광고 `adId` 만 | **아니오** | `bids.py` 가 adId 로 쓰고 adId 로 되돌린다 |
| 꺼진 소재 정리 (규칙⑥) | 광고 `adId` 만 | **아니오** | `prune.py` 가 adId 로 삭제·백업 |
| 쿠팡 복사 | `판매자상품코드 → productId` | **아니오** | `bulsaja_product_find_by_code` 가 직접 푼다 (50개/콜) |
| 광고 성과를 상품 행에 붙이기 | 광고 ↔ 불사자 | **예** | ← 리스크 |
| 썸네일 교체 (규칙②, CTR 근거) | 광고 ↔ 불사자 | **예** | ← 리스크 |
| 상세페이지 대상 선별 | 유입 + 상세상태 | **조건부** | 유입 소스를 무엇으로 잡느냐에 달렸다 (§4.5) |

> **설계 함의:** 조인 실패가 시스템 전체를 멈추면 안 된다. 조인이 0% 성공해도 입찰·정리·쿠팡 버튼은 정상 동작해야 한다. 보드를 **"광고 행"과 "상품 행" 두 뷰로 나누고, 조인은 둘을 잇는 선택적 열**로 두는 이유다.

### 4.2 키 지도 — 실측 기반

| From → To | 메커니즘 | 실측 비용 | 신뢰도 | 함정 |
|---|---|---|---|---|
| `adId` → `mallProductId` | `ads.json` 의 `referenceData.mallProductId` | 0 (run-dir 에 이미 있다) | 높음 | **검수 APPROVED 전엔 없다.** ownway1 게재중 1,360 중 988이 미보유 |
| `mallProductId` → `productId` | **역방향 조회 도구가 없다.** 후보를 좁힌 뒤 `workdata.uploadedSuccessUrl.smartstore` 로 1:1 확정 | 건당 **1~4초** | 확정되면 절대적 | **20일 물갈이로 소멸** (§4.3) |
| `판매자상품코드` → `productId` | `bulsaja_product_find_by_code(codes[≤50])` | 50건/~1초 | 높음 | 사본마다 고유. base64형(`PTk/…`) 11% 는 구조적 제외 |
| `productId` → `불사자코드` | `workdata.uploadBulsajaCode` | 0.18초 | 높음 | **사본 전체가 공유** = 병합 키. 스냅샷 파일의 `불사자코드` **필드**는 이름이 틀렸다(실제로는 판매자상품코드) |
| `productId` → `타오바오상품번호` | `workdata.productNo` | 0.18초 | 높음 | 재수집분이 공유. 쿠팡 중복 대조 키 |
| `productId` → 유입수 | `bulsaja_traffic_analytics` | 100건/0.8초 | 조인 불필요 | 의미 검증 필요 (§4.5) |
| `productId` → 상세 상태 | `workdata.uploadDetailContents` | 0.18초 | 높음 | 타입이 3종 (§6.2) |

**실측 확인(2026-09-19, 부킹=용쌤 계정):**
- `bulsaja_product_find_by_code(["11336386490"])` → `개수: 0`, `못찾은코드` 반환. **채널상품ID로는 못 찾는다.**
- `bulsaja_product_list(keyword="11336386490")` → `구분: "상품명 검색"`, 0건. **통합검색도 채널상품ID를 안 잡는다.**
- `workdata.uploadedSuccessUrl` 실구조 = `{"coupang":null,"st11":null,"gmarket":null,"smartstore":"13754777176","auction":null}`. 필드 존재 확정.

### 4.3 ★ 가장 중요한 발견 — 다리가 20일마다 썩는다

물갈이(20일 주기 삭제 → 재업로드)를 돌면 스마트스토어가 **새 채널상품ID를 발급**한다. 광고 소재에 박힌 `mallProductId` 는 옛 ID 그대로 남는다. 즉 **링크표는 시간이 지나면 조용히 전부 틀린 게 아니라 조용히 전부 비게 된다.**

**실측 증거 (2026-09-19):**

```
불사자 그룹 4번_용쌤4-1 (971건 중 160건 조회)
  현 채널상품ID 범위 : 13,754,777,133 ~ 13,754,778,922   ← 최근 재업로드분, 연속 번호
광고 pogeunae / 판매상품_4-1_서이서하컴퍼니 (소재 44건)
  mallProductId 범위 : 11,254,381,731 ~ 11,3xx,xxx,xxx    ← 물갈이 이전 세대
교집합 : 0 / 160
pogeunae 전체 1,389 소재 대비 교집합 : 0 / 160
```

같은 계정 안에서도 세대가 섞인다 — pogeunae 의 mallProductId 중앙값은 13,705,480,236(최신 세대)인데 4-1 광고그룹만 11.2B 대(옛 세대)다. 즉 **"광고에 소재를 새로 안 넣은 그룹"이 통째로 조인 불능**이다. 이건 이미 알려진 운영 사실과 정확히 맞물린다: *"물갈이 재업로드 뒤 광고에 소재를 새로 넣는 일은 아직 사람이 한다"*(naver-ads-weekly SKILL.md, 2026-08-30 실측).

**아키텍처 대응 4가지:**

1. **링크표에 세대(generation)를 박는다.** `(mallProductId, productId, 확정시각, 확정근거, 광고run, 불사자조회시각)`. 20일 넘은 링크는 **만료로 표시**하고 재확정 대상 큐에 넣는다. 삭제하지 않는다 — 과거 작업 이력의 근거다.
2. **조인은 같은 시간창 안에서만 한다.** 광고 `prep` 과 불사자 인덱싱 사이가 벌어지면 매칭률이 떨어진다. 보드에 **"광고 수집 시각 / 불사자 조회 시각 / 시차"** 를 항상 띄운다.
3. **미해상은 에러가 아니라 1급 상태다.** `해상 / 미해상(후보없음) / 미해상(검수대기라 mallProductId 없음) / 만료` 4상태를 화면에 세고, 숫자가 나빠지면 그게 "광고에 소재를 새로 넣어야 한다"는 운영 신호다. **조용히 빠뜨리면 작업 대상이 소리 없이 줄어든다.**
4. **틀린 매칭 > 없는 매칭.** 확정 근거(`uploadedSuccessUrl.smartstore` 완전 일치) 없이는 저장하지 않는다. 상품명 유사도·그룹 일치는 **후보 좁히기 용도일 뿐 확정 근거가 아니다.** 엉뚱한 상품에 크레딧을 태우거나 마켓에 수정업로드를 날리는 게 여기서 나온다.

### 4.4 해소 전략 3종 — 비싼 순서가 아니라 확정력 순서로

```
[입력] adId + mallProductId + adGroup명 + 소재 title
   │
   ├─ S0. 링크표 조회 (세대 유효)                    0초      → 히트면 끝
   │
   ├─ S1. 제목 검색 확정                              1~4초
   │     product_list(keyword=title 앞 3어절, pageSize=30~50)
   │       → 후보마다 workdata(mode=summary, 0.18초)
   │       → uploadedSuccessUrl.smartstore == mallProductId ?
   │     실측 해상률 5/8 (규칙⑤ 8건, 2026-09-19)
   │
   ├─ S2. 마켓그룹 전수 인덱싱                        그룹당 2~4분
   │     adGroup "판매상품_{N}-{M}_*" → 불사자 "{N}번_용쌤{N}-{M}"  (실측 확인된 규약)
   │     market_group_products 페이징(20건/0.2초) → 각 workdata(0.18초)
   │     → 그룹의 (ss_id → productId) 전체 인덱스를 캐시에 적재
   │     한 번 만들면 그 그룹의 모든 소재가 S0 으로 떨어진다
   │
   └─ S3. 미해상 확정                                 사람에게 보여준다
         "검수대기(mallProductId 없음)" / "물갈이 세대 불일치" / "상품 삭제됨"
```

**S1 → S2 승급 기준:** 한 광고그룹에서 S1 실패가 3건 넘으면 그 그룹을 S2 로 통째 인덱싱한다. 건별로 1~4초씩 20번 헛도는 것보다 그룹을 한 번 훑는 게 싸고, 결과가 재사용된다.

**실측 성능 근거:**

| 호출 | 실측 | 비고 |
|---|---|---|
| `workdata(mode=summary)` | **0.18초/건** (12건 2.1초) | 예상보다 훨씬 싸다. 인덱싱이 현실적인 이유 |
| `market_group_products` 20건 | 0.2초 | 페이징 비용 무시 가능 |
| `product_list(keyword)` 전역 | 1.0초 | 빠르다 |
| `product_list(keyword + marketGroupId)` | **20.2초** ⚠️ | **그룹 필터를 걸면 20배 느려진다. 걸지 마라** |
| 그룹 1개 전수 인덱싱 (971건 추정) | **약 3분** | 0.18×971. 인덱스 수명은 물갈이 주기(20일) |

> 함정 재확인: `product_list` 응답의 `그룹명`·`상태` 는 **null 로 온다**(실측). 그룹 판정에 쓰면 안 된다 — 이미 알려진 "목록 조회의 그룹 필드는 null" 사례와 동일하다.

### 4.5 ★ 두 번째 발견 — 조인을 통째로 우회하는 길이 있다

`bulsaja_traffic_analytics` 가 **productId 로 키잉된 유입수(조회수)** 를 직접 준다. 광고를 거치지 않는다.

**실측(2026-09-19):**
```
bulsaja_traffic_analytics(limit=100)
 → total 37,389 (최근 30일 유입 발생 상품)  ·  100건/0.8초
 → 행: productId · totalViews · marketGroupId · uploadCommonProductName
        · productUrl · uploadedProductDate · lastViewedAt · isZero
 → productId 지정 시 일자별 추이 (0.1초)
```

Core Value 는 *"유입이나 판매가 있는데 상세페이지가 중국어 원본인 상품을 골라 고치는 것"* 이다. 이 정의에 광고는 필수가 아니다.

| 경로 | 유입 근거 | 조인 | 커버리지 | 리스크 |
|---|---|---|---|---|
| **A. 광고 경유** (PROJECT.md 현 계획) | 규칙③ 클릭 20+ | 필요 | 광고 도는 상품만 | 물갈이 세대 불일치로 구멍 |
| **B. 불사자 유입 경유** | `traffic_analytics` totalViews | **불필요** | 유입 발생 37,389건 전체 | 지표 의미 미검증 |
| **C. 판매 경유** | 주문시트 판매자상품코드 | `find_by_code` 로 해결 | 팔린 것 전부 | 없음 — 이미 검증된 경로 |

**권고: v1 은 C + B 를 주 경로로, A 를 보조로 둔다.**
- C(판매)는 이미 `run_coupang.py prep/resolve` 가 만들어 둔 길이다. 공짜다.
- B(유입)는 조인이 0이고 커버리지가 넓다. PROJECT.md 가 *"불사자 MCP 프로필에 유입수·상품 조회 기능이 있다 — 2차 유입 소스 후보"* 라고 적어 둔 바로 그것인데, **실측 결과 2차가 아니라 1차로 쓸 만하다.**
- A(광고)는 규칙③이 주는 "클릭은 있는데 구매 0"이라는 *질 높은* 신호지만, 조인 비용과 세대 리스크를 진다. 썸네일 교체(규칙②)는 어차피 A 가 아니면 근거가 없으니 A 도 결국 필요하다 — 다만 **Core Value 를 A 에 걸지 마라.**

> **⚠️ 남은 검증(1페이즈에서 반드시):** `traffic_analytics` 의 `totalViews` 가 *스마트스토어 실제 조회수*인지 *불사자 내부 조회수*인지 확정되지 않았다. 표본 상위값이 127/108/87 로 작아, 스마트스토어 전체 유입이라기엔 낮아 보인다. **규칙⑤(실제 구매 발생) 상품들의 totalViews 와 대조**하면 1시간 안에 판명된다. 이 검증 결과가 B 경로 채택 여부를 가른다.

## 6. 상태 판정 — 화면의 신뢰도가 여기서 결정된다

### 6.1 판정 규칙 (PROJECT.md 3단계)

### 6.2 ★ 실측 함정 — `imageTranslated` 는 불리언이 아니다

PROJECT.md 는 `"imageTranslated": false` 로 기록해 뒀지만, 실제 응답에서 **세 가지 타입이 섞여 나온다.**

```
실측 2026-09-19 (유입 상위 5건 + 그룹 4-1 표본):
  imgTr='0'    (문자열)
  imgTr='1'    (문자열)
  imgTr=False  (불리언)
  imgTr=1      (정수)
```

`if data["imageTranslated"]:` 로 짜면 **문자열 `'0'` 이 참**이 되어, 중국어 원본 상품이 🟡(작업 불필요)로 분류된다. **Core Value 가 조용히 깨지는 경로가 정확히 이것이다.**

```python
def _참(v):
    """불사자 플래그 정규화 — 0/'0'/False/None/'' 은 전부 거짓."""
    if v is None:
        return False
    if isinstance(v, str):
        return v.strip() not in ("", "0", "false", "False")
    return bool(v)
```

**추가 실측:** 표본 전량(그룹 4-1 160건 + 유입 상위 100건)에서 `aiImageGenerated` 가 **`None`(필드 부재)** 였다. 즉 ⚪ 버킷은 현재 거의 비어 있다 — 작업 여지가 그만큼 크다는 뜻이자, **`.get("aiImageGenerated")` 가 KeyError 가 아니라 None 을 내도록** 반드시 `.get()` 으로 접근해야 한다는 뜻이다.

### 6.3 상세 길이 계산은 추가 호출이 0이다

`uploadDetailContents.renderContent` 는 `<img>` 나열 HTML 이고, 같은 workdata 응답에 들어 있다. 실측 이미지 수 1~24장(표본). PROJECT.md 의 `min(제품이미지 수, 10), 하한 2` 규칙은 **이미 받은 응답을 세기만 하면 된다** — 비전 호출 0, 추가 API 0 이라는 전제가 실측으로 확인됐다.

**이건 "재작성"이 아니라 "진입 shim 이식"이다.** 판정·접수·폴링·체크포인트 로직은 한 줄도 건드리지 않는다. 그러나 **1페이즈 이전에 해결되지 않으면 Core Value 버튼을 만들 수 없다.** 로드맵의 0단계에 명시적으로 넣어야 한다.

### 7.2 호출 규약 표 (실측)

| | `run_ads.py` | `detail_batch.py` | `run_coupang.py` |
|---|---|---|---|
| 인터프리터 | `.venv/bin/python3` (3.12.13) | 동일 | 동일 |
| PYTHONPATH | **불필요** (자체 탐색) | 불필요하나 **경로 깨짐** | **`.claude/lib` 필수** |
| `--run-dir` | 선택 (기본 = 오늘 날짜) | **필수** | **필수** |
| run-dir 루트 | `<data_root>/naver-ads/runs/<이름>` | 호출자가 지정 | `<data_root>/coupang/runs/<이름>` |
| 자격증명 | `~/.eroom/naver-ads.json` (600) | `~/.claude.json` mcpServers.bulsaja | 동일 + gws |
| 계정 전환 | `--account <alias...>` | `run_yong.py` 가 env 주입 | MCP 연결 계정 고정 |
| 종료코드 | `main()` 이 int 반환 (0/1/2) | `sys.exit(1/2)` | 0/2 |
| 진행 출력 | stdout 한국어 평문 | stdout | stdout |
| 취소 | 미정의 — **SIGTERM 안전성 미검증** | 체크포인트 있어 안전 | S6 이전은 전부 읽기전용이라 안전 |

**stdout 파싱 금지.** 한국어 평문이고 형식 보장이 없다. 화면에 **그대로 흘리기만** 하고, 구조화된 결과는 **run-dir 산출물 JSON 에서만** 읽는다. 출력 문구는 언제든 바뀔 수 있지만 산출물 스키마는 다른 소비자가 있어서 안 바뀐다.

**환경변수 주입 패턴은 이미 있다.** `run_yong.py` 가 `~/.claude.json` 에서 토큰을 읽어 `BULSAJA_MCP_URL`/`BULSAJA_MCP_TOKEN` 으로 넣고 `subprocess.run(argv, env=env)` 한다. 웹앱 잡 러너는 **이 패턴을 그대로 채택**한다 — 새 자격증명 저장소를 만들지 않는다.

### 7.3 ⚠️ 계정 라우팅 — 실측된 구멍

```
~/.claude.json mcpServers = ['aside', 'bulsaja']       ← bulsaja-yongssaem 이 없다
bulsaja_my_profile → "부킹님 계정 (clwkdzjavjsl@gmail.com)"
```

이 맥북의 유일한 불사자 연결이 **부킹(=용쌤)** 이다. `run_yong.py` 가 찾는 `bulsaja-yongssaem` 항목은 **존재하지 않는다** — 이 머신에서 계정 전환 경로가 끊겨 있다. 그리고 광고 계정 cy728·cy7728 상품이 부킹 계정 소유라는 사실(2026-08-29 확인)과 합치면, 지금 구성은 우연히 맞아떨어져 있다.

**구조 요구사항:** 보드 상단에 **연결 계정(닉네임·이메일)을 항상 표시**하고, 모든 쓰기 잡은 기동 직전 `bulsaja_my_profile` 로 계정을 확인해 잡 레코드에 박는다. 계정이 바뀌면 락을 계정별로 잡는다. "작업 전 프로필 확인 필수"가 사람 규율이 아니라 **코드 게이트**가 돼야 한다.

## 8. run-dir 모델 — 웹앱은 소유하지 않고 명명·색인한다

### 8.1 소유권

```
run-dir 의 내용물  → CLI 소유. 웹앱은 읽기만
run-dir 의 이름    → 웹앱 소유. 잡 레코드가 이름을 정해 --run-dir 로 넘긴다
run-dir 의 수명    → 사람 소유. 자동 삭제 금지 (§8.3)
```

### 8.2 명명

| 대상 | 현행 기본값 | 웹앱 규약 |
|---|---|---|
| 광고 | 오늘 날짜 `2026-08-30` | **그대로 둔다.** 날짜가 곧 주간 회차다. 같은 날 재수집은 같은 디렉터리에 병합되는 게 현행 동작(`prep_summary.json` 이 merge) |
| 상세 | 지정 필수 | `<data_root>/detail/runs/<YYYYMMDD-HHMM>-<대상수>` |
| 쿠팡 | `$(date +%Y%m%d-%H%M)` | **그대로 둔다** |

**웹앱 전용 run-dir 접두어를 붙이지 마라.** CLI 를 손으로도 계속 돌릴 것이고, 두 경로가 만든 회차가 한 목록에 섞여 보여야 한다. 대신 잡 레코드에 `run_dir` 절대경로를 저장해 역색인을 웹앱이 갖는다.

### 8.3 정리 정책 — 삭제는 위험하다

`coupang-candidates` SKILL.md 가 명시한다: *"`copied.jsonl` 이 유일한 방어선이니 **run-dir 를 지우지 마라.**"*

- **자동 정리 금지.** v1 은 아무것도 지우지 않는다.
- 용량이 문제되면 `accounts/*/stats_*.json` 같은 **재생성 가능한 중간 산출물만** 선택적으로 압축. `copied.jsonl`·`before_bids_*.json`·`detail_status.json` 은 영구 보존.
- 화면에 회차별 용량을 보여주고 **삭제는 사람이 건건** 누른다.

## 9. 장기 작업 수명주기

### 9.1 문제의 크기

`detail_batch.py` 는 접수 → 비동기 생성(**수십 분**) → 45초 간격 폴링 → 자동 반영이다. 브라우저 수명과 완전히 분리돼야 한다.

### 9.2 접수와 폴링을 **두 개의 잡으로 쪼갠다**

CLI 가 이미 그 이음매를 제공한다 — `--submit-only` / `--poll-only`.

```
잡 A  detail_batch --run-dir X --pages N --submit-only     짧다(분)  · 크레딧이 여기서 나간다
      └ 성공 시 detail_status.json 에 taskId 들이 박힌다   ← 재개의 유일한 정본
잡 B  detail_batch --run-dir X --poll-only                 길다(수십 분) · 멱등 · 몇 번이든 재실행 가능
      └ 미완료만 폴링. 끊기면 다시 띄우면 그만
```

**이 분할이 주는 것:**
- 폴링이 죽어도 **크레딧을 다시 태우지 않는다.** 접수는 이미 끝났다.
- 웹앱이 재시작해도 잡 B 를 다시 띄우면 완전 복구된다. 웹앱은 재개 상태를 보관할 필요가 없다 — `detail_status.json` 이 갖고 있다.
- 자동 감시가 구조로 강제된다: 잡 A 성공 시 **잡 B 를 자동 인큐**한다. "감시 없이 띄우지 마라"가 사람 규율이 아니라 상태기계가 된다.

### 9.3 상태 전이

```
queued ──> running ──> succeeded          exit 0
                 ├──> failed              exit != 0
                 ├──> cancelled           사람이 중단 (SIGTERM → 유예 → SIGKILL)
                 └──> orphaned            서버 부팅 시 PID 가 죽어 있음
                          │
                          └─> run-dir 체크포인트를 읽어 "이어서 실행" 버튼 제시
```

**`orphaned` 를 `failed` 와 반드시 구분한다.** 폴링 타임아웃·프로세스 사망을 실패로 보고 재생성하면 **크레딧을 이중 지불**한다(알려진 사고 유형). 고아 잡의 기본 제안은 *재실행*이 아니라 **`--poll-only` 로 이어서 확인**이다.

### 9.4 취소의 진실

| 잡 | 취소 안전한가 | 이유 |
|---|---|---|
| `run_ads prep/run/apply` | 안전 | 광고 API 에 아무것도 쓰지 않는다 |
| `run_ads bids/prune --commit` | **위험** | 중간에 끊기면 일부만 반영. `before_bids` 백업은 남으므로 revert 는 가능 |
| `detail_batch --submit-only` | **위험** | 접수 도중 끊기면 taskId 가 체크포인트에 안 남은 접수가 생긴다 → 크레딧 유실 |
| `detail_batch --poll-only` | 안전 | 멱등 |
| `run_coupang` S0~S5 | 안전 | 전부 읽기 전용 |
| `run_coupang apply --commit` | **위험** | `copied.jsonl` 이 방어선. 배치 20건 단위로만 원자적 |

→ **취소 버튼은 잡 종류에 따라 다른 경고를 띄워야 한다.** 일괄 "중지"는 만들지 마라.

## 10. Data Flow

### 10.1 읽기 경로 (보드 1행이 만들어지기까지)

```
run_ads.py run  ──[파일]──> result.json ──┐
                                          ├──> 보드 투영기 ──> 상품 1행
불사자 MCP ──[캐시]──> product_cache ─────┤                     ├ 상품명·계정·광고성과
                                          │                     ├ 🔴🟡⚪ 상세상태
ad_link (링크표) ─────────────────────────┤                     ├ 유입·판매
                                          │                     ├ 작업이력(잡 레지스트리)
잡 레지스트리 ────────────────────────────┘                     └ 해상상태(해상/미해상/만료)
```

**한 방향이다.** 보드는 아무것도 되쓰지 않는다. 화면이 틀렸다고 느껴지면 **캐시를 비우고 rebuild** 한다 — `matrix.py` 가 *"깨지거나 뒤처지면 rebuild() 로 원장에서 언제든 다시 만든다. 그래서 매트릭스를 믿지 못할 상황 자체가 없다"* 고 쓴 그 원칙이다.

### 10.2 쓰기 경로 (버튼 → 마켓)

```
[버튼 클릭]
   │
   ├─1─> 미리보기 잡 (dry-run)  → run-dir 산출물 → 모달에 렌더
   │       · 대상 건수 · 예상 크레딧 · 비가역 여부 · 연결 계정
   │
   ├─2─> [사람이 확인]  ──> 승인 로그에 append (신호·선택·시각)
   │
   └─3─> 실행 잡 (--commit)  → CLI → 불사자 MCP / 네이버광고 API / 마켓
             │
             └─> 완료 후: 캐시에서 **그 상품의 그 필드만** 무효화
                 (전체 캐시 퍼지 금지 — 재조회 폭풍이 난다)
```

### 10.3 승인 로그를 v1 부터 남기는 이유

`eroomlib.runner.approval_log` 가 이미 이유를 적어 뒀다: *"자동화 전환의 유일한 근거 데이터. 남지 않으면 나중에 정지 조건을 감으로 정하게 된다."*

PROJECT.md 의 2단계(일괄승인) 진입 조건이 **"1단계에서 오판정률이 실측으로 낮게 나올 것"** 이다. 그 실측치는 승인 로그 없이는 만들 수 없다. **v1 에 없으면 2단계는 영원히 감으로만 결정된다.** 스키마는 최소로: `(시각, 버튼, 대상수, 미리보기해시, 선택[승인/수정승인/보류], 사유, 잡id)`.

## 12. Anti-Patterns

### AP1. 판정 로직을 웹앱이 다시 계산한다
**하는 짓:** `ads_rules.py` 나 `coupang_rules.py` 를 import 해 화면에서 마진·CTR 을 재계산.
**왜 틀렸나:** 진실이 둘이 된다. 이 프로젝트는 같은 이유로 *"중복방지용 로컬 대장 신설"* 을 이미 거부했다. 실측에서 단순평균 31.4% vs 가중 11.6% 로 20%p 벌어진 적이 있다 — 공식이 갈라지면 게이트가 무의미해진다.
**대신:** 판정값은 run-dir 산출물에서만 읽는다. 웹앱은 포맷만 바꾼다.

### AP2. 확정 근거 없이 매칭을 저장한다
**하는 짓:** 상품명이 비슷하고 그룹이 맞으니 링크표에 넣는다.
**왜 틀렸나:** 「책꽂이 북 카트」 하나가 4개 마켓그룹에 사본으로 존재한다. 엉뚱한 사본에 크레딧을 태우거나 수정업로드를 날린다.
**대신:** `uploadedSuccessUrl.smartstore == mallProductId` 완전 일치만 확정. 나머지는 **미해상으로 남기고 화면에 센다.**

### AP3. 미해상을 조용히 거른다
**하는 짓:** 조인 실패한 행을 보드에서 뺀다.
**왜 틀렸나:** 작업 대상이 소리 없이 줄어든다. 물갈이 세대 불일치로 **광고그룹 하나가 통째로 사라져도 화면상 아무 일 없어 보인다**(실측 4-1 그룹, 160건 중 교집합 0).
**대신:** 미해상을 배지로 띄우고 사유별로 센다. 숫자가 나빠지면 그게 운영 신호다.

### AP4. stdout 을 파싱해 구조화 데이터를 만든다
**하는 짓:** `"수집 완료 → ..."` 같은 한국어 출력을 정규식으로 긁는다.
**왜 틀렸나:** 형식 보장이 없다. 문구 한 글자 바뀌면 화면이 거짓말한다.
**대신:** stdout 은 로그로만 흘린다. 구조화는 run-dir JSON.

### AP5. 파이프를 SSE 로 직결한다
**하는 짓:** `Popen(stdout=PIPE)` → 브라우저로 바로 흘린다.
**왜 틀렸나:** 브라우저를 닫았다 열면 그 사이 출력이 영영 사라진다. 수십 분짜리 잡에서 치명적이다.
**대신:** 자식 출력을 로그파일로 리다이렉트하고, SSE 는 `Last-Event-ID`(줄번호)부터 재생 후 tail. (상세 구현은 `STACK.md` §핵심결정 3)

### AP6. 폴링 타임아웃을 실패로 보고 재생성한다
**하는 짓:** 잡이 안 끝나니 다시 접수한다.
**왜 틀렸나:** **크레딧 이중 지불.** 접수는 이미 성공했고 서버가 만들고 있을 뿐이다.
**대신:** `orphaned` 상태를 따로 두고, 기본 제안은 `--poll-only` 재개다.

### AP7. 웹앱이 재개 상태를 자기 DB 에 복제한다
**하는 짓:** 어디까지 폴링했는지를 SQLite 에 별도 기록.
**왜 틀렸나:** `detail_status.json` 과 어긋난다. 재개 정본이 둘이 되는 순간 크레딧 사고가 난다.
**대신:** 잡 레지스트리는 **프로세스 수명만** 갖는다. 업무 재개 상태는 run-dir 이 소유한다.

### AP8. 불사자 쓰기 도구를 웹앱이 직접 부른다
**하는 짓:** `eroomlib.bulsaja` 로 `bulsaja_market_group_copy` 를 바로 호출.
**왜 틀렸나:** CLI 안의 게이트(중복 대조·2단계 확인토큰·배치 20건 제한)를 통째로 우회한다.
**대신:** 읽기 도구만 게이트웨이에 노출하고, 쓰기 도구는 **허용 목록에서 물리적으로 뺀다.**

## 14. Scaling Considerations

사용자 1명·로컬 단독이라 전통적 스케일 축은 무의미하다. 실제로 먼저 깨지는 건 **작업 모수**다.

| 규모 | 무엇이 먼저 깨지나 | 대응 |
|---|---|---|
| 현재 (광고 4계정 · 주당 ~120행) | 아무것도 안 깨진다 | 그대로 |
| 광고 6계정 (계획됨) | `prep` 시간이 선형 증가. 규칙① 이 이미 2,242행 (ownway1 1,195 + pogeunae 1,028) | 규칙①은 처음부터 **페이지네이션·가상스크롤**. 보드에 전량 렌더 금지 |
| 링크표 1만 행 | 없음 — SQLite 에 사소한 규모 | — |
| 상세 배치 500건 | 폴링 잡이 몇 시간. 맥북 절전으로 끊긴다 | `caffeinate -i` 로 감싼다(STACK.md) · 잡 분할 |
| 전수 인덱싱 86그룹 | 0.18초 × 수만 건 = 수 시간 | **하지 마라.** 필요한 그룹만 요청 시 인덱싱(S2) |

**첫 번째 병목은 UI 다.** 규칙① 2,242행을 한 테이블에 그리면 화면이 멈춘다. Tabulator 가상 DOM 을 처음부터 켜 둔다.
**두 번째 병목은 불사자 조회 대기.** 해소기가 동기로 돌면 버튼 누른 사람이 20초를 본다 → **해소도 잡으로 돌리고 진행률을 보여준다.**
