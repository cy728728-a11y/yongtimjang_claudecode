## Critical Pitfalls

### Pitfall 1: 엔티티 해소 팬아웃 — "상품 1건"이 실제로는 27건이다

**What goes wrong:**
광고 소재 → 상품을 잇는 순간, **어떤 키로 잇느냐에 따라 대상 집합의 크기가 달라진다.**
`coupang_rules.group_by_bulsaja_code` 의 실측 주석: *"불사자코드는 한 원본에서 복사된 사본 전체가 공유하는 키다(실측: 코드 1개에 사본 27건)."*
보드에서 "이 상품 상세 작업" 버튼을 눌렀는데 뒤에서 27건이 접수되거나, 반대로 광고가 붙어 있는 사본이 아닌 다른 마켓그룹 사본 하나만 고쳐서 **정작 광고 돌던 상품은 그대로 남는다.**

**Why it happens:**
ID 네임스페이스가 최소 6개인데 전부 "상품ID"로 불린다.

| 키 | 어디서 나오나 | 카디널리티 | 함정 |
|---|---|---|---|
| `adId` | 광고 소재 | 소재:상품 = N:1 (한 상품에 소재 여러 개) | |
| `mallProductId` | `referenceData` (= 채널상품ID) | **검수 통과(APPROVED) 전엔 `None`** | ownway1 실측: 게재중 1,360 중 988개가 미보유 |
| `originProductNo` | 커머스API | `channelProductNo` 와 **다른 값** (review-analyzer 주석 실측) | 둘을 같은 걸로 보면 조인이 전량 실패하거나 엉뚱하게 맞는다 |
| `productId` | 불사자 내부 | 사본마다 다름 | |
| `판매자상품코드` | 불사자 | 사본마다 다름 | 스냅샷 파일의 `불사자코드` **필드명이 잘못 붙어 있어 실제 값은 이것** |
| `불사자코드` | 불사자 MCP 응답 | **사본 전체가 공유 (1:N, 실측 27)** | 이걸로 조인하면 팬아웃 |

**How to avoid:**
1. **조인 키를 코드에서 단 하나로 고정한다.** 광고→상품 정본 경로는 `mallProductId(채널상품ID)` → 커머스API → 불사자 `productId` **단일 사본**이다. `불사자코드`는 **중복 방지 판정에만** 쓰고 작업 대상 선정에는 절대 쓰지 않는다.
2. **모든 조인 결과에 카디널리티 단언을 건다.** `assert len(matched) == 1` 이 깨지면 그 행은 실행 대상에서 빼고 `다중매칭` 사유로 보드에 빨간 배지를 띄운다. 조용히 첫 번째를 고르지 않는다.
3. **상품명 문자열 매칭을 폴백으로 쓰지 않는다.** `product-name` 스킬이 상품명을 리네임하고 물갈이가 재업로드한다 — 이름은 정본이 아니다. 매칭 실패는 실패로 남긴다.
4. 보드 각 행에 **매칭 근거(어떤 키로 몇 건 중 무엇을 골랐는지)** 를 접어서 보여준다. dry-run 출력에 이게 없으면 사람이 검증할 방법이 없다.
5. `mallProductId is None` 인 소재(검수중)는 **보드에 올리되 실행 버튼을 비활성**한다. 조용히 드롭하면 "왜 이 상품이 안 보이지"가 된다.

**Warning signs:**
- dry-run 대상 건수가 보드 선택 건수보다 많다 → 이미 팬아웃 중
- `매칭실패` 비율이 30%를 넘는다 → 검수중 소재 비중(ownway1 73%)을 안 거르고 있다는 뜻
- 같은 `불사자코드` 가 실행 대상 목록에 2번 이상 등장

**Phase to address:** **Phase: 엔티티 해소 (광고↔불사자 결합)** — 보드보다 먼저. 여기가 틀리면 뒤 전부가 엉뚱한 상품에 실행된다.

### Pitfall 2: 완료 플래그를 안 찍는 쓰기 경로 — 진실의 원천이 조용히 비게 된다

**What goes wrong:**
PROJECT.md 의 결정: *"중복방지 대장을 새로 만들지 않는다 — 서버 플래그(`aiImageGenerated`/`aiImageOutputCount`)가 정본."*
그런데 같은 문서의 Active 요구는 *"AI 상세 생성의 입력 소스를 `renderContent` 의 기존 상세 이미지로 교체"* 하고 *"생성 완료분을 `market_update` 로 즉시 수정업로드"* 하는 것이다.
**불사자 AI 생성기를 통과하지 않는 반영 경로**(예: `bulsaja-detail-remix` 처럼 직접 스티칭해 `bulsaja_detail_apply` 로 올리는 길)를 쓰는 순간, 상세는 바뀌었는데 `aiImageGenerated` 는 **안 찍힌다.**
결과: 다음 회차 보드가 그 상품을 🔴/🟡 미작업으로 다시 집는다 → 재접수 → 크레딧 재지출 → 또 안 찍힘 → **무한 루프.** 에러는 한 번도 안 난다.

**Why it happens:**
"서버 플래그가 정본"은 **불사자 AI 생성기가 유일한 쓰기 경로일 때만** 참인 명제다. 쓰기 경로가 둘이 되는 순간 전제가 깨지는데, 전제가 깨진 사실이 어디에도 나타나지 않는다.

**How to avoid:**
1. **Phase 0에서 이 질문에 실측으로 답하고 넘어간다**: "우리가 쓸 반영 경로가 `aiImageGenerated` 를 찍는가?" 상품 1건으로 반영 전/후 `uploadDetailContents` 를 덤프해 diff 한다. 추측 금지.
2. 안 찍히면 **선택지는 둘뿐**이고 "나중에 정하자"는 없다:
   - (a) 반영을 반드시 불사자 AI 생성기 경로로만 한다 (플래그 무료로 얻음)
   - (b) 로컬 대장을 **정본이 아니라 "서버 플래그의 보완 인덱스"로** 명시적으로 도입한다. 판정식은 `작업완료 = 서버플래그 OR 로컬기록`. OR 이라 진실이 둘로 갈라지지 않는다(둘 중 하나만 참이어도 스킵).
3. 어느 쪽이든 **회차 종료 시 "접수 N건 vs 완료 플래그 증가분 M건" 대조 리포트**를 낸다. N≠M 이 이 함정의 유일한 조기 신호다.

**Warning signs:**
- 2회차 접수 대상 수가 1회차와 거의 같다
- 같은 `productId` 가 서로 다른 run-dir 의 `detail_status.json` 에 반복 등장
- 크레딧 소모 누계가 "신규 작업 상품 수 × 장수 × 5" 를 초과

**Phase to address:** **Phase 0 (기반/계약)** 에서 실측, **Phase: 상세페이지 작업** 에서 대조 리포트 구현.

### Pitfall 3: 홍보배너 식별 — 미해결 설계 문제 (심층)

> 이 절이 이 문서에서 제일 길다. 기성 해법이 **없다**. 검색으로 확인했다 — 타오바오/1688 상세 이미지에서
> 판매사 홍보배너를 자동 식별·제거하는 공개 도구나 논문은 찾지 못했다(중국어·영어 양쪽 검색).
> 아래는 인접 분야(문서 레이아웃 분석의 머리말/꼬리말 검출, 근사중복 이미지 검출)에서 끌어온 **설계 제안**이며,
> 라벨링 세트로 실측 검증하기 전까지는 가설이다.

#### 3-1. 문제 정의와 경계

`uploadDetailContents.renderContent` 는 `<img>` 나열 HTML 이다(실측 7장). 이 중 맨 위 0~2장, 맨 아래 0~2장이 중국 판매사 자사 홍보(로고·점포명·위챗/QR·"关注店铺"·고객센터·배송안내)다. 판매사마다 장수가 다르다.

**먼저 혼동하지 말 것:** `uploadDetail_page.top_image` / `bottom_image` 는 **불사자 마켓그룹 고정 배너**로 완전히 별개다(PROJECT.md 실측 주석). 이건 우리가 붙이는 것이고, 지우려는 건 `renderContent` 안의 이미지다. 이 둘을 헷갈려 잘못된 걸 지우면 전 상품의 마켓 배너가 날아간다.

#### 3-2. 오탐·미탐의 비용은 대칭이 아니다

| | 무슨 일이 | 즉시 증상 | 실제 비용 |
|---|---|---|---|
| **오탐** (제품 이미지를 배너로 보고 버림) | AI 입력에서 제품 정보가 빠짐 | **없음** — 생성물은 멀쩡해 보인다 | 상세가 제품을 덜/잘못 설명 → 전환 손실. 장수가 줄어 크레딧은 오히려 덜 씀. **회복 가능**(재작업) |
| **미탐** (배너를 남김) | 중국 점포 로고·위챗ID·QR·경쟁사 상표가 AI 입력에 들어감 | **없음** — 생성물은 멀쩡해 보인다 | 생성 상세에 타사 상표·중국어 연락처가 반영된 채 **스마트스토어에 게시**. 상표권·플랫폼 정책 리스크. **회복 비쌈**(이미 게시됨) |

**결론: 미탐이 오탐보다 비싸다.** 임계값은 **배너 판정 쪽으로 공격적으로** 잡는다. 애매하면 버린다.
단 공격적 판정이 폭주하면 3-5의 안전장치가 잡는다.

#### 3-3. 식별 전략 비교

| 전략 | 비용 | 오탐 위험 | 미탐 위험 | 평가 |
|---|---|---|---|---|
| **A. 위치 휴리스틱** (앞 N장·뒤 M장 고정 제거) | 0 | 높음 (배너 0장인 판매사의 제품 사진을 버림) | 높음 (배너 2장인데 N=1) | **단독 사용 금지.** 장수가 0~2로 다른 게 문제의 정의 자체다 |
| **B. 종횡비·크기** (전폭 가로 띠 = 배너) | 거의 0 | 중 (가로형 제품 사진) | 중 (세로 긴 안내 이미지) | **보조 신호로 유용.** `<img>` 태그의 width/height 속성이 있으면 다운로드 0. 없으면 HTTP Range 로 헤더 수백 바이트만 받아 크기 추출 |
| **C. 코퍼스 빈도 (pHash)** | 1회 해싱 후 0 | 낮음 | 낮음 | **★주력 추천.** 아래 3-4 |
| **D. OCR 키워드** (`关注`·`收藏`·`店铺`·`客服`·전화번호·微信) | 중 | **높음** — 제품 이미지에도 중국어 스펙표가 있다 | 낮음 | **단독 사용 금지.** 가점 신호로만 |
| **E. QR/바코드 검출** (pyzbar) | 거의 0 | **매우 낮음** — 제품 사진에 QR 이 있을 일이 거의 없다 | 높음 (QR 없는 배너 많음) | **확정 신호로 채택.** QR 있으면 무조건 배너. 값싸고 정확 |
| **F. 비전 LLM 판정** | 장당 비용·지연 | 낮음 | 낮음 | **회색지대에만.** 전량에 돌리면 배보다 배꼽 |

#### 3-4. 주력 전략 — 코퍼스 빈도 (왜 이게 맞나)

**원리:** 판매사는 **같은 배너를 자기 상품 전부에 붙인다.** 제품 사진은 상품마다 고유하다.
→ 코퍼스 전체에서 **여러 상품에 걸쳐 반복 등장하는 이미지 = 배너.**

이건 문서 레이아웃 분석에서 머리말/꼬리말을 잡는 고전적 방법과 정확히 같은 원리다 — 같은 위치에 같은 내용이 페이지마다 반복되면 본문이 아니라 pagination construct다("textual variability score"). 우리 쪽은 페이지 대신 상품, 텍스트 대신 이미지다.

**구현:**
- URL 해시가 아니라 **pHash/dHash(64bit)** 를 쓴다. 불사자가 이미지를 재호스팅·재인코딩하면 URL 은 달라도 픽셀은 같다. 지각해시는 재압축·리사이즈를 견딘다. 근사중복은 Hamming distance 몇 비트 안에 들어오고 무관한 이미지는 32비트 근처라 단일 컷오프로 갈린다.
- **판정**: 어떤 pHash 가 **서로 다른 타오바오상품번호 N개 이상**에 등장 → 배너. N=3 권장, N=2 는 회색.

> ⚠️ **여기에 숨은 함정 하나 — 이거 놓치면 전략이 통째로 무너진다.**
> 물갈이 20일 주기 때문에 **같은 타오바오 상품이 여러 `productId` 로 코퍼스에 존재한다.**
> `productId` 기준으로 세면 제품 사진도 "여러 상품에 등장"으로 보여 전부 배너로 판정된다 → **전량 오탐.**
> 반드시 **타오바오상품번호 기준 distinct** 로 센다.

- **비용**: 970,695건 전수는 필요 없다. 작업 대상(광고 규칙 ③⑤로 좁힌 수백~수천 건)의 상세 이미지만 해싱하면 되고, 해시는 계정 단위로 캐시해 증분 갱신한다.

#### 3-5. 권장 하이브리드 파이프라인

```
1) 후보 수집: renderContent 파싱 → <img> src 순서 보존 리스트
2) 확정 배너:  QR 검출(E) 히트           → 배너
3) 주력 판정:  pHash 코퍼스 빈도(C) ≥ 3   → 배너
4) 보조 가점:  종횡비 w/h > 2.5(B) + OCR 키워드(D) 2개 이상 → 배너
5) 회색지대:   위에서 안 갈린 것 중 "맨 앞 1장 / 맨 뒤 1장"만 비전 LLM(F) 1콜로 판정
6) 나머지     → 제품 이미지
```

**5단계를 맨 앞/맨 뒤로만 제한하는 게 핵심이다.** 배너는 가운데 안 들어간다(A 휴리스틱을 판정이 아니라 **비전 호출 범위 제한**에 쓰는 것). 비전 콜이 상품당 최대 2회로 묶인다.

#### 3-6. 반드시 넣을 안전장치 (오탐 폭주 차단)

1. **제거율 상한**: 배너 판정이 전체 이미지의 50%를 넘으면 그 상품은 **접수하지 않고 스킵**한다. 판정기가 고장 났다는 신호다.
2. **하한 게이트**: 배너 제거 후 남은 제품 이미지가 **2장 미만이면 접수하지 않는다** (PROJECT.md 의 하한 2와 일치).
3. **회색은 사람에게 묻지 말고 상품을 스킵한다.** 판정 큐를 만들면 안 돌린다(메모리 규칙: "사람 큐를 만들지 마라"). 애매한 상품 1건 건너뛰는 비용 < 큐가 쌓여 전체가 멈추는 비용.
4. **판정 결과를 저장해 재현 가능하게 한다.** 회차마다 배너 판정이 흔들리면 생성 장수가 흔들리고, 그게 Pitfall 4를 유발한다.

#### 3-7. 검증 게이트 (이게 Phase 종료 조건이다)

**상품 100건 손라벨링 세트**를 만들어 오탐률·미탐률을 실측하기 전에는 대량 실행하지 않는다.
합격선: **미탐 0%** (배너를 남기면 안 됨), 오탐 ≤ 10% (제품 사진 일부 손실은 감수).
미탐이 하나라도 나오면 임계를 조이고 다시 잰다.

**Phase to address:** **Phase: 상세 입력 파이프라인 (배너 식별)** — 독립 phase 로 분리할 것. 상세 생성 phase 에 끼워 넣으면 검증 게이트가 생략된다.

### Pitfall 4: 동적 `sectionCount` 가 기작업 스킵 규칙을 조용히 무력화한다

**What goes wrong:**
기존 스킵 규칙은 **`기존 생성 장수 >= 이번 목표 장수(sectionCount)`** 다(bulsaja-detail-page SKILL.md).
지금까지는 목표가 **항상 10** 으로 고정이라 이 부등식이 안정적이었다.
그런데 새 요구는 *"생성 장수를 기존 상세 길이에 비례 — `min(제품이미지 수, 10)`, 하한 2"* 다.
**목표 장수가 회차마다 변한다.** 배너 판정이 1장이라도 달라지면 목표가 6→7 로 바뀌고, **이미 6장으로 완료된 상품이 "6 >= 7 거짓" 으로 재작업 대상이 된다.** 크레딧을 다시 낸다. 에러는 없다.
반대 방향도 있다: 목표가 7→5 로 줄면 1장 사고분(기존 1장)이 아닌 멀쩡한 5장 상품까지 "5>=5 참"으로 스킵돼 **재작업이 필요한 상품이 영영 안 잡힌다.**

**Why it happens:**
스킵 규칙이 "목표"라는 **변동값**을 기준으로 삼는데, 그 목표가 상수였다가 함수가 되는 변경이다. 변경 자체는 한 줄이라 리뷰에서 안 보인다.

**How to avoid:**
1. **목표 장수를 결정론적으로 만들고 상품별로 고정 저장한다.** 배너 판정 결과와 산출된 `sectionCount` 를 상품별로 기록하고, 이후 회차는 **재계산하지 않고 저장값을 쓴다.** 재계산은 `--recompute` 명시 때만.
2. **스킵 판정을 목표 장수에서 분리한다.** `스킵 = aiImageGenerated AND aiImageOutputCount >= 2` 로 바꾸고, "1장 사고분 재작업"은 `aiImageOutputCount <= 1` 이라는 **절대 조건**으로 따로 판정한다. 목표와 결합하지 않는다.
3. 크레딧 견적을 **`건수 × 10 × 5` 같은 상수식으로 내지 않는다.** 상품별 `sectionCount` 를 합산한 실제 견적을 낸다. 동적 장수에서 상수 견적은 과소보고가 되고, 과소보고는 승인 게이트를 무력화한다.

**Warning signs:**
- 접수 견적 합계와 실제 차감 크레딧이 어긋난다
- 같은 상품이 연속 두 회차 접수 목록에 있다
- `sectionCount` 분포가 회차마다 달라진다

**Phase to address:** **Phase: 상세페이지 작업** — 배너 식별 phase 와 같은 phase 로 묶지 말고, 스킵 규칙 재정의를 **명시적 작업 항목**으로 둔다.

### Pitfall 5: 낡은 스냅샷으로 판단하기 — 물갈이가 만드는 유령 상품

**What goes wrong:**
광고 판정은 **D-2 종료·30일 창** 데이터다. 게다가 구매완료 리포트는 계정당 30회 생성·폴링·다운로드라 비싸서 캐시할 수밖에 없다.
그 사이 **20일 주기 물갈이**가 상품을 삭제하고 새 ID로 재업로드한다. 결과:
- 캐시된 광고 성과의 `mallProductId` 가 **이미 없는 채널상품**을 가리킨다 → 조인 실패(그나마 다행)
- 또는 **삭제 전 옛 사본이 불사자에 남아** 있어 조인이 성공한다 → **안 팔리는 유령 사본에 상세 작업·크레딧 투입.** 이게 조용한 쪽이다.
- 판매 실적(규칙 ⑤)은 옛 ID에 붙어 있고 현재 살아 있는 건 새 ID라 **"팔린 상품"과 "지금 파는 상품"이 다른 레코드**가 된다.

기존 `prune` 은 이미 이 문제를 겪고 해결했다(references §8 Critical 3): *"commit 직전에 `collect.fetch_ads` 로 현재 상태를 재조회하고 `revived_filter` 로 교집합한다."* 웹앱이 이 패턴을 안 물려받으면 처음부터 다시 당한다.

**How to avoid:**
1. **모든 쓰기 버튼은 commit 직전 대상 상태를 재조회한다.** 미리보기 스냅샷으로 커밋하지 않는다. 재조회 비용(상품 단건 조회)은 크레딧 대비 무시할 수준이다 — `prune` 이 이미 "계정당 11~13회 조회 vs DELETE 수천 번"으로 같은 계산을 했다.
2. **보드 각 행에 데이터 나이를 표시한다.** "광고 D-2 / 상품상태 방금" 처럼 소스별로 따로. 한 줄에 뒤섞인 신선도의 데이터가 올라가는데 그게 안 보이는 게 문제다.
3. **캐시 TTL을 물갈이 주기에 못 박는다.** 상품 상태 캐시는 분 단위, 광고 성과 캐시는 회차 단위, 그리고 **캐시 나이가 20일(물갈이 주기)을 넘으면 실행 버튼을 잠근다.**
4. **`상태` 필드를 하드 필터로 쓴다.** `coupang_rules` 가 이미 `NORMAL_STATES` 로 하는 것과 같다. 삭제됨·업로드실패 사본을 작업 대상에 넣지 않는다.

**Warning signs:**
- 작업한 상품의 채널상품ID로 스마트스토어를 열면 404
- 규칙 ⑤ "판매된 상품" 목록에 잠금(`잠금`)이 안 걸린 건이 섞여 있다 (판매된 상품은 잠겨 있어야 정상)
- 재조회에서 걸러지는 건수가 0으로만 나온다 → 재조회가 실제로 안 돌고 있다는 뜻

**Phase to address:** **Phase 0 (기반)** 에서 "모든 쓰기는 재조회 후 커밋" 을 래퍼 계약으로 박는다. phase 별로 각자 구현하게 두면 빠뜨린다.

### Pitfall 6: 정지된 소재의 과거 클릭을 "유입"으로 읽는다

**What goes wrong:**
규칙 ③(클릭 20+ & 구매완료 0)은 30일 창이다. 그런데 `AD_ABNORMAL_INTERLOCK` 대량정지는 물갈이 부산물로 **계속 발생한다**(누적 7,340건 삭제, cy7728 은 5,024건이 나흘에 몰려 꺼짐).
30일 중 앞 10일만 살아 있다가 꺼진 소재도 클릭 20을 채운다. 이걸 "유입은 있는데 안 팔린다 → 상세 문제"로 읽으면, **이미 광고가 안 도는 상품의 상세를 고치는 데 크레딧을 쓴다.** 고쳐도 유입이 안 오니 성과도 안 나고, 원인도 안 보인다.

**How to avoid:**
1. 규칙 ③ 결과를 **`enable=true` 인 소재로 한 번 더 교차 필터**한다(`ads_rules.live_ads`). 판정 결과를 그대로 작업 큐로 쓰지 않는다.
2. 보드에 **"마지막 노출일"** 컬럼을 넣는다. D-7 이후 노출이 0이면 상세 작업 대상이 아니라 **광고 재투입 대상**이다(물갈이 재업로드 후 소재를 새로 넣는 건 아직 수작업 — references 명시).
3. 정지 사유가 `AD_ABNORMAL_INTERLOCK` 인 상품은 **별도 레인**으로 뺀다. 이건 상세 문제가 아니라 연동 문제다.

**Warning signs:**
- 규칙 ③ 목록 건수가 물갈이 직후 급증한다
- 상세 작업 후에도 클릭이 0으로 유지되는 상품이 다수

**Phase to address:** **Phase: 대상 선별** — 규칙 판정 결과 → 작업 큐 변환 계층에서.

### Pitfall 7: 원인 오귀인 — 규칙 ③을 전부 "상세페이지 문제"로 단정한다

**What goes wrong:**
PROJECT.md 가 *"규칙 ③의 원인 1순위가 상세페이지 미번역"* 이라고 쓴 건 맞지만, **1순위 ≠ 유일**이다.
클릭 20+ / 구매 0의 다른 원인: 품절, 배송비 과소·과다, 가격 경쟁력, 카테고리 오배치(메모리: "확신도 100%가 정답은 아니다"), 옵션 구성 붕괴, 리뷰 0.
상세만 갈고 "고쳤다"고 마킹하면 **크레딧은 나가고 전환은 그대로**인데, 그 상품이 "작업 완료"로 표시돼 **다시는 안 보게 된다.** 이게 제일 조용하다.

**How to avoid:**
1. 상세 작업 버튼을 누르기 전, 보드 행에 **저비용 배제 체크 3종을 표시**한다: 재고/판매상태, 배송비 교정 필요 여부(`shipping_diff` 이미 있음), 카테고리 확신도. 전부 추가 API 없이 기존 스냅샷에서 나온다.
2. **"작업 완료"와 "문제 해결"을 다른 필드로 둔다.** 상세를 고쳤다는 사실이 그 상품을 규칙 ③ 목록에서 영구히 빼면 안 된다. 다음 회차에 여전히 ③에 있으면 **"상세 작업했는데도 ③"** 배지를 띄운다 — 이게 원인이 상세가 아니었다는 유일한 증거다.
3. 완료 기준을 전환율이 아니라 마찰로 잡은 건 맞지만(Key Decision), **"상세 작업 후에도 ③에 남은 비율"** 정도는 세라. 이게 높으면 이 프로젝트의 Core Value 가설 자체가 틀린 것이다.

**Phase to address:** **Phase: 관제탑 보드** (배제 체크 표시) + **Phase: 대상 선별** (재발 배지).

### Pitfall 8: 크레딧 소모 작업의 사고 3종

**What goes wrong:**

| 사고 | 조용한 이유 | 기존 실측 근거 |
|---|---|---|
| **(a) 잘못된 파라미터로 접수** | 접수는 200, 결과만 1장 | `imageUrls` + `sectionCount` 를 동시에 안 보내면 1장짜리로 접수 (7/22 96건 전량 1장 사고) |
| **(b) 폴링 타임아웃을 실패로 오인 → 재생성** | 재생성도 정상 성공한다 | 메모리: "폴링 타임아웃은 접수모드 정상동작. recover 먼저" — 크레딧 이중 지불 |
| **(c) 이중 접수 (탭 두 개·버튼 연타·재시도)** | 서버가 "작업 중복"으로 막아주지만 **막아주는 건 같은 상품 동시 진행뿐** | SKILL.md §3 |

웹앱이 새로 추가하는 위험: **브라우저는 버튼을 두 번 누르기 쉽고, 탭은 두 개 열기 쉽다.** CLI 는 그렇지 않았다.

**How to avoid:**
1. **접수에 멱등키를 건다.** `(productId, sectionCount, run_id)` 해시를 접수 레코드에 저장하고, 같은 키가 이미 있으면 **접수하지 않고 기존 taskId 를 반환**한다. 서버 중복 방지에 의존하지 않는다.
2. **첫 건 자동 검증을 웹앱에도 그대로 가져온다.** 접수 응답의 `예상장수` ≠ 요청 장수면 **전량 접수 전에 중단**(`detail_batch.py` 에 이미 있는 방어 — 웹앱이 배치를 재구성하면서 이걸 빠뜨리기 쉽다).
3. **타임아웃 ≠ 실패.** 타임아웃 상태는 `실패`가 아니라 `확인필요` 로 별도 표기하고, 재생성 버튼을 **비활성**한 뒤 `recover`(상태 재조회)만 제공한다. 재생성은 recover 가 "실패 확정"을 반환한 뒤에만 열린다.
4. **접수 버튼은 클릭 즉시 비활성 + 서버측 run 락.** run-dir 단위 파일 락(`flock`)으로 같은 run 의 동시 접수를 막는다. 탭 두 개 시나리오는 클라이언트 방어로 못 막는다.
5. **견적은 접수 직전 화면에 다시 띄운다.** 대상이 3-6 게이트로 줄었을 수 있다 — 초기 견적을 그대로 쓰면 과대·과소 둘 다 난다.
6. 잔액 조회(`bulsaja_ai_credit_balance`)로 회차 비용을 역산하지 않는다(메모리: "크레딧 잔액은 세션별이 아니다"). 정본은 스크립트 집계.

**Warning signs:**
- `detail_status.json` 에 같은 productId 의 taskId 가 2개
- 결과 장수 분포에 1장이 섞여 있다
- 견적 합계와 집계 실사용량이 10% 이상 차이

**Phase to address:** **Phase: 크레딧 소모 쓰기** — 멱등키·run 락·recover 를 이 phase 의 완료 조건으로.

### Pitfall 9: 대량 선택 스코프 불일치 — 화면 20건, 실행 3,000건

**What goes wrong:**
보드에 필터를 걸면 3,000건이 잡히고 화면엔 20건이 보인다. 헤더 체크박스를 누른다. **이게 20건인가 3,000건인가?**
업계 공통 문제다 — *"selection is the most destructive control on an index and the least specified"*, *"the ambiguity around what select-all means — the twenty rows on this page, or all 340 in the filtered set — is dangerous"*. 그리고 *"silently carrying selection across page changes is how someone deletes rows they never saw."*
우리 맥락에선 이게 **크레딧 3,000건 × 장수 × 5** 거나 **되돌릴 수 없는 마켓 쓰기 3,000건**이다.

**How to avoid:**
1. **Gmail 패턴을 그대로 쓴다.** 헤더 체크박스 = **이 페이지 20건만**. 전체를 원하면 그 아래 나타나는 **"필터에 걸린 3,000건 전체 선택"** 링크를 **별도로 한 번 더** 눌러야 한다. 두 행위를 분리한다.
2. **선택 상태를 페이지 이동·필터 변경 시 명시적으로 처리한다.** 필터가 바뀌면 선택을 **비운다**(조용히 이월 금지). 페이지만 넘길 땐 유지하되 "선택 N건" 카운터를 항상 띄운다.
3. **dry-run 미리보기는 선택 건수가 아니라 실제 실행 대상 전수를 센다.** "미리보기 20건 표시 / 실행 대상 3,000건" 처럼 **두 숫자를 나란히** 보여준다. 하나만 보이면 그게 사고다.
4. **규모 게이트**: 실행 대상이 임계(예: 100건 또는 예상 5,000크레딧)를 넘으면 확인 다이얼로그에 **숫자를 직접 타이핑**하게 한다. 체크박스 확인은 통과한다.
5. **참고**: `report_md.TOP_N = 20` 은 **표시 상한일 뿐 실행 대상은 안 줄인다**(references 명시 — `bids`·`prune` 은 `result.json` 전체를 읽는다). 웹앱이 보고서를 보드에 그대로 붙이면 **"보이는 20건"과 "실행 N건"의 괴리가 구조적으로 발생**한다. 보드는 `report.md` 가 아니라 `result.json` 을 읽어야 한다.

**Warning signs:**
- 확인 다이얼로그의 건수와 실행 로그의 건수가 다르다
- 보드 상단에 "N건 중 상위 20건" 같은 문구가 있는데 실행 버튼이 같은 화면에 있다

**Phase to address:** **Phase: 관제탑 보드** — 선택 모델을 보드 구현의 **첫** 작업으로. 나중에 끼우면 전부 다시 짠다.

### Pitfall 10: 되돌릴 수 없는 마켓 쓰기 — 상세 수정업로드에는 revert 가 없다

**What goes wrong:**
입찰가와 소재 삭제는 되돌리기가 있다(`before_bids_*.json` + `--revert`, `paused_*.json` 백업).
**상세페이지 수정업로드에는 그게 없다.** 잘못된 상세(오탐으로 제품 사진이 빠졌거나, 미탐으로 중국 배너가 들어갔거나, 엉뚱한 사본에 반영했거나)를 스마트스토어에 올리면 **원래 상세로 돌아갈 방법이 기록돼 있지 않으면 없다.**
쿠팡 복사는 더하다 — 쿠팡은 취소·반품 잦으면 계정정지고, 잘못 올린 상품을 지우는 건 판매 이력이 생기면 막힌다(메모리: "판매된 상품은 잠겨 있어 영원히 안 지워진다").

**How to avoid:**
1. **쓰기 전 `renderContent` 전문을 백업한다.** `bids`/`prune` 의 `before_*.json` 패턴을 그대로. **백업 실패 시 쓰기를 중단**한다(`aborted: "backup_failed"` 와 동일 계약).
2. **`restore` 명령을 쓰기 기능과 **같은 phase 에** 만든다.** "나중에"는 안 온다. 백업만 있고 복원 경로가 없으면 백업이 아니라 위안이다.
3. **쿠팡 `apply --commit` 은 3단계 자동화 목표에서도 영구히 사람이 누른다**(PROJECT.md 명시). 웹앱에서 이 버튼만 다른 색·다른 위치에 두고, 다른 버튼들과 같은 습관으로 눌리지 않게 한다.
4. **파일럿 규모를 강제한다.** 새 쓰기 경로의 첫 실행은 **10건 상한**을 코드로 박는다. 상한 해제는 결과를 사람이 본 뒤 플래그로. (쿠팡 1차 파일럿 84건이 이미 이 방식이었다)
5. 쓰기 후 **재조회 검증**은 이미 공통 안전규칙이다(`_shared/불사자-안전규칙.md` ⑤: "성공 응답만 믿지 않는다"). 웹앱 래퍼가 이걸 건너뛰지 않게 계약에 넣는다.

**Warning signs:**
- run-dir 에 `before_*.json` 이 없는데 쓰기 로그가 있다
- 복원 명령을 한 번도 실행해본 적이 없다 (= 작동 여부 미검증)

**Phase to address:** **Phase 0 (기반 계약)** 에서 "백업 실패 시 중단" 을 래퍼 공통으로. **Phase: 마켓 쓰기** 에서 `restore` 를 완료 조건에 포함.

### Pitfall 11: 계정 라우팅 — 네임스페이스가 3개이고 개수가 다 다르다

**What goes wrong:**

| 네임스페이스 | 개수 | 위치 |
|---|---|---|
| 네이버 광고 계정 | 4 (→6 예정) | `~/.eroom/naver-ads.json` |
| 네이버 커머스 스토어 | alias 별 | `~/.eroom/naver-commerce.json` |
| 불사자 계정 | 2 (용팀장 / 용쌤=부킹) | MCP 서버 2개 (`bulsaja`, `bulsaja-yongssaem`) |

**1:1 이 아니다.** 광고 계정 4개가 불사자 계정 2개에 M:N 으로 걸린다. 보드가 행 단위로 계정을 추론하면 **틀린 불사자 계정에 쓰기를 날린다 — 즉 남의 상품을 고친다.**
`verify_creds.py` 가 이미 "채널명 불일치" 경고를 내는 걸 보면 이 정합성이 자명하지 않다는 뜻이다.

**How to avoid:**
1. **매핑을 추론하지 말고 설정 파일에 명시한다.** `광고계정alias → 커머스스토어alias → 불사자MCP키` 3열 테이블. 매핑에 없는 조합이 나오면 **실행 거부**.
2. **쓰기 직전 실시간 프로필 확인.** 메모리 규칙 그대로 — "작업 전 프로필 확인, 다르면 토큰 교체+재연결". 세션 기억으로 답하지 않는다(`_shared` §연결·역할 확인).
3. **화면에 계정을 항상 띄운다.** 보드 헤더에 현재 불사자 계정명을 크게. 색도 다르게(용팀장/용쌤).
4. **"광고 계정은 설정 파일로만 늘어난다"** 는 제약(PROJECT.md)을 테스트로 고정한다 — 계정 수가 하드코딩됐는지 검사하는 테스트 1개. 4→6 전환에서 이게 없으면 조용히 2개가 빠진다.

**Warning signs:**
- 설정에 없는 계정 조합이 로그에 등장
- 작업한 상품이 보드에서 사라진다(다른 계정에 있었던 것)

**Phase to address:** **Phase 0 (기반)**.

### Pitfall 12: 로컬 단독 웹앱이라고 인증을 안 넣으면, 인증이 없는 게 아니라 **전 인터넷이 인증된 것**이다

**What goes wrong:**
"나 혼자 로컬에서만 쓴다"(PROJECT.md Out of Scope)는 **네트워크 노출을 막지 못한다.**
`localhost:PORT` 에 뜬 무인증 서버는:
- **CSRF**: 브라우저 다른 탭에서 연 아무 웹사이트가 `fetch("http://localhost:8000/api/detail/submit", {method:"POST", mode:"no-cors"})` 로 **크레딧 소모 접수와 마켓 쓰기를 트리거할 수 있다.** CSRF 는 "사용자가 신뢰하는 애플리케이션에 인가되지 않은 명령이 제출되는" 공격이고, 쓰기 권한 남용을 막으려면 별도 CSRF 방어가 필요하다.
- **DNS rebinding**: 악성 페이지가 DNS 를 재바인딩해 same-origin policy 를 우회하고 사설 IP/로컬호스트의 서비스에 접근해 **응답까지 읽어간다.** 응답에는 상품 데이터와, 잘못 설계하면 자격증명이 실려 있다.
- 이 서버 뒤에는 **네이버 광고 4계정 시크릿 · 커머스 API bcrypt 시크릿 · 불사자 Bearer 토큰 2개**가 있다.

**How to avoid:**
1. **`127.0.0.1` 에만 바인드한다.** `0.0.0.0` 금지. 카페 와이파이에서 옆자리에 열린다.
2. **`Host` 헤더 화이트리스트** (`127.0.0.1:PORT`, `localhost:PORT` 만 허용) → DNS rebinding 차단. 이게 rebinding 의 표준 방어다.
3. **모든 쓰기 엔드포인트에 `Origin` 검증 + CSRF 토큰.** `SameSite=Strict` 쿠키만으로는 부족하다(쿠키를 안 쓰는 구조면 특히).
4. **자격증명을 API 응답에 절대 싣지 않는다.** 토큰은 서버 프로세스 안에서만. `_shared` 규칙 "토큰은 절대 출력 금지" 를 HTTP 레이어까지 확장 — 프론트엔드는 토큰의 존재조차 몰라야 한다.
5. **부팅 시 무작위 세션 토큰**을 생성해 콘솔에 찍고 쿼리스트링/헤더로 요구한다. 인증 시스템이 아니라 자물쇠 한 개다. 구현 20줄.
6. 파일 권한: `~/.eroom/*.json` 600, git 밖 (이미 준수 중 — 웹앱 설정 파일도 동일하게).

**Warning signs:**
- 서버가 LAN IP 로 열린다 (`lsof -i :PORT` 로 `*:PORT` 확인)
- API 응답 JSON 에 `token`·`secret`·`client_secret` 키가 있다

**Phase to address:** **Phase 0 (기반)** — 나중에 붙이려면 모든 엔드포인트를 손봐야 한다.

### Pitfall 13: 프로세스 고아화와 동시 실행 — "감시 없이 띄우지 마라"의 웹앱 버전

**What goes wrong:**
웹앱이 CLI 래퍼라는 건 **버튼 하나가 장시간 서브프로세스 하나**라는 뜻이다. 상세 배치는 수십 분 돈다.
- 브라우저 탭을 닫으면? 서브프로세스는 계속 돈다. 사용자는 상태를 잃는다.
- 서버를 재시작하면? 서브프로세스가 고아가 되거나 죽는다. **접수는 됐는데 폴링이 끊긴 상태 = 크레딧은 나갔고 결과는 안 받은 상태.**
- 탭을 두 개 열면? 같은 run-dir 에 두 프로세스가 체크포인트 파일을 동시에 쓴다 → 체크포인트 손상 → 재개 불가.
- 기존 스킬이 이미 이 사고를 겪었다: *"자신의 턴이 끝나는 순간 그 작업에 대한 감시·재개 수단은 완전히 사라진다"*(bulsaja-detail-page, 2026-07-24 사고 재발 방지). 메모리: "감시 없이 띄우지 마라 — 4시간 놀았다."

**How to avoid:**
1. **작업 상태를 프로세스가 아니라 파일에 둔다.** run-dir 의 `detail_status.json` 체크포인트가 이미 정본 — 웹앱은 이걸 **읽어서** 화면을 그린다. 메모리 상태를 만들지 않는다.
2. **단일 서버 인스턴스 강제.** 포트 점유 + PID 파일. 두 번째 실행은 기존 것에 붙거나 죽는다.
3. **run-dir 단위 락.** 같은 run 에 두 작업이 못 붙는다.
4. **재시작 시 미완료 run 복구 화면을 띄운다.** 부팅하면 "미완료 run 2개 발견 — 이어서 폴링하시겠습니까". 이게 없으면 접수된 크레딧이 조용히 증발한다.
5. **탭 닫힘 ≠ 취소.** 명시적 취소 버튼만 취소다. 그리고 취소는 "폴링 중단"이지 "접수 취소"가 아니라는 걸 문구로 밝힌다 — **접수된 크레딧은 안 돌아온다.**
6. 백그라운드 실행에는 **완료 감시를 항상 같이** 건다(메모리 규칙).

**Warning signs:**
- 서버 재시작 후 진행 중이던 작업이 UI에서 사라진다
- `detail_status.json` 에 JSON 파싱 오류

**Phase to address:** **Phase 0 (기반/실행 엔진)**.

### Pitfall 14: dry-run 과 commit 이 서로 다른 코드 경로를 탄다

**What goes wrong:**
PROJECT.md 의 핵심 설계는 *"모든 쓰기 버튼은 미리보기(dry-run) → 확인 → 실행 2단"* 이고, 3단계 자동화는 *"앞 두 단계를 사람 없이 통과시키는 것"* 이다.
**이 설계 전체가 "미리보기가 실행을 정확히 예측한다"는 가정 위에 서 있다.** 미리보기가 별도 쿼리·별도 필터를 쓰면 가정이 깨지고, 깨진 사실은 commit 한 뒤에야 드러난다. 그리고 자동화 3단계에 가면 **드러나지도 않는다.**

**How to avoid:**
1. **대상 선정 함수는 하나다.** `select_targets(...) -> list` 를 dry-run 과 commit 이 **똑같이** 호출하고, 차이는 마지막 `if commit:` 한 줄뿐이다. 이걸 아키텍처 규칙으로 못 박는다.
2. **미리보기 결과를 해시해 commit 요청에 실어 보낸다.** 서버가 commit 직전 재선정한 대상의 해시와 비교해 **다르면 거부**하고 미리보기를 다시 시키게 한다. Pitfall 5(재조회)와 충돌하지 않는다 — 재조회로 대상이 **줄어드는 것만** 허용하고 늘어나면 거부한다.
3. **미리보기에 반드시 포함할 것**: 실행 대상 전수, 예상 크레딧(상품별 합산), 계정명, 되돌리기 가능 여부(가능/불가), 백업 파일 경로.
4. 2단계 자동화로 넘어가는 **전제 조건을 숫자로 정의한다**: "미리보기 대비 실제 실행 불일치율 0%를 N회차 연속" 같은 것. PROJECT.md 는 "오판정률이 실측으로 낮게 나올 것"이라고만 썼는데, 무엇을 어떻게 재는지 정하지 않으면 그냥 넘어가게 된다.

**Warning signs:**
- 미리보기 건수 ≠ 실행 로그 건수 (한 번이라도)
- dry-run 과 commit 에서 서로 다른 함수 이름이 보인다

**Phase to address:** **Phase 0 (기반 계약)** + 각 쓰기 phase 의 완료 조건.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|---|---|---|---|
| 보드를 `report.md` 파싱으로 만든다 | 판정 결과를 바로 쓴다 | `report.md` 는 top_n 으로 잘린 **표시용**이다. 실행 대상과 영구히 어긋난다 | **절대 안 됨.** `result.json` 을 읽는다 |
| 조인 실패 행을 조용히 드롭 | 보드가 깨끗해진다 | 검수중 소재 73%(ownway1)가 통째로 안 보인다. "왜 이 상품이 없지"의 원인 | **절대 안 됨.** 실패는 실패 배지로 표시 |
| 크레딧 견적을 `건수×10×5` 상수식으로 | 한 줄 | 동적 장수에서 과소보고 → 승인 게이트 무력화 | 장수 고정 동안만. 동적 전환과 동시에 제거 |
| 배너 판정을 매 회차 재계산 | 캐시 불필요 | 장수가 흔들려 스킵 규칙 붕괴(Pitfall 4) | **절대 안 됨.** 상품별 고정 저장 |
| 상품 상태를 프론트엔드 메모리에 | 빠른 UI | 새로고침·재시작에 증발, 탭 간 불일치 | 읽기 전용 뷰 상태만 |

## "Looks Done But Isn't" Checklist

- [ ] **엔티티 조인**: 카디널리티 단언이 있나 — `불사자코드` 로 조인해 27배 팬아웃 나는지 실제 데이터로 확인
- [ ] **기작업 스킵**: 우리 반영 경로가 `aiImageGenerated` 를 실제로 찍는지 1건 dump/diff 로 확인 — 추측 금지
- [ ] **배너 식별**: 라벨링 100건 세트로 미탐률 0% 확인 — 눈으로 몇 개 보고 "잘 되네"는 검증이 아님
- [ ] **배너 식별**: pHash 빈도를 `productId` 가 아니라 **타오바오상품번호** distinct 로 세는지 확인
- [ ] **배너 식별**: `uploadDetail_page.top_image`/`bottom_image`(마켓그룹 고정 배너)를 건드리지 않는지 확인
- [ ] **크레딧 견적**: 상품별 `sectionCount` 합산인지, `건수×10×5` 상수식인지 확인
- [ ] **접수 검증**: 응답 `예상장수` ≠ 요청 장수 시 전량 중단이 웹앱 경로에도 살아 있나
- [ ] **멱등성**: 버튼 두 번 연타 / 탭 두 개에서 실제로 이중 접수되는지 **시험해봤나**
- [ ] **재조회**: commit 직전 재조회가 실제로 돌고, 걸러진 건수가 로그에 나오나 (0만 나오면 안 도는 것)
- [ ] **백업**: `before_*.json` 이 실제로 생기고, **`restore` 를 한 번 돌려봤나**
- [ ] **백업 실패**: 백업 실패를 주입했을 때 쓰기가 실제로 중단되나
- [ ] **선택 스코프**: 필터 3,000건 상태에서 헤더 체크박스 → dry-run 이 몇 건을 세나
- [ ] **선택 이월**: 필터를 바꿨을 때 이전 선택이 남아 있나
- [ ] **계정 라우팅**: 용쌤 계정 선택 상태로 용팀장 상품에 쓰기를 시도하면 막히나
- [ ] **네트워크**: `lsof -i :PORT` 가 `127.0.0.1:PORT` 인가 `*:PORT` 인가
- [ ] **CSRF**: 다른 오리진에서 POST 를 던져봤나 (curl 에 `Origin: https://evil.example` 붙여서)
- [ ] **응답 스키마**: 어떤 엔드포인트도 토큰/시크릿을 안 돌려주나 (grep)
- [ ] **재시작 복구**: 접수 중 서버를 죽였다 켜면 미완료 run 이 보이나
- [ ] **폴링 타임아웃**: 타임아웃이 `실패`가 아니라 `확인필요`로 표시되고 재생성이 잠기나
- [ ] **계정 확장**: 광고 계정을 설정에 1개 추가하면 코드 수정 없이 보드에 나오나
- [ ] **시트 기록**: 시트 실패해도 판정·보고서가 나오나, 그리고 **실패가 규칙 단위**라는 게 로그에 드러나나

| Pitfall | Prevention Phase | Verification |
|---|---|---|
| 1. 엔티티 팬아웃 | **P1** | 실데이터에서 `불사자코드` 조인 시 팬아웃 배수를 측정해 문서화. 카디널리티 단언 테스트 |
| 2. 완료 플래그 공백 | **P0** 실측 → **P5** 대조 리포트 | 1건 반영 전/후 `uploadDetailContents` diff. 회차별 "접수 N vs 플래그증가 M" |
| 3. 홍보배너 | **P4** (독립) | 라벨링 100건 세트: 미탐 0%, 오탐 ≤10%. 미탐 1건이라도 나오면 phase 미완료 |
| 4. 동적 장수 ↔ 스킵 붕괴 | **P5** | 같은 상품 2회차 연속 돌려 재접수 0건 확인 |
| 5. 낡은 스냅샷 | **P0** 계약 → 각 쓰기 phase | 재조회에서 걸러진 건수가 로그에 남는지. 0만 나오면 미작동 |
| 6. 정지 소재 오독 | **P2** | 규칙 ③ 결과에 `enable=false` 가 0건 |
| 7. 원인 오귀인 | **P2** + **P3** | "상세 작업 후에도 ③에 남은 비율" 지표 존재 |
| 8. 크레딧 사고 3종 | **P5** | 연타·이중탭 이중접수 시험. 타임아웃 시 재생성 잠김 확인 |
| 9. 선택 스코프 | **P3** (보드 첫 작업) | 3,000건 필터 상태에서 dry-run 건수 대조 |

| 11. 계정 라우팅 | **P0** | 교차 계정 쓰기 시도가 거부되는지 |
| 12. 로컬 웹앱 보안 | **P0** | `lsof` 바인드 확인 + 외부 Origin POST 거부 확인 |
| 13. 고아 프로세스 | **P0** | 접수 중 서버 kill → 재시작 후 복구 화면 |
| 14. dry-run ≠ commit | **P0** 계약 → **P8** 계량 | 대상 선정 함수가 단일인지 코드 리뷰. 불일치율 0% N회차 |
