## Executive Summary

이 프로젝트는 SaaS 어드민이 아니라 **"지금 쓰는 CLI + 스프레드시트"를 대체하는 1인 운영 콘솔**이다. 4개 리서치가 독립적으로 도달한 결론이 일치한다 — 새 로직을 만드는 게 아니라 **읽기(파일·MCP)와 쓰기(subprocess로 감싼 기존 CLI)를 엄격히 분리**하고, 판정값은 절대 재계산하지 않으며, "판정 → 미리보기 → 실행" 3단 계약을 처음부터 자동화(2·3단계)의 API로 설계해야 한다는 것이다. 스택은 FastAPI + htmx + Tabulator + SQLite + subprocess(큐 없음)로 수렴했고, 이는 CLI가 이미 갖춘 체크포인트·백업·게이트를 중복 없이 재사용하기 위한 선택이다.

가장 중요한 실측 발견은 두 가지다. 첫째, **작업 모수는 97만 건이 아니라 주당 ~120행**이다(광고 규칙③ 78건 + 규칙⑤ 38건, 2026-08-30 실측) — 이 숫자가 캐시·UI·성능 설계 전체를 결정한다. 둘째, **광고 소재와 불사자 상품을 잇는 다리(mallProductId)가 물갈이 20일 주기마다 세대 단절을 일으켜 조용히 끊긴다**(실측: 광고그룹 하나에서 교집합 0/160). 이 조인은 버튼 5개 중 2개(광고성과 부착, 썸네일)에서만 필수이고, Core Value(상세페이지 대상 선별)는 조인을 우회해 `bulsaja_traffic_analytics`(유입) + 쿠팡 판매경로(구매)로 대부분 해결 가능하다는 것이 아키텍처 리서치의 핵심 반전이다 — 이는 PROJECT.md의 현재 계획("유입은 광고 데이터로 대리")을 수정할 근거가 된다.

가장 큰 리스크는 "고장"이 아니라 "**조용히 틀리는 것**"이다 — 엔티티 팬아웃(불사자코드 1개가 사본 27건을 가리킴), `imageTranslated`의 타입 혼재(문자열 `'0'`이 진리값으로 참이 되는 버그), 동적 장수(sectionCount)가 기존 기작업 스킵 규칙을 무력화하는 것, 그리고 새 반영 경로가 `aiImageGenerated` 플래그를 안 찍어 "서버 플래그가 정본"이라는 핵심 제약이 조용히 깨지는 것. 이 넷은 전부 에러 없이 성공 로그를 남기며 Core Value를 훼손하므로, 로드맵 Phase 0~2에서 실측으로 먼저 닫아야 한다.

## Key Findings

### Recommended Stack

FastAPI(0.141.1) + Uvicorn(`--workers 1` 고정) + Jinja2 + htmx 2.x + Tabulator + stdlib SQLite. 태스크 큐(Celery/RQ/Huey)는 명시적으로 배제한다 — CLI의 run-dir 체크포인트가 이미 내구성을 갖고 있어 큐를 넣으면 "재개 상태의 정본이 둘"이 되는 정확히 그 실패 패턴(진실이 둘이 된다)을 만든다. 진행 스트리밍은 SSE이되 **파이프 직결 금지, 로그파일을 오프셋부터 tail**하는 방식만 "브라우저 닫았다 재접속" 요구를 만족한다.

**핵심 기술:**
- **subprocess (import 아님)**: 실물 코드가 전역 모듈명 충돌·환경변수 자격증명 주입·`sys.exit()` 종료·블로킹 I/O를 갖고 있어 in-process 통합이 구조적으로 불가능함을 확인(HIGH)
- **SQLite + 잡 락 테이블**: 동시성 제어(큐가 주는 유일한 실제 필요 기능)만 3줄 SQL로 대체
- **run-dir을 plan 아티팩트로 그대로 승격**: 새 형식을 만들지 않고 CLI가 이미 쓰는 산출물을 미리보기·실행의 단일 근거로 삼음 (Terraform plan/apply 패턴과 동형)
- **Tabulator**: 가상 DOM 렌더링이 내장이라 수천 행 규모(97만 건이 아니라 좁혀진 작업 대상 기준)에 적합

### Expected Features

이 도구가 더해야 할 가치는 "기능"이 아니라 **선택·미리보기·결과확인의 마찰 제거**다. Table stakes의 대부분은 화면이 아니라 **계약(contract)** — plan 아티팩트, job 객체, 항목 단위 결과표, 감사 JSONL — 이며, 이 넷이 곧 2·3단계 자동화의 API이기도 하다.

**Must have (table stakes):**
- 3단 선택 모델(행/페이지/필터 전체) + 실행 캡 — 최대 사고 벡터가 삭제 버튼이 아니라 "필터 전체 선택"이기 때문
- dry-run plan의 신선도 검사(stale plan 거부) — CLI `recheck_failed`를 정상 흐름으로 노출
- 위험 사다리 기반 차등 확인 — 5버튼 전부 같은 확인이면 확인이 사라짐(NN/g)
- job 객체 + 상태 페이지 — 브라우저를 닫아도 살아있어야 함
- 항목 단위 결과표 + 사유코드 3종 + 멱등(서버 재조회) — 크레딧 이중 지불의 유일한 방어선

**Should have (differentiator):**
- 오판정 1클릭 피드백 — 2단계 자동화로 가는 유일한 계측 수단, 없으면 v1이 끝나도 2단계로 못 감
- 공통 3단 프레임(G1) — 버튼 5개가 같은 골격을 쓰지 않으면 자동화 시 전부 다시 만듦
- 크레딧 가계부 — 잔액 역산은 이미 틀린다고 실측됨

**Defer (v2+):**
- 2단계(일괄승인)·3단계(스케줄) 자동화 — 오판정률 실측이 낮게 나온다는 전제가 아직 없음
- 스마트스토어 유입 통계 직접 연동 — 단, 아래 "PROJECT.md 재검토" 참조(traffic_analytics로 상당 부분 선점 가능)
- 보류 큐(E6) — 수요가 실제로 쌓일 때만

### Architecture Approach

시스템은 3개의 키스페이스(광고 adId · 불사자 productId · 마켓 채널상품ID)를 가지며, 마켓 키가 유일한 다리인데 20일마다 세대 단절로 썩는다. **읽기는 자유(run-dir 파일, 불사자 MCP 읽기 게이트웨이)이고 쓰기는 좁은 문(CLI subprocess만)** 이라는 한 줄 규칙이 척추다. 보드는 파생본(derived view)이며 CLI 산출물에서 언제든 rebuild 가능해야 하고, 판정 로직(마진 공식·6규칙)은 절대 웹앱에서 재구현하지 않는다.

**주요 컴포넌트:**
1. **보드 투영기(Board Projector)** — run-dir 산출물 → 화면 행. 판정 재계산 절대 금지
2. **엔티티 해소기(Resolver)** — `mallProductId ↔ productId` 링크표. 확정 근거(`uploadedSuccessUrl.smartstore` 완전 일치) 없으면 추측 매칭을 저장하지 않고 미해상으로 남김
3. **잡 러너(Job Runner)** — subprocess 기동·env 주입·로그파일·종료감시·잡 락. 유일한 쓰기 통로
4. **불사자 읽기 게이트웨이** — 읽기 도구만 노출, 쓰기 도구는 허용목록에서 물리적으로 제외

### Critical Pitfalls

1. **엔티티 해소 팬아웃** — 불사자코드 1개가 사본 27건을 공유. 카디널리티 단언(`assert len(matched)==1`) 없이 조인하면 엉뚱한 상품에 크레딧을 태운다
2. **완료 플래그 공백** — 새 반영 경로가 불사자 AI 생성기를 안 거치면 `aiImageGenerated`가 안 찍혀 매 회차 전량 재작업·크레딧 무한 지출로 이어진다. 에러가 없다
3. **홍보배너 미탐** — 기성 해법 없음(검색으로 확인). 미탐(배너를 남김)이 오탐보다 훨씬 비싸다(타사 상표가 스마트스토어에 게시) — 판정은 배너 쪽으로 공격적으로
4. **동적 sectionCount가 기작업 스킵을 무력화** — 목표 장수가 상수(10)에서 함수(`min(제품이미지수,10)`, 하한2)로 바뀌는 순간, 이미 완료된 상품이 재작업 대상이 되거나 반대로 재작업 필요 상품이 영원히 안 잡힌다
5. **선택 스코프 불일치** — 화면 20건, 실행 3,000건. `report.md`(top-N 표시용)를 보드 데이터로 쓰면 구조적으로 발생

## 4개 문서 간 충돌 지점 (숨기지 않고 명시)

리서치가 서로 다른 결론에 도달한 지점들이다. 판정은 **근거의 강도(실측 > 추론 > 일반론)** 순으로 내렸다.

### 충돌 1 — v1 버튼 몇 개를 만드나

- **FEATURES.md**: "원칙: 버튼은 상세페이지 1개만 완성한다." 나머지 4개는 v1.x로 미룬다. 근거는 MVP 규율(경쟁 도구 분석, 일반론 MEDIUM).
- **ARCHITECTURE.md**: 버튼 5개 중 3개(입찰가·소재정리·쿠팡복사)는 **조인이 아예 필요 없다**(실측 코드 확인, HIGH). 특히 Phase 1에서 입찰가·소재정리 버튼을 **먼저** 만들어 3단 계약과 비가역 확인 UX를 실물로 검증하라고 권고 — 이건 "기능 추가"가 아니라 "위험이 큰 Core Value(엔티티 해소) 이전에 프레임을 싸게 검증하는" 리스크 관리 전략이다.

**판정:** 둘은 실제로 상충하지 않는다 — FEATURES는 "무엇을 v1의 완성 기준(Core Value)으로 삼을지"를 말하고, ARCHITECTURE는 "무엇을 어떤 순서로 만들지"를 말한다. **로드맵은 ARCHITECTURE의 순서(입찰가/소재정리를 먼저 얇게 완성)를 따르되, 마일스톤의 완료 기준(Core Value)은 FEATURES가 말하는 상세페이지 버튼으로 유지한다.** 입찰가·소재정리는 이미 Validated된 기능이므로 먼저 만들어도 "범위 확장"이 아니라 "프레임 검증 겸 조기 납품"이다. 쿠팡 복사(조인 불필요, Phase 0만 있으면 가능)를 Phase 1과 병렬로 당길지는 로드맵 작성 시 사용자 판단 필요 — FEATURES는 이를 v1.x로 미루라 하고 ARCHITECTURE는 "조기 배치 가능한 유일한 쓰기 버튼"이라 명시적으로 열어둔다.

### 충돌 2 — 단계 구조: PITFALLS 9단계 vs ARCHITECTURE 6단계

- **ARCHITECTURE.md**: Phase 0(잡러너+shim수리) → Phase 1(조인 없는 보드+버튼 2개) → Phase 2(엔티티 해소) → Phase 3(Core Value 상세버튼) → Phase 4(나머지 버튼, 병렬) → Phase 5(자동화 준비). **보드가 해소보다 먼저** — "해소 결과를 눈으로 보면서 전략을 조정해야 한다"는 명시적 반론(실측 기반, HIGH).
- **PITFALLS.md**: P0(기반) → P1(엔티티 해소) → P2(대상선별) → P3(관제탑 보드, 읽기전용) → P4(배너식별, 독립) → P5(상세페이지/크레딧쓰기) → P6(마켓쓰기) → P7(쿠팡복사) → P8(자동화). **해소가 보드보다 먼저** — 파이프라인 자연 순서를 따른 것으로, ARCHITECTURE만큼 "왜 이 순서인가"에 대한 반론이 명시적이지 않다.

**판정:** ARCHITECTURE의 순서를 채택한다 — "화면 없이 해소율을 만들면 5/8인지 8/8인지 모른 채 다음 단계로 간다"는 근거가 더 구체적이고 실측(해상률 베이스라인 5/8) 자체가 이 논리로 나왔다. 다만 PITFALLS가 낸 세분화 — **배너식별을 독립 phase로 분리(P4)**, **크레딧쓰기(P5)와 마켓쓰기(P6)를 분리** — 는 ARCHITECTURE의 6단계보다 근거가 강하다(검증 게이트가 생략되는 구체적 실패 모드를 지목). 아래 "통합 phase 구조"는 두 문서의 강점을 합친 7단계로 정리했다.

### 충돌 3 — 유입 판단을 광고로 대리할지, 유입수로 대리할지

- **PROJECT.md/FEATURES.md 전제**: 광고 규칙③(클릭20+/구매0)이 "유입은 있는데 안 팔리는 상품"의 근거.
- **ARCHITECTURE.md §4.5**: `bulsaja_traffic_analytics`가 productId로 직접 키잉된 유입수를 준다. **조인이 아예 불필요**하고 커버리지가 37,389건으로 광고 경유(3,094건, 검수통과분만)보다 훨씬 넓다. 광고 경유는 물갈이 세대 단절로 구멍이 난다(실측 0/160).

**판정:** ARCHITECTURE 손을 들어준다(실측 HIGH) — 다만 **U1(totalViews가 스마트스토어 실 조회수인지 불사자 내부 조회수인지)이 미검증**이라는 단서가 붙는다. 이 검증은 Phase 2 착수 직후 1시간 내 완료 가능(규칙⑤ 구매 발생 상품의 totalViews 대조)하도록 이미 리서치가 방법을 제시했다. → 아래 "PROJECT.md 재검토" 항목 참조.

## PROJECT.md의 기존 결정 중 재검토가 필요한 것

리서치가 PROJECT.md 작성 시점 이후 실측으로 새로 발견한 사실들이다. 각각 "어느 결정이 어떻게 바뀌어야 하는가"를 명시한다.

### 1. 동적 sectionCount ↔ "서버 플래그가 정본" 결정의 충돌 (PITFALLS #4)

PROJECT.md Key Decision: *"중복방지 대장을 새로 만들지 않는다 — 서버 플래그가 정본"* 및 *"상세페이지 기작업 스킵 (서버 aiImageGenerated/aiImageOutputCount 기준)"* 은 **목표 장수가 상수 10일 때만** 안정적으로 작동하던 규칙이다. 그런데 같은 문서의 새 Active 요구(*"생성 장수를 min(제품이미지 수,10) 하한 2로 비례시킨다"*)가 목표를 변동값으로 만든다.

→ **PROJECT.md의 스킵 규칙 결정에 명시적 수정이 필요하다:** 스킵 판정을 목표 장수 비교(`기존장수 >= 목표장수`)에서 분리해 `aiImageGenerated AND aiImageOutputCount >= 2`라는 **절대 조건**으로 바꾸고, 계산된 `sectionCount`는 상품별로 고정 저장(재계산은 `--recompute` 명시 시만)해야 한다. 이건 새 요구사항이 아니라 **기존 Key Decision의 부작용을 막는 필수 보정**이므로 Phase 0~1 범위에 반드시 포함한다.

### 2. "로컬 대장 금지" 결정과 완료 플래그 공백의 충돌 (PITFALLS #2)

PROJECT.md Out of Scope: *"중복방지용 로컬 대장 신설 금지 — 서버 플래그가 이미 정본"*. 이 명제는 **불사자 AI 생성기가 유일한 쓰기 경로일 때만** 참이다. 그런데 Active 요구가 요구하는 반영 방식(기존 상세 이미지에서 배너 제거 → AI 생성 → `market_update`로 직접 수정업로드)이 만약 불사자 AI 생성기의 표준 경로를 그대로 타지 않는다면, `aiImageGenerated`가 안 찍혀 정본이 조용히 비게 된다 — 매 회차 재작업 무한 루프.

→ **Phase 0에서 실측으로 답해야 한다:** 우리가 쓸 반영 경로가 실제로 `aiImageGenerated`를 찍는가(상품 1건 반영 전/후 `uploadDetailContents` dump/diff). 답이 "아니오"면 PROJECT.md의 "로컬 대장 금지" 결정을 **"서버 플래그를 정본으로 하되, 안 찍히는 경로는 OR 기반 보완 인덱스로 명시적으로 보강한다(완료 = 서버플래그 OR 로컬기록)"**로 수정해야 한다. 이건 "로컬 대장 신설 금지"를 어기는 게 아니라, 정본이 하나라는 원칙을 지키면서 공백을 메우는 것이다. Key Decision 표에 조건부 각주를 추가해야 한다.

### 3. 유입 소스: 광고 대리 → traffic_analytics 직결로 격상 (ARCHITECTURE §4.5)

PROJECT.md Key Decision: *"유입 판단을 네이버광고 데이터로 대리한다 — 연동 비용 0. 스마트스토어 통계는 다음 마일스톤"* 그리고 Out of Scope: *"스마트스토어 유입 통계 연동 — 1차는 광고 데이터로 대리한다."* PROJECT.md 자체의 Context에도 *"불사자 MCP 프로필에 유입수·상품 조회 기능이 있다 — 2차 유입 소스 후보"*라고 적혀 있었다.

→ 실측 결과 이건 **2차가 아니라 1차 후보로 격상되어야 한다.** `traffic_analytics`는 조인 없이 productId로 직접 유입수(37,389건, 30일)를 주며, 광고 경유(3,094건, 물갈이로 구멍 남)보다 커버리지가 넓고 리스크가 없다. **PROJECT.md의 "유입 판단을 광고로 대리" 결정을 "유입 판단은 traffic_analytics(1차) + 쿠팡 판매경로(1차) + 광고 규칙③(보조, CTR 신호가 필요한 썸네일 버튼용)"로 수정**할 것을 권고한다. "스마트스토어 유입 통계 연동을 다음 마일스톤으로 미룬다"는 Out of Scope 항목도 재검토 대상이다 — traffic_analytics가 사실상 그 역할의 상당 부분을 대체할 수 있다. 단, **U1(totalViews의 의미) 검증이 선행 조건**이다.

## Implications for Roadmap

### 통합 Phase 구조 (ARCHITECTURE 6단계 + PITFALLS 9단계 세분화를 합친 권고안, 7단계)

이 구조는 위 "충돌 2" 판정에 따라 ARCHITECTURE의 순서(보드가 해소보다 먼저, 위험이 싼 버튼을 Core Value 앞에 배치)를 골격으로 하고, PITFALLS의 세분화(배너식별 독립 phase, 크레딧쓰기/마켓쓰기 분리)를 반영했다.

#### Phase 0: 기반 — 잡 러너 + CLI 어댑터 + 안전 계약
**Rationale:** 버튼 5개 전부가 이 위에 선다. 또한 Core Value 실행 경로(`detail_batch.py`)가 이 맥북에서 지금 안 돈다(윈도 경로 하드코딩) — 로드맵 착수 전 반드시 수리해야 함(§7.1).
**Delivers:** subprocess 잡 러너(env주입/로그파일/종료감시/잡락), SQLite 잡 레지스트리, SSE 로그 tail, 로컬 보안(127.0.0.1 바인드+Host화이트리스트+CSRF+부팅토큰), 계정 라우팅 설정(매핑 테이블+실시간 프로필 확인), dry-run=commit 대상선정 함수 단일화 계약, 쓰기 전 백업 필수 계약.
**결정적 실측 항목(착수 직후):** (a) `detail_batch.py` shim 수리, (b) 반영 경로가 `aiImageGenerated`를 찍는지 dump/diff 1건, (c) 동적 sectionCount용 스킵조건 재정의.
**Addresses:** STACK 핵심결정 1·2·3, FEATURES A6/A7 계정배지, PITFALLS #2/#4/#5(부분)/#10/#11/#12/#13/#14.
**Avoids:** 완료 플래그 공백, 낡은 스냅샷 쓰기, 계정 오라우팅, 로컬 서버 노출, 프로세스 고아화, dry-run≠commit 괴리.

#### Phase 1: 조인 없는 보드 + 조인 불필요 버튼 2개 (입찰가 인상 / 꺼진 소재 정리)
**Rationale:** 조인이 필요 없는 버튼으로 3단 계약("판정→미리보기→실행")과 위험 사다리 UX를 실물로 검증한다. Core Value의 최대 리스크(엔티티 해소)를 지기 전에 프레임을 확정한다. 선택 모델(3단 선택)은 **보드의 첫 작업**으로 넣는다 — 나중에 끼우면 다시 짠다.
**Delivers:** run-dir 리더, 회차 선택, 6규칙 탭, 3단 선택 모델(행/페이지/필터전체)+실행 캡, 위험 사다리 확인 UX, 승인 로그, `bids`/`prune` dry-run↔commit↔revert 왕복.
**Addresses:** FEATURES A1(부분:광고행만)/A4/B1/B2/B3/C1/C2/D1/D2/F1.
**Avoids:** 선택 스코프 불일치(Pitfall 9), 정지 소재 오독(Pitfall 6, 규칙 판정 결과를 그대로 큐로 안 씀).

#### Phase 2: 엔티티 해소 + 상품 캐시 (최대 리스크 격리)
**Rationale:** Phase 1의 보드가 있어야 해상률을 눈으로 보면서 전략(S1 제목검색 → S2 그룹 전수 인덱싱)을 조정할 수 있다. 착수 직후 1시간 내 U1(traffic_analytics 의미) 검증을 끝낸다 — 이 결과가 유입 소스 채택(위 재검토 3)을 가른다.
**Delivers:** 불사자 읽기 게이트웨이, `product_cache`+`ad_link` 링크표(세대 필드 포함), 해소기 S0~S3, 해상률 대시보드(해상/미해상/만료 4상태), 카디널리티 단언(팬아웃 방어).
**완료 증거:** 규칙③+⑤ 약 120행의 해상률이 숫자로 나오고 베이스라인 5/8(62.5%)을 넘김. 미해상 사유가 분류됨.
**Addresses:** FEATURES A1(완성)/A3.
**Avoids:** 엔티티 팬아웃(Pitfall 1), 낡은 스냅샷/유령사본(Pitfall 5).

#### Phase 3: 홍보배너 식별 파이프라인 (독립 phase — 상세생성과 절대 묶지 않는다)
**Rationale:** 기성 해법이 없는 미검증 설계(코퍼스 빈도 pHash + QR검출 + 회색지대만 비전LLM)이며, 상세생성 phase에 끼워 넣으면 검증 게이트가 생략된다는 게 PITFALLS의 명시적 경고다. 미탐 비용(타사 상표 게시)이 오탐 비용보다 훨씬 크므로 배너 쪽으로 공격적 판정.
**Delivers:** pHash 코퍼스 빈도 판정(**타오바오상품번호 기준 distinct**, productId 기준 금지 — 물갈이로 오염됨), QR검출 확정신호, 회색지대 비전LLM(맨앞/맨뒤 1장 한정), 제거율 상한(50%)/하한 게이트(2장 미만 스킵) 안전장치.
**완료 증거(=phase 종료 조건):** 100건 손라벨링 세트에서 **미탐 0%**, 오탐 ≤10%.
**Avoids:** 홍보배너 미탐(Pitfall 3) — 이 문서에서 가장 긴 절.

#### Phase 4: 상세 상태 판정 + 상세페이지 버튼 (Core Value)
**Rationale:** Phase 0(장기잡 인프라)+Phase 2(productId 해소)+Phase 3(깨끗한 입력) 셋 다 필요. 이 phase의 완성이 v1 마일스톤의 완료 기준(FEATURES 원칙)이다.
**Delivers:** 🔴🟡⚪ 판정(타입 정규화 함수 필수 — 문자열/불리언/정수 혼재 방어), 결정론적 sectionCount 저장(재계산 금지), 크레딧 범위 견적, 접수/폴링 2분할 잡(자동 감시 인큐), 멱등키, 타임아웃≠실패(recover 우선), market_update 반영 + 백업/restore 계약(같은 phase에 restore 포함).
**완료 증거:** 🔴 상품 5건을 접수→폴링→자동반영까지 터미널 없이 완주, 브라우저 닫아도 완주. 동일 상품 2회차 연속 실행 시 재접수 0건.
**Avoids:** imageTranslated 타입버그, 동적 sectionCount 붕괴(Pitfall 4), 크레딧 사고 3종(Pitfall 8), 되돌릴 수 없는 마켓 쓰기(Pitfall 10).

#### Phase 5: 나머지 쓰기 버튼 (병렬 가능 트랙)
**Rationale:** 쿠팡 복사는 조인이 불필요(`find_by_code` 자체 해결)하므로 Phase 0만 있으면 착수 가능 — 로드맵 배치 시 조기 병렬화 여부는 사용자 판단(위 "충돌 1" 참조). 썸네일 교체는 규칙②(CTR)가 근거라 Phase 2 필요.
**Delivers:** 쿠팡 prep→resolve→build→ship→gate→apply 원클릭(`apply --commit`만 재확인), 썸네일 교체 dry-run↔commit.
**Addresses:** FEATURES "Add After Validation" 버튼 2~5.
**Avoids:** 되돌릴 수 없는 쓰기(쿠팡 apply는 3단계 자동화에서도 영구 수동, 다른 색으로 구분).

#### Phase 6: 자동화 2단계 준비 (새 코드보다 데이터가 필요)
**Rationale:** PROJECT.md의 2단계 진입 조건("오판정률이 실측으로 낮게 나올 것")은 숫자 기준이 없으면 감으로 판단하게 된다. 승인 로그가 v1부터 쌓여 있어야 이 phase가 성립한다.
**Delivers:** 승인 로그 집계, 버튼별 오판정률/불일치율 계량 기준 확정, "전부 실행" 버튼 개방 여부 판단.
**Avoids:** dry-run≠commit 괴리가 자동화 단계에서 드러나지 않는 것(Pitfall 14).

### Phase Ordering Rationale

- **왜 조인 없는 버튼이 Core Value보다 먼저인가**: 엔티티 해소는 이 프로젝트 최대 아키텍처 리스크(실측 0/160 사례)다. 리스크가 큰 것을 먼저 만들면 프레임 자체의 결함(선택모델, 확인UX)과 조인 실패가 뒤섞여 원인 진단이 어려워진다. 조인 없는 버튼으로 프레임을 먼저 굳히면 Phase 2의 실패가 순수하게 조인 문제로 격리된다.
- **왜 배너식별이 독립 phase인가**: 검증 게이트(100건 라벨링, 미탐 0%)가 생략되기 가장 쉬운 지점이다. 상세생성 phase와 묶으면 "일단 되니까 넘어가자"는 압력이 검증을 건너뛰게 만든다.
- **왜 마켓쓰기(수정업로드)를 크레딧쓰기(AI생성)와 분리해 취급하는가**: 둘의 실패 모드와 복구 비용이 다르다 — 크레딧쓰기는 멱등키·recover로 방어하고, 마켓쓰기는 백업/restore로 방어한다. 하나의 완료 조건("성공")으로 뭉치면 어느 쪽이 실패했는지 모호해진다.

### Research Flags

Phase 진입 시 추가 리서치/실측이 필요한 곳:
- **Phase 0:** `aiImageGenerated` 기록 여부 실측(추측 금지) — 결과에 따라 PROJECT.md Key Decision 수정 여부가 갈림
- **Phase 2:** U1(traffic_analytics의 totalViews 의미) — 1시간 내 검증 가능하나 미검증 상태로 착수하면 안 됨. S2(그룹 전수 인덱싱) 후 실용 해상률 상한 재측정 필요
- **Phase 3:** 홍보배너 식별 전체 — 기성 해법이 없는 영역이므로 100건 라벨링 세트 구축과 임계값 튜닝에 반복 실험 필요
- **Phase 4:** 크레딧 견적의 사전 계산 가능성(제품이미지 수를 접수 전에 아는지), 취소(Stop)의 실제 안전 경계(접수 후 폴링 중단 시 크레딧 기소모 여부)

Standard 패턴이라 phase 리서치를 건너뛰어도 되는 곳:
- **Phase 1:** subprocess 잡 러너, SQLite 잡 락, dry-run/commit 3단 계약은 STACK.md·ARCHITECTURE.md가 코드 정독으로 이미 구체적 구현 패턴까지 제시함
- **Phase 5(쿠팡 트랙):** 기존 6단계 파이프라인이 1차 파일럿 84건으로 이미 검증됨. 웹앱은 UI 래핑만
