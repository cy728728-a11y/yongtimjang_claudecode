# Feature Research

**Domain:** 내부 운영 콘솔 (operational console) — 대량 항목 판정 + 위험한 쓰기 작업 실행. 1인 로컬 전용
**Researched:** 2026-09-19
**Confidence:** MEDIUM-HIGH (UX 패턴은 공개 설계 레퍼런스로 검증 / 프로젝트 특수사항은 PROJECT.md·기존 스크립트 실측으로 확인)

## 요약 (먼저 읽을 것)

이 도구의 경쟁 상대는 SaaS 어드민이 아니라 **지금 쓰는 CLI + 스프레드시트**다.
CLI 가 이미 `--commit` 게이트·백업·recheck·체크포인트를 다 갖고 있다. 따라서 웹앱이 더해야 할 가치는
"기능"이 아니라 **선택·미리보기·결과확인의 마찰 제거**다. 완료 기준이 "마찰"이라는 PROJECT.md 결정과 일치한다.

세 줄 요약:

1. **Table stakes 의 대부분은 UI 가 아니라 계약(contract)이다** — plan 아티팩트, job 객체, 항목 단위 결과, 감사 JSONL.
   이 넷이 없으면 화면을 아무리 예쁘게 만들어도 사고가 난다. 그리고 이 넷이 곧 2·3단계 자동화의 API 이기도 하다.
2. **확인(confirmation)은 전 버튼 동일하면 안 된다.** 위험 사다리로 차등해야 한다. 5개 버튼에 똑같이
   type-to-confirm 을 걸면 3일 안에 사람이 글자를 기계적으로 친다 (NN/g: 경고 과잉 → 주의 소멸).
3. **가장 큰 사고 벡터는 "선택"이다.** 삭제 버튼이 아니라 "필터 전체 선택"이 3,000건을 집는 순간이다.
   선택 범위 표시와 실행 캡이 확인 모달보다 효과가 크다.

## Feature Landscape

### Table Stakes (없으면 도구가 안 쓰이거나 사고 난다)

#### A. 보기 (판정 결과 표시)

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| **A1. 상품 단위 보드 (1행 = 상품 1개)** | 이게 제품 자체다. 광고소재 단위로 보면 상품 하나가 여러 줄로 쪼개져 중복 작업이 난다 | **HIGH** | 진짜 난이도는 표가 아니라 **광고 소재 ↔ 불사자 상품 조인**이다. PROJECT.md Active 에 "현재 두 데이터가 이어져 있지 않음"으로 미해결 표시됨. 조인 실패율이 이 프로젝트의 최대 미지수 |
| **A2. 상세 상태 3단계 배지 (🔴/🟡/⚪)** | 무엇을 고쳐야 하는지가 한 눈에 안 보이면 보드가 아니라 로그다 | **LOW** | `imageTranslated` × `aiImageGenerated` 플래그 조합. 실측 확인됨, 추가 API 콜 0 |
| **A3. 서버 플래그가 정본임을 화면에서 지키기** | 로컬 캐시로 "작업 완료"를 표시하면 이미 한 상품에 크레딧을 또 태운다 | **MEDIUM** | 캐시는 하되 **표시에 조회시각을 붙이고**, 실행 직전엔 반드시 재조회. PROJECT.md "진실의 원천" 제약 |
| **A4. 필터 + 정렬 (상태별·계정별·성과별·우선순위별)** | 수백~수천 행에서 대상 좁히기가 첫 동작 | **LOW** | 서버(로컬 API)측 필터. 클라이언트 필터는 "필터 전체 선택"과 충돌한다 |
| **A5. 선택 건수 상시 표시 + 선택 범위 명시** | 대량 선택의 1차 방어선 | **MEDIUM** | 후술 B1 |
| **A6. 불사자 계정 프로필 배지 (헤더 상시 + 확인창 안)** | 계정 둘(용팀장/용쌤). 잘못된 계정에 쓰면 되돌릴 수 없다 | **LOW** | 실측 사고 이력 있음. 확인 모달 본문에 계정명을 **문장으로** 박는다 |
| **A7. 크레딧 잔액 표시** | 크레딧 소모 버튼 2개(상세·썸네일)가 있다 | **LOW** | 잔액 차이로 회차 비용 역산 금지 — 잔액은 참고치, 정본은 실행 집계 |

#### B. 고르기 (대량 선택)

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| **B1. 3단 선택 모델 분리: 행 / 이 페이지 전체 / 필터 결과 전체 N건** | "보이는 것만 vs 필터 전체" 함정이 이 도구 최대 사고원 | **MEDIUM** | 업계 표준(PatternFly, Helios): 헤더 체크박스는 **페이지만**, "필터 결과 전체 3,412건 선택"은 **별도 배너로 한 번 더 눌러야** 켜진다. 자동 승격 금지 |
| **B2. 필터 전체 선택은 ID 목록이 아니라 "쿼리 + 제외목록"으로 보관** | 3,000개 ID 를 프론트가 들고 있으면 개별 해제·페이지 이동에서 어긋난다 | **MEDIUM** | 서버에 `{filter, excluded_ids[]}` 를 넘긴다. 이게 plan 입력이 된다 |
| **B3. 실행 캡 (1회 최대 N건 / 최대 크레딧)** | 확인 모달보다 강한 최후 방어선. 오타·오선택이 여기서 죽는다 | **LOW** | 설정 파일 값. 초과 시 실행 자체를 막고 "상위 N건만" 제안. blast-radius 제한의 최소 구현 |
| **B4. 선택이 필터 변경에도 살아남되 화면에 경고** | 필터 바꾸면 선택이 조용히 사라지거나 조용히 남는다 — 둘 다 사고 | **LOW** | "현재 필터 밖 12건이 선택에 남아 있음" 배너 |

#### C. 미리보기 (dry-run) — 이 도구의 척추

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| **C1. dry-run 결과가 저장되는 plan 아티팩트 (= run-dir)** | **실행은 plan 을 적용하는 것이지 다시 계산하는 게 아니다.** 재계산하면 본 것과 실행된 것이 달라진다 | **MEDIUM** | Terraform `plan -out` / `apply plan.tfplan` 패턴. 기존 CLI 가 이미 `--run-dir` 로 이걸 한다 — **UI 는 run-dir 를 새로 만들지 말고 그대로 쓴다** |
| **C2. plan 신선도 검사 (stale plan 거부)** | prep → 사람 검토 → commit 사이 몇 시간~며칠이 뜬다. 그 사이 소재가 되살아나고 상품이 팔린다 | **MEDIUM** | 기존 `prune.py` 에 `recheck_failed` 로 이미 구현돼 있음 → UI 는 이 거부를 **에러가 아니라 정상 흐름**으로 보여줘야 한다. "상태가 바뀐 3건을 뺐다. 새로 미리보기." `--force` 우회는 만들지 않는다 |
| **C3. 영향 범위 요약 (실행 N / 스킵 S / 차단 B, 사유별 그룹)** | "100건 선택 → 실제로는 62건만 바뀜"을 실행 전에 알아야 한다 | **MEDIUM** | 스킵 사유를 묶어서 보여준다: 기작업 42 · 상품잠금 3 · 이미지없음 5. 사유 클릭 → 해당 행 필터 |
| **C4. 비가역 항목 별도 표기** | 같은 미리보기 안에서 "되돌릴 수 있는 것"과 "없는 것"이 섞이면 확인이 무의미하다 | **LOW** | 상세생성·썸네일(크레딧) / 쿠팡 apply(마켓 쓰기) = 비가역. 입찰가·prune = 백업 있음 |
| **C5. 항목 단위 before/after 미리보기 (최소 상위 몇 건)** | 집계만 보면 로직 오류를 못 잡는다 | **MEDIUM** | 상세페이지: 입력으로 들어갈 제품 이미지 썸네일 나열(= 홍보배너 제거 결과). 입찰가: 100 → 110 |
| **C6. 크레딧 사전 견적 (범위로)** | 접수하면 못 무른다. PROJECT.md Constraints 명시 | **MEDIUM** | `건수 × 장수` 인데 장수가 `min(제품이미지 수, 10)` 하한 2 라 **가변** → 반드시 범위로: "52건 · 약 180~420 크레딧 (잔액 1,930 → 예상 1,510~1,750)". 단일 숫자로 쓰면 거짓말이 된다 |

#### D. 실행과 확인

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| **D1. 위험 사다리 기반 차등 확인 (아래 표 참조)** | 전부 같은 확인 = 클릭 피로 = 확인이 사라짐 | **LOW** | 설계 규칙일 뿐 구현은 싸다. **가장 값싸고 가장 효과 큰 항목** |
| **D2. 확인 문구에 숫자·계정·크레딧을 문장으로 박기** | "정말 실행할까요?"는 아무 정보가 없다 | **LOW** | "용쌤 계정 상품 52건에 AI 상세를 생성한다. 약 180~420 크레딧. 되돌릴 수 없다." |
| **D3. job 객체 + 상태 페이지 (브라우저 닫아도 살아있음)** | 상세 배치는 수십 분~시간 단위. 탭 닫힘 = 작업 유실은 즉시 신뢰 상실 | **HIGH** | UI 는 job id 만 받고 즉시 반환. 상태는 로컬 파일/SQLite 에 durable 저장, UI 는 폴링. 기존 스크립트의 체크포인트 재개와 결합 |
| **D4. 중단(Stop) 버튼** | 잘못 눌렀을 때 손실을 끊는 유일한 수단 | **MEDIUM** | 즉시 kill 이 아니라 **안전 경계에서 멈춤**(다음 항목 접수 안 함). 진행 중 접수 건은 recover 로 회수. "폴링 타임아웃 = 정상"이라 강제 kill 은 크레딧 이중지불 유발 |
| **D5. 실행 로그 실시간 tail** | 1인 도구는 운영=디버깅이다. 요약만 주면 막혔을 때 터미널로 돌아간다 | **LOW** | CLI stdout 을 그대로 흘린다. 예쁘게 만들 필요 없음 |

**위험 사다리 (D1 구체안)**

| 버튼 | 가역성 | 확인 단계 | 실행 후 |
|---|---|---|---|
| 입찰가 인상 | revert 있음 | 미리보기 → **버튼 1회** (모달 없음) | 결과 옆에 **되돌리기 버튼** 상시 노출 |
| 꺼진 소재 정리 | 백업 선행 | 미리보기 → 모달 1회 (백업 경로 표시) | 백업 파일 경로를 이력에 기록 |
| 썸네일 교체 | 크레딧 소모 | 미리보기 → 모달 + **견적 표시** | 실제 소모 크레딧 기록 |
| 상세페이지 작업 | 크레딧 + 마켓 수정 | 미리보기 → 모달 + 견적 + **건수 타이핑**(예: `52`) | 소모 크레딧 + 업로드 결과 기록 |
| 쿠팡 복사 `apply --commit` | 마켓 쓰기, 비가역 | 미리보기 → 모달 + **건수 타이핑** + 계정 확인 | 3단계 자동화에서도 **끝까지 사람이 누른다** |

> 타이핑 확인은 **상위 2개에만**. 건수를 치게 하면 "예"보다 낫다 — 숫자를 치는 동안 숫자를 본다.

#### E. 결과와 재시도 (부분 실패)

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| **E1. 항목 단위 결과표 (성공/실패/스킵/보류)** | "73/100 성공"만 주면 나머지 27건을 사람이 손으로 찾아야 한다 | **MEDIUM-HIGH** | 상단은 카운터 배지, 본문은 항목별 행: 상품명 · 상태 · 사유코드 · 재시도가능 여부 |
| **E2. 사유 코드 체계 (모호한 실패 금지)** | "실패"만으로는 다시 돌릴지 포기할지 못 정한다 | **MEDIUM** | 최소 셋으로 나눈다: **재시도 가능**(일시오류·타임아웃) / **재시도 무의미**(상품잠금·이미지없음·기작업) / **판단 필요**(보류 큐로) |
| **E3. "실패분만 재시도" 버튼** | 성공분을 다시 태우면 크레딧 이중 지불 | **MEDIUM** | 재시도는 **원래 plan 의 부분집합으로 새 plan 을 만든다**(새 run-dir). plan 재사용 금지 — 시간이 흘렀으므로 |
| **E4. 멱등 보장 = 실행 직전 서버 플래그 재조회** | 가장 비싼 실수(크레딧 이중 지불)의 유일한 확실한 방어 | **MEDIUM** | 기존 `aiImageGenerated` 스킵 로직 재사용. **UI 단 중복 방지에 의존하지 않는다** |
| **E5. 타임아웃을 실패로 표시하지 않기** | 폴링 타임아웃은 접수모드 정상동작. 실패로 보고 재생성하면 크레딧 이중 지불 | **LOW** | 별도 상태 `대기중(확인필요)` + **recover 버튼**을 재시도보다 먼저 배치 |
| **E6. 보류 큐 (판단 필요 항목)** | 애매한 건을 실행 흐름에 섞으면 전체가 멈춘다 | **MEDIUM** | 기존 썸네일 `보류(주의)` → `decisions.json` 패턴 일반화. 단, **사람 큐는 최소화** 원칙과 균형 — 틀려도 치명적이지 않으면 자동 결정 |

#### F. 이력 / 감사

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| **F1. append-only 실행 이력 (JSONL)** | "언제 뭘 얼마 써서 했나"가 없으면 중복 작업과 비용 논쟁이 영원히 반복 | **LOW-MEDIUM** | 레코드: `시각(UTC) · 작업종류 · 계정 · plan_id/run-dir · 대상건수 · 결과카운트 · 소모크레딧 · 백업경로 · 실행자(manual/auto)`. 파일 한 개면 충분, DB 불필요 |
| **F2. 보드 행에 "최근 작업" 표시** | 이력을 보러 가야만 보이면 아무도 안 본다 → 중복 작업 발생 | **LOW** | "3일 전 상세생성 ✓" 같은 한 줄 |
| **F3. 이력 → plan/로그/백업으로 역추적 링크** | 사고 났을 때 되돌릴 근거가 파일 경로다 | **LOW** | 경로만 저장하면 됨 |
| **F4. 되돌리기 버튼 (가역 작업 한정)** | `bids --revert --commit` 이 이미 있는데 터미널로 가게 하면 안 쓴다 | **LOW** | 이력 행에서 바로. **비가역 작업에는 이 버튼을 만들지 않는다**(있는 척 금지) |

### Differentiators (계속 쓰게 만드는 것 — 완료 기준이 "마찰")

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| **G1. 5버튼 전부 동일한 "판정 → 미리보기 → 실행" 프레임** | 한 번 배우면 다섯 개를 안다. 그리고 이게 2·3단계 자동화의 전제 조건(PROJECT.md) | **MEDIUM** | 공통 컴포넌트 1세트 + 작업별 어댑터. **버튼마다 다른 흐름을 만들면 자동화 때 전부 다시 만든다** |
| **G2. "오늘 할 일" 진입 큐** | 보드를 열자마자 무엇부터 할지 정해져 있다. 필터 조작 0회 = 마찰 최소 | **MEDIUM** | 규칙③(유입 있는데 안 팔림) × 🔴중국어 원본 = 최우선. 규칙⑤(팔림) × 🔴 = 그 다음. 상위 N건 고정 |
| **G3. 오판정 1클릭 피드백 ("이건 아님")** | **2단계 자동화로 올라가는 유일한 계측 수단.** PROJECT.md 가 "오판정률이 실측으로 낮게 나올 것"을 2단계 전제로 못 박았다 | **LOW-MEDIUM** | 행에 버튼 하나 + 카운터. 정교한 라벨링 UI 불필요. **이게 없으면 v1 이 끝나도 2단계로 못 간다** |
| **G4. 예측 대 실제 대조 (plan N건 vs 실제 M건)** | dry-run 을 신뢰할 수 있는지 숫자로 나온다. G3 와 같은 목적 | **MEDIUM** | 이력에 두 숫자를 같이 적어두면 공짜로 나온다 |
| **G5. 크레딧 가계부** | 건당 실제 비용을 알아야 "이 작업을 계속할지" 판단한다. 잔액 역산은 틀린다고 실측됨 | **MEDIUM** | 작업별 누적 / 주간 합계 / 건당 평균. 정본은 실행 집계 |
| **G6. 완료 알림 (맥 알림센터 / 한 줄 요약)** | "감시 없이 띄우지 마라" — 4시간 놀았던 실측 사고의 UI 판 | **LOW** | `osascript` 한 줄. 요약: "상세 52건 → 성공 44 실패 3 스킵 5, 크레딧 312" |
| **G7. 이어하기 (어제 run-dir 재개)** | 중간에 죽은 작업을 터미널 안 열고 잇는다 | **MEDIUM** | 체크포인트 재개가 이미 스크립트에 있음. UI 는 "미완료 run 2개" 목록만 띄우면 됨 |
| **G8. 키보드 조작 (j/k 이동, x 선택, Enter 미리보기)** | 1인 도구라 학습비용을 신경 쓸 필요가 없다. 수백 행 처리에서 마찰이 가장 크게 줄어드는 지점 | **LOW** | 마우스 왕복 제거. 접근성 고려 불필요(사용자 1명) |
| **G9. 실행 중에도 보드가 잠기지 않음** | 수십 분짜리 작업 돌려놓고 다른 상품을 본다 | **MEDIUM** | D3(job 객체) 의 부산물. 단 **같은 상품에 두 작업 동시 실행은 잠근다** |

### Anti-Features (일부러 안 만든다)

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| **인증·로그인·권한·역할** | "어드민이니까" | 사용자 1명 로컬. 프로젝트가 배로 커진다 | PROJECT.md Out of Scope 그대로 |
| **모든 버튼에 type-to-confirm** | 안전해 보임 | 클릭 피로 → 기계적 입력 → 확인이 사실상 사라짐 (NN/g: 과잉 경고는 주의를 죽인다) | 위험 사다리(D1). 타이핑은 상위 2개만 |
| **범용 undo / 전역 롤백 엔진** | "되돌릴 수 있으면 안전" | 마켓 쓰기·크레딧 소모는 **근본적으로 비가역**. undo 버튼이 있으면 안전하다고 착각해서 더 위험해진다 | 가역 작업에만 revert 버튼. 비가역엔 버튼 자체를 안 만든다 |
| **Optimistic UI (낙관적 업데이트)** | 반응이 빨라 보임 | 쓰기 작업에서 거짓 성공을 표시한다. 서버 플래그가 정본인 이 프로젝트와 정면 충돌 | 서버 응답 후 갱신. 느리면 job 상태로 보여준다 |
| **정밀 진행률 % 바** | 익숙함 | 접수→폴링 구조라 정확한 %를 낼 수 없다. 가짜 %는 신뢰를 깎는다 | 건수 카운터 `44/52 처리` + 경과시간 |
| **WebSocket 실시간 스트리밍 전면 도입** | 모던해 보임 | 1인 로컬에서 폴링 2~5초로 충분. 재연결·상태동기 버그만 늘어난다 | 폴링 + job 상태 파일 |
| **무한 스크롤 보드** | 요즘 UI | 대량 선택과 상극("전체"의 정의가 흔들린다), 위치 기억 안 됨 | 페이지네이션 또는 가상 스크롤 + **명시적 선택 범위**(B1) |
| **인라인 편집 가능한 스프레드시트형 보드** | "엑셀처럼 고치고 싶다" | 편집 경로가 검증된 CLI 를 우회한다 → 함정 방어(장바구니 혼동·그룹입찰·배송비 P75)가 통째로 무력화 | 읽기 전용 보드 + 정해진 5버튼만 |
| **"전부 실행" 통합 매크로 (v1)** | 편해 보임 | 5개 작업의 사고 반경이 한 번에 터진다. 오판정률 실측 전에는 근거가 없다 | 2단계에서 **버튼별로** 일괄승인 도입 |
| **작업 여부용 로컬 대장 DB** | 조회가 빨라짐 | 진실이 둘이 되어 어긋난다 (PROJECT.md 명시) | 서버 플래그 + 조회시각 표시 캐시 |
| **알림 규칙 엔진 / 이메일·슬랙 리포트** | 어드민 표준 기능 | 한 명이 화면 앞에 있다. 규칙 관리 UI 가 본 기능보다 커진다 | G6 한 줄 알림 |
| **대시보드 빌더 / 커스텀 차트 위젯** | "성과가 보이면 좋겠다" | 전환율 측정은 Out of Scope. 위젯 만들다 Core Value 를 못 끝낸다 | 이력 JSONL → 필요할 때 스크립트로 집계 |
| **휴지통 / 소프트 삭제 UI** | 삭제가 무서움 | 백업 JSON + revert 가 이미 있다. UI 를 또 만들면 복원 경로가 둘 | 백업 파일 경로를 이력에 노출(F3) |
| **모바일 반응형 / 다크모드 / i18n** | 기본 소양처럼 느껴짐 | 맥북 로컬 1인. 순수 비용 | 데스크톱 고정폭 |
| **작업 큐 우선순위 재정렬 UI** | 스케줄러 같아 보임 | 동시 작업이 1~2개다. 큐 관리할 게 없다 | FIFO + Stop |
| **CLI 로직의 웹앱 내 재구현** | "웹에서 다 하면 깔끔" | 실측으로 쌓은 가드레일 유실 (PROJECT.md 최상위 제약) | subprocess 래퍼 |

### Dependency Notes

- **모든 것이 A1(조인)에 걸려 있다.** 조인이 불확실(PROJECT.md 미해결)하므로 **1페이즈는 조인 검증 전용**이어야 한다.
  조인 성공률이 낮게 나오면 보드 단위 자체를 재설계해야 한다.
- **C1(plan 아티팩트)이 자동화 진화 경로의 유일한 접점이다.** 2단계는 "C1 을 보고 사람이 전부 실행",
  3단계는 "C1 을 사람 없이 통과". plan 을 파일로 남기지 않고 화면 상태로만 들고 있으면 자동화 때 전부 다시 만든다.
- **D3(job)이 E1·F1·G9 를 전부 낳는다.** 동기 실행으로 v1 을 만들고 나중에 비동기로 바꾸는 건 사실상 재작성이다.
  **처음부터 job 으로 간다.**
- **E4(멱등)는 UI 기능이 아니라 기존 스킵 로직 재사용이다.** UI 에서 중복 방지를 새로 구현하면 진실이 둘이 된다.
- **G3 은 싸지만 빼면 프로젝트 목표(자동화)가 막힌다.** v1 에 넣는다.

## MVP Definition

### Launch With (v1)

**원칙: 버튼은 상세페이지 1개만 완성한다.** Core Value 가 거기고, 나머지 4개는 G1 프레임 재사용이라 v1.x 가 싸진다.

- [ ] A1 광고소재↔상품 조인 + 조인 실패율 실측 — 이게 안 되면 나머지가 무의미
- [ ] A2 상태 3단계 배지 / A3 서버 정본 + 조회시각 / A4 필터·정렬
- [ ] A6 계정 프로필 배지 — 1줄, 사고 이력 있음
- [ ] B1 3단 선택 모델 + B2 쿼리+제외목록 + B3 실행 캡
- [ ] C1 plan 아티팩트(기존 run-dir 그대로) + C2 stale 거부 + C3 영향범위 요약
- [ ] C6 크레딧 견적(범위 표기) — 상세 버튼용
- [ ] D1 위험 사다리 + D2 문장형 확인 + D5 로그 tail
- [ ] D3 job 객체 + 상태 페이지 (브라우저 닫고 돌아와도 보임) + D4 Stop
- [ ] E1 항목 결과표 + E2 사유 코드 3종 + E3 실패분만 재시도 + E4 멱등 + E5 타임아웃 recover
- [ ] F1 감사 JSONL + F2 행별 최근작업
- [ ] G1 공통 3단 프레임 (다음 버튼 4개를 위한 골격)
- [ ] G3 오판정 1클릭 피드백 — 2단계 진입 티켓
- [ ] **버튼 1개: 상세페이지 작업** (미리보기 → 견적 → 건수 타이핑 → 실행 → 마켓 수정업로드)

### Add After Validation (v1.x)

- [ ] 버튼 2~5 (입찰가 / 꺼진 소재 정리 / 썸네일 / 쿠팡 복사) — **트리거: G1 프레임이 상세에서 한 바퀴 돌았을 때**
- [ ] F4 되돌리기 버튼 — 트리거: 입찰가 버튼 추가 시 동시
- [ ] C5 항목 단위 before/after — 트리거: 오판정 피드백이 쌓여 "뭐가 틀렸는지" 봐야 할 때
- [ ] G2 오늘 할 일 큐 — 트리거: 필터를 매번 같은 조합으로 만들고 있을 때
- [ ] G5 크레딧 가계부 / G4 예측 대 실제 — 트리거: 크레딧 소모가 월 단위로 유의미해질 때
- [ ] G6 완료 알림 / G7 이어하기 — 트리거: 장시간 작업을 2회 이상 놓쳤을 때
- [ ] E6 보류 큐 — 트리거: "판단 필요"가 실제로 쌓일 때. 안 쌓이면 만들지 않는다
- [ ] G8 키보드 조작 — 트리거: 하루 50행 이상 만지게 될 때

### Future Consideration (v2+)

- [ ] **2단계 자동화: 미리보기 → "전부 실행" 1버튼** — 전제: G3/G4 로 오판정률 실측이 낮게 나올 것

- [ ] 전환율 측정 — 완료 기준이 마찰이라 지금은 측정 대상이 아님

|---------|---|---|---|---|
| 미리보기 | `plan -out` 파일 → 그 파일을 apply | 워크플로 dry-run 잡 | 대량 편집 프리뷰 | **CLI 의 run-dir 를 plan 으로 그대로 승격.** 새 형식 안 만듦 |
| 미리보기 신선도 | 상태 변경 시 plan 무효 | — | — | `recheck_failed` 를 정상 흐름으로 UI 노출. `--force` 없음 |
| 확인 | `yes` 타이핑 1회 | 환경별 승인 게이트 | 삭제만 이름 타이핑 | **위험 사다리 차등** — 5개 버튼 전부 다르게 |
| 대량 선택 | 없음(코드 기반) | 잡 매트릭스 | 페이지/전체 분리 + 건수 표시 | PatternFly·Helios 표준 채택, 전체선택은 별도 배너 |
| 부분 실패 | apply 중단 후 부분 적용 상태 | 잡별 성공/실패 + 실패 잡만 재실행 | CSV 오류 리포트 | **항목 결과표 + 사유코드 + 실패분만 새 plan 으로 재시도** |
| 장기 실행 | 원격 run, URL 로 복귀 | run 페이지, 로그 영구 보관 | 비동기 작업 알림 | job id + 로컬 durable 상태 + 폴링. 브라우저 무관 |
| 비용 견적 | 인프라 비용 추정(Infracost) | — | — | AI 크레딧 **범위** 견적 + 잔액 대비 예상 |
| 감사 | run 이력 + 누가 승인 | 워크플로 이력 | 어드민 감사 로그 | JSONL 1파일. 실행자 필드로 manual/auto 구분(3단계 대비) |
| 중단 | run cancel | 잡 cancel | — | 안전 경계 Stop (강제 kill 금지 — 크레딧 이중지불) |

**의도적으로 안 베끼는 것:** 권한·승인자 체계, 알림 규칙, 조직/환경 개념, 대시보드 위젯. 전부 다인 조직 전제 기능이다.

## 남은 불확실성 (다음 리서치/1페이즈에서 풀 것)

1. **광고 소재 ↔ 불사자 상품 조인 키가 뭔지 아직 확정 안 됨** — 상품명 매칭이면 실패율이 높을 것. 조인 성공률 실측이 1페이즈 산출물이어야 한다. (Confidence: LOW)
2. **크레딧 견적 정확도** — `min(제품이미지 수, 10)` 하한 2 가 사전에 계산 가능한지(제품이미지 수를 접수 전에 아는지) 확인 필요. 모르면 "최대치만 표시"로 물러선다. (Confidence: MEDIUM)
3. **Stop 의 안전 경계가 실제로 어디인지** — 접수 후 폴링 중 중단 시 크레딧이 이미 소모됐는지. 실측 필요. (Confidence: LOW)
4. **오판정 피드백을 몇 건 모아야 2단계 판단이 되는지** — 기준선이 없다. v1 운영 중 정한다.
