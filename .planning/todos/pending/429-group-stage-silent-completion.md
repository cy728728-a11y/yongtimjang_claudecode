# 그룹 목록 조회 단계의 HTTP 429 가 "완주"로 둔갑한다

## 무슨 일이 났나

2026-09-21 14:01 인덱스 재실행에서 그룹 5·6 이
`⛔ 실패: 요청 실패(재시도 4회 초과): HTTP 429` 로 죽었다.
그런데 최종 요약은 `끝 — 그룹 30개 · 누적 27775행 · 미조회 0`.

숫자가 앞뒤를 증명한다:
`27,775` + 죽은 두 그룹(760 + 2,011 = 2,771) = **30,546** = `ss_index` 실제 행수.
**죽은 그룹을 빼고 세면서 "완주"라고 적었다.**

- `ss_index` 의 `sum(unresolved)` 도 그대로 `0` — 미조회 행이 한 줄도 안 생긴다
- 화면에서 이걸 알아챌 방법이 없다

## 왜 테스트가 못 잡나

`test_429는_미조회로_남는다` 는 **상품 단위** 429 만 본다.
**그룹 목록 조회 단계**의 429 는 그 경로를 안 탄다.

## 위험

첫 구축 중에 같은 일이 나면 **그 그룹이 통째로 비고 화면은 "완주"라고 말한다.**
→ Phase 5 가 대상 목록을 통째로 놓친다.
이 페이즈가 못 박은 **"429 를 성공으로 접지 마라"** 를 정확히 어기는 자리다.

## 왜 이번에만 났나 (가설 · 미검증)

레이트리밋이 **프로세스마다** 0.26초 간격이다.
14:01 에 인덱스 잡과 스캔 잡이 **4초 차로 같이** 떠서 합산 초당 4회 상한을 넘겼을 수 있다.
첫 완주(11:43~13:51)는 혼자 돌았고 **429 0회** — 앞뒤가 맞는다.

→ 당분간의 운용 회피책: **인덱스 잡과 스캔 잡을 동시에 띄우지 마라.**

## 고칠 때 할 일

1. 그룹 단계 429 로 죽은 그룹의 행을 **`미조회` 로 남긴다** (사유코드는 `미조회` — `번호없음` 절대 금지)
2. 최종 요약이 **실패한 그룹 수를 따로 말하게** 한다. "그룹 30개 완주"가 거짓말이 되지 않도록
3. 회귀 테스트를 **그룹 단계까지** 넓힌다 (`test_429는_미조회로_남는다` 가 상품 단계만 본다)
4. 레이트리밋을 프로세스 간 공유로 올릴지 판단 — 아니면 잡 동시 실행을 구조로 막을지

## 이번엔 손실 없었다

이미 채워진 그룹이라 데이터는 멀쩡하다: **30,546행 / 30그룹 / 미조회 0**.
