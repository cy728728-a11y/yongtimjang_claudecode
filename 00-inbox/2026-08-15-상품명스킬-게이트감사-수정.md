## 1. 결함 ① — 삭제대기 게이트가 없었다

### 무엇이 문제인가

**두 개의 상태 저장소가 서로 다른 것을 안다.**

| 저장소 | 아는 것 | 누가 쓰나 |
|---|---|---|
| 상품명 탭 **A열** | "이 상품은 상품명 작업을 했다" | `prep` 의 멱등 판정 |
| 현황판 `00_진행` | "이 상품은 제외카테고리라 삭제 예정이다" | 제외카테고리 게이트가 찍는다 |

`prep` 은 **A열만** 본다. 그래서 **"삭제 예정인데 아직 상품명 작업을 안 한 상품"** 이
멱등 판정을 그대로 통과해 대상에 들어갔다. 삭제대기 마커는 현황판에만 있고 A열에는 없다.

```
프리필터 → 뷰 생성 → 썸네일 다운로드 → 워커 판단 → 검증 → 시트 기록 → 불사자 rename
   ↑ 삭제될 상품에 이 전부를 태운다
```

### 왜 지금까지 안 드러났나

4-2 회차는 **rename 단계에서** `--ids` 로 삭제대기를 걸러냈다. 결과물은 깨끗해 보였지만
**prep~워커 비용은 이미 다 쓴 뒤**였다. 게이트가 파이프라인 맨 뒤에 있어서 낭비가 안 보였다.

### 고친 것

`run_names.py` 에 `_drop_gone(pending, m)` 을 추가하고 `cmd_prep` 의 대상 산출 직후에 건다.

```python
pending = [g for g in group if g.get("productId") not in done_ids]
# 삭제대기 게이트 — A열 멱등만으로는 안 걸린다.
pending, gone = _drop_gone(pending, _m)
if gone:
    print(f"  삭제대기·삭제완료 {gone}건 제외 (현황판 게이트)")
```

**판정 로직은 새로 쓰지 않았다** — `category_gate.already_gone` 1벌을 그대로 재사용한다
(`bulsaja-category-fix` 소유. `run_names.py` 는 이미 그 scripts 폴더를 `sys.path` 에 넣고 있어
`import category_gate` 만 추가하면 된다).

```python
# category_gate.py (기존 코드 — 손대지 않음)
GONE_PREFIXES = (matrix.DELETED_PREFIX, "삭제대기")   # ('상품삭제', '삭제대기')
GATED_TASKS   = tuple(matrix.TASKS[2:])               # 상품명·옵션·썸네일·상세·지재권·배송비·업로드

def already_gone(rec):
    vals = [(rec.get(t) or "").strip() for t in GATED_TASKS]
    return any(v == matrix.NA or v.startswith(GONE_PREFIXES) for v in vals)
```

부수적으로 현황판을 **prep 에서 1회만** 읽게 바꿨다(`_matrix_redo` 와 게이트가 공유).

### 설계 포인트 — 게이트는 열 하나가 아니라 7개를 본다

이게 이 수정의 핵심이다. `already_gone` 은 **7개 작업 열 중 하나라도** 삭제대기면 잡는다.

4-1 에서 `append` 가 `상품명` 열을 덮어써 그 열의 삭제대기 마커 134칸이 사라졌는데,
**`썸네일` 열이 안 건드려진 채 285건 온전히 남아 있어서** 사고를 발견할 수 있었고 복구도
그 열을 정본 삼아 했다. 게이트를 열 하나로 좁히면 그 성질이 사라진다.

### 현황판을 못 읽으면?

**경고를 찍는다.** 조용히 게이트 없이 도는 게 이번 사고의 본질이라 막았다.

```
[경고] 현황판을 못 읽어 삭제대기 게이트를 걸지 못했습니다 — 삭제 예정 상품이 대상에 섞일 수 있습니다.
```

## 2. 결함 ② — append 에 감사가 없었다

### 무엇이 문제인가

옵션정리 `apply` 에는 `_audit_results` 가 있어 워커 산출물을 배치 정본과 대조하고,
누락이 있으면 `--commit` 을 막는다. **상품명 `append` 에는 같은 것이 없었다.**

같은 세션에 같은 사고가 두 축에서 각 1건 났는데 결과가 갈렸다:

| 축 | 워커가 쓴 값 | 진짜 값 | 결과 |
|---|---|---|---|
| 옵션 | `U01KSER86WGCHX4DQ09JC6QW` (24자) | `U01KSER86WGCHX4DQ09JC6QWZ2J` | 감사가 `미지의 상품id(환각)` 로 잡고 **`--commit` 차단** |
| 상품명 | `U01KSER86W5QCP907SEXBMFQ4W` (26자) | `U01KSER86W5QCP907SEXBMFQP4W` | **감사가 없어 통과** → 시트 A열에 26자가 기록됨 |

정상 productId 는 **`U01` 로 시작하는 27자 고정**이다.

### 고친 것

`_audit_named(run_dir, repair=True)` 를 추가하고 `cmd_append` 맨 앞에서 부른다.

- `named/named_NNN.json` 을 `batches/batch_NNN.json` 정본과 대조
- **id 훼손 자동 교정** — 같은 배치 안에서 유일하게 일치하는 진짜 id 로 고치고 파일을 되쓴다
- **누락 상품이 있으면 append 를 막는다** (`--allow-missing` 으로만 강행)
- 미완 배치 · 환각 id · 파일명↔내부 배치번호 불일치도 보고

### 왜 접두 매칭이 아니라 부분수열인가

훼손이 **두 가지 형태**로 나온다:

```
뒤 잘림    : U01KSER86WGCHX4DQ09JC6QWZ2J → U01KSER86WGCHX4DQ09JC6QW     (접두 O)
가운데 누락: U01KSER86W5QCP907SEXBMFQP4W → U01KSER86W5QCP907SEXBMFQ4W   (접두 X — 'P'가 빠졌다)
```

접두 매칭만 쓰면 후자를 못 잡는다. **글자 몇 개가 빠진 것**(부분수열)으로 보면 둘 다 잡힌다.

```python
def _is_subseq(short, full):
    it = iter(full)
    return all(c in it for c in short)
```

후보가 **둘 이상이면 손대지 않고** 환각으로 보고한다 — 잘못 고치는 것보다 막는 게 낫다.

### 넣자마자 하나 더 잡았다

4-1 run-dir 에 돌리자 **배치 교차 오염**이 나왔다. `named_064.json` 에 그 배치 상품
(피너츠 세트) 대신 **다른 배치 상품(디퓨저)** 이 들어가 있어 원래 상품이 조용히 사라진 건이다.
사람이 눈으로 훑을 때는 못 본 것이고, 감사가 없었으면 영영 몰랐을 건이다.

## 4. 앞으로 달라지는 것

**`prep` 출력에 한 줄이 는다** — 삭제 예정 상품이 있으면 몇 건을 뺐는지 찍힌다.

```
  삭제대기·삭제완료 137건 제외 (현황판 게이트)
[2/6] 그룹 999건 / 이미처리 772건 / 대상 90건
```

**`append` 가 누락에 멈춘다** — 전에는 조용히 진행되던 자리다.

```
  [감사] id 훼손 교정 named_019.json: U01KSER86W5QCP907SEXBMFQ4W(26자) → U01KSER86W5QCP907SEXBMFQP4W
  [감사] 미완 배치 1개: [64]
  [감사] 누락 상품 1건: ['U01KSER86V7PG7M8VRR7XNXJB9T']

누락 상품이 있어 append 를 막는다. pending 재계산 → 재팬아웃으로 채우거나, 의도된 것이면 --allow-missing.
```

멈추면 **재팬아웃으로 채우는 게 정답**이다. `--allow-missing` 은 의도된 부분 반영 전용.

## 6. 이번에 배운 것 (다음에 또 밟지 않게)

1. **검증은 자기가 방금 쓴 열이 아니라 안 건드린 열로 한다.**
   rename 직전에 `--ids` 로 삭제대기를 거르려고 현황판 `상품명` 열을 읽었는데
   **그 열은 이미 `append` 가 덮은 뒤**였다. 0건이 나온 건 통과가 아니라 증거 소실이었다.
2. **게이트는 파이프라인 앞에 둔다.** 뒤에 두면 결과물은 깨끗해 보이지만 비용은 이미 나갔다.
3. **워크플로 반환값보다 디스크가 정본이다.** 워커가 파일은 쓰고 구조화 반환 직전에 죽으면
   집계에서 빠진다(4-1: 반환값 50배치 vs 디스크 59개). pending 은 항상 디스크 대조로 재계산.
4. **같은 방어선을 스킬마다 따로 만들지 않는다.** 옵션정리에 있던 두 방어선이 상품명에만
   없어서 사고가 났다. 새 축을 만들 때 **감사·게이트가 있는지부터** 본다.
