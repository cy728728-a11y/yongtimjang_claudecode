### ② `재생성횟수` 로 크레딧을 세면 두 배가 나온다

`generated.json` 의 `재생성횟수` 는 **회수(recover)할 때도 1 오른다**(접수 자체가
시도라서 의도된 동작이다). 이걸로 과금액을 세면:

```
잘못: sum(재생성횟수+1) × 5  →  10,975크레딧   (실제의 약 2배)
맞음: recover 로그의 [회수] 라인 수 × 5  →  5,745크레딧
```

```bash
# 실제 과금 건수 = 회수 라인 수 (인라인 성공분이 있으면 [생성] 라인도 더한다)
cat <R>.recover*.log | grep -c '^  \[회수\]'
grep -hc '\[생성\]' <R>.generate.log <R>.regen*.log
```

**잔액 차이로도 세면 안 된다** — 다른 세션이 같은 계정 크레딧을 동시에 쓴다. 이번에도
잔액은 약 10,000 줄었는데 이쪽 몫은 5,745 였다.

### ③ 접수모드는 **접수만 빠르고 회수는 큐를 기다린다**

메인 993건은 접수 직후 바로 회수됐는데(대기 0), 후속 56건은 **20분 넘게 "아직 생성 중"**
이었다. 큐가 밀린 시간대였다. 판별은 로그 문구로 한다:

```
[대기] U01…: task 22773 — 아직 생성 중     ← 정상. 크레딧 이미 나감. 기다렸다 다시 recover
[실패확정] U01…: 생성 실패: …               ← 서버가 못 만든 것. 재생성 대상
```

`recover` 는 멱등이라 몇 번을 불러도 안전하다. **타임아웃을 늘리지 말고 recover 를 반복해라.**

### ④ 긴 명령을 `until ! pgrep` 로 기다리면 **툴 타임아웃이 자식까지 죽인다**

`nohup … & disown` 뒤에 같은 셸에서 `until` 로 기다리다 10분 툴 타임아웃이 나면
프로세스가 함께 죽는다(첫 `recover` 가 이렇게 끊겼다). **띄우는 셸과 기다리는 셸을
나눠라** — 띄우고 즉시 반환한 뒤, 다음 호출에서 `pgrep` 로 상태만 본다.

### ⑤ 대량 회차의 `apply --commit` 은 **한 번만** 친다

`--commit` 은 `decisions.json` **전량**을 다시 저장한다(`--ids` 로 좁혀지지 않는다).
1차 판정 직후 커밋하고 재생성 뒤 또 커밋하면 991건을 두 번 저장해 429 가 쏟아진다.
**재생성 → 재판정 → 판정 합치기까지 끝낸 뒤 마지막에 한 번**이 맞다. 이번에 그렇게
돌려서 **저장실패 0** 이 나왔다(859건 저장에 약 50분).

### ⑥ 승격건 배치의 후보 경로 필드명은 `path` 다

`batches/*.json` 의 `후보이미지[]` 는 `{"index":…, "url":…, "path":…}` 다.
`경로` 로 찾으면 전부 `None` 이 나와 "이미지가 없다"고 오판한다.
